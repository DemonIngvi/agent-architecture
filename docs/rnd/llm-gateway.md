Через что агенты ходят к моделям, чтобы модель менялась без кода, у каждого агента был свой ключ, бюджет и лимит, затраты считались по запуску, а разработка шла без ключей провайдера?

**Почему LiteLLM.** Три вывода:

<div class="rnd-grid" markdown>
<div markdown>
**1. Всё нужное — в открытом ядре**

Алиасы моделей, virtual key на агента, бюджет и RPM / TPM на ключ, журнал затрат с `metadata.run_id`, fallback, mock за тем же алиасом. У Kong и Portkey часть этого — в платных изданиях или в облаке ([Э9](#e9)).
</div>
<div markdown>
**2. На LiteLLM уже завязаны три соседа**

Platform module выдаёт ключи через admin API (I15), Control plane передаёт бюджеты, Observability читает затраты из БД `litellm` (S6). Другой шлюз означает переделку трёх компонентов ([Э7](#e7)).
</div>
<div markdown>
**3. Риск — производительность, и он проверяется**

LiteLLM на Python тяжелее шлюзов на Go и Rust. Наш профиль скромный (до 1 RPS, ~55 тыс. токенов в минуту), поэтому риск проверяется нагрузочным тестом. Если накладные расходы выйдут за предел, пилотируем Bifrost ([Э8](#e8)).
</div>
</div>

## Э1. Вопрос {#e1}

**Ситуация.** Агенты вызывают модели разных провайдеров. Администратору нужны бюджеты и лимиты по агенту, пользователю — затраты по задаче, разработчику — работа без ключей.

**Осложнение.** Шлюзов много: Python (LiteLLM), Go (Bifrost), Envoy, Kong; часть функций у них в платных изданиях. Прямые вызовы проще, но без учёта и с ключом в sandbox.

**Вопрос.** Через что агенты ходят к моделям?

**Решает:** владелец продукта. **Не решаем:** проверки G4 в шлюзе ([guardrails](guardrails-engine.md)), наблюдаемость ([observability](observability.md)).

<span class="gate">G1</span> ✅ вопрос — выбор; есть владелец; связан с D5, D18.

## Э3. Опорное решение: LiteLLM Proxy {#e3}

| # | Функция | Что делает | Потребность |
|---|---|---|---|
| F1 | `model_list` и алиасы | имя для агента → реальная модель | П1, П4 |
| F2 | `drop_params` | отбрасывает неподдерживаемые параметры | П1 |
| F3 | Virtual keys | ключ на агента с бюджетом, RPM / TPM | П2 |
| F4 | Журнал затрат (spend logs) | токены, $ и `metadata` каждого запроса в БД `litellm` | П3 |
| F5 | Fallback и маршрутизация | резервная модель, повторы | П5 |
| F6 | Admin API (`/key/generate`, `/key/update`) | выдача и изменение ключей | П2 |
| F7 | 100+ провайдеров, OpenAI-совместимый API | один формат для Harness | П5 |
| F8 | Хуки guardrails | место для G4 | — |

**Вывод этапа.** LiteLLM закрывает все потребности функциями ядра. Открытый вопрос — производительность (П8).

<span class="gate">G3</span> ✅ функции из документации LiteLLM (Б) и D5 (А).
