<div class="rnd-q">Вопрос</div>
Как устроить память, чтобы агент следующего шага процесса продолжал работу, а не начинал заново, контекст не раздувался, а проекты не видели чужого?

<div class="rnd-a">Ответ: уровни M0–M6 по видам знания, область видимости — атрибут записи. Своя тонкая Memory API в Postgres ICPlan. Готовые слои памяти (Mem0, LangMem) — кандидаты для M4 после MVP.</div>

**Почему M0–M6.** Три вывода:

<div class="rnd-grid" markdown>
<div markdown>
**1. Преемственность даёт состояние задачи, а не вся история**

Следующему агенту нужно знать, что сделано, что дальше и что мешает. Это M3 — короткая запись (`m3_max_kb` 16) — плюс итоги последних запусков M2. История чата целиком раздувает контекст и не говорит, что дальше ([Э5](#e5)).
</div>
<div markdown>
**2. Пять уровней уже живут в ICPlan**

Переписку (M1), итоги запусков (M2), инструкции (M5) и документы (M6) пишет ICPlan, рабочий контекст (M0) — Harness. Своё хранилище нужно только для M3. Готовые слои памяти пришлось бы синхронизировать с ICPlan ([Э7](#e7)).
</div>
<div markdown>
**3. Лучшие функции готовых слоёв — для фактов M4**

Mem0 разрешает противоречия: новый факт обновляет или удаляет старый. Graphiti хранит срок действия факта. Это ценно для M4, а не для состояния задачи. Поэтому функции переносим в требования M4 после MVP ([Э6](#e6)).
</div>
</div>

## Э1. Вопрос {#e1}

**Ситуация.** Задача проходит шаги процесса, на каждом — свой агент (D17). Запуски короткие, между ними задача ждёт людей.

**Осложнение.** Без памяти следующий агент начинает с нуля. С полной историей контекст раздувается и дорожает. Готовые слои памяти (Letta, Mem0, Zep) решают это по-своему, но приносят свои сервисы.

**Вопрос.** Какая модель памяти и где она хранится?

**Решает:** владелец продукта с архитектором. **Не решаем:** поиск по документам и коду ([RAG](rag.md)), хранилища в целом ([хранилища](data-stores.md)).

<span class="gate">G1</span> ✅ вопрос — выбор; есть владелец; связан с D4 и требованиями agent-memory.

## Э2. Потребности {#e2}

| # | Потребность | Откуда | Что ломается без неё |
|---|---|---|---|
| П1 | следующий агент продолжает работу по задаче | R-MEM-04, R-MEM-05, D17 | шаг процесса повторяет сделанное |
| П2 | в контекст попадает только нужное | R-MEM-01, `read` | токены и деньги на лишнее |
| П3 | проекты и задачи не видят чужое | R-MEM-02 | утечка между проектами |
| П4 | переписка и итоги пишутся автоматически | R-MEM-03 | память зависит от того, вспомнит ли агент |
| П5 | срок хранения и удаление | R-MEM-08, R-MEM-07 | память растёт без предела, нельзя удалить |
| П6 | проверки записи: что, когда и куда агент пишет | R-MEM-15 | мусор и секреты в памяти |
| П7 | без нового сервиса и новой БД на MVP | D4, D15 | ещё одна система в эксплуатации |
| П8 | факты и знания проекта (M4) после MVP | R-MEM-06 | агент не накапливает знания проекта |

## Э3. Опорное решение: M0–M6 {#e3}

Опорное решение — модель проекта AI-агент на основе CoALA, принятая в D4.

| # | Уровень | Что хранит | Кто пишет | Потребность |
|---|---|---|---|---|
| F1 | M0 рабочий | контекст запуска | Harness, каждый шаг | П2 |
| F2 | M1 переписка | чат и комментарии задачи | ICPlan | П4 |
| F3 | M2 итоги | итог, статус, токены, вердикт запуска (`agent_run`) | Runner → ICPlan | П1, П4 |
| F4 | M3 состояние задачи | `M3Record`: сделано, дальше, блокировки | агент через тул памяти | П1 |
| F5 | M4 факты | факты с источником | после MVP | П8 |
| F6 | M5 процедуры | инструкция и навыки агента | администратор через Registry | — |
| F7 | M6 документы | документы проекта | люди в ICPlan | — |

Область видимости (`scope`) — атрибут записи, сроки — параметр `retention`.

**Вывод этапа.** M0–M6 закрывает П1–П7; M4 отложена.

<span class="gate">G3</span> ✅ уровни связаны с потребностями; [потоки памяти](../techspec/memory.md#how) описывают запись и чтение каждого (А).

### Как встаёт в схему

```
 ICPlan (S1: чат M1, agent_run M2, документы M6, определения M5)
      ▲ I2 итог запуска → M2                         │ чтение M1, M2
 Agent Runner                                         ▼
      └─I7─▶ Harness ──I11 (M3: запись, чтение)──▶ Memory API ──I22──▶ Postgres S4 (memory_m3; позже M4*)
                └ M0 в контексте запуска
  * — M4: Mem0 или LangMem поверх pgvector в той же БД, без новой службы БД
```

| Стык | M0–M6 | Mem0 | LangMem | Letta | Graphiti |
|---|---|---|---|---|---|
| I11 Harness → память | И2: REST, токен запуска | И2: Mem0 за Memory API | И1: хранилище LangGraph в sandbox — нет доступа к БД (D18), только через Memory API | И1: свой API и свой агент | И1 |
| I22 хранение | И2: S4 в Postgres ICPlan | И2: pgvector | И2: Postgres store | И1: своя БД сервера | И0: Neo4j / FalkorDB |
| Связь с M1, M2 в ICPlan | И4: уже в ICPlan | И1: синхронизация | И1 | И1 | И1 |
| Модель для извлечения | — | И2: через LiteLLM (I8) | И2 | И2 | И2 |

**Изменения у соседей:**

| Кандидат | Что меняется |
|---|---|
| M0–M6 | ничего |
| Mem0, LangMem (для M4) | Memory API вызывает модель через LiteLLM — новый поток Т1 (данные промпта) через Memory |
| Letta | Harness: цикл в Letta; Runner: второй исполнитель |
| Graphiti | инфраструктура: графовая БД; бэкапы; FMEA |

**Вывод этапа.** ==Своя Memory API встаёт без изменений у соседей; для M4 Mem0 и LangMem ложатся на pgvector в той же БД, но добавляют вызов модели из Memory.== Letta и Graphiti меняют чужие компоненты.

- **Утверждение.** M0–M6 со своей Memory API (D4); M4 — после MVP на Mem0 или LangMem.
- **Основания.** Закрывает 7 из 8 потребностей, 5 уровней уже в ICPlan, соседи не меняются.
- **Связка.** Преемственности шагов нужно состояние задачи, а не база фактов. Готовые слои дают факты и будут нужны для M4.
- **Опровержение.** Вывод неверен, если агенты начнут ссылаться на знания проекта чаще, чем на состояние задачи. Тогда M4 переходит в MVP.
