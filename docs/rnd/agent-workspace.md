**Почему вариант B.** Три вывода:

<div class="rnd-grid" markdown>
<div markdown>
**1. Шаги передают не только код**

Аналитик отдаёт требования, тестировщик — отчёт, ревьюер — замечания. Это файлы, а не всегда код. Папка задачи в RustFS (версии неизменяемы) плюс ветка в git передают любые артефакты. «Только git» заставил бы класть отчёты в репозиторий продукта ([Э9](#e9)).
</div>
<div markdown>
**2. Права — токенами, а не промптом**

Политика «агент × ресурс × право» превращается в манифест запуска. Runner выдаёт токены только на перечисленные ресурсы, MCP-серверы — по той же политике. Атака «прочитай всё» в промпте ничего не даёт: токена на чужое нет. Так же работают аналоги: Copilot и Codex дают агенту только репозиторий задачи ([Э5](#e5)).
</div>
<div markdown>
**3. Аналоги готовят среду до агента — у нас этого нет**

Codex выполняет скрипт подготовки (зависимости, секреты) до старта агента, а потом убирает секреты. Copilot выполняет шаги подготовки и пускает к реестрам пакетов по готовому списку. У нас по умолчанию — только сервисы платформы, и `pip install` не проходил. Решение D19 переносит этот приём к нам ([Э9](#e9)).
</div>
</div>

## Э1. Вопрос {#e1}

**Ситуация.** Задача идёт по шагам процесса, на каждом шаге — свой агент (D17). Каждый запуск — в своём одноразовом контейнере ([Sandbox](sandbox-isolation.md)).

**Осложнение.** Контейнер исчезает, а результат нужен следующему шагу. Права на ресурсы нельзя задавать промптом: его можно атаковать. Проект AI-агент пробовал репозиторий на задачу (решение 1.10) и общий том с папками агентов (решение 7.4).

**Вопрос.** Как устроить рабочее пространство и доступы агентов?

**Решает:** владелец продукта с ролью «Безопасность». **Не решаем:** изоляцию среды ([Sandbox](sandbox-isolation.md)), хранилища ([хранилища](data-stores.md)).

<span class="gate">G1</span> ✅ вопрос — выбор; есть владелец; связан с D11, D18.
