# R&D: Поиск по знаниям (RAG)

← [Все R&D](README.md) · [методология R&D v3.1](../rules/rnd-methodology.md) · компонент: **Memory, MCP / Tools** · решение: [design D13](../../openspec/changes/define-agent-platform/design.md) · спека: [agent-memory](../../openspec/changes/define-agent-platform/specs/agent-memory/spec.md) (R-MEM-06)

<div class="rnd-hero" markdown>
<div class="rnd-q">Вопрос</div>
Нужен ли агентам поиск по смыслу в документах и коде на MVP, и если да — на чём, чтобы не добавлять сервис ради того, что агент может прочитать сам?

<div class="rnd-a">Ответ: на MVP RAG не нужен: документы проекта агент читает тулом `get_document` (M6), код — поиском по файлам в своём рабочем пространстве. После MVP — pgvector в той же Postgres, гибридный поиск (по словам и по смыслу) и контекстные фрагменты.</div>

<span class="rnd-badge assess">Assess</span> pgvector + гибридный поиск после MVP · <span class="rnd-badge adopt">Adopt</span> `get_document` и поиск по файлам на MVP · данные 11.10.2026
</div>

```deck
# Покрытие потребностей П1–П6
> на MVP хватает чтения документов и поиска по файлам; векторный поиск нужен для больших корпусов позже
stack Без RAG на MVP: 4 ok, 1 part, 1 no
stack pgvector + гибридный: 5 ok, 1 part, 0 no
stack Qdrant: 5 ok, 0 part, 1 no
stack Milvus / Weaviate: 4 ok, 0 part, 2 no
# Чем точнее поиск
> гибрид и контекст снижают промахи поиска (данные Anthropic)
bar Только векторы: 100/100 базовая доля промахов no
bar + контекст фрагмента: 65/100 −35% промахов part
bar + поиск по словам: 51/100 −49% part
bar + переранжирование: 33/100 −67% ok
# Позиции ролей
side без RAG / pgvector | Qdrant
pos DevOps: -2 | без нового сервиса
pos Архитектор: -1 | векторы в той же БД, что M4
pos Разработчик: -1 | для кода точнее поиск по файлам
pos Аналитик историй: 1 | большие корпуса документов позже
# Что меняется
> D13 подтверждён; гибрид и контекст — в бэклог RAG
stack Документы: 2 ok, 0 part, 4 mute
- ✅ бэклог RAG: гибридный поиск в Postgres, контекстные фрагменты, переранжирование
```

**Почему без RAG на MVP.** Три вывода:

<div class="rnd-grid" markdown>
<div markdown>
**1. Для кода поиск по файлам точнее**

Агент-разработчик работает в клоне репозитория и ищет по файлам (`grep`, чтение). Так работают кодинг-агенты рынка: Claude Code и Copilot. Векторный индекс кода устаревает с каждым коммитом, а в категории «код» контекстный поиск даёт меньший выигрыш, чем в текстах ([Э5](#e5)).
</div>
<div markdown>
**2. Документы проекта пока помещаются**

Документов проекта немного, и агент читает их тулом `get_document` по ссылке. RAG нужен, когда корпус не помещается в навигацию, — это после MVP ([Э9](#e9)).
</div>
<div markdown>
**3. Когда понадобится — в той же Postgres и с гибридом**

pgvector уже в стандартном образе CNPG (D18), там же будут факты M4. Точность даёт не выбор векторной БД, а приём: контекст во фрагменте, поиск по словам вместе со смыслом и переранжирование. По данным Anthropic это −49%…−67% промахов ([Э6](#e6)).
</div>
</div>

<div class="rnd-grid" markdown>
<div class="take" markdown>
**Берём**

- `get_document` (M6) на MVP;
- поиск по файлам в рабочем пространстве для кода;
- pgvector после MVP в той же Postgres.
</div>
<div class="adapt" markdown>
**Адаптируем (после MVP)**

- контекстные фрагменты (Anthropic) → к фрагменту добавляется краткий контекст документа перед индексом;
- гибридный поиск: полнотекстовый в Postgres + векторы;
- переранжирование кандидатов.
</div>
<div class="drop" markdown>
**Не берём**

- отдельную векторную БД (Qdrant, Milvus, Weaviate) при объёме до миллиона векторов;
- векторный индекс кода на MVP;
- ParadeDB на MVP: AGPL-расширение ради BM25 — оценить позже.
</div>
</div>

<div class="rnd-grid" markdown>
<div class="no" markdown>
**Отсеяны до сравнения**

- **Облачные векторные БД** — своё размещение.
</div>
<div class="risk" markdown>
**Риски и пересмотр**

- Агент не находит нужный документ — ссылки в задаче и каталоге проекта.
- Пересмотр: документов проекта больше, чем агент может просмотреть по ссылкам → RAG на pgvector.
</div>
</div>

## Э1. Вопрос {#e1}

**Ситуация.** Агентам нужны документы проекта (M6) и код. M4 (факты) — после MVP.

**Осложнение.** RAG стал стандартным приёмом, но кодинг-агенты всё чаще ищут по файлам, а не по векторам. Векторных БД много, и каждая — новый сервис.

**Вопрос.** Нужен ли RAG на MVP, и на чём он будет потом?

**Решает:** владелец продукта. **Не решаем:** память агента ([память](memory-model.md)).

<span class="gate">G1</span> ✅ вопрос — выбор; есть владелец; связан с D13.

| П2 | агент находит нужное в коде | истории агентов-разработчиков | агент не знает, где менять |

## Э9. Выбор {#e9}

| Потребность | Без RAG (MVP) | pgvector + гибрид | Qdrant |
|---|---|---|---|
| П1 документы | закрывает: по ссылке | закрывает | закрывает |
| П2 код | закрывает: поиск по файлам | закрывает | закрывает |
| П3 по проекту | закрывает | закрывает | закрывает |
| П4 без сервиса | закрывает | закрывает | не закрывает |
| П5 большие корпуса | не закрывает | закрывает | закрывает |
| П6 точность | частично | закрывает: гибрид и контекст | закрывает |

- **Утверждение.** На MVP без RAG; после MVP — pgvector с гибридным поиском и контекстными фрагментами (D13).
- **Основания.** На MVP закрыты П1–П4 без индекса; после MVP pgvector закрывает П5 и П6 без нового сервиса.
- **Связка.** Точность определяется приёмом поиска, а не выбором БД, а объём у нас скромный.
- **Опровержение.** Вывод неверен, если корпус вырастет за миллион векторов или понадобится сложная фильтрация. Тогда — Qdrant.

<span class="gate">G9</span> ✅ вывод следует из покрытия и спора; есть опровержение.
