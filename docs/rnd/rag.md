## Зачем RAG

Дать агенту нужные куски из больших корпусов (документация, стандарты, код) без загрузки всего в контекст. RAG — механизм чтения M4/M6, новых уровней памяти не добавляет.

| ➕ | ➖ |
|---|---|
| Меньше токенов | Устаревший индекс → устаревшие ответы |
| Опора на наши стандарты | Шум поиска сбивает модель |
| Изоляция знаний (allowlist баз) | Документы в индексе — вектор prompt injection |
| | Эмбеддер и переиндексация — эксплуатация |

Для кода индустрия всё чаще использует агентный поиск (grep / чтение файлов тулами, как Claude Code) — точнее векторного поиска.

## Хранилище

| | pgvector | Qdrant |
|---|---|---|
| Компоненты | расширение Postgres ICPlan (уже установлено) | отдельный сервис |
| Консистентность | одна БД | две, нужна переиндексация |
| Масштаб | достаточно на старте | лучше на больших объёмах |

## Решение

Не в MVP. В MVP: документы через `get_document`, код — агентный поиск. Позже — pgvector + локальный эмбеддер.
