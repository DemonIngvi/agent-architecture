# R&D: Как проводить и подавать исследования

← [Все R&D](README.md) · [методология R&D (правило)](../rules/rnd-methodology.md) · [журнал отклонений](../rules/deviations.md) · компонент: **правила документации** · методология **v3** (этот документ — её обоснование)

<div class="rnd-hero" markdown>
<div class="rnd-q">Вопрос</div>
Как проводить R&D, чтобы были видны путь к выводу, происхождение критериев и ценность функций, а читатель за 3 минуты понимал выбор и его основания?

<div class="rnd-a">Ответ: исследование по цепочке «потребность → функции → ценность → перенос → выбор». Между этапами стоят проверки (ворота). Цифры перенесены в приложение.</div>

<span class="rnd-badge adopt">Adopt</span> методология v3 заменяет v2 · основа: Stage-Gate, разбор функций по Kano и GAO, аргумент Тулмина, пирамида Минто · эталон применения — [выбор трекера](tracker-choice.md)
</div>

**Почему так.** Три вывода, у каждого есть основание:

<div class="rnd-grid" markdown>
<div markdown>
**1. Критерий — это следствие, а не исходная точка**

В v2 критерии и веса задавались до разбора функций, поэтому было неясно, откуда они взялись. В v3 критерий получается в конце цепочки: потребность → функция, которая её закрывает → подтверждённая ценность функции. Так строят работу DSRM (цели решения выводятся из проблемы) и AoA (исследование начинается с разрыва в возможностях).
</div>
<div markdown>
**2. Функции разбираются явно, с правом не брать функцию**

Вместо «продукт целиком набрал 85» решение принимается по каждой функции: брать, адаптировать, заменить или не брать. Классы Kano показывают, без чего нельзя, а что лишь приятно. Критические элементы из TRA (GAO) показывают, от чего зависит результат.
</div>
<div markdown>
**3. Вывод доказывается, а не подсчитывается**

Каждый вывод записывается как аргумент Тулмина: утверждение, факты, связь фактов с выводом и условия, при которых вывод неверен. Ворота Stage-Gate не пускают на следующий этап без готовых выходов. На первой странице ответ стоит первым (Минто), детали ниже, данные — в приложении (Amazon).
</div>
</div>

<div class="rnd-grid" markdown>
<div class="take" markdown>
**Берём**

- ворота с решениями «дальше / вернуться / остановить» (Stage-Gate);
- классы функций (Kano);
- ключевые функции = критические элементы (GAO TRA);
- «опыт других» и вариант «ничего не делать» (Rust RFC, AoA);
- аргумент Тулмина для каждого вывода;
- ответ первым (Минто).
</div>
<div class="adapt" markdown>
**Адаптируем**

- Kano без анкеты: класс функции определяется по нашим историям и по тому, совпадает ли решение у аналогов;
- оценку функций DESMET — без баллов: «закрывает / с доработкой / нет»;
- сценарии использования Gartner CC — вместо весов;
- оценку источников MLR — как уровни доказательства А–Г.
</div>
<div class="drop" markdown>
**Не берём**

- числовую оценку возможности ODI: нужен опрос многих клиентов, а у нас две роли людей;
- финансовые пороги Stage-Gate (NPV, окупаемость): платформа внутренняя;
- тяжёлый регламент AoA: утверждение плана отдельным органом;
- взвешенную сумму как основание выбора: она остаётся в приложении для сверки.
</div>
</div>

<div markdown>**Э1 Вопрос**SCQA, кто решает <span class="gate">G1</span></div>
<div markdown>**Э2 Потребности**работы и исходы из историй <span class="gate">G2</span></div>
<div markdown>**Э3 Опорное решение**его ключевые функции <span class="gate">G3</span></div>
<div markdown>**Э4 Альтернативы**их ключевые функции <span class="gate">G4</span></div>
<div markdown>**Э5 Ценность**почему функция важна, доказательство <span class="gate">G5</span></div>
<div markdown>**Э6 Перенос**брать / адаптировать / не брать → критерии <span class="gate">G6</span></div>
<div markdown>**Э7 Выбор**отсев, сравнение, риски, пересмотр <span class="gate">G7</span></div>
</div>

**Риски и пересмотр.** v3 дороже v2, потому что требует разбора функций. Поэтому для R&D малого масштаба (выбор библиотеки, решение одной функции) допускается сокращённый путь: Э3 и Э4 сводятся в одну таблицу функций. Пересматриваем методологию, если два R&D подряд прошли все ворота, а ревью нашло вывод без основания.

## Э1. Вопрос {#e1}

**Ситуация.** У платформы 18 R&D. Методология v2 ([О-25](../rules/deviations.md)) добавила отсев по обязательным условиям (MUST), сценарии качества и шкалы с якорями. Эталон — выбор трекера.

**Осложнение.** Владелец продукта отметил в эталоне v2 три проблемы:

- не видно, откуда взяты критерии и какую ценность они несут;
- не выделены ключевые функции решений и не рассматривается, можно ли взять другую функцию или отказаться от функции;
- выводы держатся на цифрах (85 против 64), а не на логике, и первая страница — это таблица.

**Вопрос.** Какая методология даёт явную зависимость каждого шага от предыдущего, проверки между шагами и подачу результата, понятную за 3 минуты?

**Решает:** владелец продукта. **Не решаем:** методику историй ([us-methodology](../rules/us-methodology.md)) — она уже построена на потоках аналогов.

<span class="gate">G1</span> ✅ вопрос сформулирован как выбор, есть владелец решения, вопрос связан с отклонением О-25 и замечаниями владельца.

## Э2. Потребности {#e2}

Потребности выведены из замечаний владельца продукта (сообщения от 11.10.2026) и из прошлых отклонений.

| # | Потребность: исследование должно… | Откуда | Что ломается без неё |
|---|---|---|---|
| П1 | делать каждый следующий шаг из выхода предыдущего и пускать дальше только после проверки | замечание «зависимость шагов, quality gate» | выводы без основания, этапы пропускаются |
| П2 | показывать происхождение и ценность каждого критерия | замечание «откуда критерии, ценность» | критерии произвольные, веса «на глаз» |
| П3 | выделять ключевые функции решений и разбирать, брать ли их, заменить ли другими, отказаться ли | замечание «основные функции, отказаться от функций» | сравниваются продукты целиком, теряются функции аналогов |
| П4 | подтверждать ценность функции доказательством | замечание «подтвердили ценность» | функции берутся по моде |
| П5 | давать последовательность выводов, которую можно проверить | замечание «последовательность выводов» | читатель не может проверить вывод |
| П6 | показывать на первой странице ответ и основания за 3 минуты, а детали и цифры ниже | замечание о подаче | решение тонет в таблицах |
| П7 | отсекать варианты без обязательных свойств до сравнения | О-25 (облачный трекер выше открытого) | неприемлемый вариант побеждает по сумме |
| П8 | искать альтернативы широко и проверять факты на дату | О-25 (Hermes, устаревшие данные о Plane) | выбор из знакомого, устаревшие факты |

П7 и П8 — базовые: v2 их уже закрывает, и их нужно сохранить. П1–П6 — то, чего в v2 нет.

<span class="gate">G2</span> ✅ у каждой потребности есть источник и последствие отсутствия; базовые потребности отделены от недостающих.

## Э4. Альтернативы и их ключевые функции {#e4}

Поиск 11.10.2026 по трём группам источников:

- процессы исследований и разработки (Stage-Gate, DSRM, AoA, NASA trade study, GAO TRA);
- анализ функций и ценности (Kano, ODI, Opportunity Solution Tree, DESMET, Gartner CC, NN/g);
- форматы обоснования и подачи (Rust RFC, Тулмин, Минто, Amazon 6-pager, Tech Radar, MLR).

Вариант «ничего не делать» означает остаться на v2.

### Процессы с этапами и проверками

| Методика | Ключевые функции | Как устроен опубликованный результат |
|---|---|---|
| **Stage-Gate** (Cooper) | этапы работ разделены воротами; на воротах — «дальше / остановить / подождать / вернуться»; два вида критериев: обязательные (отсекают сразу) и желательные (сравниваются); ворота проверяют, что обещанные на прошлом этапе выходы готовы | пакет к воротам: выходы этапа и решение по ним |
| **DSRM** (Peffers и др., 2007) | 6 активностей: проблема и мотивация → цели решения → разработка → демонстрация → оценка → коммуникация; цели выводятся из проблемы; можно вернуться назад | статья по тем же 6 разделам, проверена на 4 кейсах |
| **AoA** (DoD) | начинается с разрыва в возможностях и операционных требований; есть базовая линия «как сейчас»; компромиссы стоимость / срок / характеристики; чувствительность; план исследования утверждается до работы | отчёт: потребность и недостатки → требования → базовая линия и альтернативы → затраты → компромиссы и чувствительность → рекомендации |
| **NASA trade study** | цели → альтернативы → критерии → оценка → документирование; явно фиксирует допущения и ограничения | отчёт: постановка, цели, критерии, альтернативы, процедура оценки, результаты, допущения, ограничения |
| **GAO TRA** (GAO-20-48G) | 5 шагов: план и команда → выделение **критических технологических элементов** → оценка их зрелости по доказательствам → отчёт → использование; качество отчёта — достоверный, объективный, воспроизводимый, полезный | отчёт по шаблону GAO, проверяемый по четырём качествам |

### Анализ функций и ценности

| Методика | Ключевые функции |
|---|---|
| **Kano** | классы функций: базовая (без неё продукт неприемлем), линейная (чем лучше, тем лучше), привлекательная (приятна, её отсутствие не замечают), безразличная, обратная (мешает); классы смещаются со временем: привлекательная становится базовой |
| **ODI** (Ulwick, JTBD) | потребность — желаемый исход работы, а не функция; важность против удовлетворённости даёт недообслуженные исходы; нужен опрос |
| **Opportunity Solution Tree** (Torres) | исход → возможности → решения → проверки допущений; у возможности должно быть несколько решений, иначе это решение под видом возможности; провал проверки — вернуться на уровень выше |
| **DESMET feature analysis** (Kitchenham) | список функций и шкалы суждений; отбор по документации, затем испытание; допустимо сравнение без числовых баллов, если цель — сравнить, а не ранжировать |
| **Gartner Critical Capabilities** | критические возможности — те, что **отличают** продукты; оценка по 3–7 сценариям использования, у каждого сценария свои веса |
| **NN/g competitive evaluation** | разбор конкурентов по функциям и задачам: что делают, как, что работает; делается до проектирования |

### Обоснование и подача

| Формат | Ключевые функции |
|---|---|
| **Rust RFC** | разделы «обоснование и альтернативы» (почему это лучшее, что ещё рассматривали, что будет, если не делать) и «опыт других» (что сработало и что нет у других; чужой пример — не довод сам по себе) |
| **Модель Тулмина** | утверждение, основания (факты), связка (почему факты ведут к выводу), подкрепление связки, оговорка («обычно»), опровержение (когда вывод неверен) |
| **Пирамида Минто, SCQA** | ответ первым; ситуация → осложнение → вопрос → ответ; каждый уровень резюмирует нижний; группы не пересекаются и покрывают всё (MECE) |
| **Amazon 6-pager** | связный текст вместо пунктов: фраза заставляет назвать причину; данные — в приложении, текст на них ссылается |
| **Tech Radar** | кольцо (Adopt / Trial / Assess / Hold) и короткий текст «почему» |
| **MLR** (Garousi и др.) | серые источники (блоги, документация) учитываются, но с оценкой качества источника |

<span class="gate">G4</span> ✅ кандидаты из трёх групп источников, дата поиска есть, у каждой методики выписаны ключевые функции со ссылкой на источник (раздел «Источники»).

## Э5. Ценность функций {#e5}

Функция ценна, если закрывает нашу потребность и это подтверждено. Уровни доказательства:

- **А** — проверено нами;
- **Б** — первичный источник (стандарт, исходная статья, документация);
- **В** — опыт практиков и вторичные обзоры;
- **Г** — заявление без деталей.

| Функция | Потребность | Почему ценна | Доказательство | Класс для нас |
|---|---|---|---|---|
| Ворота с проверкой выходов и возвратом | П1 | переход только при готовых выходах — неполный этап не тянет за собой неверный вывод | Stage-Gate широко применяется в разработке продуктов (В); проверка выходов прошлого этапа на воротах (Б, Cooper); возврат назад в DSRM (Б) | базовая |
| Цели или критерии выводятся из проблемы | П2 | у критерия есть происхождение | DSRM: «цели решения» после «проблемы» (Б); AoA: от разрыва в возможностях к требованиям (Б) | базовая |
| Ключевые функции = критические элементы | П3 | сравниваем то, от чего зависит результат, а не все свойства подряд | GAO TRA: выделение критических элементов — отдельный шаг (Б); Gartner CC: оценивают отличающие возможности (Б) | базовая |
| Классы функций Kano | П3, П2 | видно, без чего нельзя (→ MUST), что сравниваем, что приятно; можно отказаться от безразличного | Kano (Б, обзоры В); классы смещаются со временем — поэтому смотрим аналоги на дату | линейная |
| Решение по каждой функции (брать / заменить / не брать) | П3 | можно взять функцию у отсеянного продукта и отказаться от лишней у выбранного | OST: у возможности несколько решений (Б); RFC: «что ещё рассматривали» (Б); у нас — потоки аналогов уже дали истории по функциям Linear, Jira, Copilot ([R&D потоков](us-analogs-agent-tracker.md), А) | базовая |
| Уровни доказательства | П4, П8 | маркетинг не выдаётся за факт | MLR: оценка качества серых источников (Б); наш случай «у Plane нет агентов» устарел ([О-25](../rules/deviations.md), А) | базовая |
| Аргумент Тулмина для вывода | П5 | связка и опровержение явны — вывод можно проверить и оспорить | модель Тулмина (Б); NASA trade study требует допущений и ограничений (В) | линейная |
| Ответ первым, SCQA | П6 | читатель за минуты получает ответ и основания | Минто (В); краткий итог вверху в AoA и RFC (Б) | базовая |
| Связный текст, данные в приложении | П6, П5 | фраза требует причины, а таблица — нет | Amazon 6-pager (В) | линейная |
| Вариант «ничего не делать» и опыт других | П8 | есть базовая линия для сравнения | AoA — базовая линия (Б); Rust RFC (Б) | линейная |
| Сравнение без баллов | П5, П6 | оценки «закрывает / с доработкой / нет» с фактом понятнее, чем «4 из 5» | DESMET в исследовании железнодорожных инструментов: сравнение без числовой схемы (Б) | линейная |
| Оценка по сценариям использования | П2 | важность функции задаётся сценарием, а не весом «на глаз» | Gartner CC (Б); ATAM-сценарии в v2 (А) | привлекательная |

| Финансовые пороги Stage-Gate | — | — | NPV и окупаемость не применимы к внутренней платформе без выручки | безразличная — не берём |
| Утверждение плана отдельным органом (AoA) | П1 | — | у нас один владелец решения; ворота G1 его заменяют | обратная: тормозит малые R&D |

**Вывод этапа.** Базовые функции новой методологии:

- ворота;
- цепочка «проблема → цели»;
- критические функции;
- решение по каждой функции;
- уровни доказательства;
- ответ первым.

Остальные функции усиливают методологию. Две функции не берём, потому что у нас для них нет данных и цели.

<span class="gate">G5</span> ✅ у каждой функции есть потребность и доказательство уровня Б или выше; гипотез уровня Г нет.

## Э6. Перенос в нашу методологию {#e6}

| Функция | Решение | Как переносим | Становится критерием методологии |
|---|---|---|---|
| Ворота | **брать** | после каждого этапа — ворота G1–G7 с вопросами «готовы ли выходы»; исход «дальше / вернуться на этап N / остановить» | «каждый этап закрыт воротами» |
| Цели из проблемы | **брать** | Э2 «Потребности» выводит работы и исходы из историй и требований; критерий в Э6 ссылается на потребность | «у критерия есть цепочка до потребности» |
| Критические функции + Kano | **адаптировать** | ключевые функции опорного решения и альтернатив (Э3, Э4); класс Kano — по историям и по совпадению у аналогов, без анкеты | «базовые функции → MUST, линейные → сравнение» |
| Решение по каждой функции | **брать** | таблица переноса «брать / адаптировать / заменить / не брать» с причиной | «у каждой функции есть решение и причина» |
| Уровни доказательства | **адаптировать** | А–Г у каждого факта о ценности и наличии; уровень Г → прототип или «не подтверждено» | «ценность подтверждена уровнем Б или выше» |
| Аргумент Тулмина | **брать** | каждый вывод этапа и итог: утверждение — факты — почему — когда неверно | «у вывода есть опровержение» |
| Ответ первым | **брать** | первая страница: вопрос → ответ → 3 основания → берём / адаптируем / не берём → отсеяны → риски и пересмотр | «первая страница читается за 3 минуты» |
| Данные в приложении | **адаптировать** | матрица баллов, карточки и сверка — в сворачиваемом приложении; баллы необязательны | «вывод не опирается на сумму баллов» |
| «Ничего не делать», опыт других | **брать** | в длинном списке всегда есть «как сейчас» и «сделать самим» | — (уже в v2) |
| Сравнение без баллов | **брать** | в Э7 у каждого кандидата: «закрывает / закрывает с доработкой (что и сколько) / не закрывает» с фактом | — |
| Отсев MUST, сценарии, карточка, поиск, AG1–AG6 из v2 | **оставить** | MUST получаются из базовых функций; сценарии качества задают проверку функции | — |
| Взвешенная сумма v2 | **не брать как основание** | только сверка в приложении | — |
| ODI-оценка, финансовые пороги, утверждение плана | **не брать** | причины — в Э5 | — |

<span class="gate">G6</span> ✅ у каждой функции есть решение и причина; критерии оценки методологии выведены из переноса.

## Э7. Выбор {#e7}

**Отсев по базовым потребностям** (П7 и П8 обязательны, П1–П6 — недостающие):

| Вариант | П7 отсев до сравнения | П8 широкий поиск и дата | Итог |
|---|---|---|---|
| Остаться на v2 | ✅ | ✅ | проходит, но не закрывает П1–П6 |
| Взять одну методику целиком (например, Stage-Gate или DSRM) | Stage-Gate ✅; DSRM — нет | нет | ✗: ни одна методика не закрывает функции, ценность и подачу вместе |
| v3 = v2 + функции из таблицы переноса | ✅ | ✅ | проходит |

**Сравнение** по потребностям П1–П6:

| Потребность | Остаться на v2 | v3 |
|---|---|---|
| П1 зависимость шагов и ворота | частично: путь есть, ворот нет | закрывает: G1–G7, возврат на этап |
| П2 происхождение критериев | частично: критерий → сценарий | закрывает: потребность → функция → ценность → критерий |
| П3 ключевые функции, замена и отказ | не закрывает | закрывает: Э3, Э4, таблица переноса |
| П4 подтверждённая ценность | не закрывает | закрывает: уровни А–Г |
| П5 последовательность выводов | не закрывает: итог — число | закрывает: вывод каждого этапа и аргумент итога |
| П6 подача за 3 минуты | частично: таблица итога | закрывает: первая страница-презентация |

**Вывод.**

- **Утверждение:** принимаем v3.
- **Основания:** v3 закрывает П1–П6 и сохраняет закрытые v2 потребности П7–П8. Каждая перенесённая функция подтверждена первичным источником.
- **Связка:** ни одна методика из длинного списка не закрывает все потребности. Комбинация закрывает, потому что функции берутся у тех методик, где они проверены.
- **Когда неверно:** если R&D по v3 будут занимать в разы больше времени без роста качества выводов. Тогда применяем сокращённый путь для малых R&D. Признак проблемы — ревью находит вывод без основания при пройденных воротах.

**Риски.**

| Риск | Что делаем |
|---|---|
| R&D дороже: разбор функций у 5–8 кандидатов | сокращённый путь для малых R&D; функции берём только ключевые, по истории или требованию |
| Формальные ворота: галочки без проверки | у ворот — вопросы с конкретными выходами; проверка в сборке и на ревью ([роли ревью](../rules/roles.md)) |
| Классы Kano без анкеты субъективны | класс обосновывается историей и совпадением у аналогов; спорный класс — вопрос владельцу продукта |

<span class="gate">G7</span> ✅ отсев до сравнения, сравнение с фактами, вывод с условием, при котором он неверен, риски и пересмотр.

## Как оформлены опубликованные исследования

Из разобранных форматов видно, что печатают на страницах и какие качества ценят.

| Формат | Страницы (по порядку) | Ценимые качества |
|---|---|---|
| AoA (DoD) | потребность и недостатки → требования → базовая линия и альтернативы → затраты → компромиссы и чувствительность → рекомендации | трассируемость к потребности, честная базовая линия |
| NASA trade study | постановка → цели → критерии → альтернативы → процедура → результаты → допущения → ограничения | явные допущения и ограничения |
| GAO TRA | план и команда → критические элементы → оценка по доказательствам → отчёт → использование | достоверность, объективность, воспроизводимость, полезность |
| Gartner Critical Capabilities | сценарии использования → возможности → оценки по сценариям | оценка в контексте сценария, а не в целом |
| Rust RFC | кратко → мотивация → описание → обоснование и альтернативы → опыт других → открытые вопросы | что ещё рассматривали и почему нет |
| Инженерный блог (Uber, переход Postgres → MySQL) | контекст → конкретные проблемы с механизмом каждой → решение | каждая проблема объяснена механизмом, а не оценкой |
| Tech Radar | кольцо → короткий текст «почему» | одна мысль, понятная без таблиц |

**Общее у всех:** ответ или краткое изложение сверху; потребность до альтернатив; базовая линия; допущения и ограничения; условия пересмотра. Четыре качества GAO стали проверкой финальных ворот в [правиле](../rules/rnd-methodology.md#gates).

<summary>Приложение: сверка числом (необязательно)</summary>

Для сверки: доля закрытых потребностей П1–П8 («закрывает» = 1, «частично» = 0,5). v2 — 3,5 из 8, v3 — 8 из 8. Число лишь подтверждает вывод Э7, основанием выбора оно не является.
