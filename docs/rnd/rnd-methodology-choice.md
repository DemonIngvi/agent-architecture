# R&D: Как проводить и подавать исследования

← [Все R&D](README.md) · [методология R&D (правило)](../rules/rnd-methodology.md) · [журнал отклонений](../rules/deviations.md) · компонент: **правила документации** · методология **v3.1** (этот документ — её обоснование)

<div class="rnd-hero" markdown>
<div class="rnd-q">Вопрос</div>
Как проводить R&D, чтобы были видны путь к выводу, происхождение критериев и ценность функций, решение оценивалось на своём месте в архитектуре и с разных позиций, выбор доходил до спек и задач, а читатель за 3 минуты понимал выбор и его основания?

<div class="rnd-a">Ответ: R&D идёт по цепочке «потребность → функции → ценность → перенос → встраивание → спор ролей → выбор → последствия». Каждый этап закрывается воротами. Первая страница — микропрезентация с пропорциями, цифры — в приложении.</div>

<span class="rnd-badge adopt">Adopt</span> методология v3.1 заменяет v2 · основа: Stage-Gate, разбор функций (Kano, GAO TRA), IRL, диалектический спор, анализ влияния, аргумент Тулмина, пирамида Минто · эталон — [выбор трекера](tracker-choice.md)
</div>

**Почему так.** Три вывода, у каждого есть основание:

<div class="rnd-grid" markdown>
<div markdown>
**1. Критерий — это следствие, а не исходная точка**

В v2 критерии и веса задавались до разбора функций, поэтому было неясно, откуда они взялись. В v3 критерий получается в конце цепочки: потребность → функция, которая её закрывает → подтверждённая ценность функции. Так строят работу DSRM (цели решения выводятся из проблемы) и AoA (исследование начинается с разрыва в возможностях).
</div>
<div markdown>
**2. Решение оценивается на своём месте и с разных сторон**

Лучший «сам по себе» вариант может ломать стыки и владельцев данных. Поэтому в Э7 каждый кандидат проходит по I-кодам и S-кодам, а готовность его стыков оценивается шкалой И0–И4 (по IRL). Затем роли с разными интересами спорят о выборе. Обзор 52 исследований структурированного конфликта показывает, что такой спор улучшает стратегические решения ([Fjermestad](https://nowpublishers.com/article/Details/ISY-013)).
</div>
<div markdown>
**3. Вывод доказывается и доходит до документов**

Каждый вывод записывается аргументом Тулмина: утверждение, факты, связка, условие, при котором вывод неверен. Таблица последствий (Э10) переносит выбор в design, спеки, задачи и техспеки со статусом «внесено / предложено / не требуется». Сводка последствий собирается автоматически.
</div>
</div>

<div class="rnd-grid" markdown>
<div class="take" markdown>
**Берём**

- ворота «дальше / вернуться / остановить» (Stage-Gate);
- ключевые функции как критические элементы (GAO TRA);
- «опыт других» и вариант «ничего не делать» (Rust RFC, AoA);
- оппонент и «адвокат дьявола»;
- аргумент Тулмина для каждого вывода;
- ответ первым (Минто).
</div>
<div class="adapt" markdown>
**Адаптируем**

- Kano без анкеты: класс — по историям и совпадению у аналогов;
- IRL — упрощённая шкала И0–И4 по нашим I-кодам;
- оценку функций DESMET — без баллов: «закрывает / с доработкой / нет»;
- участников ATAM — роли документации и персоны;
- анализ влияния — таблицей последствий по трассировке;
- оценку источников MLR — уровнями доказательства А–Г.
</div>
<div class="drop" markdown>
**Не берём**

- числовую оценку возможности ODI: нужен опрос многих клиентов;
- финансовые пороги Stage-Gate (NPV, окупаемость);
- утверждение плана отдельным органом (AoA);
- формулу SRL (TRL × IRL): числа без данных;
- взвешенную сумму как основание выбора.
</div>
</div>

<div class="no" markdown>
**Отсеяны до сравнения**

- **Одна методика целиком** (Stage-Gate, DSRM, AoA): ни одна не закрывает вместе функции, встраивание, спор и подачу.
</div>
<div class="risk" markdown>
**Риски и пересмотр**

- R&D дороже: сокращённый путь для малых вопросов; встраивание и последствия не сокращаются.
- Пересматриваем методологию, если два R&D подряд прошли все ворота, а ревью нашло вывод без основания.
</div>

## Э1. Вопрос {#e1}

**Ситуация.** У платформы 18 R&D. Методология v2 ([О-25](../rules/deviations.md)) добавила отсев по обязательным условиям, сценарии качества и шкалы с якорями.

**Осложнение.** Владелец продукта отметил в эталоне v2 три проблемы:

- не видно, откуда критерии и какую ценность они несут;
- не выделены ключевые функции решений и не рассмотрено, брать ли функции других решений и от каких отказаться;
- выводы держатся на цифрах, а первая страница — это таблица.

После v3 он добавил ещё три проблемы:

- решение исследуется без интеграции с другими системами и без места в общей схеме;
- не прослеживается, что из R&D меняется в спеках и задачах;
- выбор не обсуждается с позиций разных ролей.

Плюс замечание о подаче: нужна наглядность — цвет и микропрезентация с пропорциями, как для заказчика.

**Вопрос.** Какая методология даёт:

- явную зависимость шагов и ворота между ними;
- оценку решения на его месте в архитектуре и с разных позиций;
- перенос выбора в документы;
- подачу, понятную за 3 минуты?

**Решает:** владелец продукта. **Не решаем:** методику историй ([us-methodology](../rules/us-methodology.md)) — она построена на потоках аналогов.

<span class="gate">G1</span> ✅ вопрос сформулирован как выбор; есть владелец; вопрос связан с О-25, О-34, О-35 и замечаниями владельца.

## Э4. Альтернативы и их ключевые функции {#e4}

Поиск 11.10.2026 по пяти группам источников. Вариант «ничего не делать» — остаться на v2.

### Процессы с этапами и проверками

| Методика | Ключевые функции | Как устроен опубликованный результат |
|---|---|---|
| **Stage-Gate** (Cooper) | этапы разделены воротами; решения «дальше / остановить / подождать / вернуться»; обязательные критерии отсекают сразу, желательные сравниваются; ворота проверяют обещанные выходы | пакет к воротам: выходы этапа и решение |
| **DSRM** (Peffers и др., 2007) | проблема → цели решения → разработка → демонстрация → оценка → коммуникация; цели из проблемы; возврат назад | статья по 6 разделам, проверена на 4 кейсах |
| **AoA** (DoD) | от разрыва в возможностях к требованиям; базовая линия «как сейчас»; компромиссы; чувствительность; план утверждается до работы | потребность → требования → базовая линия и альтернативы → затраты → компромиссы → рекомендации |
| **NASA trade study** | цели → альтернативы → критерии → оценка → документирование; допущения и ограничения | постановка, цели, критерии, альтернативы, процедура, результаты, допущения, ограничения |
| **GAO TRA** (GAO-20-48G) | выделение **критических технологических элементов**; оценка зрелости по доказательствам; качества отчёта: достоверный, объективный, воспроизводимый, полезный | отчёт по шаблону GAO |

### Анализ функций и ценности

| Методика | Ключевые функции |
|---|---|
| **Kano** | классы: базовая, линейная, привлекательная, безразличная, обратная; классы смещаются со временем |
| **ODI** (Ulwick, JTBD) | потребность — желаемый исход работы; важность против удовлетворённости; нужен опрос |
| **Opportunity Solution Tree** (Torres) | исход → возможности → решения → проверки допущений; у возможности несколько решений; провал проверки — вернуться выше |
| **DESMET feature analysis** (Kitchenham) | список функций и шкалы суждений; отбор по документации, затем испытание; сравнение без числовых баллов допустимо |
| **Gartner Critical Capabilities** | оцениваются **отличающие** возможности, по 3–7 сценариям использования |
| **NN/g competitive evaluation** | разбор конкурентов по функциям и задачам до проектирования |

### Встраивание и влияние изменений

| Методика | Ключевые функции |
|---|---|
| **IRL / SRL** (Sauser, Stevens) | готовность **интеграции** оценивается отдельно от готовности технологии: уровни от «стык описан» до «стык работает в эксплуатации»; готовность системы = технологии × стыки |
| **Анализ влияния изменений** (change impact analysis) | влияние ищется по трассировке зависимостей между артефактами; итеративно, по транзитивным связям; изменение требований распространяется на элементы архитектуры |

### Спор и позиции

| Методика | Ключевые функции |
|---|---|
| **Диалектический спор** (dialectical inquiry, Mason) | подгруппы готовят противоположные варианты и спорят о допущениях; в полевых исследованиях эффективен для стратегических решений |
| **«Адвокат дьявола»** | назначенный участник атакует предложенное решение; в экспериментах даёт лучшие решения, чем консенсус |
| **Участники ATAM** | заинтересованные стороны приносят свои сценарии качества и голосуют за важные; сценарии проверяются на архитектуре |

### Обоснование и подача

| Формат | Ключевые функции |
|---|---|
| **Rust RFC** | «обоснование и альтернативы», «опыт других», «что если не делать» |
| **Модель Тулмина** | утверждение, основания, связка, подкрепление, оговорка, опровержение |
| **Пирамида Минто, SCQA** | ответ первым; ситуация → осложнение → вопрос → ответ; MECE |
| **Amazon 6-pager** | связный текст, данные в приложении |
| **Tech Radar** | кольцо и короткий текст «почему» |
| **MLR** (Garousi и др.) | серые источники с оценкой качества |

## Э7. Отсев и встраивание {#e7}

**Отсев.** Обязательны П7 и П8 (их закрывала v2):

| Вариант | П7 отсев до сравнения | П8 поиск и дата | Итог |
|---|---|---|---|

| Одна методика целиком (Stage-Gate, DSRM, AoA) | частично | нет | ✗: ни одна не закрывает функции, встраивание, спор и подачу |
| v3.1 | да | да | проходит |

**Встраивание в систему документации.** Стыки методологии — правила, роли, сборка и цепочка документов, которая идёт после R&D.

```
 истории, требования ──▶ R&D (Э1–Э10) ──▶ design (Dn) ──▶ спеки (R-…, interfaces.md) ──▶ задачи ──▶ код
                           │   ▲    │                                                       ▲
     роли и персоны (Э8)* ─┘   │    └── Э10 последствия* ──▶ сводка последствий R&D* ────────┘
     карта I1–I23 (Э7)* ───────┘                         └──▶ процесс изменений (синхронизация спек)*
     сборка: проверка структуры, цвет, слайды*
  * — стык новый или изменён в v3.1
```

| Стык | Что идёт | v2 | v3.1 |
|---|---|---|---|
| Истории и требования → R&D | потребности | частично: сценарии качества | закрывает: Э2 с источником |
| Карта интерфейсов → R&D | I-коды, S-коды | не закрывает | закрывает: Э7, шкала И0–И4 |
| Роли → R&D | позиции | не закрывает | закрывает: Э8 |
| R&D → design, спеки, задачи | последствия | частично: плюсы и минусы | закрывает: Э10 со статусами, сводка |
| R&D → процесс изменений | синхронизация спек | не закрывает | закрывает: ссылка из Э10, строка в [процессе изменений](../rules/change-process.md) |
| Сборка → R&D | проверка, отображение | частично: только реестр | закрывает: структура v3, цвет, слайды, сводка |

**Вывод этапа.** v3.1 не меняет цепочку «R&D → design → спеки → задачи», а замыкает её: вход из карты интерфейсов и ролей, выход через последствия и процесс изменений.

<span class="gate">G7</span> ✅ отсев до сравнения; стыки методологии с правилами, сборкой и цепочкой документов перечислены.

## Э8. Спор ролей {#e8}

Роли отыграны агентом 🤖. Оппонент защищает «остаться на v2», «адвокат дьявола» атакует v3.1.

| Роль | За | Главный довод | Опасение | Согласится, если |
|---|---|---|---|---|
| Владелец продукта 🤖 | v3.1 | видна логика выбора и что меняется в документах | R&D станут дольше | сокращённый путь для малых вопросов |
| Архитектор 🤖 | v3.1 | встраивание по I-кодам ловит перестройку схемы до выбора | — | шкала И0–И4 ссылается на матрицу интерфейсов |
| Проверяющий 🤖 | v3.1 | ворота и структура проверяются сборкой | галочки без проверки | у ворот есть конкретные выходы |
| Разработчик 🤖 | нейтрально | последствия попадают в задачи | предложения висят без исполнителя | предложения собраны в сводку и разбираются по процессу изменений |
| Автор R&D 🤖 (оппонент) | v2 | v3.1 дороже: функции, схема, спор, слайды | 16 документов переписывать | перевод идёт задачей; эталон и разметка `deck` упрощают оформление |

| Спор | Разрешение |
|---|---|
| «Адвокат дьявола»: «спор ролей отыгрывает один агент — это не спор» | **условие:** роли — отдельные проходы с промптами ролей ([роли](../rules/roles.md)); итог спора подтверждает человек 👤 в approvals при изменении спек |
| Автор R&D: «слишком дорого» | **условие:** сокращённый путь; встраивание и последствия не сокращаются |
| Разработчик: «предложения потеряются» | ✅ **внесено:** сводка последствий R&D собирается сборкой |

**Вывод этапа.** Четыре роли за v3.1, одна нейтральна. Возражения сняты условиями и сводкой последствий.

<span class="gate">G8</span> ✅ у каждой роли есть позиция и условие; каждый спор разрешён.

## Как оформлены опубликованные исследования

| Формат | Страницы (по порядку) | Ценимые качества |
|---|---|---|
| AoA (DoD) | потребность → требования → базовая линия и альтернативы → затраты → компромиссы → рекомендации | трассируемость к потребности, честная базовая линия |
| NASA trade study | постановка → цели → критерии → альтернативы → процедура → результаты → допущения → ограничения | явные допущения и ограничения |
| GAO TRA | план → критические элементы → оценка по доказательствам → отчёт → использование | достоверность, объективность, воспроизводимость, полезность |
| Gartner Critical Capabilities | сценарии → возможности → оценки по сценариям | оценка в контексте сценария |
| Rust RFC | кратко → мотивация → описание → альтернативы → опыт других → открытые вопросы | что ещё рассматривали |
| Инженерный блог (Uber, Postgres → MySQL) | контекст → проблемы с механизмом каждой → решение | механизм, а не оценка |
| Tech Radar | кольцо → короткий текст | одна мысль без таблиц |

**Общее:** ответ сверху; потребность до альтернатив; базовая линия; допущения; условия пересмотра. Качества GAO стали финальной проверкой в [правиле](../rules/rnd-methodology.md#gates).
