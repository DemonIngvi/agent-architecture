<div class="rnd-q">Вопрос</div>
Как разрабатывать, выкатывать и наблюдать платформу и агентов, чтобы каждое изменение было проверено до прода, а расход токенов и построение цепочек были ограничены принудительно, а не оповещением постфактум?

<div class="rnd-a">Ответ: контроль расхода — три уровня. L1: шлюз LiteLLM с резервом стоимости до вызова и отказом при сбое счётчика. L2: оркестратор со своим резервом на run и issue, потому что эту иерархию шлюз не знает. L3: детекторы аномалий и kill switch. Изменения идут по одному конвейеру: PR, CI на mock-LLM, eval-гейт, staging на модели, выбранной владельцем для прода, с малым бюджетом, прод. Версия агента откатывается на явный baseline за ≤ 5 мин. MVP (этапы 1–3) — L1, L2, CI с eval-гейтом, среды и базовые алерты стоимости с получателем. GitOps, канарейка агентов, SLO, детекторы по базе и DORA — этап 4.</div>

<span class="rnd-badge assess">Assess</span> готовых порогов для агентов нет (SLO и аномалии — стартовые, по базе 2–4 недели) · своё измерение — на staging после этапа 3 · данные 14.10.2026
</div>

**Почему так.** Четыре вывода, у каждого есть основание:

<div class="rnd-grid" markdown>
<div markdown>
**1. Лимит, а не оповещение**

AWS Agentic AI Lens (документ с практиками; сервисы AWS/Azure не выбираются и не используются) (AGENTCOST07) требует проверок до вызова на цикл, задачу и день, вне цикла агента, а не «алертов после факта». Резерв стоимости до вызова в LiteLLM включён по умолчанию; без него параллельные запросы могут превысить бюджет.
</div>
<div markdown>
**2. Иерархию run и issue шлюз не знает**

Бюджеты LiteLLM идут по организации, команде, пользователю, ключу. Бюджет задачи и запуска — наш слой с тем же резервом из max_tokens: «зарезервировано + потрачено > лимита — отказ».
</div>
<div markdown>
**3. Изменение промпта — изменение кода**

Anthropic: evals на каждое изменение агента и обновление модели. AWS (AGENTOPS02-BP03) — неизменяемая версия, явный baseline, откат < 5 мин. Поэтому гейт обязателен и для промптов, и для моделей.
</div>
<div markdown>
**4. Деградацию провайдера ловит только прод**

В постмортеме Anthropic (сентябрь 2025) evals пропустили ошибку, доля затронутых запросов выросла с 0,8% до 16%. Нужна непрерывная оценка доли трафика на проде, а не только тесты до выката.
</div>
</div>

## Э3. Опорное решение: как сейчас {#e3}

- **Бюджеты.** R-GRD-11: потолок max output, затем run, budget.issue, agent_day, project_month; принудительно в Runner (G1) и в LiteLLM на каждом вызове (G4); 80% — предупреждение, 100% — отказ. Задача 4.5. `key.max_budget ≤ budget.daily_usd`.
- **Защита от петель.** runaway-protection F1–F7: повтор вызовов 3, шаги без прогресса 8, max_steps 30, аномалия шага 5× → ожидание подтверждения, circuit 3 ошибки, kill switch (R-GRD-15). R-AP-25: maxRuns, maxTotalRuns 8.
- **Наблюдаемость.** run_event в Postgres, затраты из журнала LiteLLM (R-OBS-05), сводка и стоимость на принятую задачу (R-OBS-13, 3.9). Имена событий сопоставлены с OTel GenAI. Алертинга нет.
- **Деплой.** R-INF-03 Helm с версией и values по средам; сборка по тегу в CI-системе (в techspec описаны GitHub Actions и `ghcr.io`, выбор — В-CI), digest-pin, SBOM, Trivy блокирует critical; обновление и откат в techspec (PITR перед upgrade, миграции только вперёд); проверка после развёртывания — ручной чек-лист.
- **Валидность.** mock-LLM и LiteLLM (1.1), fitness D28 F1–F9 (4.4.33), версии агента и откат ≤ 5 мин (R-REG-14, 4.4.30), R-MEM-16.
- **Среды.** R-INF-12: docker compose (этапы 1–2) и k3d (этап 4); один узел k3s с namespaces (R-INF-18). GitOps и Sealed Secrets в статусе Hold.

**Вывод этапа.** Лимиты есть на бумаге (R-GRD-11), но нет резерва run и issue на уровне Runner с проверкой гонки, нет сверки счётчика, нет конвейера доставки, алертов и сред.

## Э5. Ценность функций {#e5}

### Слой 1: критерии (из методики валидной оценки)

Качество работы с независимой приёмкой и pass^k (τ-bench, ABC checklist); стоимость на принятую задачу совместно с качеством (AI Agents That Matter: LATS в 50 раз дороже без выигрыша, SWE-agent при лимите $4 на задачу — более $8000 за прогон); разброс, а не одно число (Adding Error Bars to Evals). Метрики качества, на которые смотрит eval-гейт, считаются так же.

### Что обязательно для «гарантированного» контроля токенов

| Функция | Класс | Основание | Следует из источников? |
|---|---|---|---|
| Резерв максимальной стоимости до вызова (L1) | обязательная | LiteLLM; AWS AGENTCOST07: проверки до вызова | да, прямо |
| Отказ при недоступности счётчика (`fail_closed`) | обязательная | LiteLLM: без Postgres бюджеты не блокируют; Azure: счётчик на gateway | да, прямо |
| max_tokens и `default_estimated_output_tokens` всегда заданы | обязательная | резерв считается по max_tokens | да, прямо |
| Свой слой run и issue с резервом (L2) | обязательная | LiteLLM: иерархия run ≤ issue ≤ agent_day нативно не ложится | вывод из ограничений шлюза |
| Лимиты кругов, вызовов, глубины (L2) | обязательная | AWS: лимиты итераций и вызовов тулов | да |
| Детекторы аномалий и kill switch (L3) | обязательная | AWS BP02; контроль вне цикла агента | да |
| Замедление при 70–80%, стоп при 100% | ожидаемая | AWS: «обычный пик замедляется, патологическая сессия останавливается» | да; 70–80% — наша оценка, к замеру |
| Сверка Redis и БД, TTL резервов | обязательная | LiteLLM: Redis после рестарта может быть ниже факта; issue №27639 | да, косвенно |
| Слепые зоны: batch, маршруты без цены, модели с нулевой ценой | обязательная | LiteLLM: резерв не работает | да; запрет таких маршрутов в проде |
| Теги стоимости и один trace на задачу | ожидаемая | AWS AGENTCOST05, OTel | да |

**Следует ли три уровня из источников.** Да: AWS требует лимиты до вызова и вне цикла агента (L1, L2), отдельно детекторы аномалий и аварийную остановку (L3); LiteLLM показывает, что один L1 не покрывает run и issue и не видит слепые зоны. Слабое звено — иерархия run и issue: источника готового решения нет, это наш слой, помечено в [Э9](#e9).

**Вывод этапа.** Десять функций контроля токенов, девять из них прямо следуют из источников, одна (слой run и issue) — вывод из ограничений шлюза.

## Э6. Перенос и критерии {#e6}

### Расхождение CI: решение по фактам

### Решения

1. **Контроль токенов — B.** L1: LiteLLM с Postgres, Redis, резервом, `fail_closed_budget_enforcement`, обязательные max_tokens и `default_estimated_output_tokens`; в проде запрещены маршруты без цены и batch в обход резерва. L2: резерв run и issue в Runner по формуле «зарезервировано + потрачено > лимита — отказ». L3: детекторы AWS и kill switch, до базы — алерты и замедление.
2. **Замедление при 70–80%, стоп при 100%** (проценты — наша оценка, к замеру).
3. **Алерты стоимости получает владелец проекта и администратор** (канал по умолчанию — уведомления в самом ICPlan; внешний канал — только по решению владельца). 📌 вопрос В-алерты: канал и получатель.
4. **Конвейер.** PR → CI (линт, юнит, контракт тулов на mock-LLM) → eval-гейт (promptfoo; 20–50 задач из реальных сбоев; pass^k; детерминированные проверки раньше судьи) → staging (модель, выбранная владельцем для прода, малый бюджет) → прод. Единица релиза — связка «модель + промпт + настройки + права тулов + оркестрация».
5. **Среды.** dev и CI — mock-LLM; staging — модель, выбранная владельцем для прода, с потолком; прод; БД, секреты, namespaces разделены. Совместимо с R-INF-12.
6. **Версии агента.** Неизменяемые, semver, ссылка на eval, метка baseline; откат — перенос метки.
7. **Платформа.** Этапы 1–3: Helm из конвейера выбранной CI-системы с smoke; этап 4: Argo CD + Rollouts; миграции expand/contract.
8. **SLO и on-call (этап 4).** Три слоя SLI + доля run в бюджете; burn rate; раннбук вне платформы, учения раз в квартал.
9. **Отчёт затрат** владельцу раз в неделю (С11).

### Поэтапный план

| Этап | Что входит | Привязка |
|---|---|---|
| MVP (1–3) | L1 с резервом и `fail_closed`; L2 резерв run и issue; CI в выбранной владельцем системе с mock-LLM и eval-гейтом; среды dev/CI (mock) и staging (модель владельца, малый бюджет); алерты стоимости 80% и 100% с получателем; отчёт затрат; baseline и откат версий агента | 1.1, 3.3, 3.9, 4.5 (часть) |
| Этап 4 | Argo CD + Rollouts, канарейка агентов, SLO и on-call, детекторы по базе 2–4 недели, Langfuse и OTel полностью, DORA, хаос-тест провайдера, нагрузочный k6 | 4.4.30, 4.5, 4.6, 4.7, 4.8 |

Часть 4.5 (резерв, лимиты) переносится в MVP, потому что без неё «гарантии» нет. 📌 внести в Э10; согласие владельца — вопрос В-4.5.

- **Утверждение.** Принимаем решения 1–9. Сроки: 1, 2 — вместе с первым вызовом реальной модели (граница этапов 1–2); 3, 4, 5, 9 — этап 3; 6 — этап 3, развитие в 4.4; 7, 8 — этап 4.
- **Когда неверно.** Если L2 даёт ошибки гонки при F1 — переходим на резерв только в L1 с ключом на run. Если ложные отказы по фантомным резервам превышают порог — режим резерва выключается по агенту при сохранении лимитов кругов. Если нагрузка вырастет — канарейка переносится раньше.

**Вывод этапа.** Выбран B и поэтапный D1 → D2; CI-система — вопрос владельцу В-CI (рекомендация (в)); 10 fitness-функций (9 автоматических, 1 ручная — слабое место); ADR D29 по MADR; план делит MVP и этап 4.

<span class="gate">G9</span> ⚠️ не подтверждено: пороги замедления (70–80%), SLO, пороги аномалий, срок обнаружения деградации ≤ 1 дня, потолок staging и eval, трудоёмкости. 📌 **Вопросы владельцу:** (1) В-CI: CI-система и реестр образов, варианты и рекомендация в Э7; (2) В-алерты: канал и получатель алертов стоимости; внешний мессенджер или почтовый сервис — выбор владельца, self-hosted вариант — уведомления в самом ICPlan (рекомендуется для MVP); (3) В-потолок: месячный потолок staging и eval; (4) В-4.5: согласие перенести часть 4.5 в MVP. Следующий шаг: после изменений Э10 — реализация F1 как первого теста; замер на staging, калибровка порогов по базе 2–4 недели; выбор варианта B не зависит от калибруемых значений.
