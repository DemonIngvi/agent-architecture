**Почему процесс в ICPlan.** Три вывода:

<div class="rnd-grid" markdown>
<div markdown>
**1. Агент на переходе процесса — общий приём рынка**

Jira + Rovo ставят агента на переход workflow, Plane Agents запускают агента по изменению задачи. Мы делаем так же: шаг процесса знает своего агента. Ручное делегирование оставляет процесс человеку, и он стоит ([Э4](#e4)).
</div>
<div markdown>
**2. Переход делает трекер, а не агент**

Если агент сам двигает задачу (`update_issue`), правила процесса живут в промптах и расходятся. У нас переход делает ICPlan по итогу запуска, по правилам шага. В движках workflow это классика: условия, валидаторы, действия после перехода ([Э5](#e5)).
</div>
<div markdown>
**3. Внешний оркестратор — вторая очередь и второй интерфейс**

n8n или Temporal умеют ветвления и ожидания, но процесс уходит из трекера, а задачи синхронизируются через вебхуки. Очередь агента уже есть в ICPlan, поэтому оркестратор продублировал бы её ([Э7](#e7)).
</div>
</div>

## Э1. Вопрос {#e1}

**Ситуация.** В ICPlan агент запускается при смене поля «Делегат» или упоминании. Автоназначение на колонке ставит только исполнителя и запуск не создаёт (проверено по коду форка, `issues/service.ts`).

**Осложнение.** Командам нужен процесс «задача пришла в шаг → агент взял → по итогу дальше». Ревью 2 нашло разночтение: кто и когда переводит задачу.

**Вопрос.** Как задача сама попадает к агенту и переходит дальше?

**Решает:** владелец продукта с администратором. **Не решаем:** когда стартует запуск ([Runner](runner-and-scheduling.md)), выбор трекера ([трекер](tracker-choice.md)).

<span class="gate">G1</span> ✅ вопрос — выбор; есть владелец; связан с D17.

## Э7. Отсев и встраивание {#e7}

### Отсев по MUST

| Кандидат | M1 в ICPlan без кода | M2 сам к агенту | M3 один участник | Итог |
|---|---|---|---|---|
| Процесс типа задачи | да | да | да: ICPlan | проходит |
| Автоназначение + триггер | частично: два места | да | **нет**: агент двигает сам | ✗ |
| Внешний оркестратор | **нет** | да | да: оркестратор | ✗ |
| Ручное делегирование | да | **нет** | да: человек | ✗ |

### Как встаёт в схему

```
 Администратор ──I20──▶ ICPlan: тип задачи → процесс → шаги (колонка, агент, переходы, лимит, проверка)
 задача входит в шаг ──▶ очередь агента (ICPlan) ──I1 claim──▶ Agent Runner ──▶ запуск
                                                 ◀──I2 итог─── (success / failed / canceled)
 ICPlan по итогу и правилам шага: переход при успехе / при неудаче / повтор / ждать проверки человека
```

| Стык | Процесс в ICPlan | Внешний оркестратор |
|---|---|---|
| I1 выдача запуска | И2: очередь агента не меняется | И1: оркестратор кладёт запуск через API ICPlan |
| I2 итог → переход | И2: ICPlan применяет правила шага | И1: вебхук в оркестратор, переход через API |
| I20 редактор процесса | И2: настройки проекта ICPlan | И0: внешний редактор |

**Изменения у соседей:** процесс в ICPlan — Runner и Harness не меняются (переход не их дело). Порядок разделён: ICPlan выдаёт запуск из очереди агента по приоритету задачи и времени постановки (R-AP-17); взятый запуск ждёт свободных слотов в порядке `fifo | priority` планировщика Runner (D14, R-RUN-02). Оркестратор — новый сервис, вебхуки ICPlan, новый I-код, синхронизация статусов.

**Вывод этапа.** ==Процесс в ICPlan не меняет ни Runner, ни Harness: они видят только запуск и итог.==

<span class="gate">G7</span> ✅ отсев; готовность стыков; изменения у соседей.
