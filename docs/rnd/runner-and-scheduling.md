**Почему свой Runner со слотами.** Три вывода:

<div class="rnd-grid" markdown>
<div markdown>
**1. Очередь уже есть — в ICPlan**

ICPlan держит очередь каждого агента с арендой (`claim → heartbeat → result`, аренда 300 с). Runner забирает запуск и решает только одно — **когда стартовать**. Внешний движок (Hatchet, Temporal) стал бы второй очередью с двойным учётом статусов ([Э7](#e7)).
</div>
<div markdown>
**2. Лимит на модель и на задачу — наша специфика**

Запуск стартует, когда свободны все его слоты: глобальный, агента, модели и задачи. Лимит модели — это rate limit ключа провайдера, общий для всех агентов. Ключи параллельности по выражению это умеют только в Hatchet и River Pro, а River Pro платный ([Э4](#e4)).
</div>
<div markdown>
**3. Цена своих слотов — тесты на гонки**

Своя логика слотов — главный риск. Он закрывается конкурентным тестом: несколько Runner и много запусков, лимиты не превышены ни разу. Голодание закрывает повышение приоритета `aging_s` (D18). Тест добавлен в задачу 2.7 ([Э10](#e10)).
</div>
</div>

## Э1. Вопрос {#e1}

**Ситуация.** ICPlan ставит запуски агентов в очередь и отдаёт их внешним раннерам по протоколу `@itsaplan/runner` (D8). Агентов несколько, они делят модели с лимитами провайдера.

**Осложнение.** Раннер ICPlan из коробки исполняет агента без изоляции. Очереди с лимитами есть в готовых движках (Hatchet, Temporal, River), но у нас очередь уже есть в ICPlan.

**Вопрос.** Кто исполняет запуски и как решает, когда их стартовать?

**Решает:** владелец продукта по предложению архитектора. **Не решаем:** изоляцию среды ([Sandbox](sandbox-isolation.md)), цикл агента ([фреймворк](harness-framework.md)), переход на Kubernetes ([K8s](kubernetes-runtime.md)).

<span class="gate">G1</span> ✅ вопрос — выбор; есть владелец; связан с D8, D14 и требованиями agent-runner.

## Э3. Опорное решение: раннер ICPlan {#e3}

Опорное решение — то, что есть в ICPlan: очередь запусков и раннер `@itsaplan/runner`.

| # | Функция | Что делает | Потребность |
|---|---|---|---|
| F1 | Очередь запусков агента | порядок по приоритету, затем по времени (D17) | П1, П9 |
| F2 | Аренда запуска | `claim` выдаёт запуск на 300 с; `heartbeat` продлевает; повтор до 3 попыток | П1, П5 |
| F3 | Возврат итога | `result` со статусом `success` / `failed` / `canceled` | П7 |
| F4 | Отмена через heartbeat | `heartbeat` возвращает `false`, если запуск больше не активен | П7 |
| F5 | Ключ агента | раннер обслуживает агентов по их API-ключам | П1 |
| F6 | Исполнение агента | раннер запускает агента локально | П6 ✗: без sandbox, LiteLLM, G1 |

**Вывод этапа.** Протокол ICPlan (F1–F5) закрывает получение работы и возврат итога. Исполнение (F6) и слоты (П2–П5) — то, чего нет.

<span class="gate">G3</span> ✅ функции из кода ICPlan (А) и протокола раннера (Б).

- **Утверждение.** Свой Agent Runner на Go со слотами в Postgres (D8, D14).
- **Основания.** Закрывает 8 из 9 потребностей без нового сервиса. Очередь остаётся одна — в ICPlan. Соседи не меняются.
- **Связка.** Движки решают задачу очереди, которую уже решает ICPlan. От них нужна только логика лимитов по ключу, а её объём меньше, чем эксплуатация нового сервиса.
- **Опровержение.** Вывод неверен, если задача 2.7 выйдет за 5 дн или тест гонок окажется нестабильным. Тогда переходим на Hatchet (или River Pro, если лицензия приемлема).
