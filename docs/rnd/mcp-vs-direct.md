**Что показал разбор.** Три вывода:

<div class="rnd-grid" markdown>
<div markdown>
**1. Правила R-MCP-04 подтверждены**

Внутренние вызовы платформы — напрямую, без лишнего прыжка. Действия, которые выбирает модель, — тулы. Тул для нескольких агентов или с секретом — MCP-сервер. Стабильный тул только для Harness — нативный. Аналоги делают так же: MCP — для внешних систем ([Э5](#e5)).
</div>
<div markdown>
**2. Список тулов проверяется не там**

Allowlist (R-MCP-02) и G2 (R-GRD-03) исполняются в Harness — внутри sandbox, где исполняется код агента. Egress-прокси подставляет ключ агента к разрешённым MCP-хостам. Поэтому `curl` из bash-тула может вызвать любой тул MCP-сервера в обход Harness ([Э7](#e7)).
</div>
<div markdown>
**3. MCP-шлюз закрывает дыру и даёт больше**

Шлюз вне sandbox (ContextForge, agentgateway) собирает «виртуальный сервер» из разрешённых тулов, проверяет токен запуска и держит секреты. G2 для вызовов MCP переезжает в шлюз. Это новый сервис и изменение четырёх стыков — поэтому вопрос к владельцу продукта ([Э8](#e8)).
</div>
</div>

## Э1. Вопрос {#e1}

**Ситуация.** Агентам нужны тулы: ICPlan, git, память, внешние системы. MCP стал стандартом для тулов, которые выбирает модель.

**Осложнение.** Описания тулов MCP занимают контекст, вызов через модель медленнее прямого, а секреты MCP-серверов нельзя отдавать в sandbox. Плюс в 2025–2026 годах появились новые способы: исполнение кода поверх MCP, поиск тулов и MCP-шлюзы.

**Вопрос.** По каким правилам подключать тулы и где проверять, какие тулы агенту можно?

**Решает:** владелец продукта с ролью «Безопасность». **Не решаем:** движок правил ([guardrails](guardrails-engine.md)), изоляцию ([Sandbox](sandbox-isolation.md)).

<span class="gate">G1</span> ✅ вопрос — выбор; есть владелец; связан с R-MCP-01 – R-MCP-04.

|---|---|---|---|

## Э3. Опорное решение: гибрид по R-MCP-04 {#e3}

| # | Функция | Что делает | Потребность |
|---|---|---|---|
| F1 | Правила выбора типа интеграции | прямой вызов / тул / MCP-сервер / нативный тул | П1, П3 |
| F2 | MCP Streamable HTTP | внешние системы и ICPlan (`itsaplan-core`) как MCP-серверы | П1 |
| F3 | Allowlist тулов в определении агента | Harness фильтрует `tools/list` и отклоняет вызов вне списка | П2 |
| F4 | Подстановка ключа egress-прокси | ключ агента добавляется к запросу к MCP-хосту, агент его не видит | П4 |
| F5 | G2 из Harness | OPA перед вызовом тула (I10) | П5 |
| F6 | Таймаут 30 с, обрезка 64 КБ | защита запуска и контекста | П7 |

**Вывод этапа.** Опорное решение закрывает подключение, задержку и защиту контекста. П2 и П5 закрыты только при условии, что вызов идёт через Harness.

### Как встаёт в схему

Сейчас:

```
 sandbox ┌──────────────────────────────────────────────┐
         │ Harness: allowlist + G2 ──I10──▶ OPA          │
         │    └─ tools/call ─┐                           │
         │ код агента (bash) ─┼─ curl ──▶ Squid* ──I9──▶ MCP itsaplan-core, git
         └────────────────────┴──────────────────────────┘    * подставляет ключ агента любому процессу
```

С MCP-шлюзом:

```
 sandbox ┌──────────────────────────────┐
         │ Harness ── токен запуска ─────┼──I9*──▶ MCP-шлюз: виртуальный сервер запуска
         │ код агента ── без ключа ──────┼──✗       ├─ allowlist агента (из Platform module)
         └──────────────────────────────┘          ├─ G2 ──I10*──▶ OPA
                                                    ├─ секреты серверов
                                                    └──▶ MCP itsaplan-core, git
  * — стыки меняются
```

| Стык | Как сейчас | С MCP-шлюзом |
|---|---|---|
| I9 Harness → MCP | И2: напрямую через Squid | И1: через шлюз, токен запуска |
| I10 G2 → OPA | И2: из Harness | И1: из шлюза для вызовов MCP; из Harness — для нативных тулов |
| I17 Squid | И2: подставляет ключ агента | И2: к MCP только шлюз, ключ не подставляется |
| Platform module → шлюз | — | И1: allowlist агента и серверы |

**Изменения у соседей (если шлюз):** Sandbox (R-SBX-06 — разрешённые хосты, R-SBX-07 — подстановка ключа), Guardrails (R-GRD-03 — G2 для MCP в шлюзе), Platform module (отдаёт allowlist шлюзу), инфраструктура и техспека (новый сервис), задачи 1.4, 2.4, 4.2.

**Вывод этапа.** ==Сейчас проверка списка тулов и G2 живёт в той же среде, где исполняется код агента, — любая утилита в sandbox может её обойти.== Шлюз переносит проверку наружу ценой нового сервиса и изменения четырёх стыков.

<span class="gate">G7</span> ✅ отсев; готовность стыков; изменения у соседей.

## Э8. Спор ролей {#e8}

Роли 🤖. Оппонент — DevOps за «как есть», «адвокат дьявола» атакует шлюз.

| Роль | За | Довод | Опасение | Согласится, если |
|---|---|---|---|---|
| Безопасность 🤖 | шлюз | проверка внутри недоверенной среды обходится одним `curl` (Э7) | — | — |
| Архитектор 🤖 | шлюз | один вход к MCP, секреты вне sandbox | новый сервис на пути каждого вызова | шлюз лёгкий, таймауты прежние |
| Администратор 🤖 | шлюз | список тулов агента виден и проверяется в одном месте | — | — |
| Разработчик 🤖 | нейтрально | Harness почти не меняется: другой адрес и токен | — | — |
| DevOps 🤖 (оппонент) | как есть | ещё один сервис, ещё одна точка отказа | отказ шлюза = агенты без тулов | FMEA и fail-closed |
| Владелец продукта 🤖 | как есть | сроки этапа 2 | — | временная мера до шлюза |

| Спор | Разрешение |
|---|---|
| Безопасность против DevOps: «шлюз или как есть» | 📌 **вопрос владельцу продукта** в tool-integration: шлюз (ContextForge / agentgateway) или проверка в MCP ICPlan по токену запуска |
| Владелец продукта: «до решения — что?» | **условие:** агентам с bash-тулом не выдавать MCP-серверы с записью, пока проверка не вынесена; записано в вопросе |
| Адвокат дьявола: «исполнение кода экономит 98% токенов — почему нет?» | **условие:** вернуться, когда G2 будет в шлюзе; сейчас код обойдёт проверку на каждый тул |

**Вывод этапа.** Спор о шлюзе фактами не решается: это выбор между безопасностью и сроками, поэтому он вынесен владельцу продукта. Временная мера записана.

<span class="gate">G8</span> ✅ у каждого спора есть разрешение или вопрос 📌.

- **Утверждение.** Правила R-MCP-04 оставляем. Проверку allowlist и G2 для MCP нужно вынести из sandbox; рекомендуем MCP-шлюз. Окончательно решает владелец продукта.
- **Основания.** Гибрид закрывает подключение, задержку и секреты. Но П2 и П5 нарушаются любым процессом в sandbox, а шлюз их закрывает.
- **Связка.** Sandbox по D18 — недоверенная среда. Проверка в ней — не проверка.
- **Опровержение.** Шлюз не нужен, если у агентов не будет тулов, исполняющих произвольные команды, или если MCP ICPlan сам проверяет список тулов по токену запуска. Второе — альтернатива в вопросе.
