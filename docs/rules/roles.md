# Роли участников процесса

← [Правила документации](README.md) · [промпты](prompts.md) · [персоны продукта](../stories/personas.md)

Роли документации — кто пишет, проверяет и утверждает документы. Агент (Claude) может выполнять любую роль, но **проверяющий — всегда отдельный проход**, не тот же, что писал. Персоны продукта (пользователь, администратор, агент…) — отдельно, в [personas.md](../stories/personas.md); их отыгрывают при исследовании историй и процессов.

## Участники

| Роль | Отвечает на вопрос | Выход готов, когда |
|---|---|---|
| **Владелец продукта** | Что важно, сколько стоит, что выбрать? | закрыты вопросы 📌, приоритеты и бюджет утверждены |
| **Постановщик** | Зачем и что меняем? | proposal: проблема, границы, затронутые capability |
| **Аналитик историй** | Кто что делает и что может пойти не так? | персоны, истории, процессы BPMN с артефактами, конфликты отыграны |
| **Автор R&D** | Почему именно так? | итог сверху, матрица, источники, решение D-номер |
| **Автор критериев приёмки** | Как поймём, что сделано? | спека проходит критерии полноты, RTM без разрывов |
| **Архитектор** | Где живут данные, как связаны модули, как развёрнуто? | interfaces.md, схемы, вид развёртывания, TECHNOLOGIES |
| **DevOps-инженер (эксплуатация)** | Как развернуть, обновить, восстановить, что будет при отказе? | нагрузка и развёртывание, параметры L0, бэкапы, FMEA; подтверждения в `approvals.md` |
| **Инженер сборки и поставки** | Как собрать, откуда взять и как безопасно запустить? | техспека компонента ([правило](tech-spec.md)): образы, запуск, переменные, CI, проверка после развёртывания |
| **Разработчик** | Реализуемо ли требование так, как написано? | параметры, интерфейсы и сценарии проверены на реализуемость; подтверждения в `approvals.md` |
| **Администратор (настройки)** | Понятны ли настройки агентов и процессов, разумны ли значения? | настройки L1–L3, значения по умолчанию и границы; подтверждения в `approvals.md` |
| **Пользователь** | Решает ли это мою задачу? | истории пользователя подтверждены в `approvals.md` |
| **Безопасность** | Где утечка, лишние права, лицензионный риск? | guardrails, секреты, сетевые политики, лицензии проверены |
| **Тестировщик (QA)** | Как проверить каждое требование? | сценарии превращены в тесты, нагрузочный тест спланирован |
| **Проверяющий** (подроли: аналитик, техлид, архитектор) | Всё ли верно и связано? | ревью в `docs/reviews/`, `validate --strict` и сборка зелёные |
| **Агент-исполнитель** | Как реализовать задачу по спеке? | задача выполнена, приёмка пройдена, документы не изменены без роли |

## Права на документы

**W** — пишет · **R** — проверяет и предлагает правки · **A** — утверждает · пусто — только читает.

| Документ | Владелец продукта | Постановщик | Аналитик историй | Автор R&D | Автор критериев | Архитектор | Эксплуатация | Безопасность | QA | Агент-исполнитель |
|---|---|---|---|---|---|---|---|---|---|---|
| proposal.md | A | W | R | | R | R | | | | |
| User Stories, персоны, BPMN (`stories.py`) | A | R | W | | R | R | | R | R | |
| R&D (`docs/rnd`) | A | | R | W | | R | R | R | | |
| design.md | A | | | W | | R | R | R | | |
| architecture.md, данные сайта | | | | R | | W | R | R | | |
| spec.md | | R | R | | W | R | R | R | R | |
| interfaces.md (конфигурация, данные, интерфейсы, FMEA, нагрузка) | | | | | R | W | W | R | R | |
| traceability.md, open-questions.md | A | R | R | R | W | R | | | R | |
| Потоки (`docs/flows`) | | | R | | R | W | | | R | |
| TECHNOLOGIES.md | A | | | W | | R | R | R | | |
| Задачи (`docs/tasks`), ROADMAP, TASKS | A | W | | | W (приёмка) | R | R | | R | статус задачи |
| Ревью (`docs/reviews`) | R | | | | | W (проверяющий) | W | W | W | |
| Правила (`docs/rules`) | A | R | R | R | R | W | R | R | R | |
| Код реализации | | | | | | R | R | R | R | W |

Подтверждение требований (`approvals.md` спеки): каждая роль ставит ✅ или ❌ только в свою строку; обязательные роли по видам требований — [виды спек и подтверждение](spec-kinds.md#approvals). Агент, выступающий в роли, отмечается 🤖, человек — 👤.

Правила: агент-исполнитель **не меняет** спеки и правила — расхождение спеки и реализации оформляет как открытый вопрос. Вопросы 📌 закрывает только владелец продукта.

## Порядок

```
Владелец продукта ─▶ Постановщик ─▶ Аналитик историй ─▶ Автор R&D ─▶ Автор критериев ─▶ Архитектор / Эксплуатация / Безопасность ─▶ QA ─▶ Проверяющий
        ▲                                                                                                                                       │
        └──────────────────────────── 📌 вопросы и замечания ◀──────────────────────────────────────────────────────────────────────────────────┘
                                                                                                    Агент-исполнитель ◀── задачи (после ревью)
```

## Подроли проверяющего

| Подроль | Разрезы вопросов |
|---|---|
| **Аналитик** | полнота поведения (S1–S12), пользователь, данные, трассировка (RTM), согласованность с потоками |
| **Техлид** | реализуемость, интерфейсы, отказы (FMEA), тестируемость, пороги и лимиты |
| **Архитектор** | границы модулей, хранилища и владельцы, протоколы, развёртывание, безопасность, единые точки отказа, эволюция |

Результат ревью — документ в `docs/reviews/` со статусами ✅ закрыто · ❓ открыто · 📌 на решение пользователя; открытые вопросы переносятся в `open-questions.md` спек.
