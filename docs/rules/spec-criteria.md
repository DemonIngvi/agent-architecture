# Критерии полноты спеки

← [Правила документации](README.md)

Спека — контракт поведения capability. Чек-лист применяют при написании (роль «автор критериев») и при ревью (роль «проверяющий» с подролями аналитик / техлид / архитектор). Неприменимый пункт — объяснить, а не пропускать.

## 0. Методологическая основа

| Методология | Что даёт спеке | Где применяется |
|---|---|---|
| **OpenSpec** | формат: Purpose, дельты требований, SHALL/MUST, сценарии WHEN/THEN | раздел 1 |
| **ISO/IEC/IEEE 29148** — требования к требованиям | 9 характеристик отдельного требования: необходимое, однозначное, полное, единичное (одно поведение), реализуемое, проверяемое, корректное, соответствующее, **трассируемое**; 5 характеристик набора: полный, согласованный, реализуемый, понятный, ограниченный | разделы 2, 5, RTM |
| **Трассировка (RTM)** | каждое требование трассируется вверх (User Story, исследование, решение) и вниз (задача, тест) | `traceability.md` |
| **User Stories + BPMN** | требования выводятся из историй пользователей и их процессов, включая ветки ошибок | [User Stories](../stories/README.md) |
| **Software FMEA** | режимы отказа по точкам зрения: требования, интерфейсы, данные, тайминги, последовательность, обработка ошибок | раздел 3, `interfaces.md` |
| **Классы сценариев S1–S12** (эквивалентные классы и граничные значения тест-дизайна) | покрытие поведения, а не только основного пути | раздел 2 |
| **ISO/IEC 25010 — эффективность** (time behaviour, resource utilisation, capacity) | нефункциональные требования: профиль нагрузки, время ответа, ёмкость | раздел 3, «Нагрузка и развёртывание» |
| **C4 / arc42 — вид развёртывания** | где и как запущен модуль: кластер, namespace, реплики, ресурсы, ingress | раздел 3, спека `platform-infrastructure` |
| **SDD: EARS, Spec Kit** ([методология](sdd-methodology.md)) | шаблоны текста требования (WHEN, WHILE, WHERE, IF…THEN) и цепочка constitution → specify → plan → tasks | разделы 1, 3 |
| **AIDLC** ([openspec/config.yaml](https://github.com/DemonIngvi/agent-architecture/blob/main/openspec/config.yaml)) | quality gate, уровни автономии R0–R5, правило «98/2», трассировка требование → задача → запуск | раздел 4 |
| **Персоны и отыгрыш конфликтов** | у каждой сущности: что может, что хочет; конфликты разыгрываются по промптам персон, результат — истории, требования и открытые вопросы | [персоны](../stories/personas.md), [R&D](../rules/rnd-methodology.md) |
| **Артефакты процесса** | у каждого шага процесса указаны созданные артефакты — основа для их моделирования | таблица под диаграммой BPMN (`stories.py`, ARTIFACTS); на самой диаграмме артефакты не рисуются, потоки |
| **Ревью по ролям** — аналитик, техлид, архитектор | вопросы в разных разрезах, см. [роли](roles.md) | [ревью](../reviews/2026-10-10-spec-review.md) |

## 1. Формат OpenSpec (проверяет `openspec validate --strict`)

- [ ] `## Purpose` — 1–2 предложения, ≥ 50 символов, в конце `Обоснование: [R&D](<путь к R&D>)`
- [ ] Дельты в `## ADDED / MODIFIED / REMOVED / RENAMED Requirements`
- [ ] Требование — `### Requirement: <имя>`, одно поведение, описание ≤ 500 символов, слова **SHALL / MUST**
- [ ] Сценарии — `#### Scenario:` (4 решётки), формат **WHEN / THEN**
- [ ] MODIFIED — блок целиком; REMOVED — с **Reason** и **Migration**
- [ ] Нет имён классов и шагов реализации (это design / tasks)

## 2. Покрытие сценариев (≥ 3 на требование)

| # | Класс | Вопрос |
|---|---|---|
| S1 | Основной путь | Нормальный вход? |
| S2 | Альтернативный путь | Другие допустимые ветки? |
| S3 | Неверный вход | Ошибочные или отсутствующие данные? |
| S4 | Границы и лимиты | На пороге и сразу за ним? |
| S5 | Права и безопасность | Кто может / не может, секреты? |
| S6 | Сбой зависимости | Сервис недоступен, таймаут? |
| S7 | Параллельность | Одновременные запросы, гонки? |
| S8 | Повтор и идемпотентность | Повторная отправка, дубли? |
| S9 | Конфигурация | Включено / выключено, другие значения? |
| S10 | Состояние и восстановление | Падение посреди процесса? |
| S11 | Данные и хранение | Срок хранения, удаление, приватность? |
| S12 | Наблюдаемость и аудит | Видно ли, что и почему произошло? |

## 3. Обязательные части каждой capability

Файлы в папке `specs/<capability>/`:

| Файл | Содержание |
|---|---|
| `spec.md` | требования и сценарии |
| `architecture.md` | схема устройства, блоки, расширения, плюсы / минусы ([FORMAT](../../FORMAT.md)) |
| `interfaces.md` | уровни конфигурации L0–L3; параметры модуля с уровнем и хранилищем; хранилища данных (S-коды: что, владелец, бэкап / срок); интерфейсы (I-коды: от → к, протокол, формат, аутентификация, режим, таймаут, повтор, идемпотентность); таблица отказов FMEA (отказ, обнаружение, поведение, восстановление); **нагрузка и развёртывание** |
| `traceability.md` | RTM: требование → обоснование (R&D, design) → задача → число сценариев; разрывы явно |

Обязательные требования в `spec.md`:

- [ ] **Конфигурация модуля** — уровни, приоритет, потолок L0, отсутствие обязательного параметра
- [ ] **Хранилища данных** — только перечисленные хранилища, чужие данные через API, секреты не в БД / git
- [ ] **Интерфейсы обмена** — протокол, таймаут, повтор; неидемпотентное не повторяется
- [ ] **Поведение при отказах зависимостей** — строка FMEA в `interfaces.md` и сценарий отказа требования говорят одно и то же: меняешь одно — меняешь другое в той же правке (Z-ICP-118); сценарии из FMEA (не меньше трёх)
- [ ] **Нагрузка и производительность** — показатели профиля нагрузки (RPS, p95, одновременность, токены), поведение при превышении
- [ ] **Развёртывание** — namespace, объект Kubernetes, реплики, requests / limits, ingress
- [ ] Текст требования — по шаблонам EARS ([методология SDD](sdd-methodology.md)); отказы — шаблоном IF … THEN

Справочники (единые для всех спек): уровни L0–L3 — конфиг деплоя / Platform module / определение агента / запуск; хранилища S1–S11; интерфейсы I1–I23 — в `interfaces.md` любой спеки; технологии — [TECHNOLOGIES.md](../TECHNOLOGIES.md).

## 4. Дополнения AIDLC

- [ ] **Quality gate** — отдельное требование со сценариями «прошёл / не прошёл», если результат проверяется
- [ ] **Уровень автономии R0–R5** для действий с подтверждением человека
- [ ] **«98/2»** — детерминированные проверки описаны как проверки кодом, не LLM
- [ ] **Трассировка** — каждое требование в RTM имеет задачу (или решение «не в MVP»)

## 5. Связность

- [ ] Не противоречит [architecture.md](../../architecture.md) и design
- [ ] Каждое требование выводится из User Story компонента (или явно помечено как техническое)
- [ ] Процессы BPMN: у шагов указаны артефакты; конфликты персон отыграны
- [ ] У каждого требования ID и задача («Реализует задача»), задача ссылается на требование обратно ([трассировка](change-process.md#req-task-trace))
- [ ] Каждое открытое замечание ревью по спеке есть в её `open-questions.md`
- [ ] Таблица параметров: по умолчанию с обоснованием, мин, макс, на что опираться ([виды спек](spec-kinds.md#params))
- [ ] Обязательные роли подтвердили требования (`approvals.md`)
- [ ] Данные: для каждого хранилища и вида данных указано, кто пишет, кто читает, кто удаляет и по какому триггеру (поток компонента)
- [ ] Значение параметра записано в одном месте (таблица параметров); в профиле нагрузки и тексте — ссылка на параметр
- [ ] FMEA: строка на каждое своё хранилище и каждый интерфейс модуля
- [ ] Интерфейсы внешних систем сверены с их кодом или документацией (источник указан)
- [ ] Внешний вызов описан полным составом запроса (поле → параметр, уровень, хранилище); новый интерфейс отнесён к типам данных в [data-types.md](../data-types.md)
- [ ] Механизм описан даже при открытом решении о варианте (вариант — открытым вопросом)
- [ ] Требования «Конфигурация», «Хранилища», «Интерфейсы», «Отказы» — со своим содержанием спеки (свои параметры, S- и I-коды, сценарии), не шаблонный текст ([правило](change-process.md#cross-spec))
- [ ] Открытые вопросы спеки — в `open-questions.md` (❓ / 📌, блокирует ли, кто решает)
- [ ] Типы данных совпадают с [потоками](../../architecture.md#interaction)
- [ ] Параметры совпадают с таблицей «Конфигурация» компонента
- [ ] Проверяет lint (`./tools/doc lint`): у каждой строки FMEA — сценарий с тем же именем отказа (хранилище S<n> — «S<n> недоступно»); строка RTM = требование: задача = «Реализует задача», «Сценариев» = число сценариев. Совпадение смысла FMEA и сценария — роль
- [ ] Спека привязана к компоненту (`components.py`, вкладка «Спеки»); у компонента есть «Как работает» с подразделом «Порядок работы и сценарии» (`docs/how/<компонент>.md`)

## 6. Процент готовности

Считается при сборке сайта (`html-view/build.py`, `spec_readiness`), показывается на странице спеки и в обзоре спек.

| Часть | Вес | Как считается |
|---|---|---|
| Формат | 15 | Purpose ≥ 50 (4), SHALL/MUST у всех (4), сценарии у всех (4), описание ≤ 500 (3) |
| Сценарии | 25 | среднее min(сценариев, 3) / 3 |
| Трассировка | 20 | доля требований с **двусторонней** связью: задача в «Реализует задача» спеки и это требование в «Закрывает требования» задачи (или решение «бэклог») |
| Обоснование | 10 | «Обоснование» в Purpose (5), обоснование в RTM (5) |
| Интерфейсы, отказы, нагрузка | 15 | 5 разделов `interfaces.md` (по 2, включая «Нагрузка и развёртывание»), требование об отказах с ≥ 3 сценариями (3), требования о нагрузке и развёртывании (2) |
| Связность | 15 | схема `architecture.md` рядом (5), спека привязана к компоненту в `components.py` (5), у компонента «Как работает» с порядком работы и сценариями в `docs/how` (5) |
| Открытые вопросы | минус | ❓ −2 (не более −10), 📌 −4 (не более −16) по `open-questions.md` |
| Шаблонный текст | минус | −2 за требование, текст которого совпадает с требованием другой спеки > 80% (словесные триграммы), не более −10 ([правило](change-process.md#cross-spec)) |
| Без User Story | минус | −2 за требование с «техническое» в RTM, если в нём есть пользователь, администратор, задача, уведомление, экран (кроме «Конфигурация», «Хранилища», «Интерфейсы», «Отказы», «Нагрузка», «Развёртывание»), не более −10 |
| Потолок без ревью | потолок | пока в последнем ревью (`docs/reviews`) есть открытые ❓ / 📌 по спеке (или по «все»), готовность не выше 90; 100 — только после ревью без открытых пунктов |
| Потолок без подтверждений | потолок | пока есть обязательные подтверждения ⏳ или ❌ в `approvals.md`, готовность не выше 90 ([правило](spec-kinds.md#approvals)) |

| Шкала | Статус |
|---|---|
| 90–100 | готова |
| 75–89 | почти |
| 60–74 | в работе |
| 40–59 | черновик |
| 0–39 | заготовка |

**Достаточность.** Процент — измеримый минимум, а не доказательство полноты: форма проверяется формулой, содержание — проверками уникальности, историй и ревью. Спека считается достаточной, когда: готовность ≥ 90, в RTM нет разрывов без решения, ревью тремя ролями не оставило открытых вопросов уровня «блокирует реализацию».

## 7. Готовность к ревью

- [ ] `openspec validate <change> --strict` — без ошибок
- [ ] Сайт собирается (`python html-view/build.py`)
- [ ] Разделы 1–5 пройдены, неприменимое объяснено
- [ ] Ревью ролями — в `docs/reviews/`
