# Критерии полноты спеки

← [Правила документации](README.md)

Спека (`openspec/.../specs/<capability>/spec.md`) — контракт поведения. Чек-лист применяют при написании и при ревью. Пункт не применим — пишем почему (в ревью), а не пропускаем молча.

## 1. Формат OpenSpec (обязательно, проверяет `openspec validate --strict`)

- [ ] Новая capability начинается с `## Purpose` — 1–2 предложения, ≥ 50 символов; в конце — «Обоснование: [R&D](…)», если решение исследовалось
- [ ] Дельты в разделах `## ADDED / MODIFIED / REMOVED / RENAMED Requirements`
- [ ] Каждое требование — `### Requirement: <имя>`, одно поведение, описание ≤ 500 символов
- [ ] Нормативные слова **SHALL / MUST** (не should / may)
- [ ] У каждого требования ≥ 1 `#### Scenario:` (ровно 4 решётки) в формате **WHEN / THEN**
- [ ] MODIFIED — блок требования целиком; REMOVED — с **Reason** и **Migration**
- [ ] В спеке нет имён классов, библиотек, шагов реализации — это design / tasks

## 2. Покрытие сценариев

Для каждого требования проверить, какие классы сценариев нужны:

| # | Класс | Вопрос | Пример |
|---|---|---|---|
| S1 | Основной путь | Что происходит при нормальном входе? | агент взял задачу и вернул итог |
| S2 | Альтернативный путь | Есть ли другие допустимые ветки? | итог с вложением / без |
| S3 | Неверный вход | Что при ошибочных или отсутствующих данных? | неизвестный `agent_id` |
| S4 | Границы и лимиты | Что на пороге и сразу за ним? | ровно `max_steps`, 80% / 100% бюджета |
| S5 | Права и безопасность | Кто может / не может? Что со секретами? | нет прав на approve |
| S6 | Сбой зависимости | Сервис недоступен, таймаут? | OPA не отвечает → deny |
| S7 | Параллельность | Два запроса одновременно, гонки? | два запуска по одной задаче |
| S8 | Повтор и идемпотентность | Повторная отправка, дубли? | повторный вход в статус |
| S9 | Конфигурация | Включено / выключено, другие значения? | `g2.enabled: false` |
| S10 | Состояние и восстановление | Падение посреди процесса, возобновление? | Harness упал → продолжение с checkpoint |
| S11 | Данные и хранение | Срок хранения, удаление, приватность? | истёк TTL M2 |
| S12 | Наблюдаемость и аудит | Видно ли, что произошло и почему? | отказ guardrail в таймлайне |

## 3. Дополнения AIDLC

- [ ] **Quality gate.** Если результат проверяется перед переходом дальше — отдельное требование со сценариями «прошёл» и «не прошёл»
- [ ] **Уровень автономии R0–R5.** Для действий агента с подтверждением человека указан уровень: R0 — только предлагает; R1 — действует после подтверждения каждого шага; R2 — подтверждение опасных действий; R3 — подтверждение только необратимых; R4 — сам, с аудитом; R5 — полностью сам
- [ ] **«98/2».** Проверки формата, полей, лимитов описаны как детерминированные (кодом), а не LLM
- [ ] **Трассировка.** Каждое требование покрыто задачей в `tasks.md` / `docs/tasks/` (задача ссылается на требование); от запуска агента можно дойти до требования

## 4. Связность

- [ ] Требования не противоречат [architecture.md](../../architecture.md) и [design](../../openspec/changes/define-agent-platform/design.md)
- [ ] Типы данных из сценариев совпадают с [потоками](../flows/README.md)
- [ ] Параметры и значения по умолчанию совпадают с таблицей «Конфигурация» компонента
- [ ] Новое решение имеет R&D или ссылку на существующее
- [ ] Рядом со `spec.md` есть `architecture.md` (схема), если у capability есть внутренняя структура

## 5. Готовность к ревью

- [ ] `openspec validate <change> --strict` — без ошибок
- [ ] Сайт собирается (`python html-view/build.py`)
- [ ] Чек-листы 1–4 пройдены, неприменимые пункты объяснены

## 6. Процент готовности

Считается автоматически при сборке сайта (`html-view/build.py`, `spec_readiness`) и показывается на странице спеки и в обзоре «Спеки по компонентам».

| Часть | Вес | Как считается |
|---|---|---|
| Формат | 20 | Purpose ≥ 50 символов; у всех требований SHALL/MUST; у всех есть сценарий; описание ≤ 500 символов — по 5 |
| Сценарии | 40 | Среднее по требованиям: min(сценариев, 3) / 3 — цель ≥ 3 сценариев на требование (основной путь + классы S3–S12) |
| Трассировка | 15 | На спеку ссылается задача (`docs/tasks/` или `tasks.md` change) |
| Обоснование | 10 | В Purpose есть «Обоснование:» со ссылкой на R&D |
| Связность | 15 | Рядом `architecture.md` (5), спека упомянута в `architecture.md` (5), у компонента есть документ потоков (5) |

| Шкала | Статус |
|---|---|
| 90–100 | готова |
| 75–89 | почти |
| 60–74 | в работе |
| 40–59 | черновик |
| 0–39 | заготовка |
