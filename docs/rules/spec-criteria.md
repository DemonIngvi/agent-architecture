# Критерии полноты спеки

← [Правила документации](README.md)

Спека — контракт поведения capability. Чек-лист применяют при написании (роль «автор критериев») и при ревью (роль «проверяющий» с подролями аналитик / техлид / архитектор). Неприменимый пункт — объяснить, а не пропускать.

## 0. Методологическая основа

| Методология | Что даёт спеке | Где применяется |
|---|---|---|
| **OpenSpec** | формат: Purpose, дельты требований, SHALL/MUST, сценарии WHEN/THEN | раздел 1 |
| **ISO/IEC/IEEE 29148** — требования к требованиям | 9 характеристик отдельного требования: необходимое, однозначное, полное, единичное (одно поведение), реализуемое, проверяемое, корректное, соответствующее, **трассируемое**; 5 характеристик набора: полный, согласованный, реализуемый, понятный, ограниченный | разделы 2, 5, RTM |
| **Трассировка (RTM)** | каждое требование трассируется вверх (User Story, исследование, решение) и вниз (задача, тест) | `traceability.md` |
| **User Stories + BPMN** | требования выводятся из историй пользователей и их процессов, включая ветки ошибок | [User Stories](../stories/README.md) |
| **Software FMEA** | режимы отказа по точкам зрения: требования, интерфейсы, данные, тайминги, последовательность, обработка ошибок | раздел 3, `interfaces.md` |
| **Классы сценариев S1–S12** (эквивалентные классы и граничные значения тест-дизайна) | покрытие поведения, а не только основного пути | раздел 2 |
| **AIDLC** ([openspec/config.yaml](../../openspec/config.yaml)) | quality gate, уровни автономии R0–R5, правило «98/2», трассировка требование → задача → запуск | раздел 4 |
| **Ревью по ролям** — аналитик, техлид, архитектор | вопросы в разных разрезах, см. [роли](roles.md) | [ревью](../reviews/2026-10-10-spec-review.md) |

## 1. Формат OpenSpec (проверяет `openspec validate --strict`)

- [ ] `## Purpose` — 1–2 предложения, ≥ 50 символов, в конце «Обоснование: [R&D](…)»
- [ ] Дельты в `## ADDED / MODIFIED / REMOVED / RENAMED Requirements`
- [ ] Требование — `### Requirement: <имя>`, одно поведение, описание ≤ 500 символов, слова **SHALL / MUST**
- [ ] Сценарии — `#### Scenario:` (4 решётки), формат **WHEN / THEN**
- [ ] MODIFIED — блок целиком; REMOVED — с **Reason** и **Migration**
- [ ] Нет имён классов и шагов реализации (это design / tasks)

## 2. Покрытие сценариев (≥ 3 на требование)

| # | Класс | Вопрос |
|---|---|---|
| S1 | Основной путь | Нормальный вход? |
| S2 | Альтернативный путь | Другие допустимые ветки? |
| S3 | Неверный вход | Ошибочные или отсутствующие данные? |
| S4 | Границы и лимиты | На пороге и сразу за ним? |
| S5 | Права и безопасность | Кто может / не может, секреты? |
| S6 | Сбой зависимости | Сервис недоступен, таймаут? |
| S7 | Параллельность | Одновременные запросы, гонки? |
| S8 | Повтор и идемпотентность | Повторная отправка, дубли? |
| S9 | Конфигурация | Включено / выключено, другие значения? |
| S10 | Состояние и восстановление | Падение посреди процесса? |
| S11 | Данные и хранение | Срок хранения, удаление, приватность? |
| S12 | Наблюдаемость и аудит | Видно ли, что и почему произошло? |

## 3. Обязательные части каждой capability

Файлы в папке `specs/<capability>/`:

| Файл | Содержание |
|---|---|
| `spec.md` | требования и сценарии |
| `architecture.md` | схема устройства, блоки, расширения, плюсы / минусы ([FORMAT](../../FORMAT.md)) |
| `interfaces.md` | уровни конфигурации L0–L3; параметры модуля с уровнем и хранилищем; хранилища данных (S-коды: что, владелец, бэкап / срок); интерфейсы (I-коды: от → к, протокол, формат, аутентификация, режим, таймаут, повтор, идемпотентность); таблица отказов FMEA (отказ, обнаружение, поведение, восстановление) |
| `traceability.md` | RTM: требование → обоснование (R&D, design) → задача → число сценариев; разрывы явно |

Обязательные требования в `spec.md`:

- [ ] **Конфигурация модуля** — уровни, приоритет, потолок L0, отсутствие обязательного параметра
- [ ] **Хранилища данных** — только перечисленные хранилища, чужие данные через API, секреты не в БД / git
- [ ] **Интерфейсы обмена** — протокол, таймаут, повтор; неидемпотентное не повторяется
- [ ] **Поведение при отказах зависимостей** — сценарии из FMEA (не меньше трёх)

Справочники (единые для всех спек): уровни L0–L3 — конфиг деплоя / Platform module / определение агента / запуск; хранилища S1–S11; интерфейсы I1–I20 — в `interfaces.md` любой спеки.

## 4. Дополнения AIDLC

- [ ] **Quality gate** — отдельное требование со сценариями «прошёл / не прошёл», если результат проверяется
- [ ] **Уровень автономии R0–R5** для действий с подтверждением человека
- [ ] **«98/2»** — детерминированные проверки описаны как проверки кодом, не LLM
- [ ] **Трассировка** — каждое требование в RTM имеет задачу (или решение «не в MVP»)

## 5. Связность

- [ ] Не противоречит [architecture.md](../../architecture.md) и design
- [ ] Каждое требование выводится из User Story компонента (или явно помечено как техническое)
- [ ] Типы данных совпадают с [потоками](../flows/README.md)
- [ ] Параметры совпадают с таблицей «Конфигурация» компонента
- [ ] Спека упомянута в architecture.md; у компонента есть документ потоков

## 6. Процент готовности

Считается при сборке сайта (`html-view/build.py`, `spec_readiness`), показывается на странице спеки и в обзоре спек.

| Часть | Вес | Как считается |
|---|---|---|
| Формат | 15 | Purpose ≥ 50 (4), SHALL/MUST у всех (4), сценарии у всех (4), описание ≤ 500 (3) |
| Сценарии | 25 | среднее min(сценариев, 3) / 3 |
| Трассировка | 20 | доля требований с задачей в RTM |
| Обоснование | 10 | «Обоснование» в Purpose (5), обоснование в RTM (5) |
| Отказы и интерфейсы | 15 | 4 раздела `interfaces.md` (по 2), требование об отказах с ≥ 3 сценариями (4), требование о конфигурации (3) |
| Связность | 15 | `architecture.md` рядом (5), упоминание в architecture.md (5), документ потоков (5) |

| Шкала | Статус |
|---|---|
| 90–100 | готова |
| 75–89 | почти |
| 60–74 | в работе |
| 40–59 | черновик |
| 0–39 | заготовка |

**Достаточность.** Процент — измеримый минимум, а не доказательство полноты. Спека считается достаточной, когда: готовность ≥ 90, в RTM нет разрывов без решения, ревью тремя ролями не оставило открытых вопросов уровня «блокирует реализацию».

## 7. Готовность к ревью

- [ ] `openspec validate <change> --strict` — без ошибок
- [ ] Сайт собирается (`python html-view/build.py`)
- [ ] Разделы 1–5 пройдены, неприменимое объяснено
- [ ] Ревью ролями — в `docs/reviews/`
