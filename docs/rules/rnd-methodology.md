# Методология R&D

← [Правила документации](README.md) · [все R&D](../rnd/README.md) · [методика историй](us-methodology.md) · [типы документов](doc-types.md) · [журнал отклонений](deviations.md)

Как проводить исследование: какой путь пройти, какие данные собрать, как из данных получить критерии и оценки, как оформить документ. Два вида R&D: **выбор решения** (технология, архитектурный подход) и **потоки пользователей** (для историй, [ниже](#us-rnd)).

## Почему методология переписана

Прежняя версия давала одну таблицу из 10 общих критериев с одинаковыми весами для всех R&D и баллы без фактов. В итоге: облачный Linear получил больше баллов, чем открытый трекер, хотя доработка кода и своё размещение для нас обязательны; не рассмотрены открытые альтернативы (Hermes Agent, RuRdesk); устарел факт «у Plane нет агентов» (Plane Agents вышли 18.09.2026). Отклонение [О-25](deviations.md).

## Опорные практики

| Практика | Что берём |
|---|---|
| **Kepner-Tregoe Decision Analysis** | обязательные условия (MUST, да / нет) отсекают варианты **до** баллов; желательные (WANT) — веса и сравнение; риски лидеров (вероятность × тяжесть) |
| **ATAM** (Architecture Tradeoff Analysis Method) | сценарии качества «стимул → ожидаемый отклик» из историй и требований; компромиссы и чувствительные места решения |
| **QSOS** (Qualification and Selection of Open Source) | карточка open-source кандидата: функции, риски для пользователя, риски поставщика; фильтрация весами под наш контекст |
| **CHAOSS / OpenSSF Scorecard** | здоровье проекта: активность, контрибьюторы, релизы, реакция на issue, безопасность сборки |
| **Прототип (spike)** | ограниченный по времени эксперимент, когда факты не подтверждены или итоги близки |
| **ADR / MADR**, **ISO/IEC 25010**, **Tech Radar** | структура документа, словарь качеств, статус технологии |

## Путь исследования

| # | Шаг | Что делаем | Выход в документе |
|---|---|---|---|
| 1 | Вопрос и границы | формулируем вопрос решения, что не решаем, кто решает, срок исследования | «Вопрос и границы» |
| 2 | Сценарии качества | из историй и требований — 3–7 сценариев «стимул → отклик» (например, «Runner упал → запуск продолжен другим через ≤ 5 мин») | «Сценарии» |
| 3 | Обязательные условия (MUST) | из ограничений проекта; каждое — да / нет с фактом и источником | «Обязательные условия и отсев» |
| 4 | Широкий поиск | длинный список ≥ 5 кандидатов из источников (ниже), включая «как сейчас» и «сделать самим»; дата поиска | «Длинный список» |
| 5 | Отсев | кандидат, не прошедший MUST, выбывает и **не получает баллов**; остаётся в таблице отсева с причиной | «Обязательные условия и отсев» |
| 6 | Сбор данных | карточка каждого оставшегося кандидата (ниже); неизвестное — «не подтверждено», а не догадка | «Профиль технологий», «Альтернативы» |
| 7 | Критерии и шкалы | 3–7 желательных критериев **из сценариев и данных**; у каждого — измеримые якоря 1–5 и вес с обоснованием | «Критерии и шкалы» |
| 8 | Сравнение и оценка | сначала факты по каждому критерию, затем баллы по якорям; балл без факта не ставится | «Сравнение по существу вопроса», «Матрица» |
| 9 | Риски лидеров | для двух лучших — неблагоприятные последствия: вероятность × тяжесть | «Риски» |
| 10 | Чувствительность | меняется ли лидер при ±20% весов; итоги в пределах 5 баллов или ключевой факт не подтверждён → прототип | «Чувствительность» |
| 11 | Решение | вариант, статус Tech Radar, условия пересмотра (что должно случиться, чтобы вернуться к вопросу) | «Итог» |

## Где искать альтернативы

| Источник | Что смотреть |
|---|---|
| GitHub: поиск по темам и ключевым словам | звёзды, лицензия, дата последнего коммита (за 12 месяцев), архивирован ли |
| Списки «awesome-…», CNCF Landscape | открытые проекты области |
| AlternativeTo, Product Hunt | новые продукты (за год) и аналоги известных |
| Документация и changelog лидеров рынка | новые функции конкурентов — проверять **на дату** исследования |
| Статьи «<технология> alternatives <год>» | кандидаты, о которых не знали |
| Проект AI-агент и наш стек | что уже есть и работает |

## Карточка кандидата (какие данные собирать)

| Группа | Данные | Источник |
|---|---|---|
| Функции | покрытие каждого сценария: есть / частично / нет | документация, код, демо |
| Расширяемость | открыт ли код; лицензия и её обязательства; можно ли форкнуть и дорабатывать; точки расширения (API, плагины, MCP) | репозиторий, LICENSE |
| Издания и цена | что входит в бесплатное / открытое издание, что только в платном | страница изданий и цен |
| Размещение | у себя / только облако; зависимости; ресурсы | документация по установке |
| Здоровье проекта | звёзды, контрибьюторы за 12 мес, релизы, время реакции на issue, OpenSSF Scorecard | GitHub API, scorecard.dev |
| Безопасность | известные уязвимости, модель прав, аудит | GitHub Advisories, документация |
| Интеграция | совместимость с ICPlan, LiteLLM, Postgres, Kubernetes, Python / Go | документация, прототип |
| Для агентных технологий | AG1–AG6 на прототипе (ниже) | прототип с evals |

## Как получить критерии и шкалы из данных

1. **Критерий = сценарий или ограничение.** Каждый желательный критерий ссылается на сценарий (шаг 2) или ограничение проекта. Общие 10 критериев ниже — подсказка, а не готовая таблица: копировать их в документ без адаптации нельзя.
2. **Якоря шкалы — до оценки.** Для каждого критерия заранее пишем, что значит 1, 3 и 5 в измеримых терминах. Пример для «расширяемости»: 1 — только публичный API; 3 — плагины / webhooks; 5 — исходный код с правом форка и доработки.
3. **Вес — с обоснованием.** 100 баллов распределяются между критериями; у каждого веса — одна фраза «почему столько». Если сомнения — попарное сравнение критериев (упрощённый AHP).
4. **Балл — по якорю и факту.** В матрице рядом с баллом — ссылка на факт из «Сравнения по существу».
5. **Обязательное не взвешивается.** Если без свойства решение неприемлемо (своё размещение, доработка кода, лицензия), это MUST, а не критерий с весом.

Подсказка общих качеств (ISO/IEC 25010 и практика): функциональность, производительность, затраты на токены, надёжность, безопасность, интеграция со стеком, лицензия и стоимость, зрелость, распространённость, эксплуатация.

## Дополнительные измерения для технологий ИИ-агентов

| Код | Измерение | Вопрос |
|---|---|---|
| AG1 | Выполнение задачи | Доводит ли агент задачу до результата на нашем наборе задач? |
| AG2 | Выбор тулов и аргументы | Правильно ли выбирает тул и формирует аргументы? |
| AG3 | Восстановление после ошибок | Продолжает ли после сбоя тула или модели? |
| AG4 | Связность плана | Не теряет ли цель на длинной задаче? |
| AG5 | Эффективность | Токены, задержка, стоимость на задачу |
| AG6 | Наблюдаемость и evals | Даёт ли трейсы, совместимые с инструментами оценки |

**Прототип с evals.** 5–10 эталонных задач на mock-LLM и реальной модели, замер AG1–AG5. Без прототипа статус технологии — не выше **Trial**.

## Разобранные кейсы

**Кейс 1. Выбор трекера** ([R&D](../rnd/tracker-choice.md)). MUST: своё размещение; исходный код с правом доработки; агенты как исполнители задач или возможность их добавить. Отсев: Linear, Jira (облако, закрытый код) — выбывают до баллов. Длинный список: It's a Plan, Plane (Community Edition, AGPL; Plane Agents — бета с 18.09.2026, издание не подтверждено), Huly (EPL-2.0), Hermes Agent (MIT; канбан внутри агента, не командный трекер), RuRdesk и Arc (агентные трекеры, зрелость низкая), свой интерфейс. Критерии — из сценариев «агент берёт задачу из процесса», «внешний раннер платформы», «доработка под процесс».

**Кейс 2. Агентный фреймворк** ([R&D](../rnd/harness-framework.md)). Сценарии: пауза на подтверждение и продолжение после сбоя; любая модель через LiteLLM; стрим шагов. Прототип с evals обязателен (AG1–AG6), без него — Trial.

**Кейс 3. Ёмкость** ([R&D](../rnd/load-profile.md)). Данные — профиль нагрузки (пользователи, RPS, запуски); критерии — ёмкость, отказ узла, стоимость; решение поэтапное с условием пересмотра (рост нагрузки → второй узел).

## Антипаттерны

- Одна и та же таблица критериев и весов во всех R&D.
- Баллы без фактов; факты «по памяти» без даты и источника.
- Обязательное свойство как взвешенный критерий: вариант без него может победить по сумме.
- Отсеянный вариант в строке «Оценка» выше выбранного.
- Поиск только среди знакомых вариантов; данные о конкурентах не проверены на дату исследования.
- «Нет функции» без проверки издания (функция может быть только в платном).

## R&D пользовательских потоков {#us-rnd}

1. Взять идею компонента и сформулировать работы (JTBD) по акторам.
2. Найти 3–5 аналогов и выписать их потоки: точки входа, состояния, действия людей и агентов.
3. Матрица «поток × аналог × у нас» → истории или осознанное «не делаем».
4. Отыграть персон, отфильтровать ненужное ([фильтр необходимости](us-methodology.md)).

## Персоны и отыгрыш конфликтов {#personas}

1. **Сущности.** Участники и объекты процесса; у каждой — что **может** и что **хочет**.
2. **Персоны.** Промпт персоны ([personas.md](../stories/personas.md)); новые — добавить.
3. **Отыгрыш.** Сыграть цель каждой персоны, искать конфликты с другими и с системой.
4. **Таблица конфликтов:** кто → что хочет → с кем конфликт → что должно произойти.
5. **Артефакты** каждого шага процесса.
6. Итог — истории, требования, открытые вопросы.

## Шаблон документа R&D

1. **Итог** (наверху): решение, технология и версия, лицензия, стоимость, ключевые параметры, статус Tech Radar, условия пересмотра, ссылка на решение в design.
2. Вопрос и границы.
3. Сценарии качества.
4. Обязательные условия и отсев (таблица: кандидат × MUST → да / нет с фактом).
5. Длинный список и источники поиска (с датой).
6. Альтернативы (прошедшие отсев): что это, как решает вопрос, когда подходит.
7. Критерии и шкалы: критерий → сценарий, якоря 1 / 3 / 5, вес с обоснованием.
8. Сравнение по существу вопроса: факты по каждому критерию.
9. Матрица оценки: баллы по якорям.
10. Профиль технологий (карточки): лицензия, издания, здоровье проекта, размещение.
11. Риски лидеров и чувствительность.
12. Последствия.
13. Источники с датой.
