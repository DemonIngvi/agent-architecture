# Методология R&D

← [Правила документации](README.md) · [все R&D](../rnd/README.md) · [обоснование методологии (R&D)](../rnd/rnd-methodology-choice.md) · [методика историй](us-methodology.md) · [типы документов](doc-types.md) · [журнал отклонений](deviations.md)

**Версия 3.1.** Исследование идёт по цепочке **потребность → ключевые функции → ценность → перенос → встраивание в схему → спор ролей → выбор → последствия**. Каждый этап начинается с выхода предыдущего и закрывается воротами. Критерии выбора получаются в конце цепочки, а не задаются заранее. Выводы доказываются фактами, цифры — только для сверки, в приложении.

Почему так: [R&D о методологии](../rnd/rnd-methodology-choice.md). Отклонения, которые привели к этой версии: [О-25](deviations.md) (v1 → v2) и [О-34](deviations.md) (v2 → v3), [О-35](deviations.md) (v3 → v3.1: встраивание, спор ролей, последствия, цветовая разметка). Эталон применения: [выбор трекера](../rnd/tracker-choice.md).

Два вида R&D: **выбор решения** (технология, архитектурный подход, методика) и **потоки пользователей** (для историй, [ниже](#us-rnd)).

| Этап | Вход | Что делаем | Выход | Ворота: идём дальше, если… | Иначе |
|---|---|---|---|---|---|
| **Э1 Вопрос** | история, требование, решение design, замечание | описываем ситуацию, осложнение и вопрос (SCQA): вопрос — выбор между вариантами; кто решает; что не решаем | раздел «Вопрос» | вопрос сформулирован как выбор; есть владелец; есть связь с историей, требованием или решением | вопрос не ставится — это задача, а не R&D |
| **Э2 Потребности** | выход Э1, истории, требования, ограничения | выписываем, что должно получаться (работа и желаемый исход, JTBD), а не функции; у каждой потребности — источник и «что ломается без неё» | таблица потребностей | у каждой потребности есть источник; нет потребностей «на всякий случай» | → Э1: вопрос шире или уже, чем потребности |
| **Э3 Опорное решение** | выход Э2 | разбираем то, что есть или предполагается (текущее решение, продукт-кандидат): его **ключевые функции** — без них работа из Э2 не выполняется (критические элементы); у функции — что делает, какую потребность закрывает, факт | таблица функций опорного решения | каждая функция связана с потребностью или помечена «не к нашей потребности»; у наличия функции есть факт уровня Б и выше | → Э2: функции закрывают потребности, которых нет в списке, — дописать или убрать |
| **Э4 Альтернативы** | выходы Э2, Э3 | широкий поиск ([источники](#search)) с датой; в список всегда входят «как сейчас / ничего не делать» и «сделать самим»; у каждой альтернативы — ключевые функции **по тем же потребностям** и функции, которых нет у опорного решения | длинный список, таблица функций альтернатив | ≥ 5 кандидатов из ≥ 3 видов источников; для каждой потребности видно, как её закрывает каждый кандидат или «не подтверждено» | → Э4: расширить поиск |
| **Э5 Ценность** | функции из Э3 и Э4 | для каждой функции: какую потребность закрывает, **почему ценна** (механизм: что станет лучше и за счёт чего), доказательство ([уровни А–Г](#evidence)), класс ([Kano](#kano)) | таблица ценности функций | у каждой функции, которую предлагаем брать, ценность подтверждена уровнем Б и выше; уровень Г → прототип или «не берём» | → Э4: искать подтверждение или прототип (spike) |
| **Э6 Перенос и критерии** | выход Э5 | решение по каждой функции: **брать / адаптировать / заменить другой функцией / не брать**, с причиной; из базовых функций получаются MUST, из линейных — критерии сравнения, из привлекательных — дополнительные критерии | таблица переноса, таблица критериев с цепочкой | у каждой функции есть решение и причина; у каждого критерия цепочка «потребность → функция → ценность → класс» | → Э5 |
| **Э7 Отсев и встраивание** | выход Э6, [карта интерфейсов](../data-types.md) | 1) отсев по MUST до сравнения; 2) для каждого прошедшего — **как встаёт в общую схему** ([ниже](#integration)): какие интерфейсы (I-коды) занимает, с кем и в какую сторону вызовы, чьи хранилища, вид развёртывания, что меняется у соседних компонентов, готовность интеграции И0–И4; схема для лидеров | таблица отсева, таблица встраивания, схема C1 (mermaid) | у каждого прошедшего есть строка встраивания по всем затронутым I-кодам; изменения у соседей названы | → Э4: ни один кандидат не встаёт без перестройки схемы — искать дальше или вынести перестройку в вопрос |
| **Э8 Спор ролей** | выходы Э6, Э7 | роли, чьи требования, истории или интерфейсы затронуты, спорят о выборе ([ниже](#debate)): позиция, главный довод, опасение, условие согласия; лучшую альтернативу защищает назначенный оппонент, лидера атакует «адвокат дьявола» | таблица позиций, таблица разрешения споров | у каждого спора есть разрешение (условие, задача, требование) или вопрос 📌 владельцу продукта | → Э5–Э7: спор вскрыл неучтённую функцию или интеграцию |
| **Э9 Выбор** | выходы Э6–Э8 | 1) сравнение по критериям словами: «закрывает / закрывает с доработкой (что и сколько) / не закрывает» с фактом, включая встраивание; 2) риски лидера; 3) вывод аргументом ([Тулмин](#argument)); 4) условия пересмотра | раздел «Выбор», первая страница | вывод следует из сравнения и разрешения споров; у вывода есть условие, при котором он неверен | → Э5 или прототип: факты близки или не подтверждены |
| **Э10 Последствия** | выход Э9, трассировка | что меняет выбор во **всей цепочке** документов ([ниже](#consequences)): решения design, требования спек, interfaces.md, потоки, API, техспеки, задачи, TECHNOLOGIES; у каждого изменения — статус «внесено / предложено / не требуется» | таблица последствий | у каждого изменения есть целевой документ и статус; внесённые прошли [процесс изменений](change-process.md) и сборку | → Э9: последствия дороже выигрыша — пересмотреть выбор |

**Финальные проверки качества** (четыре качества отчёта по GAO TRA):

| Качество | Вопрос |
|---|---|
| Достоверность | у каждого факта есть источник и дата; уровни доказательства указаны |
| Объективность | рассмотрены «ничего не делать» и «сделать самим»; функции отсеянных кандидатов разобраны в Э5–Э6; роли с противоположными интересами выслушаны (Э8); у вывода есть опровержение |
| Воспроизводимость | по документу можно повторить путь: источники поиска, дата, критерии с цепочкой |
| Полезность | первая страница отвечает на вопрос и говорит, что делать (решение, перенос функций, что меняется в схеме и документах, пересмотр) |

**Сокращённый путь** — для малого вопроса (библиотека, решение одной функции): Э3 и Э4 сводятся в одну таблицу функций, в Э8 — 2–3 роли. Встраивание (Э7) и последствия (Э10) не сокращаются; ворота и первая страница — те же.

## Встраивание в общую схему {#integration}

Решение оценивается не само по себе, а **на своём месте в архитектуре**. Кандидат с лучшими функциями может требовать перестройки соседних компонентов — это цена выбора.

Для каждого кандидата, прошедшего отсев:

| Что смотрим | Откуда | Вопрос |
|---|---|---|
| Интерфейсы | [матрица I1–I23](../data-types.md), `interfaces.md` спек | какие I-коды занимает или меняет; совпадают ли протокол и формат с описанными |
| Направление вызовов | потоки (`docs/flows`) | кто кого вызывает; не ломаются ли pull-модель (Runner берёт работу у ICPlan) и границы модулей |
| Данные и владельцы | хранилища S1–S10 в `interfaces.md` | чьи хранилища читает и пишет; не появляется ли второй владелец данных |
| Развёртывание | [виды развёртывания](spec-kinds.md), техспеки | свой сервис, часть ICPlan, образ на запуск или внешний образ; новые зависимости эксплуатации |
| Изменения у соседей | спеки соседних компонентов | что придётся поменять в других компонентах: требования, интерфейсы, задачи |
| Безопасность на стыках | guardrails, egress, секреты | какие новые пути данных и секретов появляются |

**Готовность интеграции** (упрощённая шкала IRL Sauser):

| Уровень | Что значит |
|---|---|
| **И0** | стык не описан: неизвестно, как подключать |
| **И1** | стык описан в документации кандидата (API, протокол) |
| **И2** | протокол и модель данных совпадают с нашими I-кодами, или расхождение описано |
| **И3** | стык проверен прототипом у нас |
| **И4** | стык работает у нас (в эксплуатации или в коде форка) |

Для лидеров рисуется схема C1 места решения (mermaid по [FORMAT.md](../../FORMAT.md), изменённое — классом `new`): соседние компоненты, I-коды, направление вызовов. Изменённые стыки на схеме помечаются `*`.

## Спор ролей {#debate}

Выбор обсуждается с позиций ролей, у которых разные интересы. Основа — диалектический спор (dialectical inquiry), «адвокат дьявола» и участники ATAM со своими сценариями. Роли берутся из [ролей документации](roles.md) и [персон продукта](../stories/personas.md); агент, играющий роль, отмечается 🤖.

1. **Состав.** Роли, чьи требования, истории, интерфейсы или эксплуатация затронуты выбором. Обычно это 4–6 ролей из списка: Архитектор, Разработчик, DevOps, Безопасность, Владелец продукта, Пользователь, Администратор, Тестировщик.
2. **Позиции.** Каждая роль называет:
   - за какой вариант;
   - главный довод со ссылкой на факт из Э3–Э7;
   - главное опасение;
   - при каком условии согласится.
3. **Тезис и антитезис.** Назначенный оппонент защищает лучшую альтернативу, «адвокат дьявола» ищет, где лидер провалится.
4. **Разрешение.** Каждый спор закрывается одним из исходов:
   - условием;
   - задачей;
   - требованием;
   - сменой выбора;
   - вопросом 📌 владельцу продукта, если фактами спор не решается.
5. **Возврат.** Если спор вскрыл неучтённую функцию или стык — назад в Э5–Э7.

## Последствия во всей цепочке {#consequences}

R&D — начало цепочки. Из выбора вытекают решения design, требования, интерфейсы, потоки, API, техспеки и задачи. Поэтому каждый R&D заканчивается таблицей последствий.

| Изменение | Документ | Статус |
|---|---|---|
| что меняется | design (Dn), спека (R-…), interfaces.md (I-, S-код, параметр) **всех спек-участников**, `html-view/datamodel.py` (интеграции, модели, таблицы), поток, API (эндпоинты и примеры), техспека, задача, TECHNOLOGIES | ✅ внесено · 📌 предложено (ссылка на задачу или вопрос) · — не требуется (почему) |

Правила:

- **Подтверждение без изменений** — тоже результат. Пишем «решение не меняется, D-номер подтверждён» и перечисляем затронутые документы со статусом «не требуется».
- **Если выбор меняет решение, стек или описание**, отметка в таблице обязательна. Изменение вносится по [процессу изменений](change-process.md): синхронизируются все спеки-участники, подтверждения ролей сбрасываются, сборка должна пройти. Если изменение слишком большое, чтобы вносить его вместе с R&D, оформляется задача.
- **Смена версии или технологии** обновляет [TECHNOLOGIES](../TECHNOLOGIES.md) и техспеку компонента.

## Цветовая разметка {#colors}

Сборка сама подсвечивает в R&D ключевые слова в начале ячейки таблицы. Автор пишет обычный текст, цвет добавлять вручную не нужно.

| Что | Слова в начале ячейки | Цвет |
|---|---|---|
| Оценка | закрывает · да · проходит · ✅ | <span class="hl ok">зелёный</span> |
| | с доработкой · частично · можно добавить | <span class="hl part">жёлтый</span> |
| | не закрывает · нет · ✗ | <span class="hl no">красный</span> |
| Решение по функции | брать · оставить | <span class="hl ok">зелёный</span> |
| | адаптировать · заменить | <span class="hl info">синий</span> |
| | не брать | <span class="hl mute">серый</span> |
| Класс функции | базовая · линейная · привлекательная · безразличная · обратная | <span class="hl kano-base">базовая</span> <span class="hl kano-lin">линейная</span> <span class="hl kano-att">привлекательная</span> <span class="hl mute">безразличная</span> <span class="hl no">обратная</span> |
| Уровень доказательства | (А) (Б) (В) (Г) в любом месте | <span class="ev a">А</span> <span class="ev b">Б</span> <span class="ev c">В</span> <span class="ev d">Г</span> |
| Готовность интеграции | И0 … И4 в начале ячейки | <span class="hl no">И0</span> <span class="hl part">И1</span> <span class="hl part">И2</span> <span class="hl ok">И3</span> <span class="hl ok">И4</span> |

Абзац, который начинается с «**Вывод этапа.**», выводится в рамке. Главную мысль внутри текста автор выделяет маркером `==так==` — не больше одной-двух на раздел.

## Классы функций (Kano для нас) {#kano}

Класс определяется по нашим историям и требованиям и по тому, есть ли функция у аналогов. Анкета не нужна.

| Класс | Признак | Что делаем в Э6 |
|---|---|---|
| **Базовая** | без неё работа из Э2 не выполняется или вариант неприемлем (своё размещение, доработка кода); функция есть у всех аналогов | → **MUST**: отсев до сравнения |
| **Линейная** | чем лучше, тем лучше закрыта потребность (объём доработки, зрелость, функции для людей) | → **критерий сравнения** |
| **Привлекательная** | улучшает работу, но её отсутствие не мешает | → дополнительный критерий, решает при равенстве |
| **Безразличная** | не закрывает нашу потребность | → **не берём**, указываем причину |
| **Обратная** | мешает нашей работе или противоречит решению (например, агент сам двигает задачу по доске вопреки R-AP-16) | → **не берём**; если она у выбранного кандидата — отключить или убрать |

Классы со временем смещаются: привлекательная функция становится базовой, когда она есть у всех аналогов. Поэтому факты о функциях аналогов проверяются **на дату** исследования.

## Уровни доказательства {#evidence}

| Уровень | Что это | Пример |
|---|---|---|
| **А** | проверено нами | прочитан код, прототип, замер |
| **Б** | первичный источник | документация, код, changelog продукта, стандарт, исходная статья |
| **В** | опыт практиков | статьи, обзоры, issue, отчёты пользователей |
| **Г** | заявление без деталей | маркетинг, «скоро будет», слухи |

**Наличие** функции подтверждается уровнем Б и выше. **Ценность** — нашей историей или требованием плюс одним из подтверждений:

- функция есть у ≥ 2 аналогов (на рынке так решают);
- опыт практиков (уровень В);
- наш прототип (уровень А).

## Аргумент вывода {#argument}

Вывод каждого этапа и итог пишутся по модели Тулмина:

| Часть | Вопрос | Пример (трекер) |
|---|---|---|
| Утверждение | что решили | берём форк It's a Plan |
| Основания | какие факты | агент — участник проекта, очередь запусков с арендой, внешний раннер в открытом коде (Б, код) |
| Связка | почему факты ведут к выводу | эти функции — базовые для С1 и С2; у других кандидатов их нужно писать |
| Оговорка | насколько сильно | при текущем сообществе проекта |
| Опровержение | когда вывод неверен | если релизы прекратятся дольше 6 месяцев или агенты Plane появятся в открытом издании с внешним исполнителем |

## Подача результата {#layout}

Документ строится «ответ первым» (пирамида Минто). Порядок разделов — порядок получения данных.

**Первая страница — презентация для заказчика на 3 минуты** (без таблиц баллов):

1. **Вопрос и ответ** — блок `rnd-hero`: вопрос, ответ одной фразой, статус Tech Radar, ссылка на решение в design.
2. **Микропрезентация** — 4–6 слайдов ([ниже](#deck)): покрытие потребностей, объём доработки, встраивание, позиции ролей, что меняется.
3. **Почему** — 3 карточки (`rnd-grid`): каждая — вывод, ключевой факт, ссылка на этап.
4. **Что берём / адаптируем / не берём** из опорного решения и аналогов (`take`, `adapt`, `drop`).
5. **Отсеяны** — кто и одна причина у каждого (`no`); **риски и пересмотр** (`risk`).
6. **Путь исследования** — цепочка этапов (`rnd-chain`).

### Микропрезентация {#deck}

Слайды 16:9 показывают **соотношения**: сколько потребностей закрывает каждый вариант, у кого больше доработки, на чьей стороне роли, сколько изменений в документах. Читатель видит пропорции раньше, чем читает текст.

**Правила слайда:**

- **Один слайд — один вопрос заказчика** и строка-вывод (`>`), которая на него отвечает.
- **Пропорции берутся из таблиц этапов**, а не придумываются:
  - покрытие — из сравнения Э9 (по числу потребностей);
  - объём доработки — из порядковой шкалы Э9 («малый / средний / крупный / всё писать» = 1–4 из 4) или из оценок задач в днях, если они есть;
  - позиции ролей — из Э8;
  - последствия — из Э10.
- **Без сумм баллов.** Число допустимо, только если это количество (потребностей, интерфейсов, изменений) или оценка задачи.
- **Цвета** — те же, что в [разметке](#colors): зелёный — закрывает или внесено, жёлтый — с доработкой или предложено, красный — не закрывает, синий — альтернатива или адаптация, серый — не требуется.

**Набор слайдов** (не больше 6):

| Слайд | Вопрос заказчика | Элемент |
|---|---|---|
| Покрытие потребностей | кто закрывает то, что нам нужно? | `stack` по каждому кандидату |
| Объём доработки | сколько придётся сделать самим? | `bar` по каждому кандидату |
| Встраивание | что меняется в схеме? | `bar` или пункты: затронутые и изменённые I-коды, готовность И0–И4 |
| Позиции ролей | кто за, кто против и почему? | `side` + `pos` по каждой роли |
| Что меняется | что будет с документами и задачами? | `stack` по статусам последствий |

**Разметка** — блок кода `deck`; сборка превращает его в слайды:

````
```deck
# Покрытие потребностей П1–П8
> только It's a Plan закрывает агентную часть без написания с нуля
stack It's a Plan: 5 ok, 3 part, 0 no
stack Plane CE: 3 ok, 3 part, 2 no
# Позиции ролей
side It's a Plan | Plane CE
pos Разработчик: -2 | агентная часть уже есть
pos DevOps: 1 | у Plane больше сообщество
```
````

| Строка | Что рисует |
|---|---|
| `# Заголовок` | новый слайд |
| `> вывод` | строка-вывод слайда |
| `stack Метка: N ok, N part, N no` | сегментная полоса (также `info`, `mute`) |
| `bar Метка: значение/максимум подпись [цвет]` | полоса доли |
| `side Левый \| Правый` | подписи концов шкалы позиций |
| `pos Роль: −2…2 \| довод` | точка роли на шкале: −2 — полностью за левый вариант, 2 — за правый |
| `- текст` | пункт |

**Дальше — раскрытие по этапам Э1–Э10.** Каждый этап заканчивается строкой «**Вывод этапа**» и воротами `<span class="gate">Gn</span> ✅ …` с тем, чем они пройдены.

**Приложение** (сворачиваемое, `<details>`): карточки кандидатов, числовая сверка (необязательна; если есть — подписана «сверка, не основание»), сырые данные.

**Источники** — с датой и уровнем доказательства.

Правила текста:

- вывод — связной фразой с причиной («берём X, потому что Y»), а не пунктом из двух слов;
- у каждого факта о продукте — ссылка;
- «нет функции» пишется только после проверки изданий: функция может быть в платном издании.

## Технологии ИИ-агентов: проверка прототипом

Ценность функций агентной технологии подтверждается прототипом (уровень А) по измерениям ниже. Без прототипа статус — не выше **Trial**.

| Код | Измерение | Вопрос |
|---|---|---|
| AG1 | Выполнение задачи | доводит ли агент задачу до результата на нашем наборе задач |
| AG2 | Выбор тулов и аргументы | правильно ли выбирает тул и формирует аргументы |
| AG3 | Восстановление после ошибок | продолжает ли после сбоя тула или модели |
| AG4 | Связность плана | не теряет ли цель на длинной задаче |
| AG5 | Эффективность | токены, задержка, стоимость на задачу |
| AG6 | Наблюдаемость и evals | даёт ли трейсы, совместимые с инструментами оценки |

Прототип: 5–10 эталонных задач на mock-LLM и реальной модели, замер AG1–AG5.

## Антипаттерны

| Антипаттерн | Почему плохо | Как правильно |
|---|---|---|
| Критерии и веса заданы до разбора функций | не видно, откуда критерий | критерий — результат Э6 с цепочкой |
| Итог — сумма баллов | вывод нельзя проверить | вывод аргументом; баллы — сверка в приложении |
| Сравниваются продукты целиком | теряются функции отсеянных кандидатов | решение по каждой функции, в том числе у отсеянных |
| Обязательное свойство как взвешенный критерий | неприемлемый вариант побеждает по сумме | базовая функция → MUST, отсев до сравнения |
| Ценность «очевидна» | функции берутся по моде | механизм ценности и доказательство |
| Первая страница — таблица | читатель не видит, почему так | вопрос → ответ → 3 основания → перенос → риски |
| Решение оценено отдельно от схемы | лучший «сам по себе» вариант ломает стыки и владельцев данных | встраивание по I- и S-кодам, изменения у соседей (Э7) |
| Выбор с одной позиции | не услышаны эксплуатация, безопасность, пользователи | спор ролей с оппонентом и «адвокатом дьявола» (Э8) |
| R&D без последствий | выбор не доходит до спек, задач и техспек | таблица последствий со статусами (Э10) |
| Факты по памяти, «нет функции» без проверки изданий | устаревшие или неверные данные | ссылка и дата; проверка изданий |
| Общая таблица критериев для всех R&D | критерии не по вопросу | критерии каждого R&D — из его потребностей |

## R&D пользовательских потоков {#us-rnd}

Тот же принцип «функции аналогов → ценность → перенос», только единица анализа — поток пользователя, а не функция продукта.

1. Взять идею компонента и сформулировать работы (JTBD) по акторам — Э2.
2. Найти 3–5 аналогов и выписать их потоки: точки входа, состояния, действия людей и агентов — Э3–Э4.
3. Матрица «поток × аналог × у нас» → истории или осознанное «не делаем» с причиной — Э5–Э6.
4. Отыграть персон, отфильтровать ненужное ([фильтр необходимости](us-methodology.md)).

## Персоны и отыгрыш конфликтов {#personas}

1. **Сущности.** Участники и объекты процесса; у каждой — что **может** и что **хочет**.
2. **Персоны.** Промпт персоны ([personas.md](../stories/personas.md)); новые — добавить.
3. **Отыгрыш.** Сыграть цель каждой персоны, искать конфликты с другими и с системой.
4. **Таблица конфликтов:** кто → что хочет → с кем конфликт → что должно произойти.
5. **Артефакты** каждого шага процесса.
6. Итог — истории, требования, открытые вопросы.
