# Методология R&D

**Версия 3.3** ([изменения](#changes)). Исследование идёт по цепочке **потребность → ключевые функции → ценность → перенос → встраивание в схему → спор ролей → выбор → последствия**. Каждый этап начинается с выхода предыдущего и закрывается воротами. Критерии выбора получаются в конце цепочки, а не задаются заранее. Выводы доказываются фактами, цифры — только для сверки, в приложении.

Почему так: [R&D о методологии](../rnd/rnd-methodology-choice.md). Отклонения, которые привели к этой версии: [О-25](deviations.md) (v1 → v2) и [О-34](deviations.md) (v2 → v3), [О-35](deviations.md) (v3 → v3.1: встраивание, спор ролей, последствия, цветовая разметка), [О-65](deviations.md) (v3.1 → v3.2: разделы по этапам, новый продукт, ворота ⚠️). Эталон применения: [выбор трекера](../rnd/tracker-choice.md).

Два вида R&D: **выбор решения** (технология, архитектурный подход, методика) и **потоки пользователей** (для историй, [ниже](#us-rnd)).

**Как читать.** Этап — отдельный раздел с якорем `#e1`…`#e10`; читать нужный этап и подразделы, на которые он ссылается, а не весь файл (карта — в сценарии `doc-rnd`).

## Этапы {#stages}

В документе R&D каждый этап — раздел `## Эn. … {#en}`, заканчивается строкой «**Вывод этапа.**» и воротами `<span class="gate">Gn</span> ✅ …` (или ⚠️ — [статус ворот](#gate-status)).

### Э1 Вопрос {#e1}

- **Вход:** история, требование, решение design, замечание; в новом продукте — запрос владельца ([ниже](#greenfield)).
- **Что делаем:** ситуация, осложнение и вопрос (SCQA): вопрос — выбор между вариантами; кто решает; что не решаем.
- **Выход:** раздел «Вопрос».
- **G1:** вопрос сформулирован как выбор; есть владелец; есть связь с историей, требованием или решением (в новом продукте — с запросом владельца с датой).
- **Иначе:** вопрос не ставится — это задача, а не R&D.

### Э2 Потребности {#e2}

- **Вход:** выход Э1, истории, требования, ограничения.
- **Что делаем:** выписываем, что должно получаться (работа и желаемый исход, JTBD), а не функции; у каждой потребности — источник и «что ломается без неё».
- **Выход:** таблица потребностей.
- **G2:** у каждой потребности есть источник; нет потребностей «на всякий случай».
- **Иначе:** → Э1: вопрос шире или уже, чем потребности.

### Э3 Опорное решение {#e3}

- **Вход:** выход Э2.
- **Что делаем:** разбираем то, что есть или предполагается (текущее решение, продукт-кандидат): его **ключевые функции** — без них работа из Э2 не выполняется (критические элементы); у функции — что делает, какую потребность закрывает, факт. Новый продукт — «как пользователь решает задачу без нас» ([ниже](#greenfield)).
- **Выход:** таблица функций опорного решения.
- **G3:** каждая функция связана с потребностью или помечена «не к нашей потребности»; у наличия функции есть факт уровня Б и выше ([уровни](#evidence)).
- **Иначе:** → Э2: функции закрывают потребности, которых нет в списке, — дописать или убрать.

### Э4 Альтернативы {#e4}

- **Вход:** выходы Э2, Э3.
- **Что делаем:** сначала список кандидатов и видов источников под G4, затем все поиски одной пачкой ([где искать](#search)), с датой. В список всегда входят «как сейчас / ничего не делать» и «сделать самим». У каждой альтернативы — ключевые функции **по тем же потребностям** и функции, которых нет у опорного решения.
- **Выход:** длинный список, таблица функций альтернатив; остальное о кандидате — в [карточке](#candidate-card) приложения.
- **G4:** ≥ 5 кандидатов из ≥ 3 видов источников; для каждой потребности видно, как её закрывает каждый кандидат или «не подтверждено».
- **Иначе:** → Э4: расширить поиск.

### Э5 Ценность {#e5}

- **Вход:** функции из Э3 и Э4.
- **Что делаем:** для каждой функции — какую потребность закрывает, **почему ценна** (механизм: что станет лучше и за счёт чего), доказательство ([уровни А–Г](#evidence)), класс ([Kano](#kano)). Агентные технологии — прототип по [AG1–AG6](#ag).
- **Выход:** таблица ценности функций.
- **G5:** у каждой функции, которую предлагаем брать, ценность подтверждена уровнем Б и выше; уровень Г → прототип или «не берём».
- **Иначе:** → Э4: искать подтверждение или прототип (spike).

### Э6 Перенос и критерии {#e6}

- **Вход:** выход Э5.
- **Что делаем:** решение по каждой функции — **брать / адаптировать / заменить другой функцией / не брать**, с причиной; из базовых функций — MUST, из линейных — критерии сравнения, из привлекательных — дополнительные критерии ([Kano](#kano)). R&D потоков — здесь матрица «поток × аналог × у нас», отыгрыш персон и фильтр необходимости ([ниже](#us-rnd)).
- **Архитектурное решение:** здесь же шаги 1–3 [слоя 2](#layer2) — практики-кандидаты слоя 1, дерево качества с приоритетом H/M/L, сценарии атрибутов с количественным response measure.
- **Выход:** таблица переноса, таблица критериев с цепочкой (для потоков — матрица потоков); для архитектурного решения — дерево качества и сценарии.
- **G6:** у каждой функции (потока) есть решение и причина; у каждого критерия цепочка «потребность → функция → ценность → класс».
- **Иначе:** → Э5.

### Э7 Отсев и встраивание {#e7}

- **Вход:** выход Э6, [карта интерфейсов](../data-types.md).
- **Что делаем:** 1) отсев по MUST до сравнения; 2) для каждого прошедшего — **как встаёт в общую схему** ([встраивание](#integration)): I-коды, направление вызовов, чьи хранилища, вид развёртывания, изменения у соседей, готовность И0–И4; схема C1 для лидеров.
- **Архитектурное решение:** шаг 4 [слоя 2](#layer2) — варианты ≥ 2 плюс «ничего не делать», с тактиками.
- **Выход:** таблица отсева, таблица встраивания, схема C1 (mermaid).
- **G7:** у каждого прошедшего есть строка встраивания по всем затронутым I-кодам; изменения у соседей названы.
- **Иначе:** → Э4: ни один кандидат не встаёт без перестройки схемы — искать дальше или вынести перестройку в вопрос.

### Э8 Спор ролей {#e8}

- **Вход:** выходы Э6, Э7.
- **Что делаем:** роли, чьи требования, истории или интерфейсы затронуты, спорят о выборе ([спор](#debate)): позиция, главный довод, опасение, условие согласия; лучшую альтернативу защищает оппонент, лидера атакует «адвокат дьявола».
- **Архитектурное решение:** шаг 5 [слоя 2](#layer2) — ATAM-lite и CBAM-lite; проходит роль-ревьюер, не автор.
- **Выход:** таблица позиций, таблица разрешения споров.
- **G8:** у каждого спора есть разрешение (условие, задача, требование) или вопрос 📌 владельцу продукта.
- **Иначе:** → Э5–Э7: спор вскрыл неучтённую функцию или интеграцию.

### Э9 Выбор {#e9}

- **Вход:** выходы Э6–Э8.
- **Что делаем:** 1) сравнение по критериям словами: «закрывает / закрывает с доработкой (что и сколько) / не закрывает» с фактом, включая встраивание; 2) риски лидера; 3) вывод аргументом ([Тулмин](#argument)); 4) условия пересмотра.
- **Архитектурное решение:** шаги 6–7 [слоя 2](#layer2) — fitness-функции на каждый принятый сценарий и ADR по MADR. Без принятой методологии и метрик слоя ворота G9 не проходятся ([правило](#no-method)).
- **Выход:** раздел «Выбор», первая страница ([подача](#layout)).
- **G9:** вывод следует из сравнения и разрешения споров; у вывода есть условие, при котором он неверен.
- **Иначе:** → Э5 или прототип: факты близки или не подтверждены.

### Э10 Последствия {#e10}

- **Вход:** выход Э9, трассировка.
- **Что делаем:** что меняет выбор во **всей цепочке** документов ([последствия](#consequences)): решения design, требования спек, interfaces.md, потоки, API, техспеки, задачи, TECHNOLOGIES; у каждого изменения — статус «внесено / предложено / не требуется».
- **Выход:** таблица последствий.
- **G10:** у каждого изменения есть целевой документ и статус; внесённые прошли [процесс изменений](change-process.md) и сборку. Новый продукт — допустим полный набор 📌 со следующим шагом ([ниже](#greenfield)).
- **Иначе:** → Э9: последствия дороже выигрыша — пересмотреть выбор.

## Архитектурное решение: два слоя {#layer2}

R&D, у которого вопрос — архитектурное решение (в шапке: «тип: архитектурное решение»), состоит из двух слоёв.

1. **Слой 1 — общее исследование.** Что работает и ценой чего. Критерии берём из методических публикаций; для LLM-агентов:
   - качество работы с независимой приёмкой и устойчивостью pass^k (τ-bench, ABC checklist);
   - стоимость на принятую задачу совместно с качеством, а не отдельно (AI Agents That Matter);
   - качество самообучения, измеренное на отложенных задачах;
   - разброс результатов, а не одно число (Adding Error Bars to Evals).
2. **Слой 2 — техническое решение.** Перенос результатов слоя 1 на нашу архитектуру по атрибутам качества. Выход слоя 1 (практики-кандидаты) — вход слоя 2.

Методика слоя 2, 7 шагов:

| № | Шаг | Что должно быть | Этап |
|---|---|---|---|
| 1 | Вход | список практик-кандидатов из слоя 1, у каждой источник и уровень | Э6 |
| 2 | Дерево качества | arc42 раздел 10.1, характеристики ISO/IEC 25010:2023 или Q42; у каждого листа приоритет H/M/L | Э6 |
| 3 | Сценарии | длинная форма: source, stimulus, artifact, environment, response, response measure; типы usage и change; **response measure обязателен и количественный** | Э6 |
| 4 | Варианты | ≥ 2 варианта плюс «ничего не делать»; у каждого тактики, которыми он закрывает сценарии | Э7 |
| 5 | ATAM-lite и CBAM-lite | риски, точки чувствительности, точки компромисса; стоимость против выгоды по сценариям; проходит роль-ревьюер, не автор | Э8 |
| 6 | Fitness-функции | по одной на каждый принятый сценарий; оси: atomic/holistic, triggered/continual/temporal, static/dynamic, automated/manual; неавтоматизируемое — ручное ревью с периодом, отмечается как слабое место | Э9 |
| 7 | ADR по MADR | Decision Drivers, Considered Options, Decision Outcome с Consequences и Confirmation (fitness-функции, тесты) | Э9 |

### Базовый набор атрибутов агент-платформы {#qa-base}

Отправная точка дерева качества; сценарии и пороги задаёт каждое R&D (в чек-листе AWS Agentic AI Lens числовых порогов нет — это источник практик). Характеристики ISO/IEC 25010:2023: maintainability = modularity, reusability, analysability, modifiability; flexibility = adaptability, scalability, installability, replaceability. Testability по arc42 относится к flexibility, по тексту стандарта [не проверено].

| Атрибут | Пример сценария | Response measure | Fitness-функция | Источник |
|---|---|---|---|---|
| Гибкость | новый тип агента или роль без правки ядра | правок ядра = 0; ≤ 1 дня | агент из конфига проходит контракт | ISO 25010 (flexibility); Bass |
| Настраиваемость | роль, промпт, обучение меняются без деплоя | доля поведения под конфигом ≥ X %; ≤ N мин | все параметры в схеме, нет хардкода | Azure WAF; Fowler |
| Расширяемость | внешний инструмент или компонент памяти через MCP или адаптер | изменения без правки ядра | плагины не импортируют внутренности | Azure WAF; Bass |
| Сопровождаемость | локализовать причину ошибки агента | время диагностики ≤ N мин | пороги зависимостей и покрытия | ISO 25010 (maintainability), 25023 |
| Наблюдаемость | восстановить цепочку решений | 100 % прогонов с трассой | trace ID в каждом логе | AWS AGENTOPS05 |
| Безопасность | агент выходит за права роли | нарушений = 0; 100 % вызовов с авторизацией | тест политик, red team | AWS AGENTSEC02/03; SAIF |
| Контроль человека | критичное действие или изменение агента | 100 % с одобрением | без одобрения блокируется | AWS AGENTREL02-BP05, AGENTSEC04-BP02; NIST MANAGE 2.4 |
| Отключаемость | остановить агента или обучение при аномалии | ≤ N с; охват 100 % | учебный прогон отключения | Fowler (ops toggles); AWS AGENTREL06-BP05 |
| Откат | вернуть прежнюю версию правил или памяти | ≤ N мин; 100 % версий пригодны | тест отката на staging | AWS AGENTOPS02-BP03 |
| Стоимость | превышение бюджета токенов | стоимость на задачу ≤ X; 100 % прогонов с лимитом | тест лимита, алерт аномалии | AWS AGENTCOST05/07; Azure |
| Надёжность | сбой модели во время задачи | доля завершённых после сбоя; MTTR | chaos-тест fallback | AWS AGENTREL; Azure |
| Изменяемость | частота безопасных релизов | DF, lead time, CFR, TTR | метрики пайплайна | DORA [не проверено] |
| Управляемость памяти | ложный факт в памяти | 100 % записей с источником и TTL; время очистки | проверка схемы записи | AWS AGENTSEC01, AGENTREL03 |
| Заменяемость | замена модели при deprecation | ≤ N дн.; доля сценариев на новой модели | регресс-набор на новой модели | ISO 25010 (replaceability); Azure WAF |

### Без методологии и метрик решение не принимается {#no-method}

Если для слоя нет принятого списка метрик или методики, сначала исследуется методология (с источниками в [разделе источников](#sources-method)), затем решение. Пока методики нет, ворота выбора (G9) не проходятся: ✅ нельзя, только ⚠️ с 📌 владельцу и следующим шагом — исследовать методологию ([статус ворот](#gate-status)).

### Собственный эксперимент {#own-experiment}

Эксперимент — доказательство (уровень А), только если выполнены все условия:

1. воспроизводит ключевые механизмы целевой архитектуры;
2. сравнивает все исследуемые варианты, включая «ничего не делать»;
3. n повторов, результат с разбросом (Miller, Adding Error Bars to Evals);
4. тесты заданы до прогона и независимы от проверяемого варианта;
5. нет потолка (результаты не упираются в максимум шкалы).

Иначе это только проверка методики: в выводы не идёт, ссылаться на неё как на доказательство нельзя.

## Новый продукт {#greenfield}

**Когда:** продукта ещё нет — нет историй, требований, решений и проекта документов (вопрос «делать ли и какой»). Ворота G1, G3, G10 проходятся **по этому правилу** — ✅, а не ⚠️.

| Этап | Обычно | В новом продукте |
|---|---|---|
| Э1 (G1) | связь с историей, требованием, решением | связь — **запрос владельца с датой** (ссылка на сообщение, встречу или цитата) |
| Э2 | источник — наши истории и требования | источник — запрос владельца и внешние факты (рынок, исследования, отзывы); непроверенное у пользователей — 📌 |
| Э3 (G3) | функции существующего решения, наличие — Б+ | **«как пользователь решает задачу без нас»**: обходные пути (звонок, бумага, конкуренты, ничего); наличие — уровень В+ (практики, отзывы, исследования) или ответ владельца; неизвестное о нашей стороне (каналы, системы) — 📌 вопрос владельцу |
| Э10 (G10) | внесено ✅ или предложено 📌 | допустим **полный набор 📌**: у каждой строки — будущий документ и следующий шаг (сценарий, задача); первая строка — реестр R&D и решений в `README.md` корня проекта ([структура](structure-methodology.md)) |

Остальные этапы и ворота — без изменений.

## Статус ворот {#gate-status}

| Статус | Значит | Когда |
|---|---|---|
| ✅ пройдено | условие ворот выполнено (в том числе по правилу [нового продукта](#greenfield)) | всегда, когда условие выполнено |
| ⚠️ пройдено условно | условие выполнено не полностью, работа идёт дальше | только если недостающий факт **нельзя получить внутри R&D** (нужен ответ владельца, доступ, пилот), а выбор от него не зависит или зависит явно (условие в Э9) |
| — (не пройдено) | условие не выполнено | возврат по пункту «Иначе» этапа |

⚠️ недопустим, если факт можно найти поиском или чтением, — тогда возврат. В строке ⚠️ обязательно: **что не подтверждено**, **📌 вопрос владельцу** и **следующий шаг**, который снимает условие (задача, пилот, этап). Ворота ⚠️ выносятся в «Риски и пересмотр» первой страницы. Проверка — `doctool rnd-check`.

## Встраивание в общую схему {#integration}

Решение оценивается не само по себе, а **на своём месте в архитектуре**. Кандидат с лучшими функциями может требовать перестройки соседних компонентов — это цена выбора.

Для каждого кандидата, прошедшего отсев:

| Что смотрим | Откуда | Вопрос |
|---|---|---|
| Интерфейсы | [матрица I1–I23](../data-types.md), `interfaces.md` спек | какие I-коды занимает или меняет; совпадают ли протокол и формат с описанными |
| Направление вызовов | потоки (`docs/flows`) | кто кого вызывает; не ломаются ли pull-модель (Runner берёт работу у ICPlan) и границы модулей |
| Данные и владельцы | хранилища S1–S10 в `interfaces.md` | чьи хранилища читает и пишет; не появляется ли второй владелец данных |
| Развёртывание | [виды развёртывания](spec-kinds.md), техспеки | свой сервис, часть ICPlan, образ на запуск или внешний образ; новые зависимости эксплуатации |
| Изменения у соседей | спеки соседних компонентов | что придётся поменять в других компонентах: требования, интерфейсы, задачи |
| Безопасность на стыках | guardrails, egress, секреты | какие новые пути данных и секретов появляются |

**Готовность интеграции** (упрощённая шкала IRL Sauser):

| Уровень | Что значит |
|---|---|
| **И0** | стык не описан: неизвестно, как подключать |
| **И1** | стык описан в документации кандидата (API, протокол) |
| **И2** | протокол и модель данных совпадают с нашими I-кодами, или расхождение описано |
| **И3** | стык проверен прототипом у нас |
| **И4** | стык работает у нас (в эксплуатации или в коде форка) |

Для лидеров рисуется схема C1 места решения (mermaid по [FORMAT.md](../../FORMAT.md), изменённое — классом `new`): соседние компоненты, I-коды, направление вызовов. Изменённые стыки на схеме помечаются `*`.

## Спор ролей {#debate}

Выбор обсуждается с позиций ролей, у которых разные интересы. Основа — диалектический спор (dialectical inquiry), «адвокат дьявола» и участники ATAM со своими сценариями. Роли берутся из [ролей документации](roles.md) и [персон продукта](../stories/personas.md); агент, играющий роль, отмечается 🤖.

1. **Состав.** Роли, чьи требования, истории, интерфейсы или эксплуатация затронуты выбором. Обычно это 4–6 ролей из списка: Архитектор, Разработчик, DevOps, Безопасность, Владелец продукта, Пользователь, Администратор, Тестировщик.
2. **Позиции.** Каждая роль называет:
   - за какой вариант;
   - главный довод со ссылкой на факт из Э3–Э7;
   - главное опасение;
   - при каком условии согласится.
3. **Тезис и антитезис.** Назначенный оппонент защищает лучшую альтернативу, «адвокат дьявола» ищет, где лидер провалится.
4. **Разрешение.** Каждый спор закрывается одним из исходов:
   - условием;
   - задачей;
   - требованием;
   - сменой выбора;
   - вопросом 📌 владельцу продукта, если фактами спор не решается.
5. **Предложение в своей зоне.** Каждая роль **обязана** дать предложение, а не только риск:
   - Архитектор — гибкость: всё новое включается и отключается конфигом и донастраивается;
   - Разработчик — что взять из открытых источников и что оптимизировать;
   - Безопасность — конкретный набор ограничений: пороги, откат, карантин, аудит;
   - Владелец продукта или Финансы — ценность и потолок затрат с метрикой.

   Ценность фичи оценивается **атомарно** (для одного агента или проекта), а не только внутри обсуждаемой схемы.
6. **Возврат.** Если спор вскрыл неучтённую функцию или стык — назад в Э5–Э7.

## Последствия во всей цепочке {#consequences}

R&D — начало цепочки. Из выбора вытекают решения design, требования, интерфейсы, потоки, API, техспеки и задачи. Поэтому каждый R&D заканчивается таблицей последствий.

| Изменение | Документ | Статус |
|---|---|---|
| что меняется | design (Dn), спека (R-…), interfaces.md (I-, S-код, параметр) **всех спек-участников**, `html-view/datamodel.py` (интеграции, модели, таблицы), поток, API (эндпоинты и примеры), техспека, задача, TECHNOLOGIES | ✅ внесено · 📌 предложено (ссылка на задачу или вопрос) · — не требуется (почему) |

Правила:

- **Подтверждение без изменений** — тоже результат. Пишем «решение не меняется, D-номер подтверждён» и перечисляем затронутые документы со статусом «не требуется».
- **Если выбор меняет решение, стек или описание**, отметка в таблице обязательна. Изменение вносится по [процессу изменений](change-process.md): синхронизируются все спеки-участники, подтверждения ролей сбрасываются, сборка должна пройти. Если изменение слишком большое, чтобы вносить его вместе с R&D, оформляется задача.
- **Смена версии или технологии** обновляет [TECHNOLOGIES](../TECHNOLOGIES.md) и техспеку компонента.

## Классы функций (Kano для нас) {#kano}

Класс определяется по нашим историям и требованиям и по тому, есть ли функция у аналогов. Анкета не нужна.

| Класс | Признак | Что делаем в Э6 |
|---|---|---|
| **Базовая** | без неё работа из Э2 не выполняется или вариант неприемлем (своё размещение, доработка кода); функция есть у всех аналогов | → **MUST**: отсев до сравнения |
| **Линейная** | чем лучше, тем лучше закрыта потребность (объём доработки, зрелость, функции для людей) | → **критерий сравнения** |
| **Привлекательная** | улучшает работу, но её отсутствие не мешает | → дополнительный критерий, решает при равенстве |
| **Безразличная** | не закрывает нашу потребность | → **не берём**, указываем причину |
| **Обратная** | мешает нашей работе или противоречит решению (например, агент сам двигает задачу по доске вопреки R-AP-16) | → **не берём**; если она у выбранного кандидата — отключить или убрать |

Классы со временем смещаются: привлекательная функция становится базовой, когда она есть у всех аналогов. Поэтому факты о функциях аналогов проверяются **на дату** исследования.

## Уровни доказательства {#evidence}

| Уровень | Что это | Пример |
|---|---|---|
| **А** | проверено нами | прочитан код, прототип, замер |
| **Б** | первичный источник | документация, код, changelog продукта, стандарт, исходная статья |
| **В** | опыт практиков | статьи, обзоры, issue, отчёты пользователей |
| **Г** | заявление без деталей | маркетинг, «скоро будет», слухи |

**Наличие** функции подтверждается уровнем Б и выше. **Ценность** — нашей историей или требованием плюс одним из подтверждений:

- функция есть у ≥ 2 аналогов (на рынке так решают);
- опыт практиков (уровень В);
- наш прототип (уровень А).

## Подача результата {#layout}

Документ строится «ответ первым» (пирамида Минто). Порядок разделов — порядок получения данных.

**Первая страница — презентация для заказчика на 3 минуты** (без таблиц баллов):

1. **Вопрос и ответ** — блок `rnd-hero`: вопрос, ответ одной фразой, статус Tech Radar, ссылка на решение в design.
2. **Микропрезентация** — 4–6 слайдов ([ниже](#deck)): покрытие потребностей, объём доработки, встраивание, позиции ролей, что меняется.
3. **Почему** — 3 карточки (`rnd-grid`): каждая — вывод, ключевой факт, ссылка на этап.
4. **Что берём / адаптируем / не берём** из опорного решения и аналогов (`take`, `adapt`, `drop`).
5. **Отсеяны** — кто и одна причина у каждого (`no`); **риски и пересмотр** (`risk`).
6. **Путь исследования** — цепочка этапов (`rnd-chain`).

### Микропрезентация {#deck}

Обязательный слайд — **«Объём доработки»**: часы или дни из подзадач задач, которые делают выбранный вариант (`./tools/doc lint`, Z-ICP-110).

Слайды 16:9 показывают **соотношения**: сколько потребностей закрывает каждый вариант, у кого больше доработки, на чьей стороне роли, сколько изменений в документах. Читатель видит пропорции раньше, чем читает текст.

**Правила слайда:**

- **Один слайд — один вопрос заказчика** и строка-вывод (`>`), которая на него отвечает.
- **Пропорции берутся из таблиц этапов**, а не придумываются:
  - покрытие — из сравнения Э9 (по числу потребностей);
  - объём доработки — из порядковой шкалы Э9 («малый / средний / крупный / всё писать» = 1–4 из 4) или из оценок задач в днях, если они есть;
  - позиции ролей — из Э8;
  - последствия — из Э10.
- **Без сумм баллов.** Число допустимо, только если это количество (потребностей, интерфейсов, изменений) или оценка задачи.
- **Цвета** — те же, что в [разметке](#colors): зелёный — закрывает или внесено, жёлтый — с доработкой или предложено, красный — не закрывает, синий — альтернатива или адаптация, серый — не требуется.

**Набор слайдов** (не больше 6):

| Слайд | Вопрос заказчика | Элемент |
|---|---|---|
| Покрытие потребностей | кто закрывает то, что нам нужно? | `stack` по каждому кандидату |
| Объём доработки | сколько придётся сделать самим? | `bar` по каждому кандидату |
| Встраивание | что меняется в схеме? | `bar` или пункты: затронутые и изменённые I-коды, готовность И0–И4 |
| Позиции ролей | кто за, кто против и почему? | `side` + `pos` по каждой роли |
| Что меняется | что будет с документами и задачами? | `stack` по статусам последствий |

**Разметка** — блок кода `deck`; сборка превращает его в слайды:

````
```deck
# Покрытие потребностей П1–П8
> только It's a Plan закрывает агентную часть без написания с нуля
stack It's a Plan: 5 ok, 3 part, 0 no
stack Plane CE: 3 ok, 3 part, 2 no
# Позиции ролей
side It's a Plan | Plane CE
pos Разработчик: -2 | агентная часть уже есть
pos DevOps: 1 | у Plane больше сообщество
```
````

| Строка | Что рисует |
|---|---|
| `# Заголовок` | новый слайд |
| `> вывод` | строка-вывод слайда |
| `stack Метка: N ok, N part, N no` | сегментная полоса (также `info`, `mute`) |
| `bar Метка: значение/максимум подпись [цвет]` | полоса доли |
| `side Левый \| Правый` | подписи концов шкалы позиций |
| `pos Роль: −2…2 \| довод` | точка роли на шкале: −2 — полностью за левый вариант, 2 — за правый |
| `- текст` | пункт |

**Дальше — раскрытие по этапам Э1–Э10.** Каждый этап заканчивается строкой «**Вывод этапа**» и воротами `<span class="gate">Gn</span> ✅ …` с тем, чем они пройдены (⚠️ — по [статусу ворот](#gate-status)).

**Приложение** (сворачиваемое, `<details>`): [карточки кандидатов](#candidate-card) — только то, чего нет в Э4; числовая сверка (необязательна; если есть — подписана «сверка, не основание»), сырые данные.

**Источники** — одна строка на источник: ссылка, дата, уровень доказательства, 3–5 слов «что взято». Описание кандидата из Э4 не повторяется. Дата — у строки или одна на раздел («обращение 2026-10-13»), если все источники открыты в один день:

```
- [W3] [каталог Ruward: iClinicapp](https://…) — 2026-10-13, Г, сроки запуска коробки
```

Правила текста:

- вывод — связной фразой с причиной («берём X, потому что Y»), а не пунктом из двух слов;
- у каждого факта о продукте — ссылка;
- «нет функции» пишется только после проверки изданий: функция может быть в платном издании.

## Карточка кандидата (приложение) {#candidate-card}

Только то, чего **нет в Э4**: функции по потребностям не повторяются (они в таблицах Э3–Э4). Непроверенное — клеткой 📌 «не проверено». Для малого R&D карточку можно не вести, если всё есть в Э4 и Э7.

| Группа | Данные | Источник |
|---|---|---|
| Расширяемость | открыт ли код; лицензия и её обязательства; точки расширения (API, плагины, MCP) | репозиторий, LICENSE |
| Издания и цена | что в открытом издании, что только в платном | страница изданий и цен |
| Размещение | у себя или только облако; зависимости; ресурсы | документация по установке |
| Здоровье проекта | звёзды, контрибьюторы за 12 месяцев, релизы, реакция на issue, OpenSSF Scorecard | GitHub API, scorecard.dev |
| Безопасность | известные уязвимости, модель прав | GitHub Advisories, документация |
| Интеграция | совместимость с ICPlan, LiteLLM, Postgres, Kubernetes, Python и Go | документация, прототип |

## Технологии ИИ-агентов: проверка прототипом {#ag}

Ценность функций агентной технологии подтверждается прототипом (уровень А) по измерениям ниже. Без прототипа статус — не выше **Trial**.

| Код | Измерение | Вопрос |
|---|---|---|
| AG1 | Выполнение задачи | доводит ли агент задачу до результата на нашем наборе задач |
| AG2 | Выбор тулов и аргументы | правильно ли выбирает тул и формирует аргументы |
| AG3 | Восстановление после ошибок | продолжает ли после сбоя тула или модели |
| AG4 | Связность плана | не теряет ли цель на длинной задаче |
| AG5 | Эффективность | токены, задержка, стоимость на задачу |
| AG6 | Наблюдаемость и evals | даёт ли трейсы, совместимые с инструментами оценки |

Прототип: 5–10 эталонных задач на mock-LLM и реальной модели, замер AG1–AG5.

## Антипаттерны

| Антипаттерн | Почему плохо | Как правильно |
|---|---|---|
| Критерии и веса заданы до разбора функций | не видно, откуда критерий | критерий — результат Э6 с цепочкой |
| Итог — сумма баллов | вывод нельзя проверить | вывод аргументом; баллы — сверка в приложении |
| Сравниваются продукты целиком | теряются функции отсеянных кандидатов | решение по каждой функции, в том числе у отсеянных |
| Обязательное свойство как взвешенный критерий | неприемлемый вариант побеждает по сумме | базовая функция → MUST, отсев до сравнения |
| Ценность «очевидна» | функции берутся по моде | механизм ценности и доказательство |
| Первая страница — таблица | читатель не видит, почему так | вопрос → ответ → 3 основания → перенос → риски |
| Решение оценено отдельно от схемы | лучший «сам по себе» вариант ломает стыки и владельцев данных | встраивание по I- и S-кодам, изменения у соседей (Э7) |
| Выбор с одной позиции | не услышаны эксплуатация, безопасность, пользователи | спор ролей с оппонентом и «адвокатом дьявола» (Э8) |
| R&D без последствий | выбор не доходит до спек, задач и техспек | таблица последствий со статусами (Э10) |
| Факты по памяти, «нет функции» без проверки изданий | устаревшие или неверные данные | ссылка и дата; проверка изданий |
| Общая таблица критериев для всех R&D | критерии не по вопросу | критерии каждого R&D — из его потребностей |

## R&D пользовательских потоков {#us-rnd}

Тот же принцип «функции аналогов → ценность → перенос», только единица анализа — поток пользователя, а не функция продукта.

1. Взять идею компонента и сформулировать работы (JTBD) по акторам — Э2.
2. Найти 3–5 аналогов и выписать их потоки: точки входа, состояния, действия людей и агентов — Э3–Э4 (источники — [продуктовые](#search)).
3. Ценность потока — Э5, как у функции.
4. **В Э6** — матрица «поток × аналог × у нас», затем отыгрыш персон и фильтр необходимости; итог — истории или осознанное «не делаем» с причиной.

**Матрица «поток × аналог × у нас»** (Э6):

| Поток (актор, работа П…) | Аналог 1 … Аналог N | У нас | Решение |
|---|---|---|---|
| строка — поток: точка входа → действие → результат | клетка: **есть** (уровень, ссылка) · **частично** — чего нет · **нет** · 📌 не проверено | **есть** · **частично** · **нет** · **история** US-… (если уже описана) | **брать** / **адаптировать** (что меняем) / **не делаем** (причина) → история |

Поток с «есть» у ≥ 2 аналогов и без «у нас» — кандидат в базовые (Kano); «не делаем» без причины недопустимо.

**Отыгрыш и фильтр** (Э6, после матрицы, до критериев): отыграть персон по [правилу ниже](#personas) на потоках с решением «брать» и «адаптировать» — конфликты дают новые потоки или вопросы 📌; затем [фильтр необходимости](us-methodology.md) (раздел 7а): у потока есть (1) работа из Э2, (2) путь — актор, канал, данные, (3) он нужен для функции продукта. Не прошёл (1) или (2) — «не делаем»; сомнение в (3) — 📌 владельцу.

**Составной вопрос** «какие потоки + как делать» (новый продукт: состав и путь реализации) — **один R&D, два уровня**:

- Э2–Э6 — по потокам: матрица даёт состав (потоки «брать» — MUST, остальное — критерии);
- кандидаты Э4 — **пути реализации** (коробка, своя разработка, агрегатор, ничего не делать), у каждого — покрытие потоков той же матрицы;
- Э7–Э9 — выбор пути по потокам-MUST и встраиванию;
- если пути не зависят от состава потоков — два R&D: сначала потоки, затем путь.

## Персоны и отыгрыш конфликтов {#personas}

1. **Сущности.** Участники и объекты процесса; у каждой — что **может** и что **хочет**.
2. **Персоны.** Промпт персоны ([personas.md](../stories/personas.md)); новые — добавить.
3. **Отыгрыш.** Сыграть цель каждой персоны, искать конфликты с другими и с системой.
4. **Таблица конфликтов:** кто → что хочет → с кем конфликт → что должно произойти.
5. **Артефакты** каждого шага процесса.
6. Итог — истории, требования, открытые вопросы.
