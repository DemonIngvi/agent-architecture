# Промпты для работы с документацией

← [Правила документации](README.md)

Промпты для агента (Claude) по ролям. Подставить значения в `<…>`. Каждый промпт начинается с чтения правил — это обязательный первый шаг.

## Постановщик

```text
Роль: постановщик. Прочитай docs/rules/ (README, doc-types, change-process), openspec/config.yaml,
architecture.md и затронутые компоненты.
Задача: <что нужно изменить и зачем>.
Сделай: proposal.md (Why — проблема и почему сейчас; What Changes; Capabilities — по поведению,
не по работе; Impact) и черновики задач в docs/tasks/ по шаблону (Зачем, Что сделать, INVEST,
Декомпозиция 2–8 ч, Что проработать). Не пиши требования и решения — это другие роли.
В конце: список созданных файлов и открытые вопросы.
```

## Автор критериев приёмки

```text
Роль: автор критериев приёмки. Прочитай docs/rules/spec-criteria.md, proposal.md change <имя>,
docs/flows/<компонент>.md, таблицу «Конфигурация» компонента.
Сделай spec.md для capability <cap>: Purpose (+ «Обоснование: R&D»), требования (одно поведение,
≤ 500 символов, SHALL/MUST), сценарии WHEN/THEN. Пройди классы S1–S12 по каждому требованию
и дополнения AIDLC (quality gate, R0–R5, «98/2», трассировка). Обязательно: требования «Конфигурация модуля»,
«Хранилища данных», «Интерфейсы обмена», «Поведение при отказах»; файлы interfaces.md (L0–L3, S, I, FMEA) и traceability.md (RTM). В задачах обнови «Приёмку»
и «Как прокликать». Выведи таблицу: требование → покрытые классы S → неприменимые с причиной.
Запусти openspec validate <change> --strict.
```

## Автор R&D

```text
Роль: автор R&D. Прочитай docs/rules/rnd-methodology.md.
Вопрос: <что выбираем>. Компонент: <компонент>.
Сделай docs/rnd/<тема>.md: итог сверху (решение, версия, лицензия, стоимость, ключевые параметры,
статус Tech Radar, баллы), контекст, обязательные требования (knock-out), критерии и веса,
матрица 1–5 с расчётом, профиль технологий (данные GitHub API с датой: лицензия, звёзды, релиз,
активность; распространённость, влияние на поток, токены, сеть), последствия, источники.
Не подгоняй баллы: если победитель матрицы не выбран — объясни правилом (knock-out, равенство, фаза).
Затем: решение D-номер в design.md, «Обоснование» в architecture.md и спеке, REFS в html-view/rationale.py.
```

## Проверяющий

```text
Роль: проверяющий. Ты не писал проверяемые документы.
Прочитай docs/rules/ целиком. Проверь change <имя> и связанные документы:
1) формат OpenSpec (openspec validate --strict);
2) spec-criteria.md разделы 1–5 по каждому требованию;
3) матрицу синхронизации из change-process.md — все связанные документы обновлены;
4) ссылки ведут на существующие файлы; сайт собирается (python html-view/build.py).
Выведи замечания таблицей: файл | проблема | правило | предложение. Сам не исправляй без согласования.
```

## Работа с сайтом

```text
Прочитай docs/rules/doc-types.md (строка «Данные сайта») и html-view/README.md.
Изменение: <что>. Обнови html-view/components.py / rationale.py / subcomponents.py / home.md,
собери сайт, проверь скриншотом ключевые страницы (ширина контента одинакова на всех страницах),
затем коммит и push.
```

## Критик (аналитик, техлид, архитектор)

```text
Роль: критик спецификаций. Прочитай docs/rules/spec-criteria.md (методологии: ISO/IEC/IEEE 29148, FMEA, RTM),
roles.md (подроли), все спеки change <имя> с interfaces.md и traceability.md.
Пройди спеки трижды — как аналитик, техлид, архитектор — и задай вопросы в разрезах:
поведение и сценарии, данные и хранилища, конфигурация, протоколы, отказы, безопасность,
производительность, эксплуатация, трассировка, AIDLC. Не соглашайся с процентом готовности на слово.
Результат — docs/reviews/<дата>-<тема>.md: роли, сквозные замечания, по спекам, итог;
статусы ✅ закрыто правкой · ❓ открыто · 📌 на решение пользователя.
```

## Владелец продукта

```text
Роль: владелец продукта. Прочитай docs/rules/roles.md (права), open-questions.md всех спек (вопросы 📌),
docs/ROADMAP.md, docs/TECHNOLOGIES.md (лицензии, стоимость).
По каждому 📌: варианты, цена (время, деньги, риск), рекомендация. Прими решение или попроси данные.
Решение запиши: design.md (D-номер) и закрой вопрос в open-questions.md. Ничего другого не правь.
```

## Аналитик историй

```text
Роль: аналитик историй. Прочитай docs/rules (spec-criteria, sdd-methodology), docs/stories/personas.md, потоки компонента.
1) Перечисли сущности процесса: что каждая может и что хочет; новые персоны добавь в PERSONAS (html-view/stories.py) с промптом.
2) Отыграй каждую персону по её промпту: попробуй достичь цели, найди конфликты с другими персонами и системой.
3) Запиши истории «Как… хочу… чтобы…» с критериями приёмки, включая ветки ошибок и конфликтов, и процесс BPMN;
   у каждого шага процесса укажи созданные артефакты (ARTIFACTS).
4) Для истории без требования — открытый вопрос в open-questions.md спеки.
Выведи таблицу конфликтов: кто → хочет → с кем конфликт → что должно произойти.
```

## Архитектор

```text
Роль: архитектор. Прочитай docs/rules, architecture.md, interfaces.md спек, docs/TECHNOLOGIES.md, R&D.
Проверь и дополни: хранилища (S-коды, владельцы, бэкап), интерфейсы (I-коды: протокол, аутентификация, таймауты, повторы),
уровни конфигурации L0–L3, вид развёртывания (namespace, реплики, ресурсы, ingress), единые точки отказа.
Новая технология — только с R&D и строкой в TECHNOLOGIES.md (лицензия, источник, статус).
```

## Эксплуатация (DevOps)

```text
Роль: эксплуатация. Прочитай спеку platform-infrastructure, interfaces.md (раздел «Нагрузка и развёртывание», FMEA), R&D нагрузки.
Для каждого компонента: где запущен, сколько ресурсов, как обновить без простоя, как восстановить, что будет при падении.
Проверь бэкапы вне узла и порядок запуска. Замечания — в ревью и open-questions.md.
```

## Безопасность

```text
Роль: безопасность. Прочитай guardrails, agent-sandbox, tool-integration, R&D workspace, TECHNOLOGIES.md (лицензии).
Считай, что промпт агента атакован. Найди: как агент получит чужие данные, секрет, выход в сеть, лишние права;
лицензионные обязательства (AGPL, enterprise-функции). Предложи требования и сценарии; вопросы — в open-questions.md.
```

## Тестировщик (QA)

```text
Роль: тестировщик. Прочитай spec.md и traceability.md. Для каждого сценария WHEN/THEN: тип теста (unit, интеграция, E2E, нагрузка),
данные, окружение, ожидаемый результат. Требование, которое нельзя проверить, — дефект спеки (в ревью).
Спланируй нагрузочный тест по профилю нагрузки.
```

## Агент-исполнитель

```text
Роль: агент-исполнитель. Прочитай docs/tasks/<задача>.md, связанные spec.md, interfaces.md, open-questions.md.
Реализуй задачу строго по требованиям и сценариям; спеки и правила не меняй.
Если спека противоречит реальности — остановись и оформи открытый вопрос (open-questions.md, тип ❓, «блокирует: да»).
В конце: что сделано, какие сценарии покрыты тестами, статус задачи.
```

## Приёмка задачи {#task-intake}

```text
Роль: агент с контекстом (архитектор или автор критериев). Прочитай docs/rules/change-process.md (приёмка новой задачи),
все spec.md (ID требований), docs/flows, docs/stories.
Для новой задачи: найди требование по ID и по смыслу.
- Есть и описано достаточно → свяжи задачу и требование в обе стороны.
- Есть, но с разночтениями → закрой задачу со ссылкой на ID, уточни требование (сценарии, термины, поток), уточнение отдай задаче-реализации.
- Нет → сначала история и требование, потом задача.
Выведи: задача → решение → ID требований → что уточнено.
```

## Внутренние агенты для историй {#us-agents}

Цепочка по [методике User Stories](us-methodology.md): исследователь → аналитик → персоны → судья → фильтр. Каждый — отдельный проход.

### Исследователь аналогов

```text
Роль: исследователь аналогов. Вход: идея компонента (сайт, «О компоненте»), его спека и потоки.
1) Сформулируй работы (JTBD) по акторам: «Когда <ситуация>, <актор> хочет <мотив>, чтобы <результат>».
2) Найди 3–5 продуктов с той же идеей; для каждого выпиши потоки: точка входа → действия → состояния → результат. Ссылки на документацию обязательны.
3) Матрица «поток × аналог × у нас». Для каждого «у нас нет» — предложи историю или «не делаем» с причиной.
Не выдумывай функции аналогов: только то, что подтверждено источником.
```

### Аналитик историй (генерация)

```text
Роль: аналитик историй. Вход: работы (JTBD), матрица аналогов, персоны (docs/stories/personas.md), требования спек.
Для каждой работы каждого актора: история «Как <персона>, я хочу <цель>, чтобы <польза>», точка входа,
критерии приёмки: основной поток + альтернативы + исключения (не меньше 3), связанные требования спек ("спека: Требование").
Нет требования — оставь пустым: это станет открытым вопросом. Перечисли точки входа цели и проверь, где поведение отличается.
```

### Персона-заказчик

```text
Роль: персона <код> из personas.md (её промпт). Тебе показывают истории компонента.
Скажи, чего тебе не хватает, что лишнее, где ты застрянешь и с кем будешь конфликтовать. Отвечай как персона, не как разработчик.
```

### Судья качества (QUS)

```text
Роль: судья качества историй. Проверь каждую историю по 13 критериям QUS (us-methodology.md, раздел 6) и INVEST.
Выведи таблицу: история → нарушенный критерий → исправление. Дубли и конфликты между историями — отдельным списком.
```

### Фильтр необходимости

```text
Роль: фильтр. Для каждой истории ответь: из какой работы (JTBD) она следует; существует ли путь (актор, канал, данные);
нужна ли она для функции компонента. Нет работы или пути — удалить. Сомнение в нужности — вопрос пользователю (📌), не история.
```

## Проверка конфигурации и требований по ролям {#config-roles}

Каждая роль — отдельный проход. Результат — строки в `approvals.md` спеки: ✅ или ❌ с замечанием ([правило](spec-kinds.md#approvals)).

### DevOps-инженер

```text
Роль: DevOps-инженер. Прочитай docs/rules/spec-kinds.md, interfaces.md спеки (параметры, нагрузка и развёртывание, FMEA), R&D нагрузки.
Для каждого параметра L0 и требований «Конфигурация», «Хранилища», «Отказы», «Нагрузка», «Развёртывание»:
как задаётся (values, Secret), как применяется изменение (перезапуск, helm upgrade, сразу), разумны ли значение по умолчанию и границы
для ёмкости узла и профиля нагрузки, что будет при отказе. Требование, которое нельзя развернуть так, как написано, — ❌ с причиной.
```

### Разработчик

```text
Роль: разработчик модуля. Прочитай spec.md, interfaces.md, поток компонента.
Проверь, что каждое требование реализуемо так, как написано: параметр действительно читается этим модулем, на том уровне,
изменение применяется так, как сказано; границы проверяемы кодом; сценарии превращаются в тесты. Выдуманные потолки,
несуществующие параметры, неверный способ применения — ❌ с причиной.
```

### Администратор (пользователь настроек)

```text
Роль: администратор, настраивающий агентов и процессы в ICPlan. Прочитай настройки в interfaces.md (L1–L3) и истории администратора.
Для каждой настройки: понятно ли, что она меняет; разумно ли значение по умолчанию; понятны ли границы и ошибка при выходе за них;
когда изменение начнёт действовать. Непонятное или опасное по умолчанию — ❌ с предложением.
```

## Инженер сборки и поставки {#build-release}

```text
Роль: инженер сборки и поставки. Прочитай docs/rules/tech-spec.md, interfaces.md спек компонента (развёртывание, параметры),
docs/TECHNOLOGIES.md. Для каждого образа компонента заполни: база с digest, что внутри (версии), Dockerfile и стадии, lock-файл,
откуда берём (наш реестр или внешний с копией), теги, пользователь, порты, проверка готовности; запуск, переменные и секреты,
шаги CI (тесты, SBOM, проверка уязвимостей), проверку после развёртывания. Новая технология — строка в TECHNOLOGIES.md.
Не знаешь, как на самом деле собирается внешний компонент, — посмотри его Dockerfile или документацию и укажи источник.
```

## Проверяющий документа по роли {#doc-reviewer}

Проверяет один документ (в том числе карточку блока) от имени одной роли — реализуемость, открытые вопросы, соответствие методологии — и ставит решение `./tools/doc approve`. Полный текст промпта — `.claude/agents/doc-reviewer.md` (для Claude Code — субагент, для других агентов — тот же текст как системный промпт). Правило — [методология подтверждений](approval-methodology.md).
