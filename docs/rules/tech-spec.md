# Методология Deploy

← [Правила документации](README.md) · [типы документов и вкладки](doc-types.md) · [роли](roles.md) · [процесс изменения](change-process.md)

Как вести вкладку «Deploy» компонента (`docs/techspec/<компонент>.md`): образы, запуск, переменные и секреты, сборка и поставка, проверка после развёртывания.

## Назначение и читатель

Отвечает на вопрос **«как это собрать, откуда взять и как безопасно запустить»**. Читатель — инженер сборки и поставки (Build & Release), DevOps-инженер и безопасность. Порядок работы компонента («Как работает») сюда не входит: он в `docs/how/<компонент>.md`, на сайте — на вкладке «Архитектура» ([методология архитектуры](architecture-methodology.md)).

Правило появилось потому, что спеки описывали поведение и параметры, но не технику поставки: как собирается образ, на какой базе, откуда кластер его скачивает, под каким пользователем он работает ([отклонение О-17](deviations.md)). Пишет роль «Инженер сборки и поставки», промпт — [prompts.md](prompts.md#build-release).

## Основа

| Практика | Что берём |
|---|---|
| [12-Factor App](https://12factor.net) | конфигурация — в переменных среды; сборка, выпуск и запуск разделены |
| [Kubernetes Pod Security Standards](https://kubernetes.io/docs/concepts/security/pod-security-standards/) (restricted) | non-root, без лишних capabilities, `no-new-privileges`, seccomp RuntimeDefault, read-only rootfs |
| [SLSA](https://slsa.dev), SBOM | воспроизводимая сборка, закреплённые базы, SBOM и проверка уязвимостей до публикации |

## Из чего состоит

Заголовок страницы — `# Deploy: <компонент>`; шапка — ссылки на компонент и эту методологию.

| Раздел | Что указать |
|---|---|
| Образы | имя; база (закреплённая по digest); что внутри (версии ключевых библиотек); как собирается (Dockerfile, стадии, lock-файл); откуда берём (наш реестр `ghcr.io/demoningvi/*` или внешний с копией у себя); политика тегов (semver + sha, без `latest`); пользователь (non-root); порты; проверка готовности |
| Запуск | namespace, реплики, команда старта (миграции до старта), ограничения безопасности (read-only rootfs, capabilities, `no-new-privileges`, seccomp), сеть, тома |
| Переменные и секреты | каждая переменная: зачем, откуда (values, Secret, Runner на запуск); секреты — только из Secret; значение — ссылкой на `interfaces.md` спеки |
| Сборка и поставка | шаги CI по одному разу: сборка, тесты, SBOM, проверка уязвимостей, публикация, pull-секрет |
| Проверка после развёртывания | короткий список действий, подтверждающих, что компонент работает |
| Обновление и откат (если у компонента есть данные или миграции) | порядок обновления, точка восстановления, откат образа и откат после миграции, ключи, без которых данные не прочитать (Z-ICP-18, Z-ICP-38) |
| Конфигурация (генерируется) | все настраиваемые параметры компонента — из таблиц «Параметры модуля» `interfaces.md` его спек: имя **как в конфиге** (англ.: `agent.kind`, `AGENT_RUN_LEASE_SECONDS`), что задаёт, уровень (L0–L3) и где задаётся — по хранилищу параметра (S9 — values и переменные деплоя; S2 — Platform module; S1 — настройки в ICPlan; S8 — git), по умолчанию, мин–макс. Русское название вместо имени — не параметр: сначала имя в `interfaces.md`. Руками раздел не пишется |
| Пример конфигурации (если у компонента есть файлы настроек) | как настройки лежат в развёртывании: values, профили, `model_list`, правила Rego; значения — из `interfaces.md` спеки, новых здесь нет |

**Компонент — чужой форк** (ICPlan): «Образы», «Запуск», «Переменные и секреты», «Сборка и поставка» — **по коду форка** (Dockerfile, чарт и `values.yaml`, `.env.example`, `.github/workflows`), с пометкой даты сверки; расхождение «как в форке» и «как нужно» — обе колонки и задача на доработку (Z-ICP-37, Z-ICP-39, Z-ICP-43). Dockerfile и база образа — из upstream. «Пример конфигурации» форка **переопределяет умолчания чарта**, которые не подходят платформе: образ (`image.repository` форка, `imagePullSecrets`), встроенные БД и S3 чарта выключены в пользу общих (CloudNativePG, RustFS), `secrets.existingSecret` вместо секретов в values, тома для записи при read-only rootfs (Z-ICP-98, Z-ICP-102). Мы закрепляем базу по digest в своём CI при сборке форка; если upstream пишет базу тегом, в таблице «Образы» указываем тег upstream и то, где закрепляется digest. Тег — версия форка в semver + sha.

**Встроенный компонент** ([связность](architecture-methodology.md#connectivity), `components.HOST`): у хоста — строка «Встроенные компоненты» со ссылками на их Deploy; у встроенного — «в составе образа <хост>», без второго описания образа.

Каждая технология из Deploy — строка в [TECHNOLOGIES.md](../TECHNOLOGIES.md) (лицензия, источник). Значения параметров — в `interfaces.md` спек, здесь — ссылка.

## Как вести

| Триггер | Что сделать |
|---|---|
| Новый компонент или сервис | создать страницу Deploy до первой задачи реализации |
| Новая технология, база образа, реестр | обновить «Образы» и TECHNOLOGIES.md |
| Изменение развёртывания: реплики, ресурсы, порты, переменные, секреты | обновить «Запуск» и «Переменные и секреты» |
| Приёмка задачи, затрагивающей сборку или развёртывание (Definition of Ready) | проверить, что Deploy описывает нужное; иначе дополнить до начала работ |
| Перед выпуском версии (Definition of Done выпуска) | сверить образы, теги и проверки готовности с фактом; закрыть расхождения |
| Обновление версии зависимости (Tech Radar) | обновить версию и digest базы, перепроверить уязвимости |

## Чек-лист качества

- [ ] Заголовок «Deploy: <компонент>», шапка ведёт на компонент и методологию.
- [ ] База образа закреплена по digest, или для форка указано, где закрепляется.
- [ ] Тег — semver + sha, `latest` нет.
- [ ] В «Запуске» есть ограничения безопасности.
- [ ] Значения параметров — ссылками на `interfaces.md`, а не числами; раздел «Конфигурация» не правится руками.
- [ ] Каждый шаг сборки и поставки — один раз.

## Проверки в сборке

- У каждого компонента есть `docs/techspec/<компонент>.md`; заголовок — «Deploy: …».
- Есть разделы «Образы», «Запуск», «Переменные и секреты», «Сборка и поставка», «Проверка после развёртывания».
- `flows_check`: в Deploy нет «Как работает».
- Раздел «Конфигурация» собирается из `interfaces.md`; у параметра — имя из латиницы, цифр, `.`, `_` (`config_check`).
