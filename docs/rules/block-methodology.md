# Методология блоков

← [Правила документации](README.md) · [типы документов и вкладки](doc-types.md) · [методология архитектуры](architecture-methodology.md#entity) · [подтверждения](approval-methodology.md)

Как вести блоки — части устройства компонента (C3): карточку блока в `html-view/subcomponents.py` и его страницу на сайте.

## Назначение и читатель

Карточка блока отвечает на вопросы **исполнителя, который берётся сделать блок**: что сделать, как это выглядит или вызывается, с чем связано, что хранит, как настраивается, по каким требованиям и задаче, что при сбое. Если на вопрос ответа нет — блок не готов к реализации, и это видно на его странице.

## Основа

| Практика | Что берём |
|---|---|
| [C4 model](https://c4model.com), уровень C3 | блок — часть одного контейнера, без своего контракта наружу |
| Definition of Ready (Scrum) | блок готов к работе, когда карточка полная, открытых вопросов нет, роли подтвердили |
| Инвентаризация «как есть» | то, что уже существует в форке ICPlan, описывается по коду, а не по памяти и не исследованием |

## Блок, встроенный блок, компонент

| | Блок | Встроенный блок | Компонент |
|---|---|---|---|
| Свой контракт наружу (I-код) | нет | вызывают по сети (`iface`) | да |
| Документы | карточка блока | карточка + I-коды + Deploy хоста | полный набор вкладок ([методология архитектуры](architecture-methodology.md#entity)) |

Если у блока появляется свой контракт с соседями и его можно поручить отдельно — это уже компонент: сначала решение, потом перенос.

## Из чего состоит карточка

| Поле | Вопрос исполнителя | Как заполнять | Проверка |
|---|---|---|---|
| `does` | что блок делает | 2–4 пункта, глаголом | есть |
| `tech` | на чём сделан | технология и версия — из TECHNOLOGIES | есть |
| `stories` | для кого и в каком процессе | US-коды; процесс пользователя берётся из историй | история существует |
| `io` | откуда приходит работа и кому отдаёт | `(«←» / «→», с кем, что: модель или I-код)` | I-код есть в `INTEG` |
| `data` | что читает и пишет | `(таблица или S-код, «чтение» / «запись»)` | таблица есть в модели данных |
| `params` | как называются настройки | имя **как в конфиге** из `interfaces.md` спеки; у блока без настроек — строка `нет: <почему>` (поле заполнено) | имя есть в «Параметрах модуля» |
| `reqs` | какие требования выполняю | R-коды | требование существует |
| `tasks` | по какой задаче делаю | номера задач | задача существует |
| `failures` | что при сбое | поведение при отказе блока и зависимостей; ссылка на FMEA | есть |
| по виду (ниже) | как выглядит или вызывается | см. «Вид блока» | есть |
| `why`, `rnd` | почему так | 1–2 предложения + R&D | есть |

### Вид блока

| Вид (`kind`) | Поле | Что в нём |
|---|---|---|
| `ui` — интерфейс | `screens` | экран: путь в интерфейсе, что на нём (поля, действия), `есть` / `доработка` / `новое`, файл в коде форка, история |
| `service` — сервис или модуль | `ops` | операция: эндпоинт или функция, кто вызывает, I-код или «внутри» |
| `store` — хранилище, конфиг | `schema` | ссылка на «Данные» (таблицы, база и схема) или на конфиг |

## Как вести

| Когда | Шаги |
|---|---|
| Новый блок | 1) строка в `BLOCKS` (схема C3); 2) карточка в `SUB` со всеми полями; 3) нет требования — сначала требование ([приёмка задачи](change-process.md#task-intake)) |
| Экран с действием | у каждого действия экрана — операция API (эндпоинт в «Что на нём»); нет эндпоинта — сначала строка в каталоге API (Z-ICP-1) |
| «Данные» блока | все таблицы, которые читают и пишут его экраны и операции, — **именами таблиц**, не S-кодами; чужая таблица — с пометкой владельца (Z-ICP-20, Z-ICP-23, Z-ICP-28) |
| Требования блока | все требования, на которые опираются его операции, экраны и сбои (Z-ICP-25) |
| Экраны из задач | экран, который делает задача блока, — строкой в `screens` (Z-ICP-33) |
| Блок уже есть в форке | поля `screens` / `ops` — **инвентаризация по коду форка** (`D:\АИ агент\itsaplan`): путь, файл, что есть; доработку отмечать `доработка` с требованием |
| Есть выбор, как сделать (экран, протокол, хранение) | **R&D** по [методологии](rnd-methodology.md) → решение D → карточка; до решения — открытый вопрос в `open-questions.md` спеки |
| Неизвестно, как устроено | не придумывать: код форка, OpenAPI, design; нет — открытый вопрос |
| Изменилась карточка | подтверждения блока сбрасываются ([подтверждения](approval-methodology.md)) |

## Готовность блока к реализации {#ready}

Блок готов, когда: карточка заполнена полностью (`./tools/doc blocks`), по требованиям блока нет открытых вопросов, роли блока подтвердили карточку. На странице блока — заполненность карточки и значки подтверждений.

## Чек-лист

- [ ] Тип и вид блока указаны.
- [ ] Каждое поле карточки отвечает на свой вопрос; ссылки существуют.
- [ ] Экраны или операции — по коду форка или по решению D, не по памяти.
- [ ] Параметры — имена из `interfaces.md`.
- [ ] Открытых вопросов по требованиям блока нет или они названы.

## Проверки в сборке

`block_check` — ссылки карточки существуют (I-коды, таблицы, требования, задачи, истории); `./tools/doc blocks` — заполненность карточек; `./tools/doc lint` — неполная карточка, экраны «новое» / «доработка» без эндпоинта, S-коды в «Данных»; проверяющий агент (`.claude/agents/doc-reviewer.md`) — реализуемость и открытые вопросы.
