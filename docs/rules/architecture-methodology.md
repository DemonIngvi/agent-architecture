# Методология архитектуры

← [Правила документации](README.md) · [типы документов и вкладки](doc-types.md) · [работа с документами](doc-work.md#architecture)

Как вести архитектуру платформы: общую схему (`architecture.md`), страницы компонентов и блоков, раздел взаимодействия компонентов и слой поставки.

## Назначение и читатель

Архитектура отвечает на вопрос **«как устроена платформа и почему так»**. Читатель — тот, кто впервые видит платформу: разработчик, архитектор, владелец продукта. Он должен за 10 минут понять, из каких частей система, как они связаны и где читать подробности. Подробности (значения параметров, поля данных, конфиги, задачи) живут в своих вкладках — архитектура на них ссылается.

## Основа

| Практика | Что берём |
|---|---|
| [C4 model](https://c4model.com) (Simon Brown) | уровни: C1 — система в окружении, C2 — контейнеры (сервисы и хранилища), развёртывание; одна схема — один уровень |
| [arc42](https://arc42.org) | разделы «решения» (что выбрано и почему), «сквозные концепции», «развёртывание»; ссылки на решения вместо пересказа |
| ADR ([методология решений](decision-methodology.md)) | у каждого сквозного решения — D-номер и R&D |
| [FORMAT.md](../../FORMAT.md) | ASCII-схемы: блоки, стрелки с подписью данных и I-кодом |

## Из чего состоит

| Документ | Разделы | Источник |
|---|---|---|
| `architecture.md` (на сайте — обзор на главной) | C1; C2; **взаимодействие компонентов** (сквозной сценарий шаг за шагом с I-кодами); развёртывание; **поставка** (сборка, реестр, зеркало — вне рантайма); сквозные решения (что выбрано и почему, 2–4 предложения + ссылки на D, R&D, страницу компонента); блоки; расширения; плюсы и минусы по модулям | пишется руками |
| Страница компонента (вкладка «Архитектура») | схема блоков, «почему так», конфигурация (значения — из спеки), как работает (`docs/how/<компонент>.md`), контракты данных, хранилища | генерируется из `components.py`, `rationale.py`, `docs/how`, `datamodel.py` |
| Схема C1 компонента (вкладка «Интеграции») | компонент и соседи, стрелка — кто вызывает, подпись — I-коды; внешние системы и общая инфраструктура выделены | генерируется из `datamodel.py` (mermaid) |
| Страница блока | технология, ключевые параметры (значения — из спеки), что делает, почему так | генерируется из `subcomponents.py` |
| Схема capability (`specs/<cap>/architecture.md`) | схема модуля, блоки, расширения, плюсы и минусы | генерируется `archgen.py` |

**Чего в архитектуре нет:** значений параметров и порогов (→ `interfaces.md` спек), конфигов и переменных (→ техспеки), полей данных (→ [Модель данных](../../data-model.md)), списков доработок и статусов (→ задачи), порядка работы одного компонента (→ техспека, «Как работает»).

## Как вести

| Когда | Кто | Шаги |
|---|---|---|
| Новый компонент | Архитектор | 1) R&D и решение D; 2) блок на C2 и строка в таблице блоков; 3) `components.py` (COMPONENTS, BLOCKS, ABOUT), `rationale.py`; 4) интеграции и данные — `datamodel.py`; 5) спека, техспека, задачи |
| Новая связь между компонентами | Архитектор | 1) I-код в `datamodel.py` (стрелка = кто вызывает) и `interfaces.md` всех спек-участников; 2) стрелка на C2 с подписью; 3) шаг во «Взаимодействии компонентов», если связь в сквозном сценарии |
| Новое сквозное решение | Автор R&D → Архитектор | 1) R&D → D-номер; 2) раздел решения: что и почему кратко + ссылки; 3) последствия Э10 по цепочке |
| Изменение развёртывания или поставки | Архитектор, эксплуатация | схема развёртывания / поставки; детали — техспека; значения — `interfaces.md` инфраструктуры |
| Устаревшее после решения | тот, кто принял решение | найти в `architecture.md` и схемах всё, что противоречит новому D, и исправить в том же изменении |

## Чек-лист качества

- [ ] На каждой схеме — один уровень C4; стрелки подписаны данными и I-кодом.
- [ ] У каждого сквозного решения есть D-номер и ссылка на R&D.
- [ ] Нет значений параметров, YAML, JSON, переменных среды, списков задач.
- [ ] Названия компонентов совпадают с меню сайта и `components.py`.
- [ ] Плюсы и минусы — по каждому модулю, а не по схеме целиком.
- [ ] Ответ по архитектуре в обсуждении: схема + таблица блоков + расширения + плюсы и минусы по модулям.

## Проверки в сборке

- `architecture_check`: в `architecture.md` нет блоков `yaml` / `json` и таблиц значений («Порог», «По умолчанию», «Значение», «Переменная»).
- `IG.check`: интеграции на страницах компонентов = `interfaces.md` спек; модели и таблицы сверены.
- Значения параметров на страницах блоков и компонентов подставляются из спек (`spec_value`).

## Типичные ошибки

| Ошибка | Пример | Отклонение |
|---|---|---|
| Копия значений и конфигов | `max_output_tokens` 4 000 в архитектуре и 8192 в спеке | [О-49](deviations.md), [О-50](deviations.md) |
| Решение изменилось, схема — нет | окружение Sandbox с прямым доступом к MCP после D19 | [О-49](deviations.md) |
| Отменённый вариант на схеме | «Integration API» при модели pull (D8) | [О-50](deviations.md) |
| Порядок работы компонента в архитектуре | таблицы шагов вместо ссылки на техспеку | [О-52](deviations.md) |
