← [Правила документации](README.md)

## Расхождения: проверка страниц по их правилам {#audit}

Проверка 11.10.2026: каждая страница сверена со своей строкой таблицы выше (обязательные разделы, правила, что синхронизировать) и с методологией. **Ничего не исправлено** — это список на решение. «Править» — где устранять причину: **методология**, если страница ошибается потому, что правило молчит или само задаёт дубль; **страница**, если правило ясное, а страница от него отстала.

| Тип | Что расходится | Править | Как |
|---|---|---|---|
| Главная | карта на главной написана руками: у Control Plane UI «сделано», у ICPlan в `components.py` «частично»; нет «Инфраструктуры»; Guardrails «данные в БД» (по D18 — Platform module) | **методология**, затем страница | правило не говорит, откуда карта: генерировать карту из `components.py` (статусы, описания) или задать синхронизацию с проверкой |
| Главная | правило требует на одной странице и карту, и схему C2 — два изображения одной структуры | **методология** | оставить одно: карту как C2 или C2 без карты |
| Корень (README) | таблица компонентов с интеграциями руками: у Memory указан Platform module, которого нет в интеграциях; нет «Инфраструктуры»; «Memory: M1–M6» (Memory API — M3, позже M4); «как читать документацию» ведёт на правила | **методология**, затем страница | правило не описывает таблицу: убрать её из README (ссылка на сайт) или генерировать из `components.py` и `datamodel.py` |
| Архитектура | шаг ⑫ сквозного сценария «агент сменил статус (`update_issue`)» противоречит D17 (переход делает ICPlan) | **страница** | исправить шаг и схему над таблицей |
| Архитектура | значения в тексте при правиле «без значений»: «до 50 пользователей, 400 запусков, 4 активных», `events.level: всё` | **страница** + проверка | заменить ссылками; `architecture_check` ловит только таблицы и YAML — расширить на числа с единицами |
| Архитектура | нет раздела «Поставка», который требует методология; есть «Доработки», которого нет в обязательных; строка таблицы не называет «взаимодействие компонентов», методология — называет | **методология** | согласовать список разделов в строке и методологии; «Поставка» — после R&D поставки образов |
| Формат схем | `FORMAT.md` разрешает только ASCII, а для C1 нужна наглядная схема (на вкладке «Интеграции» уже mermaid) | **методология** | правило: ASCII — в ответах и спеках, mermaid — генерируемые схемы C1 и ER на сайте |
| Типы данных | заголовок «Типы данных и потоки», ссылки «Все потоки», «потоки памяти» | **страница** | переименовать и поправить ссылки |
| Граф связности | в `doc-graph.md` строки «spec.md → Потоки», «interfaces.md → Потоки»; в `docgraph.py` — «Как работает (техспека)» (сейчас — `docs/how`, вкладка «Архитектура») | **страница** (данные графа) | обновить узлы и связи под вкладки: Архитектура (Как работает), Интеграции, Данные, Deploy |
| План документации | иерархия сайта: «Архитектура (… интеграции, контракты данных, хранилища)», вкладки «API», «Техспека» | **страница** | обновить под вкладки Интеграции, Данные, Deploy |
| Роли | строка «Техспека: «Как работает» (`docs/techspec`)» | **страница** | «Как работает (`docs/how`)» |
| Deploy | страницы называются «Техспека: …», шапка «← Все техспеки (README)» — сводной страницы нет | **страница** | заголовок «Deploy: …», шапка — компонент и правило |
| Данные сайта | `components.py`: блок Harness ссылается на «Memory: M1–M6»; описания Memory и Guardrails «в БД ICPlan» без уточнения схемы | **страница** | «Memory API: M3 (позже M4)»; схема `platform` |
| R&D, последствия R&D | в Э10 R&D «Вид работы агента» подписи «поток ICPlan», «потоки Observability» — вкладки нет; R&D «Автоматизация правил» не знает команд `pre`, `post`, `staged`, `tooling_check` | **методология** | правило не говорит, правится ли R&D после принятия: зафиксировать — R&D исторический документ, Э10 меняет только ссылки (их ведёт сборка), новое — новым R&D |
| Технологии | 27 строк без ссылки на R&D при правиле «у технологии есть R&D» | **методология** | R&D — только для выбора между альтернативами; для базовых зависимостей — «в составе X» или источник |
| Бэклог | колонки «Тема, Что, Почему отложено, Основа»; методология требует «условие возврата» и требование | **страница** | добавить колонку «Когда вернуться» и ссылку на требование |
| Подтверждения спеки | 13 подтверждений человеком против 604 агентом по ролям | **процесс** (не страница) | список ключевых требований на подпись владельцу |
| Персоны | в «Справке», которая «только общее», а персоны — пользователи нашего продукта | **методология** | определить: персоны — общий справочник ролей для отыгрыша (дополняются вместе с промптами), продуктовые детали — в историях компонентов |

**Проверено, расхождений нет:** задачи, Roadmap, сводная таблица, proposal, спеки, интерфейсы, RTM, открытые вопросы, ревью, design, tasks изменений, страницы блоков, индексы, «Как работает», «Интеграции», «Данные», «Справка», журнал отклонений, правила (кроме названных выше страниц).

**Итог.** Причина большинства расхождений — в методологии, а не на страницах: правило молчит, откуда берётся содержимое (карта, таблица README), задаёт дубль (карта + C2) или не определено (правится ли R&D после принятия, нужен ли R&D каждой технологии). На страницах — отставание текстов от последних перестроек вкладок (потоки, техспека, API) и одно смысловое противоречие (шаг ⑫).

### Пересечения данных в рамках одного компонента (Memory) {#overlap}

Проверка 11.10.2026: 17 документов Memory (главная, вкладки компонента, спека с соседними файлами, задача 2.5, R&D, design) — сколько раз повторяется один и тот же факт. Источник факта — где он **должен** жить; остальное — копии.

| Факт | Мест | Где встречается | Источник (одно место) | Лишние копии |
|---|---|---|---|---|
| Где хранится M3 (`memory_m3`, схема `platform`) | 9 | главная, Архитектура, Интеграции, Данные, interfaces, схема спеки, задача 2.5, R&D, design | вкладка «Данные» (из `datamodel.py`) + interfaces (S-код) | главная, Архитектура, схема спеки, задача |
| Область видимости — атрибут записи, не уровень | 8 | главная, Архитектура, Интеграции, истории, спека, схема спеки, задача, R&D | спека (требование R-MEM-02) | главная, Архитектура, схема спеки, задача, истории |
| M4 и RAG — после MVP | 8 | главная, Архитектура, истории, спека, interfaces, схема спеки, R&D, design | design (D13) + спека (R-MEM-06) | главная, Архитектура, истории, interfaces, схема спеки |
| `m2_last_runs` = 3 | 7 | Архитектура, Deploy, истории, спека, interfaces, схема спеки, R&D | interfaces (параметр) | все остальные — значением; допустимо только ссылкой (на Архитектуре и в блоках значение уже подставляется из interfaces) |
| Сроки хранения M1 / M2 / M3 | 5 | главная (типы данных Т2), Архитектура, Deploy, истории, interfaces | interfaces (`retention`) | главная, истории, Deploy (пример конфигурации — допустим, если значения из interfaces) |
| Поля M3: сделано / дальше / блокеры | 5 | главная, блок M3, Интеграции, спека, задача | Интеграции (контракт `M3Record`) | главная, блок M3, задача (ссылкой) |
| Уровни памяти M0–M6 таблицей | 4 | **главная дважды** («Память M0–M6» и «Термины и коды»), спека, схема спеки, R&D | спека (R-MEM-01) | главная (обе), схема спеки |
| Плюсы и минусы Memory | 1 | только главная | вкладка «Архитектура» компонента («Почему так») | — (сейчас на странице компонента их нет) |

**Вывод про главную.** Большая часть главной дублирует вкладки компонентов: раздел «Сквозные решения» — это десять «Почему так» компонентов (Harness, Guardrails, очередь — Runner, исполнение — Sandbox, память — Memory, конфигурация — Platform module, MCP — MCP / Tools, наблюдаемость — Observability); «Блоки» повторяют карту и «Устройство» компонентов; «Плюсы и минусы по модулям» должны жить у компонентов; таблица типов данных повторяет хранилища и сроки из interfaces; матрица интерфейсов повторяет карточки «Интеграций».

**Предложение (не внесено):** на главной оставить только то, что не принадлежит одному компоненту — карту (она же C2), C1, взаимодействие компонентов (сквозной сценарий), развёртывание и поставку. Сквозные решения — по одной строке-ссылке на D-номер и компонент; плюсы и минусы — на вкладку «Архитектура» каждого компонента; «Блоки» — убрать (есть карта); термины и коды — в «Справку» (это легенда, общая для всех страниц); типы данных и матрица интерфейсов — убрать (есть на вкладках «Интеграции» и «Данные»). Внутри компонента — ссылки вместо значений: значения параметров только в interfaces, контракт M3 только на «Интеграциях», хранилища только на «Данных».

## Вкладки и их наполнение {#tabs}

Правило из отклонения [О-46](deviations.md). Каждая вкладка отвечает на **свой** вопрос. Факт живёт в одной вкладке, остальные ссылаются на неё ([один источник](change-process.md#single-source)). Если тянет написать в вкладке то, что относится к другой, — ставим ссылку.

**Вкладки компонента** (в навигации — под именем компонента):

| Вкладка | Отвечает на вопрос | Обязательно | Чего здесь нет → где это | Источник | Проверка | Методология |
|---|---|---|---|---|---|---|
| **Архитектура** (страница компонента) | из чего состоит, почему так и как работает | схема блоков, «Почему так», конфигурация, как работает (`docs/how`) | стыки и контракты → Интеграции; хранилища → Данные; процесс пользователя → User Stories; требования → Спека; развёртывание → Deploy | `components.py`, `rationale.py`, `docs/how` | «Как работает» без конфигов (`flows_check`) | [архитектура](architecture-methodology.md) |
| **Компоненты** (блоки) | что делает блок и на чём сделан | технология, ключевые параметры, что делает, почему так | значения параметров → `interfaces.md` спеки | `subcomponents.py` | у блока схемы есть страница | [архитектура](architecture-methodology.md) |
| **User Stories** | кто и зачем пользуется, как проходит процесс пользователя | истории, BPMN, критерии приёмки; процесс и правила пользователя (например, процесс задачи ICPlan, что пользователь видит в чате запуска) | требования → Спека; работа системы → Техспека | `stories.py`, `stories_extra/` | у истории есть требование | [User Stories](us-methodology.md) |
| **Спеки** | что компонент обязан делать | требования SHALL / MUST со сценариями; `interfaces.md` — параметры, хранилища, интерфейсы, нагрузка, FMEA; RTM; открытые вопросы; подтверждения; схема | порядок работы → Техспека; данные → Модель данных | `openspec/changes/…` | [критерии полноты](spec-criteria.md), `openspec validate` | [SDD](sdd-methodology.md), [критерии полноты](spec-criteria.md), [виды спек](spec-kinds.md) |
| **Задачи** | что сделать, сколько стоит, как принять | оценки, требования, приёмка, декомпозиция | зачем так устроено → R&D, design | `docs/tasks/*.md` | трассировка требование ↔ задача | [задачи и план](task-methodology.md) |
| **Интеграции** | с кем связан компонент, через что, что передаётся и какие вызовы | схема C1 (стрелка — кто вызывает, подпись — I-коды), карточки интеграций, контракты данных (поля, источник, сноска «почему так», пример), эндпоинты со структурой запросов и ответов | хранилища → Данные | `docs/api/*.md` + `datamodel.py` + OpenAPI форка | карточки = `interfaces.md` спек; модели «форк» = OpenAPI; статус ✅ = путь в OpenAPI; у каждого эндпоинта есть структура | [интеграции и API](api-methodology.md), [данные и интеграции](data-methodology.md) |
| **Данные** | что компонент хранит и как | хранилища, ER-диаграмма, таблицы полей, индексы, срок, очистка, миграции | контракты обмена → Интеграции; значения сроков → `interfaces.md` | `datamodel.py` (генерируется) | FK с индексом, у таблицы есть политика, коммит схемы форка = импорт | [данные и интеграции](data-methodology.md) |
| **Deploy** | как компонент собирается, разворачивается и настраивается | образы, запуск, переменные и секреты, сборка, проверка, пример конфигурации | порядок работы → «Как работает» на вкладке «Архитектура»; значения параметров → `interfaces.md` | `docs/techspec/*.md` | [правило Deploy](tech-spec.md); нет раздела «Как работает» (`flows_check`) | [Deploy](tech-spec.md) |
| **R&D** | почему выбрано именно так | исследование по [методологии](rnd-methodology.md), последствия Э10 | решение → design | `docs/rnd/*.md` | структура v3, Э10 в сводке | [R&D](rnd-methodology.md) |
