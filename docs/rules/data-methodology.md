# Методология данных и интеграций

← [Правила документации](README.md) · [типы документов и вкладки](doc-types.md) · [работа с документами](doc-work.md)

Как вести модель данных, контракты обмена, интеграции между компонентами, таблицы БД и типы данных: вкладки компонента «Интеграции» (схема C1, карточки, контракты) и «Данные» (хранилища, ER, политика таблиц), [типы данных и интерфейсы](../data-types.md) на главной.

## Назначение и читатель

Отвечает на вопросы **«кто с кем связан, что передаётся, что хранится и почему так названо»**. Читатель — разработчик, который будет реализовывать интерфейс, и проверяющий, который сверяет спеки. Он должен по одной странице понять поле: что оно значит, откуда взято (код ICPlan, внешний протокол или наше решение) и почему так называется.

## Основа

| Практика | Что берём |
|---|---|
| Контракт данных (data contract), JSON Schema | у модели — поля, типы, обязательность, описание, владелец |
| OpenAPI 3 | структура существующих API ICPlan — из OpenAPI работающего форка, не по памяти |
| ER-модель | таблицы, ключи, связи; индексы на внешних ключах; срок хранения и очистка |
| Один источник ([single source](change-process.md#single-source)) | всё описано в YAML по единице в `data/` ([ниже](#yaml)), страницы генерируются |
| [Проверка двумя читателями](dual-read.md) | понятность имён и описаний проверяется независимыми читателями |

## Из чего состоит

| Что | Где задаётся | Что генерируется |
|---|---|---|
| Интерфейс (I-код) | `INTEG` (кто вызывает → кого, через что, что передаётся, модели), `DATA_IN_RESPONSE`, `INTEG_TYPES`, `ALSO`; строка в `interfaces.md` спек-участников (протокол, доступ, таймауты, повторы) | вкладка «Интеграции» (схема C1, карточки), «Получает / отдаёт», матрица интерфейсов |
| Модель (контракт JSON) | `MODELS` (поля), `MODEL_META` (источник ✅ / 📘 / 🧩, сноска «почему так»), `PLANNED`, `FIELD_SRC`; пример — `docs/api/README.md` | «Контракты данных» на вкладке «Интеграции» |
| База данных и схема | `DATABASES`: кластер → база → схема; у схемы — владелец (компонент), роль БД сервиса, кто мигрирует, S-код; у базы — пул PgBouncer, бэкап; доступ к чужим таблицам — только явным `GRANT` (`grants`) | вкладка «Данные» Инфраструктуры — «Базы данных»; «Данные» компонента — строка «Где лежит»; схема развёртывания на главной |
| Таблица БД | `PLATFORM_TABLES`, `TABLE_POLICY` (индексы, срок, очистка, миграции); таблицы форка — импорт схемы | вкладка «Данные»: ER-диаграммы, таблицы полей, политика |
| Тип данных Т1–Т8 | `docs/data-types.md` (типы), `INTEG_TYPES` (по интерфейсам) | матрица интерфейсов |
| Имена | `naming` в `data/datamodel.yaml` (`NAMING`) | раздел «Правило имён» |

Имена в «Где задаётся» — значения модулей сборки (`datamodel.INTEG` и т. д.); файл, в котором они правятся, — по таблице [ниже](#yaml).

## Источник данных — YAML по единице {#yaml}

Все данные сайта лежат в `data/` в корне репозитория (на сайт не попадает): **один файл — одна единица** (1–3 КБ), читается и правится целиком. Модули `html-view/datamodel.py`, `subcomponents.py`, `stories.py`, `components.py` только загружают значения (`html-view/yamldata.py`), Python-литералов данных в них нет.

| Единица | Файл | Значения модулей |
|---|---|---|
| Компонент | `data/components/<slug>.yaml` (порядок — `_order.yaml`) | `COMPONENTS`, `ABOUT` (`about`), `BLOCKS` (`blocks`), `STORES` (`stores`), `ICPLAN_TABLES` (`icplan_tables`) |
| Блок компонента | `data/blocks/<компонент>/<slug>.yaml`, имя = адрес страницы блока | `SUB[(компонент, title)]` |
| Встроенные | `data/hosts.yaml` | `HOST` |
| Модель | `data/models/<Имя>.yaml` | `MODELS`, `MODEL_META` (`source`), `FIELD_SRC`, `PLANNED` |
| Таблица | `data/tables/<имя>.yaml`, `kind`: platform / fork / litellm | `PLATFORM_TABLES`, `SCHEMA_OF`, `TABLE_POLICY` (`policy`), `FORK_COLUMNS`, `FORK_WRITTEN` (`written`), `LITELLM_TABLES` |
| Эндпоинты страницы API | `data/endpoints/<страница docs/api>.yaml` | `ENDPOINT_IO` |
| Интерфейсы | `data/integrations.yaml` (запись на I-код) | `INTEG`, `INTEG_TYPES` (`types`), `ALSO` (`also`), `DATA_IN_RESPONSE` |
| Базы и общее | `data/databases.yaml`, `data/datamodel.yaml` | `DB_CLUSTER`, `DATABASES`, `DB_GRANTS`, `MIGRATE`; `NAMING`, `LITELLM_REF`, `S1_DOMAINS`, `TREES` |
| История, процесс, персоны | `data/stories/<компонент>/<US-ID>.yaml` (`chain` — сквозная цепочка), `data/processes/<компонент>.yaml`, `data/personas.yaml` | `STORIES`, `CHAINS`, `BPMN`, `ARTIFACTS`, `ROLES`, `PERSONAS` |

- **Правится только YAML.** Строки таблиц — `[a, b, c]` в одну строку, записи — словари; поля, типы и допустимые значения — схема `yamldata.SCHEMAS`, проверка — `doctool yaml-check`.
- **Сгенерированные страницы руками не правятся**: `doctool generated <файл>` называет источник, хук до правки не даёт изменить такой файл.
- Читать единицу — `doctool unit <ID>` (YAML без пустых полей + связанные ID), а не страницу и не весь файл данных.
- Формат — `doctool yaml-fmt [путь]` (порядок ключей по схеме, `_order.yaml`); новый файл без строки в `_order.yaml` — замечание `yaml-check`.
- Сборка (`python html-view/build.py`) — **один раз в конце пути изменений**, не после каждой единицы ([порядок](change-process.md#yaml-path)).

**Правило имён (кратко):** JSON наших контрактов — camelCase, как в API ICPlan; задача — `issueId` + `issueIdentifier`; агент — `agentId`, автор — `username`; единица — суффиксом (`readyMs`, `ttlSec`); внешние протоколы (OpenAI, LiteLLM, MCP, AG-UI, OPA) — в их стиле; колонки БД и параметры конфигурации — snake_case. Полностью — [ниже](#naming).

## Как вести

| Когда | Шаги |
|---|---|
| Новый интерфейс | 1) `INTEG`: стрелка — кто вызывает; если данные идут в ответе — `DATA_IN_RESPONSE`; 2) `INTEG_TYPES`; 3) строка с I-кодом в `interfaces.md` **всех** спек-участников; 4) эндпоинты в каталоге API; 5) проверка двумя читателями |
| Поле контракта хранится в БД | колонка в таблице-источнике: своя таблица — `PLATFORM_TABLES`, таблица форка — `FORK_COLUMNS` с пометкой 🛠 и решением; заметка «+ колонка» у таблицы форка без строки в `FORK_COLUMNS` — ошибка (Z-ICP-10, Z-ICP-13) |
| Новая модель или поле | 0) модель указана в интерфейсе `INTEG`, по которому передаётся (иначе контракт не показывается на «Интеграциях»); 1) поля с описанием каждого; 2) источник: поле есть в OpenAPI форка — ✅, доработка — в `PLANNED` с D / R, внешний протокол — 📘, наше — 🧩; 3) сноска «почему так» — со ссылкой на **существующие** D или R; 4) пример в `docs/api/README.md` |
| Новая база, схема или роль | 1) `DATABASES` (владелец, роль, миграции, S-код); 2) Deploy сервиса — `DATABASE_URL` с базой и ролью; 3) решение о размещении — R&D и D-номер, если меняется граница (схема на сервис, отдельная база) |
| Новая таблица | колонки, ключи, FK; политика: индекс на каждом FK, срок, очистка, кто мигрирует |
| Компонент пользуется общей инфраструктурой интерфейса (БД, S3, вход) | `ALSO[I-код]`: на схеме C1 — пунктир к инфраструктуре с I-кодом; карточка с пометкой «общая инфраструктура», путь — как у интерфейса (кто → куда), без «получает / отдаёт» |
| Интерфейс внутри компонента (интерфейс ↔ API одного компонента) | в `INTEG` кто = кому; на C1 не рисуется (C1 — стыки с соседями); карточка с пометкой «внутри компонента» |
| Таблица форка, в которую пишет платформа (запуски, сообщения чата, история задачи) | `TABLE_POLICY` с индексами «как в форке»; срок и очистка — по коду форка (`packages/db`, worker); форк срок не задаёт — так и написать и вопрос в `open-questions.md` спеки; список таких таблиц — `FORK_WRITTEN` |
| На ER-диаграмме нужна таблица другого домена | показывается одним ключом (заглушка), на странице это сказано в пояснении к диаграмме |
| Изменилась схема ICPlan | `python html-view/schema_import.py`; OpenAPI — `python html-view/openapi_import.py` |
| Нашли непонятное | вопрос в `open-questions.md` спеки, а не догадка в описании |

## Чек-лист качества

- [ ] У каждого поля — описание; у модели — источник и «почему так».
- [ ] Ссылки на D и R существуют (проверено поиском); параметров, которых нет в спеках, нет.
- [ ] Поля «форк» совпадают с OpenAPI ICPlan; добавленные — с решением.
- [ ] Стрелка интерфейса — кто вызывает; данные в ответе отмечены; общая инфраструктура — пунктиром, интерфейс внутри компонента — не на C1.
- [ ] Каждая таблица лежит в схеме из `DATABASES`; у схемы есть владелец и роль; Deploy владельца называет базу и роль.
- [ ] У таблиц форка, в которые пишет платформа, есть политика: срок и очистка — по коду форка или открытый вопрос.
- [ ] Имена — по правилу; один объект — одно имя во всех моделях.
- [ ] Двое читателей объяснили модели одинаково по смыслу.

## Проверки в сборке

`IG.check`: I-коды = `interfaces.md` спек в обе стороны; модели «форк» = OpenAPI; примеры API = поля моделей (точные имена); FK покрыты индексами; `db_check`: схема каждой таблицы есть в `DATABASES`, владелец схемы — компонент, его Deploy упоминает базу; у таблиц платформы и у таблиц форка из `FORK_WRITTEN` есть политика; коммит схемы форка = коммит импорта; версия LiteLLM = TECHNOLOGIES.
