# Процесс изменения документации

← [Правила документации](README.md)

## Шаги

1. **Определить тип** каждого затрагиваемого документа ([типы](doc-types.md)) и взять порядок работы с ним ([работа с документами](doc-work.md)).
2. **Определить роль** для шага ([роли](roles.md)) и взять её промпт ([промпты](prompts.md)).
3. **Внести изменение** по правилам типа — **в источнике факта** ([таблица источников](#single-source)), а не в производном документе. Данные сайта (компоненты, блоки, модели, таблицы, эндпоинты, интеграции, истории, процессы) — только в YAML по единице, [порядок ниже](#yaml-path).
4. **Синхронизировать связанные документы** по матрице ниже.
5. **Проверить:**
   - `openspec validate <change> --strict` для затронутых changes;
   - для спек — [критерии полноты](spec-criteria.md);
   - `python html-view/build.py` — **один раз в конце пути изменений**: сайт собирается, ссылки ведут на существующие страницы, сверки источников (ниже) без замечаний.
   - Найдено расхождение — сначала [отклонение](#deviations) с причиной, затем правило **и** проверка в сборке, чтобы следующий переход его не повторил.
6. **Отчитаться** пользователю: список изменённых файлов и что в каждом.
7. **Коммит** с описанием; публикация — push в `main`.

Наглядно связи показаны на [графе связности документов](doc-graph.md).

### Правка данных — YAML по единице {#yaml-path}

Источник — `data/` ([раскладка](data-methodology.md#yaml)); Python-модули и сгенерированные страницы не правятся.

1. `doctool unit <ID>` — прочитать карточку единицы (блок `компонент/slug`, `US-…`, `I…`, модель, таблица, «МЕТОД путь», компонент) вместо страницы и целого файла данных.
2. Править файл единицы (`data/…/<единица>.yaml`); новая единица — новый файл, затем `doctool yaml-fmt <папка>` (внесёт в `_order.yaml`).
3. `doctool yaml-check <файл>` — поля, типы, значения, ссылки; `doctool lint <компонент>` — полнота по методологиям.
4. `doctool next <файл>` — что перегенерируется и какой документ следующий; по одному, каждый по своей методологии (повторить 1–4).
5. В конце пути — один раз: `python html-view/build.py` (и `python html-view/archgen.py`, если менялись компоненты или блоки) → `doctool check` → коммит.

## Приёмка новой задачи {#task-intake}

Задачу или замечание мог поставить агент без контекста — это нормально. До попадания в ROADMAP её проверяет агент **с контекстом** (роль «Архитектор» или «Автор критериев», [промпт](prompts.md#task-intake)):

1. **Найти требование**, которое закрывает задача (поиск по ID и смыслу во всех `spec.md`, потоках и историях).
2. **Требование есть и описано достаточно** → задача получает ссылку на требование (ID в разделе «Закрывает требования»), требование — ссылку на задачу.
3. **Требование есть, но описано недостаточно** (разночтения: кто, когда, что дальше) → **задача закрывается** с указанием ID требования; требование уточняется (сценарии, термины, поток), уточнение — в задачу, которая его реализует. Пример: [1.7](../tasks/1.7-dev-ui.md).
4. **Требования нет** → сначала история и требование в спеке (с ID), потом задача.
5. Задача без требования в ROADMAP не попадает — это проверяет сборка (`check_req_tasks`).
6. В сводной таблице (`TASKS.md`) у каждой открытой строки (⬜, ⚠️) — ссылка на документ задачи; ссылка на `architecture.md` допустима только у выполненного (✅). Тоже проверяет сборка.

## Двусторонняя трассировка требование ↔ задача {#req-task-trace}

- У каждого требования — постоянный ID `R-<спека>-NN` и строка «Реализует задача» в `spec.md`; ID не меняется при переименовании и не переиспользуется.
- У каждой задачи — раздел «Закрывает требования»; в ROADMAP и TASKS — колонка «Требования».
- Сборка проверяет: каждое требование покрыто задачей или решением «бэклог»; связь совпадает с обеих сторон; у открытой задачи есть требование; закрытая задача ссылается на существующее требование.

## Изменение, касающееся нескольких спек {#cross-spec}

- **Частная история каждой спеки** (своя конфигурация, свои хранилища, свои интерфейсы, свои отказы): правка вносится **во все** затронутые спеки, в каждой — своим содержанием (свои параметры, свои S- и I-коды, свои сценарии). Шаблонный одинаковый текст в нескольких спеках — дефект: значит, частное описано как общее.
- **Связующее** (интерфейс между модулями, общий формат, сквозной процесс): правка вносится **обязательно во все** спеки-участники (О-42; раньше «рекомендуется» — и вторую сторону пропускали). Для интерфейса — строка с его I-кодом в `interfaces.md` каждого основного участника (от, к, через); сопутствующие участники (общий Postgres, S3) — в `datamodel.ALSO`. Сборка сверяет обе стороны; в каждой — своя сторона связи: что модуль отдаёт или принимает, по какому интерфейсу (I-код), что делает при отказе другой стороны. Связь и интеграция прописываются явно (ссылка на спеку-партнёра и интерфейс).
- Реализация может пересекаться (общая библиотека, один сервис), но в спеках это собственные требования каждого модуля.

## Один факт — один источник {#single-source}

Правило из отклонений [О-41…О-43](deviations.md). **Почему документы расходились** — во всех найденных случаях одна из четырёх причин:

| Причина | Пример | Чем исключается |
|---|---|---|
| **Ручная копия факта** в двух местах | список «Получает / отдаёт» в `components.py` и таблица «Интерфейсы обмена»; SQL-черновик `run_event` в потоке и модель; JSON-примеры API и поля моделей | у факта один источник; производное генерируется, а что нельзя сгенерировать — сверяется сборкой |
| **Одностороннее изменение связи** | I2, I3, I21 не было в спеке ICPlan, I23 — у sandbox, I14 — у инфраструктуры, I12 — у Runner | правка связующего — обязательно во все спеки-участники ([выше](#cross-spec)), сверка обеих сторон |
| **Цепочка последствий без производных источников** | D20 изменил шаг процесса и M3, а примеры API и модели остались прежними | в Э10 R&D и в матрице ниже — `datamodel.py` и примеры API как обязательные цели |
| **Нет проверки или она мягкая** | ссылки в режиме `info` (О-40), IO без сверки | новое правило вводится вместе с проверкой в `build.py`; правило без проверки — временное, с задачей на проверку |

| Факт | Источник (правится здесь) | Производное (генерируется) | Сверка в сборке |
|---|---|---|---|
| Интерфейс: стороны, назначение, модели | `interfaces.md` спек-участников (протокол, режим, отказы) + `data/integrations.yaml` (INTEG, ALSO) | карточки «Интеграции», «Получает / отдаёт» компонентов | I-код есть в INTEG и в спеках; карточка компонента = I-коды его спеки в обе стороны |
| Модель данных (поля, типы) | `data/models/<Имя>.yaml` (MODELS) | «Модели данных» компонентов, [Модель данных](../../data-model.md) | примеры JSON в `docs/api/README.md` используют только поля модели; у каждого примера есть модель |
| Таблицы БД | схема форка ICPlan — только через `python html-view/schema_import.py` (`icplan_schema.json` + коммит в `.meta.json`); `data/tables/<имя>.yaml` (PLATFORM_TABLES, TABLE_POLICY, LITELLM_TABLES; LITELLM_REF — `data/datamodel.yaml`) | ER-диаграммы по доменам, таблицы полей, индексы, сроки, миграции | SQL `create table` в документах запрещён; коммит схемы = коммит форка; число таблиц = число `pgTable`; FK ведут на описанные таблицы и покрыты индексом; у таблицы проекта есть политика; версия LiteLLM = TECHNOLOGIES |
| Пример модели в техспеке | `docs/api/README.md` (пример), `data/models/` (поля) | — | в «Как работает» — имя модели (ссылка добавляется сборкой); JSON только с подписью-моделью, ключи сверяются |
| Параметр, который настраивается в другом модуле | спека-владелец (`interfaces.md`, значение, границы) | строка в спеке-настройщике (control-plane) | значения и границы в обеих спеках совпадают (при правке — обе строки сразу) |
| Ссылка на требование | якорь `<a id="r-…">` перед `### Requirement:`, строка ID — подпись | ссылки из задач, трассировки, R&D | якорь у заголовка своего требования; якоря всех ссылок `файл.md#якорь` существуют |
| Эндпоинты | `docs/api/*.md` | список эндпоинтов в карточках интеграций | — (одна копия) |
| Задачи | `docs/tasks`, ROADMAP | `tasks.md` изменений | `tasksmd.check` |
| Схемы спек | `data/components/`, `data/blocks/`, R&D «Риски и пересмотр» | `architecture.md` спек | `archgen.py` |

## Изменение правил, методологий и «Справки» {#rules-change}

Правило из отклонения [О-56](deviations.md). Правила и методологии — источник для людей **и** для инструментов: выжимки `doctool route` строятся из таблиц правил, навыки и `AGENTS.md` ссылаются на пути, проверки сборки реализуют правила. Поэтому правка методологии — это правка трёх слоёв, в таком порядке:

1. **Сначала инструменты** (первостепенно — иначе агент продолжит работать по старому правилу):
   - `html-view/doctool.py`: разбор таблиц (`route`), список генерируемых файлов (`generated`), проверки (`check`, `tooling_check`);
   - проверки сборки (`html-view/build.py`, `integrations.py`) — новое правило с проверкой, если её можно автоматизировать;
   - хуки: `.claude/settings.json`, `.githooks/pre-commit`;
   - навыки `.claude/skills/doc-*` и `AGENTS.md` — пути, команды, порядок работы;
   - память агента — указатель, если поменялся способ работы.

   Готово, когда `python html-view/doctool.py route <файл этого типа>` показывает новое правило, а `doctool.py check` чист (в том числе `tooling_check`: методологии из таблицы существуют, пути в навыках и `AGENTS.md` есть, `route` узнаёт основной путь каждого типа).
2. **Затем документы этого типа:** пройти все документы по шаблону из колонки «Где» и привести к новой методологии; если не в этом изменении — записать расхождения в колонку «Расхождения» [таблицы типов](doc-types.md) и завести задачу.
3. **Таблицы правил:** строка в [типах документов и вкладках](doc-types.md) (колонки «Обязательные разделы», «Правила», «Синхронизировать», «Методология»), в [работе с документами](doc-work.md) и, если меняется вкладка, — в меню (`nav_yaml`) и верхней панели (`pagebar.py`).

«Справка» содержит только общее: правила, методологии, формат схем, персоны, промпты, журнал отклонений. Новая страница там — только если она не про данные наших компонентов ([сопровождающие документы](support-docs-methodology.md)).

## Массовые изменения {#bulk}

Когда исправлений много (результат проверки ролями, ревью, смена методологии), цикл «по одному документу» тратит слишком много ресурсов: одни и те же источники, проверки и сборки повторяются десятки раз. Порядок для массовых изменений:

| Шаг | Что делаю | Сколько раз |
|---|---|---|
| 1. Все проверки | проверка ролями, `doctool check`, сборка — полный список замечаний сразу; замечания — в файл компонента ([«Замечания»](review-methodology.md#findings)) | один раз до правок |
| 2. Зафиксировать состояние | коммит и публикация: решения ролей и список замечаний в репозитории | один раз |
| 3. Партия исправлений | замечания группируются по слою и источнику (решения и требования → данные и интеграции → блоки → Deploy → истории → задачи → R&D); партия — все правки одного источника за один проход | по партии |
| 4. Связанные документы партии | по графу связности — для всей партии сразу, а не после каждого документа; методологию документа читаю один раз на партию | по партии |
| 5. Проверка и коммит партии | `doctool check`, сборка, `openspec validate`, статусы замечаний (`doctool finding`), коммит | один раз на партию |
| 6. Повторная проверка ролями | только документы, у которых сброшены подтверждения | один раз в конце |

Единичное изменение по-прежнему идёт по [пути изменения](agent-workflow.md): документ за документом.

## Переименование, перенос и новый документ {#links}

Ссылки — не смысл документа, поэтому правило «по одному документу» к ним не относится.

| Случай | Что делаю | Инструмент и проверка |
|---|---|---|
| Документ переименован или перенесён | **сразу, одним шагом**: файл и все ссылки и упоминания пути во всех документах; смысл не меняется — цепочку по графу не запускаю | `./tools/doc move <старый> <новый>`; сборка: битых ссылок 0 |
| Изменился якорь раздела | найти ссылки на `<файл>#<якорь>` и заменить в том же шаге; генерируемые страницы — правкой источника | сборка: битых якорей 0 |
| Новый документ | у него должна быть **входящая ссылка**: строка «←» на родителя, место в навигации или строка в индексе своего типа (ROADMAP — задача, `REFS` — R&D, `components.py` — спека, README правил — правило); остальные связи по смыслу дадут шаги по графу связности | сборка: «сирот» нет — у страницы есть входящая ссылка или место в навигации |

## Объединение задач {#task-merge}

- Если на уровне постановки задач виден **общий модуль или компонент** (например, общий резолвер конфигурации), задачи можно объединить в одну; она перечисляет **все** закрываемые требования разных спек.
- Объединение не должно нарушать INVEST: задача остаётся независимой, оцениваемой и небольшой (до ~5 дней человека). Если не помещается — делить по модулям.
- Требование может закрываться несколькими задачами: общей (общий модуль) и задачей компонента (его использование и проверка).

## Отклонения {#deviations}

Найдено отклонение (ошибка в документах, расхождение, пропуск) → **сначала причина**: почему правила его допустили → **затем правило** в `docs/rules` (и, если можно, проверка в сборке) → запись в [журнал отклонений](deviations.md) → исправление самого документа. Исправление без правила не считается законченным.

## Матрица синхронизации

Изменили слева → проверить справа.

| Изменение | Проверить и при необходимости обновить |
|---|---|
| Новое решение / смена технологии | R&D → design (D-номер) → architecture.md («Обоснование») → спека (Purpose) → rationale.py (RATIONALE, REFS) → блоки `data/blocks/` → карточка компонента (`data/components/<slug>.yaml`: about, blocks; `data/integrations.yaml`, `data/models/`; `rationale.py`) → схемы спек (`python html-view/archgen.py`) |
| Новая или изменённая User Story | `data/stories/<компонент>/<US-ID>.yaml`, процесс BPMN — `data/processes/<компонент>.yaml` → spec.md (требования и сценарии) → traceability.md (колонка US) → задачи → ROADMAP / TASKS |
| Новое требование в спеке | задача (Приёмка, ссылка на требование) → техспека «Как работает» (порядок работы) → конфигурация компонента |
| Новая задача | docs/tasks → ROADMAP (строка и итоги) → TASKS → tasks.md change (`python html-view/tasksmd.py`) → `data/components/<slug>.yaml` (tasks) |
| Новый параметр конфигурации | rationale.py (config) → блок `data/blocks/<компонент>/<slug>.yaml` (params) → спека (сценарий S9) → architecture.md при необходимости |
| Новый блок на схеме компонента | `data/components/<slug>.yaml` (blocks) → `data/blocks/<компонент>/<slug>.yaml` (SUB; `doctool yaml-fmt` внесёт в `_order.yaml`) |
| Новая или изменённая модель, интеграция, имя | [проверка двумя читателями](dual-read.md): протокол в `docs/reviews/`; расхождения — исправить в источнике и повторить |
| Новый тип данных или поле | `data/models/<Имя>.yaml` (MODELS) → пример в `docs/api/README.md` (сборка сверяет поля) → техспека «Как работает» (именем модели) → спека (сценарии) |
| Новый интерфейс, хранилище или таблица | `interfaces.md` спек-участников (I / S) → `data/integrations.yaml` (INTEG, ALSO), `data/tables/<имя>.yaml`, хранилища — `stores` в `data/components/<slug>.yaml` (таблицы ICPlan — из схемы форка) → API в `docs/api/` → сборка: карточки «Интеграции», «Модели данных», ER-диаграммы и [Модель данных](../../data-model.md) строятся сами, проверка `IG.check` |
| Новый компонент | README → architecture.md → `data/components/<slug>.yaml` и `_order.yaml` (COMPONENTS, BLOCKS, ABOUT, STORES) → `data/integrations.yaml` (INTEG) → rationale.py → техспека «Как работает» → спека → R&D |
| Новая технология / версия | R&D → TECHNOLOGIES.md (лицензия, источник) → design → interfaces.md → задачи |
| Изменение профиля нагрузки | R&D «Профиль нагрузки» → требования «Нагрузка и производительность» всех спек → ёмкость в platform-infrastructure → лимиты планировщика |
| Новый открытый вопрос | `open-questions.md` спеки → ревью → «Что проработать» задачи; 📌 — владельцу продукта |
| Решение по вопросу 📌 | design (D-номер) → спека → `open-questions.md` (удалить) → задачи → карточка компонента и схемы спек (как у «Новое решение») |
| Новая сущность процесса | `data/personas.yaml` (PERSONAS, промпт) → истории → отыгрыш конфликтов → требования / открытые вопросы |
| Новое хранилище или интерфейс | inventory (S / I коды) → `interfaces.md` всех затронутых спек → техспека «Как работает» → требование «Хранилища данных» / «Интерфейсы обмена» |

## Архивация изменений {#archive}

Правило из отклонения [О-39](deviations.md).

- **Когда.** Change архивируется командой `openspec archive <change>` после **реализации и приёмки** всех его задач. Тогда его спеки становятся действующим описанием системы в `openspec/specs/`. До этого спеки живут в `openspec/changes/` — это описание того, что будет сделано.
- **Почему не раньше.** По OpenSpec `archive` — архивация завершённого изменения: перенос нереализованных спек объявил бы действующим то, чего нет в коде.
- **Что переносится вместе со спекой.** `interfaces.md`, `traceability.md`, `approvals.md`, `architecture.md`, `open-questions.md` — копируются в папку спеки в `openspec/specs/<capability>/`; ссылки в документах и сборке (`html-view/build.py`, `SOURCES`) переключаются на новый путь, затем сборка и `openspec validate --strict`.
- **Чем проверяется.** Сборка сверяет `tasks.md` изменений с ROADMAP (`html-view/tasksmd.py`); у каждого изменения есть `tasks.md` с разделом «Архивация».
