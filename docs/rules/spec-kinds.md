# Виды спек и подтверждение требований

← [Правила документации](README.md) · [критерии полноты](spec-criteria.md) · [роли](roles.md) · [процесс изменений](change-process.md)

## Почему это правило

10.10.2026 требования «Конфигурация модуля» всех 13 спек были сгенерированы **одним шаблоном** — как для сервиса, который читает параметры при старте. Для спек другого вида это дало невалидные требования:

| Где | Что получилось | Почему неверно |
|---|---|---|
| платформа (инфраструктура) | «`k3s.version` не задан → применяется v1.37.1»; «изменение `ingress` → после перезапуска модуля» | у инфраструктуры нет «модуля»: параметры — Helm values, применяются `helm upgrade`, версии закрепляются явно |
| модули ICPlan | «тип задачи задан выше потолка L0»; «модуль не стартует без колонки шага» | это настройки сущностей в интерфейсе: проверяются при сохранении, потолков L0 у них нет |
| сервисы | «`delegation_delay_sec` выше потолка L0», «бюджет LiteLLM действует со следующего запуска» | потолка L0 у параметра нет; бюджет LiteLLM применяется сразу |

Причины: (1) не различались виды спек; (2) сгенерированный текст не проверяли роли, которые отвечают за эти параметры (DevOps, разработчик, администратор). Правило ниже закрывает обе.

## Виды спек

| Вид | Спеки | Что такое «конфигурация» | Как применяется изменение | Кто подтверждает конфигурацию |
|---|---|---|---|---|
| **Сервис платформы** | agent-runner, agent-harness, agent-sandbox, agent-memory, llm-gateway, guardrails, observability, tool-integration | параметры уровня L0 (конфиг деплоя) и L1–L3 (настройки агента, запуск) | L0 — при перезапуске сервиса; L1–L3 — со следующего запуска, если не сказано иное (бюджеты LiteLLM — сразу) | Разработчик, DevOps-инженер |
| **Модуль ICPlan** | icplan-integration, agent-registry, control-plane, icplan-agent-autopickup | настройки сущностей в интерфейсе ICPlan (агент, процесс, шаг, задача) | проверка при сохранении; действует со следующего запуска или перехода | Разработчик, Администратор |
| **Образ на запуск** | agent-harness (среда sandbox) | параметры запуска в `RunBundle`, образ закреплён по digest | новый образ — для новых запусков, активные доделываются на прежнем | Разработчик, DevOps-инженер, Инженер сборки |
| **Инфраструктура** | platform-infrastructure | Helm values и манифесты кластера | `helm upgrade` с поочерёдной заменой реплик; проверка схемой `values.schema.json` | DevOps-инженер |

## Таблица параметров {#params}

У каждого параметра в `interfaces.md` — колонки: **Параметр · Что задаёт · Уровень · Хранилище · По умолчанию · Почему так по умолчанию · Мин · Макс · На что опираться при выборе**.

- «Почему так по умолчанию» — источник значения: профиль нагрузки, константа ICPlan, лимит провайдера, принцип наименьших прав.
- «Мин» / «Макс» — допустимые границы; для перечислений — крайние допустимые значения; граница может ссылаться на другой параметр (`scheduling.global_max`).
- «На что опираться при выборе» — какие данные смотреть, меняя значение (статистика запусков 3.9, нагрузочный тест 4.8, лимиты аккаунта провайдера).
- «Тип» (необязательная колонка, после «Макс») — формальный тип, когда он не выводится из «По умолчанию / Мин / Макс» (число с единицей, длительность, вкл/выкл, слаги). Если в таблице спеки есть хоть один такой параметр, колонка добавляется в таблицу целиком (у выводимых — пустая). Грамматика (разбор — `yamlcat.parse_decl`):
  `число [ед.]` · `длительность` · `одно из: a, b` · `список <каталог>` (tools, servers, skills, projects, sources, доменов …) · `ссылка <что>` (Secret, алиас LiteLLM …) · `строка [<мин>–<макс> симв.]` · `доля окна %` · составной — части через ` / ` в порядке имени параметра (`число $ / число $ / число $`). Имя составного параметра остаётся одной строкой.

## Сквозные требования по видам

| Требование | Сервис платформы | Модуль ICPlan | Инфраструктура |
|---|---|---|---|
| Конфигурация модуля | по умолчанию, границы, обязательные L0 → не стартует | по умолчанию, границы и обязательные поля → проверка при сохранении; со следующего запуска | значения в схеме Helm, `helm upgrade`, закреплённые версии |
| Хранилища данных | свои S-коды, роль БД на схему | таблицы форка ICPlan, миграции | тома, бэкапы, S3 |
| Интерфейсы обмена | I-коды: таймауты, повторы, идемпотентность | API ICPlan и протокол раннера | ingress, сетевые политики |
| Поведение при отказах | FMEA зависимостей сервиса | отказ ICPlan API / БД | отказ узла, хранилища |

## Подтверждение требований {#approvals}

Сгенерированное или изменённое требование считается принятым, когда его подтвердили **все обязательные роли**. Подтверждения — в файле `approvals.md` рядом со спекой. Сборка сама добавляет строки «⏳ ждёт» для каждой обязательной пары «требование × роль»; роль ставит решение.

| Колонка | Что писать |
|---|---|
| Требование | ID (`R-RUN-11`) |
| Роль | из таблицы ниже |
| Кто | имя человека или агента (`Claude, роль DevOps`) |
| Тип | 👤 человек · 🤖 агент |
| Дата | ГГГГ-ММ-ДД |
| Решение | ✅ подтверждено · ❌ замечание · ⏳ ждёт |
| Комментарий | замечание или что проверено |

Агент может подтверждать как роль, но отмечается 🤖; подтверждение человеком (👤) нужно для решений 📌 и для выпуска.

### Обязательные роли

| Требование | Роли |
|---|---|
| Конфигурация модуля | по виду спеки (таблица выше) |
| Хранилища данных | Архитектор, DevOps-инженер |
| Интерфейсы обмена | Архитектор, Разработчик |
| Поведение при отказах зависимостей | DevOps-инженер, Тестировщик |
| Нагрузка и производительность | DevOps-инженер, Тестировщик |
| Развёртывание | DevOps-инженер |
| Функциональное требование | Аналитик историй, Тестировщик и роли персон связанных историй (Пользователь, Администратор, Безопасность, DevOps-инженер, Владелец продукта; агент — Разработчик) |
| Любое требование спек guardrails и agent-sandbox | + Безопасность |

### Готовность

Пока по спеке есть обязательные подтверждения ⏳ или ❌, её готовность не выше 90 ([критерии](spec-criteria.md)). На странице спеки видно «подтверждено X из Y».

## Граница доверия и ограничения по умолчанию {#trust}

Правила из отклонений [О-36, О-37](deviations.md).

- **Проверка вне среды, которую она ограничивает.** Всё, что ограничивает агента (allowlist тулов, G2, права), MUST исполняться вне sandbox: в Runner, прокси или сервисе. Проверка в Harness — подсказка модели, а не граница.
- **Ограничение по умолчанию проверяется типовой работой.** У параметра «наименьших прав» (`network.egress_allow`, `tools`, источники) есть сценарий типовой работы агента, который при этом значении выполним; если нет — нужен отдельный путь (как шаг подготовки D19).
