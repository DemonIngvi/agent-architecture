# Методология подтверждений

← [Правила документации](README.md) · [роли](roles.md) · [типы документов](doc-types.md) · [сводная таблица](../approvals-summary.md)

Какие роли подтверждают какие документы, как ставится решение и как его видно на странице.

## Назначение и читатель

Документ считается принятым, когда его подтвердили **все роли, которые отвечают за его тип**. Подтверждение — это ответ роли на свой вопрос из [ролей](roles.md): архитектор — «где живут данные и как связаны модули», разработчик — «реализуемо ли так, как написано», тестировщик — «как проверить». Читатель — владелец продукта и любой исполнитель: по значкам в углу страницы видно, можно ли опираться на документ.

Расход: см. [проверка ролями](token-costs.md#review-pack), [перевод отказов в lint](token-costs.md#lint-conversion) на странице «Расход токенов».

## Основа

| Практика | Что берём |
|---|---|
| Ревью по ролям (RACI, «approver») | у каждого типа документа — список подтверждающих ролей |
| Definition of Ready | документ готов, когда все его роли подтвердили |
| Версия под подтверждением | решение относится к конкретному тексту: текст изменился — решение сбрасывается |

## Роли и буквы

Значок роли — круг с одной буквой: зелёный с ✓ — подтвердил, красный с ✕ — отказ (причина — в комментарии), серый — ждёт.

| Буква | Роль | Вопрос |
|---|---|---|
| **В** | Владелец продукта | что важно, сколько стоит, что выбрать |
| **А** | Архитектор | где живут данные, как связаны модули, как развёртывается |
| **Р** | Разработчик | реализуемо ли так, как написано |
| **Т** | Тестировщик | как проверить каждое утверждение |
| **И** | Аналитик историй | кто что делает и что может пойти не так |
| **П** | Пользователь | решает ли это мою задачу |
| **Н** | Администратор (настройки) | понятны ли настройки |
| **Д** | DevOps-инженер | как развернуть, обновить, восстановить |
| **Б** | Безопасность | где утечка, лишние права, лицензионный риск |
| **С** | Инженер сборки и поставки | как собрать и откуда взять |

## Кто подтверждает какой документ

| Тип документа | Страница | Роли |
|---|---|---|
| Главная | `index.md` | А, В |
| Архитектура компонента | `components/<компонент>/` | А, Р |
| Блок | `components/<компонент>/<блок>/` | А, Р, Т |
| Интеграции | `docs/api/<компонент>.md` | А, Р, Т |
| Данные | `data-by-component/<компонент>/` | А, Р, Д |
| Deploy | `docs/techspec/<компонент>.md` | С, Д, Б |
| User Stories | `docs/stories/<компонент>.md` | И, П, В |
| Задача | `docs/tasks/<N.M>-….md` | Р, Т, В |
| R&D | `docs/rnd/*.md` | В, А |
| Решения | `design.md` | В, А |
| Методология | `docs/rules/*-methodology.md`, `tech-spec.md` | В, А |
| Спека | `spec.md` | по требованиям: роли из [видов спек](spec-kinds.md#approvals) в `approvals.md` рядом со спекой; значок спеки — сводка по требованиям |

Источник правила для сборки — `html-view/approvals.py` (`RULES`, `ROLES`); при изменении этой таблицы — сначала он ([изменение правил](change-process.md#rules-change)).

## Как ставится решение

1. Сборка добавляет в реестр [`docs/approvals.md`](../approvals.md) строку ⏳ для каждой пары «документ × роль».
2. Роль проверяет документ по своему вопросу и методологии его типа. Агент-роль — проверяющий агент `.claude/agents/doc-reviewer.md` (промпт роли — [prompts.md](prompts.md)); человек — сам.
3. Решение — командой: `./tools/doc approve <страница> <буква> ok|no "<комментарий>"` (агент — 🤖; человек добавляет `--human`). Отказ — всегда с причиной и ссылкой на то, что исправить.
4. Текст страницы изменился — сборка сбрасывает решение в ⏳ с пометкой «текст изменён после решения».
5. Что ждёт роли — `./tools/doc review-queue <буква>`.

Подтверждение агентом (🤖) и человеком (👤) различаются в реестре и в подсказке значка; агент не ставит 👤.

## Экономная проверка {#economy}

Проверка ролями дорогая: на две проверки ICPlan ушло около 1,1 млн токенов агентов. Порядок, который её удешевляет:

| Правило | Как |
|---|---|
| Сначала автоматика | `./tools/doc check` и `./tools/doc lint <компонент>` до ролей; роли не ищут то, что ловит инструмент. Повторяющееся замечание ролей — повод для новой проверки в lint |
| Пачка — основной режим | `./tools/doc review-batch <компонент>`: один файл с компактными карточками всех ⏳-страниц компонента (≤ 2500 символов, блок ≤ 1500) и вопросами ролей |
| Пачка: ответ | агент читает пачку один раз, решает за все страницы и роли, пишет один JSON и применяет его `./tools/doc approve-batch <файл.json>`; в источники — не больше 2 раз на пачку |
| Пачка: цель | ~1–1,5 тыс. токенов на документ за все роли вместо 15–25 тыс. при пакете на роль |
| Пачка: агент и размер | агент **без тяжёлых инструментов** (`doc-batch-reviewer`: Read, Write, Bash; до его загрузки — Explore): накладные ~19 тыс. против ~33 тыс. у агента общего назначения; пачка **~40 страниц** (`--max 40`, компоненты через запятую), чтобы накладные делились на много документов; замер 13.10 по журналу вызовов: 16 страниц агентом общего назначения — 8,6 тыс. на документ, 40 страниц Explore — **3,7 тыс.**, полный прогон 104 страниц (3 агента, 19 вызовов) — 7,2 тыс. ([расход](token-costs.md#review-batch); прежние 1,4 тыс. — итоговый контекст, а не расход, см. [как замерять](token-costs.md#measure)) |
| Пачка: только чистые компоненты | `review-batch` не берёт компонент с непустым `./tools/doc lint` (`--force` — обойти): за механику роли не платят (замер 13.10: 8 из 8 отказов пачки — карточки, которые уже показывал lint) |
| Пачка: защита от шаблона | `approve-batch` отклоняет JSON целиком, если один комментарий у > 10% пар или у решения нет проверенного факта (≥ 40 символов, ID / поле / номер). Причина (13.10): три пачки, 295 пар — все ✅ с одним комментарием, одна сгенерирована скриптом; решения откачены |
| Пачка: модель | первая проверка и перепроверка — Sonnet. Haiku не годится: перепроверка 13.10 — 6 из 7 отказов неверны (перепутал требования, не учёл решённое, судил по изъянам карточки) |
| Пачка: документы | `review-batch --pages <префикс>[,…] [--max 40]` — пачка ⏳-пар документов по префиксу пути (`docs/rules,docs/rnd,docs/stories,index.md`…), тот же формат и `approve-batch`; lint-барьер не применяется (механику ловит `doctool check`) |
| Пачка: оценка | кириллица ≈ 1,6–2 символа на токен (не 3–4, как латиница): `review-batch` печатает оценку с накладными на страницу — сверять с замером ±2× |
| Пакет вместо поиска (запасной) | агент читает **один файл** `./tools/doc review-pack <страница> <буква>`: страница, вопрос роли, чек-лист методологии типа, требования страницы, открытые вопросы, прежние замечания, lint; в источники идёт только за фактом, которого в пакете нет |
| Только блокирующее | отказ — если без исправления нельзя ответить на вопрос роли; у замечания — факт-источник (файл, строка кода, требование); не больше 3 на документ; мелочь без последствий не записывается |
| Повторная — по изменённому | после правок роль проверяет закрытие своих прежних замечаний и изменённые разделы, а не документ заново |
| Несколько ролей — один проход | один агент на документ сразу за все его роли (пакет на каждую роль), а не агент на роль по всем документам |
| Модель | проверяющим агентам — модель попроще (Sonnet); основной агент сводит решения и разбирает замечания |
| Разбор замечаний | перед правкой каждое замечание проверяется по источнику: безосновательное — «отклонено» с причиной; затем — что закрывается правилом методологии; правка документов — последней |

## Готовность документа

Документ готов, когда все его роли — ✅. Блок готов к реализации, когда документ готов, карточка заполнена и открытых вопросов по его требованиям нет ([методология блоков](block-methodology.md#ready)).

## Проверки в сборке

Проверяет lint (`./tools/doc lint`) до ролей — роль не отказывает за то, что он ловит: покрытие требований приёмкой задачи, оценка = сумма подзадач, FMEA ↔ сценарий, RTM ↔ спека, эндпоинт экрана ↔ API, требования и таблицы карточки блока, ссылки на закрытые ОВ, миграции и пример конфигурации в Deploy.

`approvals.sync`: строки ⏳ для обязательных пар, сброс по изменённому тексту, удаление строк по удалённым документам; значки — на странице; [сводная таблица](../approvals-summary.md) — документ × роли.
