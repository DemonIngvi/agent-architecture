# Методика User Stories

← [Правила документации](README.md) · [персоны](../stories/personas.md) · [SDD-методика](sdd-methodology.md) · [критерии спек](spec-criteria.md)

Как строить истории, чтобы они покрывали **всех пользователей и все сценарии**. Сочетает пять признанных практик и адаптирует их под ИИ-агентов. Истории — вход для требований спек: требование без истории — дефект (кроме внутренних технических).

## Итог

| Шаг | Практика | Что даёт | Чем проверяется покрытие |
|---|---|---|---|
| 1. Кто | **Список «актор — цель»** (Cockburn) | все участники: люди, агенты, внешние системы, время (расписание) | матрица «персона × компонент» без пустых строк |
| 2. Что делают | **Карта историй** (Patton, User Story Mapping) | хребет деятельности → шаги → истории; видны дыры в пути пользователя | у каждого шага хребта есть история; MVP — «ходячий скелет» |
| 3. Над чем | **Жизненный цикл сущностей** (CRUD+) | истории на создание, просмотр, изменение, удаление, архив, передачу каждой сущности | матрица «сущность × операция × актор» без пустых нужных клеток |
| 4. Как бывает | **Use-Case 2.0** (Jacobson): основной и альтернативные потоки, срезы | у каждой истории — основной поток, альтернативы, исключения | ≥ 1 основной + ≥ 2 альтернативных / ошибочных критерия |
| 5. Что именно | **Example Mapping** (Wynne, BDD) | правила → примеры → вопросы | каждое правило с примером; вопросы → `open-questions.md` |
| 6. Качество | **QUS** (Lucassen et al., 13 критериев) + **INVEST** | однозначные, атомарные, без конфликтов | проверка ролью «Аналитик историй» и LLM-судьёй по чек-листу |
| 7. Отыгрыш | **Персоны-агенты** (multi-agent elicitation) | конфликты и забытые сценарии | таблица конфликтов, каждый — история или вопрос |

## 1. Акторы и цели

Перечислить **всех**, кто взаимодействует с компонентом, — не только «пользователя»:

| Тип актора | Примеры в платформе |
|---|---|
| Человек — основной | пользователь ICPlan, владелец процесса, ревьюер |
| Человек — обеспечивающий | администратор платформы, эксплуатация, безопасность, QA |
| Агент | агент-исполнитель, агент-ревьюер, агент-аналитик |
| Система | Agent Runner, ICPlan, LiteLLM, OPA, git-провайдер |
| Время | расписание (`agent_schedule`), сроки хранения, таймауты |

Для каждого актора — список целей (что хочет получить). Каждая цель → минимум одна история. Персоны с промптами — в [personas.md](../stories/personas.md).

## 2. Карта историй

```
Хребет (деятельность):  Настроить процесс ─▶ Поставить задачу ─▶ Агент работает ─▶ Проверить ─▶ Принять / вернуть ─▶ Разобрать затраты
Шаги:                    типы, шаги, агенты    создать, описать     взять, выполнить   approve, ответ   переход, комментарий   отчёт
Истории (по приоритету):  ── MVP (ходячий скелет) ──────────────────────────────────────────────────────────────────────────────
                          ── этап 4 ─────────────────────────────────────────────────────────────────────────────────────────────
```

Карта строится по сквозному процессу и по каждому компоненту. Пустая клетка под шагом хребта — дыра.

## 3. Жизненный цикл сущностей

Для каждой сущности компонента (процесс, шаг, агент, запуск, артефакт, политика, бюджет, память…) пройти операции:

| Операция | Вопрос |
|---|---|
| Создать / Импортировать | кто создаёт, из чего, с какой проверкой |
| Посмотреть / Найти | кто видит, где, какие фильтры |
| Изменить / Версия | кто меняет, когда вступает в силу, что с активными запусками |
| Удалить / Архивировать | что со ссылками и историей |
| Передать / Сменить владельца | кому, с какими правами |
| Истечь по сроку | что удаляется автоматически |

Нужная клетка без истории — дыра или осознанное решение «не делаем» (бэклог).

## 4. Потоки истории (Use-Case 2.0)

Каждая история описывается потоками, а критерии приёмки — по одному на поток:

- **Основной поток** — самый простой путь к цели.
- **Альтернативные потоки** — другой путь к той же цели (ручной шаг, другой агент, повтор).
- **Исключения** — что ломается: нет прав, нет данных, зависимость недоступна, лимит, таймаут, конфликт.

Минимум: 1 основной + 2 альтернативных или исключения. Срез (slice) — часть потоков, которую можно сделать и проверить отдельно; срезы истории попадают в разные задачи.

## 5. Example Mapping

Для истории: **правила** (бизнес-ограничения) → **примеры** на каждое правило (конкретные данные) → **вопросы**, на которые нет ответа. Примеры становятся сценариями WHEN/THEN требований; вопросы — строками `open-questions.md` спеки.

## 6. Качество истории (QUS + INVEST)

| Группа | Критерий QUS | Проверка |
|---|---|---|
| Синтаксис | корректная форма | «Как <роль>, я хочу <цель>, чтобы <польза>» |
| | атомарность | одна цель на историю |
| | минимальность | без пояснений и решений в тексте истории |
| Семантика | концептуальная точность | цель — действие, польза — результат |
| | ориентация на проблему | без «как сделать» |
| | однозначность | термины из потоков и спек, без «и т. п.» |
| | бесконфликтность | не противоречит другим историям |
| Прагматика | полное предложение | читается без контекста |
| | оцениваемость | понятен объём |
| | уникальность | нет дубля |
| | единообразие | одинаковая форма во всех историях |
| | независимость | без скрытых зависимостей |
| | полнота набора | нет дыр по шагам 1–4 |

Плюс INVEST — для задач, в которые режутся срезы историй.

## 7. Адаптация под ИИ-агентов

- **Персоны-агенты.** Каждая персона — промпт ([personas.md](../stories/personas.md)); агент отыгрывает её цель и ищет конфликты с другими персонами и системой ([методика R&D](../rnd/METHOD.md#personas)).
- **Многоагентный сбор требований.** Роли «аналитик» (спрашивает), «заказчик» (персона отвечает), «QA» (оценивает качество по QUS), «владелец продукта» (приоритизирует) — по образцу исследований многоагентного выявления требований.
- **LLM-судья.** Истории, сгенерированные агентом, проверяются отдельным проходом по таблице QUS; спорное — человеку.
- **Агент — тоже актор.** Для агента-исполнителя истории пишутся так же: что он получает (задание, контекст, права), что делает, что возвращает, что при отказе.
- **Человек утверждает.** Итог отыгрыша и генерации — предложение; историю в `stories.py` утверждает владелец продукта ([роли](roles.md)).

## 8. Проверки покрытия (автоматические)

Считаются при сборке, страница [покрытие историй](../stories/coverage.md):

- матрица «персона × компонент»: число историй, пустые клетки видны;
- истории с менее чем 3 критериями приёмки (нет альтернатив и исключений);
- истории без требований (→ открытый вопрос);
- пользовательские требования без истории (штраф готовности спеки).

## Процесс

1. Аналитик историй строит списки 1–3 (акторы, карта, сущности).
2. Для каждой цели — история с потоками (4) и примерами (5).
3. Отыгрыш персон (7) → новые истории и вопросы.
4. Проверка качества (6) отдельным проходом.
5. Требования спек: из примеров — сценарии, из правил — требования; связь история ↔ требование.
6. Пройти с пользователем по сценариям, закрыть вопросы.
