# 1.2. Формат определения агента (YAML)

## Зачем

Формат YAML — контракт между ICPlan, Harness и экспортом/импортом. Зафиксировав его первым, мы делаем Harness сейчас, а в ICPlan потом переносим тот же формат без переделок.

## Что сделать

- Схема (JSON Schema) определения агента: id, версия, модель-алиас, инструкция, скиллы, тулы, MCP-серверы с allowlist, лимиты, профиль памяти, формат результата
- Валидатор схемы + проверка ссылок (MCP, скиллы существуют)
- 2 примера: агент-аналитик (без тулов записи), агент с MCP и approve на опасном туле
- Документ формата с примерами

## Приёмка

- [ ] Примеры проходят валидацию
- [ ] Битая ссылка и неверное поле отклоняются с понятной ошибкой
- [ ] Схема покрывает всё, что Harness читает

**Как прокликать:** Запуск валидатора на примерах: ✅ на корректных, ❌ с текстом ошибки на испорченных

## INVEST

| | |
|---|---|
| **I** Independent | Не зависит от кода Harness |
| **N** Negotiable | Поля обсуждаем |
| **V** Valuable | Единый контракт для всех компонентов |
| **E** Estimable | Ясный объём |
| **S** Small | 1–2 дня |
| **T** Testable | Тесты валидатора |

## Что проработать

Список открытых вопросов — пройдём отдельно и заполним упущения.

- [ ] Соответствие полям агента в ICPlan (имя, модель, инструкция, тулы, навыки, проекты) — какие поля наши, какие из ICPlan
- [ ] Версионирование схемы (`apiVersion`) и миграции старых определений
- [ ] Как задаются «опасные» тулы для approve — в агенте, в MCP-сервере или в политике
- [ ] Секреты: только ссылки (`secret_ref`), где резолвятся
- [ ] Скилл: формат Anthropic SKILL.md (как в ICPlan) или свой
