## Зачем

Следующий агент должен получать итог предыдущего, а пользователь — понимать, почему агент начал работу.

## Что сделать

- Передача по контракту шага (D20): M3, ссылки на артефакты, предложенные критерии; ссылка на итог
- Запись «агент взял задачу по правилу…» в истории

## Приёмка

- [ ] Процесс из двух шагов с агентами A и B: шаг A успешен → задача на шаге B, задание B содержит ссылку на итог A (R-AP-06 «Смена агента»)
- [ ] Задача на первом шаге без прошлых запусков → задание без ссылки на итог; последний запуск упал → ссылка на итог с пометкой ошибки (R-AP-06 «Первый этап», «Предыдущий запуск упал»)
- [ ] Агент шага A предложил критерий шагу B с `criteria_approval: auto` → критерий у задачи с пометкой «предложено: A» и действует для B; при `review` или проверке шага — ждёт подтверждения до старта B (R-AP-06 «Критерии от предыдущего шага», «Подтверждение на шаге с проверкой»)
- [ ] Итог без обязательного раздела, повторы исчерпаны → `gate_failed` с перечнем; без критериев → «gate не задан» (R-HRN-08 «Gate не пройден», «Критериев нет»)
- [ ] Агент шага пытается изменить критерий своего шага → отказ, событие с причиной (R-HRN-08 «Попытка ослабить критерий»)
- [ ] История задачи: «Агент Y взял задачу: процесс …, шаг …», «Итог: успех → шаг …»; ручное делегирование — «делегировано пользователем» (R-AP-07)

**Как прокликать:** Процесс «Фича» из двух шагов с агентами → создать задачу → задача сама проходит оба шага, в истории видны правила подхвата и переход

## Декомпозиция

Подзадачи по 2–8 часов; каждая проверяема сама по себе.

| 3.2.2 | Запись «агент взял задачу по правилу …» в истории | 4 | событие в истории |
| 3.2.3 | Отображение в UI истории | 3 | видно правило |
