## Зачем

Профиль нагрузки — гипотеза; без замера нельзя выпускать в продуктив и настраивать лимиты.

## Что сделать

- Сценарии k6: UI ICPlan, опрос Runner, события, вызовы LiteLLM (mock)
- Замер `kubectl top`, p95, RPS, ошибки
- Сравнение с профилем, обновление R&D и лимитов

## Приёмка

- [ ] Отчёт: p95 API < 300 мс при 20 RPS
- [ ] Потребление узла записано
- [ ] Профиль в R&D обновлён
- [ ] Нагрузка достигла профиля модуля → потребление в пределах ёмкости узла 8 vCPU / 32 ГБ / 400 ГБ, запуски в очереди не теряются; нагрузка выше профиля → очередь или отказ с причиной, поды не выходят за limits; замер 4.8 → фактические значения записаны и сравнены с профилем (R-ICP-14, R-HRN-14, R-MEM-13, R-REG-11, R-RUN-15, R-SBX-12, R-CP-12, R-GRD-21, R-LLM-12, R-OBS-11, R-MCP-11, R-AP-13)
- [ ] 15 пользователей ICPlan и 4 запуска → p95 API < 300 мс, запуски не теряются; 12 запусков «coder» → лишние в очереди, узел не уходит в нехватку памяти; замер перед продуктивом → p95, RPS и потребление записаны, гипотезы профиля обновлены; больше 6 запусков «coder» или упор в RAM → шаг роста: узел для `itsaplan-agents` с taint (R-INF-01)
- [ ] Пик профиля (~20 RPS, до 6 запусков) → ~13 ГБ RAM и ~5 vCPU в ёмкости узла; нагрузка вдвое выше → поды в limits, предупреждение эксплуатации до отказа; замер 4.8 → значения записаны и сравнены с профилем (R-INF-17)

**Как прокликать:** запустить k6 → отчёт с графиками и сравнением с профилем
