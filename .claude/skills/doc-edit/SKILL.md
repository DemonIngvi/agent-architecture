# Правка документа: по одному, по цепочке

Документы меняются **последовательно**: закончил один — перешёл к следующему по графу связности. Не правь пачкой все места сразу. Порядок и стоп-условия — `docs/rules/agent-workflow.md`.

## Цикл для каждого документа

1. **Место в иерархии:** `python html-view/doctool.py route <файл>` — тип, вкладка, обязательное, источник, методология. Генерируемый файл (`generated <файл>`) — правь его источник.
2. **Методология этого типа:** открой файл из строки «Методология» и прочитай «Из чего состоит», «Как вести», «Чек-лист».
3. **Методология устарела?** Если она молчит о том, что ты меняешь, или противоречит текущему устройству сайта — сначала поправь её. Цепочка методологии: `doctool next docs/rules/<методология>.md` → инструменты (doctool, навыки, хуки), потом документы этого типа.
4. **Факт живёт в одном месте:** значение, поле, конфиг — найди источник (`docs/rules/change-process.md#single-source`), здесь ставь ссылку.
5. **Правка** этого одного документа. Многострочные замены — через Edit или скрипт в файле, не heredoc с обратными слешами (О-14).
6. **Проверка:** `python html-view/doctool.py check`.
7. **Следующий:** `python html-view/doctool.py next <файл>` — документы на концах стрелок, у каждого своя методология. Берёшь их **по одному** и повторяешь цикл с шага 1. Если документ по смыслу не меняется — по его стрелкам дальше не идёшь.

## Когда остановиться и спросить

- нужен выбор продукта, изменение противоречит принятому решению D, удаление или новая вкладка;
- факт неизвестен — не придумывай: код форка, OpenAPI, design; нет — открытый вопрос в спеке.

## Конец цепочки

Очередь пуста → `python html-view/build.py`, `openspec validate <change> --strict` → коммит (хук `pre-commit` проверит). Расхождение по пути — строка в `docs/rules/deviations.md`: что → почему → правило и проверка.

Модели, интеграции, имена — навык `doc-dual-read`; данные — `doc-data`; новое исследование — `doc-rnd`.
