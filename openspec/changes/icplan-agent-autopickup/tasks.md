Только ICPlan (форк `itsaplan`). Формат INVEST: каждая задача независима, ценна сама по себе, проверяема. Сроки — при планировании.

## 0. Уже есть (основа)

- [x] 0.1 Запуск при смене делегата — `enqueueDelegateRun`. **Зачем:** единая точка постановки запуска; все новые правила ставят делегата, а запуск создаётся этим механизмом.
- [x] 0.2 Автоназначение исполнителя на статус — `autoAssignUserId`. **Зачем:** образец поля на колонке и очистки при выходе агента.
- [x] 0.3 Тул `update_issue` у агента. **Уточнено:** для задачи в процессе колонку меняет ICPlan по итогу запуска (6.2, 6.3); агент меняет остальные поля.

## 1. Агент шага процесса

- [ ] 1.1 Агент у шага процесса (`process_step.agent_id`, проверка, что агент — участник проекта). **Зачем:** шаг процесса = колонка + агент; без агента шаг ручной. **Приёмка:** интеграционный тест: шаг с агентом сохраняется, с не-участником — 400.
- [ ] 1.2 При входе задачи в колонку шага ставить делегата — агента шага и запуск; ручной шаг снимает делегата. **Зачем:** ключевой сценарий «задача вошла в шаг — агент взял». **Приёмка:** тест: перевод задачи создаёт запуск агента шага.
- [ ] 1.3 UI: редактор процесса в настройках проекта (шаги, агенты, переходы). **Зачем:** пользователь настраивает процесс сам. **Приёмка:** Настройки проекта → Процессы: процесс сохраняется.

## 2. Тип задачи задаёт процесс

- [ ] 2.1 Связь тип задачи → процесс (не более одного процесса на тип). **Зачем:** разные типы — разные процессы. **Приёмка:** тест сохранения.
- [ ] 2.2 Создание задачи типа или смена типа → первый шаг процесса; активный запуск прежнего шага отменяется. **Зачем:** задача сразу идёт по процессу. **Приёмка:** тест: создание задачи типа создаёт запуск агента первого шага.

## 3. Эффект Действия «делегировать агенту» (T-04)

- [ ] 3.1 Новый тип эффекта `delegate_agent` в `actions`. **Зачем:** условия сложнее шага процесса (метка, поле). **Приёмка:** тест: действие по метке создаёт запуск.
- [ ] 3.2 UI: выбор агента в редакторе действий. **Приёмка:** агенты доступны в списке эффекта.

## 4. Правила и надёжность

- [ ] 4.1 Приоритет (R-AP-04): явный делегат → агент шага процесса → эффект Действия. **Зачем:** предсказуемость, когда правил несколько. **Приёмка:** тест на конфликт шага и Действия.
- [ ] 4.2 Защита от дублей: не ставить запуск при активном запуске агента по задаче. **Зачем:** нет двойной работы и трат. **Приёмка:** тест двойного перевода.
- [ ] 4.3 Очистка ссылок на агента в шагах процессов и Действиях при выходе агента из проекта (R-AP-08); шаг становится ручным. **Зачем:** без висящих правил. **Приёмка:** тест снятия проекта у агента.

## 5. Передача между этапами и видимость

- [ ] 5.1 В задание запуска добавлять передачу предыдущего шага по контракту D20 (M3, ссылки на артефакты, предложенные критерии) и ссылку на итог. **Зачем:** следующий агент продолжает, а не начинает с нуля. **Приёмка:** тест: промпт содержит ссылку на комментарий предыдущего агента.
- [ ] 5.2 Запись в истории задачи «агент взял задачу по правилу …». **Зачем:** пользователь понимает, почему агент начал работу. **Приёмка:** событие видно в истории.

## 6. Процесс: переходы по итогу и очередь агента

- [ ] 6.1 Таблицы `process`, `process_step`; проверка структуры процесса. **Зачем:** тип задачи задаёт процесс, шаг — колонку, агента и переходы (R-AP-15). **Приёмка:** ошибка структуры → 400 с шагом.
- [ ] 6.2 Переход по итогу запуска: успех, ошибка, ожидание, отмена; переход в другой процесс. **Зачем:** задачу переводит ICPlan, а не агент (R-AP-16). **Приёмка:** тест четырёх итогов и смены процесса.
- [ ] 6.3 Лимит запусков на шаге; запрет смены колонки агентом в `update_issue`. **Зачем:** защита от циклов и обхода процесса. **Приёмка:** четвёртый вход при лимите 3 → переход при ошибке.
- [ ] 6.4 Порядок очереди агента при выдаче: приоритет задачи, затем время (R-AP-17). **Приёмка:** срочная задача выдаётся раньше.
