## Переход от задачи к задаче, от агента к агенту

```
┌───────────────┐ задача вошла   ┌──────────────────────┐ delegate  ┌────────────────┐
│ Задача в      ├───────────────▶│ Правило подхвата     ├──────────▶│ Очередь        │
│ статусе S1    │ / создана с    │ 1 явный делегат      │ = агент   │ запусков ICPlan│
└───────▲───────┘ типом T        │ 2 агент статуса S1   │           └───────┬────────┘
        │                        │ 3 агент типа T       │                   │ run
        │                        │ 4 эффект Действия    │                   ▼
        │                        └──────────────────────┘           ┌────────────────┐
        │                                                           │ Агент A        │
        │ update_issue: статус S2                                   │ (Runner или    │
        │ + комментарий/вложения с итогом                           │ внутренний)    │
        │                                                           └───────┬────────┘
┌───────┴───────┐ задача вошла в S2 → правило → агент B                     │
│ Задача в      │◀──────────────────────────────────────────────────────────┘
│ статусе S2    │  агент B получает ссылки на итог агента A (M2/M3)
└───────────────┘
```

Процесс (какие статусы, типы и агенты) настраивает пользователь в ICPlan, в коде не зашит.

## Что есть / что нет

✅ есть · ⚠️ частично · ❌ нет

| Механизм | ICPlan | Где в коде |
|---|---|---|
| Запуск при смене делегата | ✅ | `issues/service.ts` → `enqueueDelegateRun` |
| Запуск по упоминанию `@агент` | ✅ | `agents/core` |
| Автоназначение исполнителя на статус | ⚠️ только «Исполнитель», без запуска | `columns/service.ts` (`autoAssignUserId`) |
| Агент-делегат на статус | ❌ | — |
| Агент-делегат на тип задачи | ❌ | — |
| Эффект Действия «делегировать агенту» | ❌ (T-04 в AI-агенте) | `actions` |
| Агент сам переводит статус | ✅ тул `update_issue` | `agents/core/runtime/tools/catalog.ts` |
| Передача итога следующему агенту | ⚠️ через комментарии задачи | — |

## Блоки

| Блок | Задача | Нужен? |
|---|---|---|
| Правило подхвата | Определить агента для задачи по приоритету | Да — ядро автоматизации |
| Агент статуса | Этап процесса = статус | Да |
| Агент типа | Тип задачи сразу идёт своему агенту | Да |
| Эффект Действия | Гибкие условия (метка, поле) | Да |
| Защита от дублей | Один активный запуск на задачу и агента | Да |

## Плюсы / минусы по модулям

| Модуль | ➕ | ➖ |
|---|---|---|
| Агент статуса | Процесс видно прямо на доске | Один агент на статус |
| Агент типа | Разные типы — разные исполнители без лишних статусов | Конфликт с агентом статуса — нужен приоритет |
| Эффект Действия | Любые условия | Сложнее отлаживать цепочки |
| Защита от дублей | Нет двойной работы и трат | Нужен явный повторный запуск |
