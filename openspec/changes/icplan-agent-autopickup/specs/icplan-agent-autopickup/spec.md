# Spec Delta

## Purpose

Автоматическая работа задачи по процессу в ICPlan: тип задачи задаёт процесс, шаг процесса — колонку и агента, итог запуска — переход на следующий шаг; агент берёт задачи из своей очереди, чтобы процесс шёл без ручного делегирования. Обоснование: [R&D](../../../../../docs/rnd/autopickup-rules.md).

## ADDED Requirements

### Requirement: Агент шага процесса
Шаг процесса SHALL иметь необязательного агента-исполнителя. Когда задача входит в колонку шага своего процесса, ICPlan SHALL сделать агента делегатом задачи и поставить запуск в очередь агента; шаг без агента — ручной, задача ждёт человека.

#### Scenario: Задача вошла в шаг с агентом
- **WHEN** задачу типа «Фича» переводят в колонку «Анализ», где у шага процесса «Фича» агент «Аналитик»
- **THEN** делегат задачи — «Аналитик», в его очереди появляется запуск

#### Scenario: Ручной шаг
- **WHEN** задача входит в колонку, шаг которой без агента
- **THEN** делегат снимается, запуск не создаётся, исполнитель — по автоназначению колонки

#### Scenario: Агент не участник проекта
- **WHEN** в статусе указан агент, которого убрали из проекта
- **THEN** запуск не создаётся, в истории предупреждение

<a id="r-ap-01"></a>**ID:** `R-AP-01` · **Реализует задача:** [3.1](../../../../../docs/tasks/3.1-icplan-autodelegate-status.md)

### Requirement: Тип задачи задаёт процесс
Тип задачи SHALL быть типом процесса: у типа не более одного процесса. При создании задачи этого типа или смене типа на него ICPlan SHALL поставить задачу в колонку первого шага процесса.

#### Scenario: Создана задача типа
- **WHEN** создаётся задача типа «Исследование», первый шаг процесса — колонка «R&D» с агентом «Ресёрчер»
- **THEN** задача в колонке «R&D», делегат — «Ресёрчер», запуск в очереди

#### Scenario: Смена типа
- **WHEN** тип задачи меняют на тип с процессом
- **THEN** задача переходит на первый шаг нового процесса, активный запуск прежнего шага отменяется

#### Scenario: Тип без процесса
- **WHEN** создаётся задача типа без процесса
- **THEN** работает обычная доска: задача без делегата, переходы вручную

<a id="r-ap-02"></a>**ID:** `R-AP-02` · **Реализует задача:** [3.1](../../../../../docs/tasks/3.1-icplan-autodelegate-status.md)

### Requirement: Эффект Действия «делегировать агенту»
Движок Действий SHALL поддерживать эффект, назначающий агента делегатом задачи.

#### Scenario: Действие по метке
- **WHEN** на задачу ставят метку «нужен ревью» и действие делегирует агенту «Ревьюер»
- **THEN** делегат — «Ревьюер», запуск в очереди

#### Scenario: Условие не выполнено
- **WHEN** метка не поставлена
- **THEN** действие не срабатывает

#### Scenario: Агент отключён
- **WHEN** действие ссылается на отключённого агента
- **THEN** запуск не создаётся, ошибка в истории задачи

<a id="r-ap-03"></a>**ID:** `R-AP-03` · **Реализует задача:** [3.5](../../../../../docs/tasks/3.5-icplan-type-actions-cost.md)

### Requirement: Приоритет правил
При нескольких применимых правилах ICPlan SHALL выбирать агента в порядке: явный делегат в запросе → агент шага процесса → эффект Действия.

#### Scenario: Шаг и Действие
- **WHEN** задача входит в шаг с агентом Y, и Действие по метке даёт агента Z
- **THEN** делегат — Y

#### Scenario: Явный делегат
- **WHEN** пользователь вручную указал делегата при переводе
- **THEN** используется явный делегат, шаг процесса не меняется

#### Scenario: Только Действие
- **WHEN** шаг ручной, Действие даёт агента Z
- **THEN** делегат — Z

<a id="r-ap-04"></a>**ID:** `R-AP-04` · **Реализует задача:** [3.1](../../../../../docs/tasks/3.1-icplan-autodelegate-status.md)

### Requirement: Защита от дублей
ICPlan MUST NOT ставить второй запуск, если у этого агента по этой задаче уже есть запуск в очереди или в работе.

#### Scenario: Повторный вход в статус
- **WHEN** задачу дважды подряд переводят в тот же статус, пока запуск активен
- **THEN** в очереди один запуск

#### Scenario: После завершения
- **WHEN** задачу снова переводят в статус после завершения запуска
- **THEN** создаётся новый запуск

#### Scenario: Разные агенты
- **WHEN** статус и действие дают разных агентов
- **THEN** создаётся запуск только по правилу с высшим приоритетом

<a id="r-ap-05"></a>**ID:** `R-AP-05` · **Реализует задача:** [3.1](../../../../../docs/tasks/3.1-icplan-autodelegate-status.md)

### Requirement: Передача результата следующему этапу
Запуск, созданный автоподхватом, SHALL получать в задании ссылки на итог предыдущего запуска по задаче (комментарий, вложения).

#### Scenario: Смена агента
- **WHEN** агент A перевёл задачу в статус агента B
- **THEN** задание агента B содержит ссылку на итог агента A

#### Scenario: Первый этап
- **WHEN** у задачи нет предыдущих запусков
- **THEN** задание без ссылки на итог

#### Scenario: Предыдущий запуск упал
- **WHEN** последний запуск завершился ошибкой
- **THEN** ссылка ведёт на итог с пометкой ошибки

<a id="r-ap-06"></a>**ID:** `R-AP-06` · **Реализует задача:** [3.2](../../../../../docs/tasks/3.2-icplan-handoff.md)

### Requirement: Видимость подхвата
Каждый автоподхват и каждый переход процесса SHALL записываться в историю задачи с указанием правила (шаг процесса, Действие) и итога запуска.

#### Scenario: Разбор
- **WHEN** пользователь открывает историю задачи
- **THEN** видит «Агент Y взял задачу: процесс "Фича", шаг "Анализ"»

#### Scenario: Переход по итогу
- **WHEN** запуск завершился успешно и задача перешла на следующий шаг
- **THEN** в истории «Итог: успех → шаг "Спецификация"»

#### Scenario: Ручное делегирование
- **WHEN** пользователь назначил делегата сам
- **THEN** запись «делегировано пользователем», без правила

<a id="r-ap-07"></a>**ID:** `R-AP-07` · **Реализует задача:** [3.2](../../../../../docs/tasks/3.2-icplan-handoff.md)

### Requirement: Очистка при выходе агента из проекта
Когда агент перестаёт работать в проекте, ICPlan SHALL снимать его с шагов процессов и Действий этого проекта; такие шаги становятся ручными.

#### Scenario: Агента убрали из проекта
- **WHEN** у агента сняли проект
- **THEN** шаги процессов проекта больше не ссылаются на агента, они ручные

#### Scenario: Агент удалён
- **WHEN** агент удалён из команды
- **THEN** ссылки на него сняты во всех проектах

#### Scenario: Агент остался в проекте
- **WHEN** у агента сняли другой проект
- **THEN** правила этого проекта не меняются

<a id="r-ap-08"></a>**ID:** `R-AP-08` · **Реализует задача:** [3.1](../../../../../docs/tasks/3.1-icplan-autodelegate-status.md)

### Requirement: Определение процесса
Процесс SHALL задаваться в настройках проекта для типа задачи как упорядоченный список шагов. Шаг: колонка проекта, агент (необязательно), переход при успехе (следующий шаг, другой процесс или «завершить»), переход при ошибке (шаг или «остаться»), лимит запусков на шаге. ICPlan MUST NOT сохранять процесс с ошибкой структуры.

#### Scenario: Корректный процесс
- **WHEN** администратор сохраняет процесс «Фича»: R&D (Ресёрчер) → SDD (Аналитик) → Код (Разработчик) → Ревью (человек) → завершить
- **THEN** процесс сохранён, у каждого шага одна колонка и явные переходы

#### Scenario: Ошибка структуры
- **WHEN** переход ведёт на несуществующий шаг, колонка повторяется в процессе или шаг недостижим от первого
- **THEN** сохранение отклонено с указанием шага и причины

#### Scenario: Переход в другой процесс
- **WHEN** у последнего шага процесса «Исследование» переход при успехе — процесс «Фича»
- **THEN** при успехе тип задачи меняется на «Фича», задача встаёт на первый шаг процесса «Фича»

<a id="r-ap-15"></a>**ID:** `R-AP-15` · **Реализует задача:** [3.1](../../../../../docs/tasks/3.1-icplan-autodelegate-status.md)

### Requirement: Переход по итогу запуска
После завершения запуска агента на шаге ICPlan SHALL перевести задачу по итогу: успех — по переходу при успехе; ошибка, лимит или непройденный quality gate — по переходу при ошибке с уведомлением владельца процесса; ожидание ответа — задача остаётся на шаге; отмена человеком — без перехода. Агент MUST NOT менять колонку задачи сам: он возвращает итог, переход делает ICPlan.

#### Scenario: Успех
- **WHEN** агент «Аналитик» на шаге SDD завершил запуск успешно
- **THEN** задача переходит на шаг «Код», делегат — «Разработчик», в его очереди запуск

#### Scenario: Ошибка
- **WHEN** запуск на шаге «Код» упал или не прошёл quality gate
- **THEN** задача — по переходу при ошибке (например, «Нужна помощь»), делегат снят, исполнитель — владелец процесса, уведомление

#### Scenario: Лимит запусков на шаге
- **WHEN** задача входит в шаг «Код» в четвёртый раз при лимите 3
- **THEN** запуск не создаётся, задача — по переходу при ошибке с причиной «лимит шага»

#### Scenario: Агент пытается сменить колонку
- **WHEN** агент вызывает `update_issue` со сменой колонки задачи, которая идёт по процессу
- **THEN** смена колонки отклонена, остальные поля обновлены

<a id="r-ap-16"></a>**ID:** `R-AP-16` · **Реализует задача:** [3.6](../../../../../docs/tasks/3.6-icplan-process-engine.md)

### Requirement: Очередь агента
У каждого агента SHALL быть очередь запусков по всем процессам, где он исполнитель шага. Runner SHALL забирать запуск из головы очереди: порядок — приоритет задачи, затем время постановки; запуск выдаётся одному Runner с арендой, у задачи не более одного активного запуска.

#### Scenario: Порядок очереди
- **WHEN** в очереди агента задача «срочно» поставлена позже задачи «обычный»
- **THEN** Runner получает сначала задачу «срочно»

#### Scenario: Задача уже в работе
- **WHEN** задача уже имеет активный запуск
- **THEN** второй запуск по ней не выдаётся, пока первый не завершён

#### Scenario: Runner пропал с арендой
- **WHEN** Runner взял запуск и перестал отвечать
- **THEN** по истечении аренды запуск снова доступен в голове очереди

<a id="r-ap-17"></a>**ID:** `R-AP-17` · **Реализует задача:** [3.6](../../../../../docs/tasks/3.6-icplan-process-engine.md)

### Requirement: Конфигурация модуля
Модуль SHALL брать свои параметры (9, таблица «Параметры модуля» в `interfaces.md`) с уровней L2 (S1): значение — с самого конкретного уровня. Без обязательного `Модель агента`, `Инструкция агента` модуль MUST NOT стартовать.

#### Scenario: Значение по умолчанию
- **WHEN** `Статусы доски` (этапы процесса) не задан на уровне L2
- **THEN** применяется значение по умолчанию: по проекту

#### Scenario: Нет обязательного параметра
- **WHEN** при старте не задан `Модель агента` (провайдер и модель (алиас))
- **THEN** модуль не стартует, ошибка называет `Модель агента` и уровень L2

#### Scenario: Неверное значение
- **WHEN** `Агент шага процесса` задан неверного типа или вне допустимых значений
- **THEN** модуль не стартует, ошибка называет `Агент шага процесса` и уровень L2

<a id="r-ap-09"></a>**ID:** `R-AP-09` · **Реализует задача:** [3.1](../../../../../docs/tasks/3.1-icplan-autodelegate-status.md)

### Requirement: Хранилища данных
Модуль SHALL хранить и читать свои данные только в S1 (PostgreSQL 17 (CloudNativePG), БД `itsaplan`) (`interfaces.md`); к данным других модулей — только через их API. Секреты MUST NOT храниться в БД и git.

#### Scenario: Запись в своё хранилище
- **WHEN** модуль сохраняет задачи, агенты, `agent_run`, `issue_activity`, статусы, документы
- **THEN** запись попадает в S1 (PostgreSQL 17 (CloudNativePG), БД `itsaplan`)

#### Scenario: S1 недоступно
- **WHEN** S1 (PostgreSQL 17 (CloudNativePG), БД `itsaplan`) не отвечает
- **THEN** операция завершается ошибкой без частичной записи, поведение — по FMEA, событие оператору

#### Scenario: Прямой доступ к чужим данным
- **WHEN** код модуля обращается к таблицам другого модуля
- **THEN** доступа нет: роль БД ограничена своими хранилищами

<a id="r-ap-10"></a>**ID:** `R-AP-10` · **Реализует задача:** [3.1](../../../../../docs/tasks/3.1-icplan-autodelegate-status.md)

### Requirement: Интерфейсы обмена
Интерфейсы модуля (I20, I1) SHALL соблюдать протокол, формат, аутентификацию, таймаут и политику повтора из `interfaces.md`; неидемпотентные вызовы MUST NOT повторяться автоматически.

#### Scenario: Таймаут I1
- **WHEN** ICPlan Run Queue → Agent Runner (I1) не ответил за 10 с
- **THEN** вызов прерывается; повтор: backoff до 60 с

#### Scenario: Аутентификация I20
- **WHEN** собеседник по I20 отклонил учётные данные (сессия пользователя)
- **THEN** вызов не повторяется, событие с причиной

#### Scenario: Повтор I1 без дублей
- **WHEN** вызов I1 повторён после сбоя
- **THEN** дубля нет: аренда запуска: выдаётся одному Runner

<a id="r-ap-11"></a>**ID:** `R-AP-11` · **Реализует задача:** [3.1](../../../../../docs/tasks/3.1-icplan-autodelegate-status.md)

### Requirement: Поведение при отказах зависимостей
Модуль SHALL вести себя при отказах зависимостей по таблице FMEA (`interfaces.md`): отказ обнаруживается, поведение предсказуемо и безопасно (fail-closed для проверок безопасности), восстановление не теряет данные.

#### Scenario: Агент правила не участник проекта
- **WHEN** агент правила не участник проекта
- **THEN** запуск не создаётся, предупреждение в истории

#### Scenario: Очередь недоступна
- **WHEN** очередь недоступна
- **THEN** делегат установлен, запуск ставится повторно

#### Scenario: Цикл переходов статусов
- **WHEN** цикл переходов статусов
- **THEN** защита от дублей + лимит запусков на задачу

<a id="r-ap-12"></a>**ID:** `R-AP-12` · **Реализует задача:** [3.1](../../../../../docs/tasks/3.1-icplan-autodelegate-status.md)

### Requirement: Нагрузка и производительность
Модуль SHALL выдерживать нагрузку профиля (`interfaces.md`, раздел «Нагрузка и развёртывание»): срабатывание правила на каждый перевод статуса (~100 в час в пике); постановка в очередь < 1 с. Превышение профиля MUST приводить к очереди или отказу с причиной, а не к деградации всей платформы.

#### Scenario: Пиковая нагрузка профиля
- **WHEN** нагрузка достигает пика профиля
- **THEN** целевые показатели времени ответа и пропускной способности выполняются

#### Scenario: Превышение профиля
- **WHEN** нагрузка превышает профиль
- **THEN** лишние запросы ждут в очереди или получают отказ с причиной, остальные обслуживаются

#### Scenario: Замер
- **WHEN** выполняется нагрузочный тест
- **THEN** фактические показатели записаны и сравнены с профилем

<a id="r-ap-13"></a>**ID:** `R-AP-13` · **Реализует задача:** [4.8](../../../../../docs/tasks/4.8-load-test.md)

### Requirement: Развёртывание
Модуль SHALL разворачиваться так: часть api / worker ICPlan (`itsaplan-core`). Ресурсы MUST задаваться requests / limits, публичный доступ — только через ingress, если указан.

#### Scenario: Установка
- **WHEN** модуль разворачивается в кластере
- **THEN** объекты созданы в указанном namespace с заданными ресурсами

#### Scenario: Нехватка ресурсов
- **WHEN** узлу не хватает ресурсов для пода модуля
- **THEN** под ждёт размещения, событие для оператора

#### Scenario: Обновление
- **WHEN** выходит новая версия модуля
- **THEN** обновление проходит без потери данных и по правилам Helm-релиза

<a id="r-ap-14"></a>**ID:** `R-AP-14` · **Реализует задача:** [4.6](../../../../../docs/tasks/4.6-k8s-helm-ingress.md)
