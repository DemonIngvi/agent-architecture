# Spec Delta

## Purpose

Автоматическая работа задачи по процессу в ICPlan: тип задачи задаёт процесс, шаг процесса — колонку и агента, итог запуска — переход на следующий шаг; агент берёт задачи из своей очереди, чтобы процесс шёл без ручного делегирования. Обоснование: [R&D](../../../../../docs/rnd/autopickup-rules.md).

## ADDED Requirements

<a id="r-ap-01"></a>
### Requirement: Агент шага процесса
Шаг процесса SHALL иметь необязательного агента-исполнителя. Когда задача входит в колонку шага своего процесса, ICPlan SHALL сделать агента делегатом задачи и поставить запуск в очередь агента; шаг без агента — ручной, задача ждёт человека.

#### Scenario: Задача вошла в шаг с агентом
- **WHEN** задачу типа «Фича» переводят в колонку «Анализ», где у шага процесса «Фича» агент «Аналитик»
- **THEN** делегат задачи — «Аналитик», в его очереди появляется запуск

#### Scenario: Ручной шаг
- **WHEN** задача входит в колонку, шаг которой без агента
- **THEN** делегат снимается, запуск не создаётся, исполнитель — по автоназначению колонки

#### Scenario: Агент не участник проекта
- **WHEN** в шаге процесса указан агент, которого убрали из проекта
- **THEN** запуск не создаётся, в истории предупреждение

**ID:** `R-AP-01` · **Реализует задача:** [3.1](../../../../../docs/tasks/3.1-icplan-process-step-agent.md)

<a id="r-ap-02"></a>
### Requirement: Тип задачи задаёт процесс
Тип задачи SHALL быть типом процесса: у типа не более одного процесса. При создании задачи этого типа или смене типа на него ICPlan SHALL поставить задачу в колонку первого шага процесса.

#### Scenario: Создана задача типа
- **WHEN** создаётся задача типа «Исследование», первый шаг процесса — колонка «R&D» с агентом «Ресёрчер»
- **THEN** задача в колонке «R&D», делегат — «Ресёрчер», запуск в очереди

#### Scenario: Смена типа
- **WHEN** тип задачи меняют на тип с процессом
- **THEN** задача переходит на первый шаг нового процесса, активный запуск прежнего шага отменяется

#### Scenario: Тип без процесса
- **WHEN** создаётся задача типа без процесса
- **THEN** работает обычная доска: задача без делегата, переходы вручную

**ID:** `R-AP-02` · **Реализует задача:** [3.1](../../../../../docs/tasks/3.1-icplan-process-step-agent.md)

<a id="r-ap-03"></a>
### Requirement: Эффект Действия «делегировать агенту»
Движок Действий SHALL поддерживать эффект, назначающий агента делегатом задачи.

#### Scenario: Действие по метке
- **WHEN** на задачу ставят метку «нужен ревью» и действие делегирует агенту «Ревьюер»
- **THEN** делегат — «Ревьюер», запуск в очереди

#### Scenario: Условие не выполнено
- **WHEN** метка не поставлена
- **THEN** действие не срабатывает

#### Scenario: Агент отключён
- **WHEN** Действие ссылается на выключенного агента
- **THEN** запуск не создаётся, ошибка в истории задачи

**ID:** `R-AP-03` · **Реализует задача:** [3.5](../../../../../docs/tasks/3.5-icplan-type-actions-cost.md)

<a id="r-ap-04"></a>
### Requirement: Приоритет правил
При нескольких применимых правилах ICPlan SHALL выбирать агента в порядке: явный делегат в запросе → агент шага процесса → эффект Действия. Явный делегат — выбор пользователя в поле «Делегат» карточки задачи в любой момент или при переводе; при смене делегата активный запуск прежнего агента по задаче MUST отменяться.

#### Scenario: Шаг и Действие
- **WHEN** задача входит в шаг с агентом Y, и Действие по метке даёт агента Z
- **THEN** делегат — Y

#### Scenario: Явный делегат
- **WHEN** пользователь вручную указал делегата при переводе
- **THEN** используется явный делегат, шаг процесса не меняется

#### Scenario: Делегат из карточки без перевода
- **WHEN** пользователь выбрал агента Z в поле «Делегат» карточки, задача стоит на шаге с агентом Y, запуска Y нет
- **THEN** делегат — Z, запуск Z в очереди; колонка и шаг задачи не меняются

#### Scenario: Другой агент посреди шага
- **WHEN** запуск агента шага Y идёт, пользователь выбрал делегатом агента Z
- **THEN** запуск Y отменён (в истории — «отменено пользователем»), запуск Z на том же шаге в очереди

#### Scenario: Делегат — человек
- **WHEN** запуск агента шага идёт, пользователь выбрал делегатом человека
- **THEN** запуск агента отменён, делегат-агент снят, работу ведёт выбранный человек; шаг для этой задачи ручной до следующего входа в шаг

#### Scenario: Итог запуска явного делегата
- **WHEN** запуск явного делегата завершился
- **THEN** итог пишется в задачу, перехода по процессу нет: задача остаётся на шаге, её дальше двигает человек или агент шага при следующем входе

#### Scenario: Только Действие
- **WHEN** шаг ручной, Действие даёт агента Z
- **THEN** делегат — Z

**ID:** `R-AP-04` · **Реализует задача:** [3.1](../../../../../docs/tasks/3.1-icplan-process-step-agent.md)

<a id="r-ap-05"></a>
### Requirement: Защита от дублей
ICPlan MUST NOT ставить второй запуск, если у этого агента по этой задаче уже есть запуск в очереди или в работе.

#### Scenario: Повторный вход в шаг
- **WHEN** задачу дважды подряд переводят в колонку того же шага, пока запуск активен
- **THEN** в очереди один запуск

#### Scenario: После завершения
- **WHEN** задачу снова переводят в колонку шага после завершения запуска
- **THEN** создаётся новый запуск

#### Scenario: Разные агенты
- **WHEN** шаг процесса и Действие дают разных агентов
- **THEN** создаётся запуск только по правилу с высшим приоритетом

**ID:** `R-AP-05` · **Реализует задача:** [3.1](../../../../../docs/tasks/3.1-icplan-process-step-agent.md)

<a id="r-ap-06"></a>
### Requirement: Передача результата следующему этапу
Запуск следующего шага SHALL получать в задании передачу предыдущего (M3: сделано, дальше, ссылки на артефакты, вопросы, предложенные критерии) и ссылку на итог. Предложенные критерии MUST добавляться к задаче с пометкой автора и подтверждаться по `criteria_approval` шага (D20).

#### Scenario: Смена агента
- **WHEN** шаг агента A завершён успешно и ICPlan перевёл задачу на шаг агента B
- **THEN** задание агента B содержит ссылку на итог агента A

#### Scenario: Первый этап
- **WHEN** у задачи нет предыдущих запусков
- **THEN** задание без ссылки на итог

#### Scenario: Предыдущий запуск упал
- **WHEN** последний запуск завершился ошибкой
- **THEN** ссылка ведёт на итог с пометкой ошибки

#### Scenario: Критерии от предыдущего шага
- **WHEN** аналитик в передаче предложил критерий «есть миграция БД» для шага «Код», у шага `criteria_approval: auto`, проверки нет
- **THEN** критерий добавлен с пометкой «предложено: Аналитик» и действует для запуска разработчика

#### Scenario: Подтверждение на шаге с проверкой
- **WHEN** у следующего шага `criteria_approval: review` или включена проверка
- **THEN** предложенный критерий ждёт подтверждения человеком до старта шага

**ID:** `R-AP-06` · **Реализует задача:** [3.2](../../../../../docs/tasks/3.2-icplan-handoff.md)

<a id="r-ap-07"></a>
### Requirement: Видимость подхвата
Каждый автоподхват и каждый переход процесса SHALL записываться в историю задачи с указанием правила (шаг процесса, Действие) и итога запуска.

#### Scenario: Разбор
- **WHEN** пользователь открывает историю задачи
- **THEN** видит «Агент Y взял задачу: процесс "Фича", шаг "Анализ"»

#### Scenario: Переход по итогу
- **WHEN** запуск завершился успешно и задача перешла на следующий шаг
- **THEN** в истории «Итог: успех → шаг "Спецификация"»

#### Scenario: Ручное делегирование
- **WHEN** пользователь назначил делегата сам
- **THEN** запись «делегировано пользователем», без правила

**ID:** `R-AP-07` · **Реализует задача:** [3.2](../../../../../docs/tasks/3.2-icplan-handoff.md)

<a id="r-ap-08"></a>
### Requirement: Очистка при выходе агента из проекта
Когда агент перестаёт работать в проекте, ICPlan SHALL снимать его с шагов процессов и Действий этого проекта; такие шаги становятся ручными. История задач с результатами агента MUST сохраняться.

#### Scenario: Агента убрали из проекта
- **WHEN** у агента сняли проект
- **THEN** шаги процессов проекта больше не ссылаются на агента, они ручные; Действия проекта «делегировать агенту» с ним выключены

#### Scenario: Активные запуски при снятии проекта
- **WHEN** у агента сняли проект, а по задачам этого проекта у него есть запуски в очереди или в работе
- **THEN** интерфейс предупреждает о числе активных запусков; после подтверждения они отменяются, делегат снят, задачи остаются на своих шагах

#### Scenario: История сохраняется
- **WHEN** у агента сняли проект
- **THEN** комментарии, итоги и записи «агент взял / закончил» в истории задач проекта (`issue_activity`) остаются

#### Scenario: Агент удалён
- **WHEN** агент удалён из команды
- **THEN** ссылки на него сняты во всех проектах

#### Scenario: Удаление агента с активными запусками
- **WHEN** администратор удаляет агента, у которого есть активные запуски
- **THEN** интерфейс предупреждает о числе активных запусков; после подтверждения запуски отменяются, шаги процессов с этим агентом становятся ручными, Действия «делегировать агенту» с ним выключаются

#### Scenario: Агент остался в проекте
- **WHEN** у агента сняли другой проект
- **THEN** правила этого проекта не меняются

**ID:** `R-AP-08` · **Реализует задача:** [3.1](../../../../../docs/tasks/3.1-icplan-process-step-agent.md)

<a id="r-ap-15"></a>
### Requirement: Определение процесса
Процесс SHALL задаваться в настройках проекта для типа задачи как упорядоченный список шагов. Шаг: колонка проекта, агент (необязательно), переход при успехе (следующий шаг, другой процесс или «завершить»), переход при ошибке (шаг или «остаться»), лимит запусков на шаге. ICPlan MUST NOT сохранять процесс с ошибкой структуры. Шаг MAY задавать «результат шага», «готовность шага» и `criteria_approval` (`auto` / `review` / `always`) — контракт шага (D20).

#### Scenario: Корректный процесс
- **WHEN** администратор сохраняет процесс «Фича»: R&D (Ресёрчер) → SDD (Аналитик) → Код (Разработчик) → Ревью (человек) → завершить
- **THEN** процесс сохранён, у каждого шага одна колонка и явные переходы

#### Scenario: Ошибка структуры
- **WHEN** переход ведёт на несуществующий шаг, колонка повторяется в процессе или шаг недостижим от первого
- **THEN** сохранение отклонено с указанием шага и причины

#### Scenario: Переход в другой процесс
- **WHEN** у последнего шага процесса «Исследование» переход при успехе — процесс «Фича»
- **THEN** при успехе тип задачи меняется на «Фича», задача встаёт на первый шаг процесса «Фича»

#### Scenario: Готовность шага
- **WHEN** у шага «SDD» задана готовность «есть разделы Проблема, Требования, Критерии»
- **THEN** этот критерий получает каждая задача на шаге с пометкой «процесс», без чек-листа человека

#### Scenario: Декомпозиция — дочерние задачи
- **WHEN** агенту шага нужно разбить задачу на части
- **THEN** он создаёт дочерние задачи тулом `create_issue`, у каждой свой тип и свой процесс; сам процесс задач не создаёт

#### Scenario: Один переход при успехе
- **WHEN** администратор задаёт шагу два перехода при успехе
- **THEN** сохранение отклонено: параллельные работы делаются дочерними задачами

**ID:** `R-AP-15` · **Реализует задача:** [3.1](../../../../../docs/tasks/3.1-icplan-process-step-agent.md)

<a id="r-ap-16"></a>
### Requirement: Переход по итогу запуска
После завершения запуска агента на шаге ICPlan SHALL перевести задачу по итогу: успех — по переходу при успехе; ошибка, лимит или непройденный quality gate — по переходу при ошибке с уведомлением владельца процесса; ожидание ответа — задача остаётся на шаге; отмена человеком — без перехода. Агент MUST NOT менять колонку задачи сам: он возвращает итог, переход делает ICPlan.

#### Scenario: Успех
- **WHEN** агент «Аналитик» на шаге SDD завершил запуск успешно
- **THEN** задача переходит на шаг «Код», делегат — «Разработчик», в его очереди запуск

#### Scenario: Ошибка
- **WHEN** запуск на шаге «Код» упал или не прошёл quality gate
- **THEN** задача — по переходу при ошибке (например, «Нужна помощь»), делегат снят, исполнитель — владелец процесса, уведомление

#### Scenario: Лимит запусков на шаге
- **WHEN** задача входит в шаг «Код» в четвёртый раз при лимите 3
- **THEN** запуск не создаётся, задача — по переходу при ошибке с причиной «лимит шага»

#### Scenario: Агент пытается сменить колонку
- **WHEN** агент вызывает `update_issue` со сменой колонки задачи, которая идёт по процессу
- **THEN** смена колонки отклонена, остальные поля обновлены

#### Scenario: Ждёт ответа
- **WHEN** запуск на шаге завершился итогом «ждёт ответа» (вопрос пользователю или approve)
- **THEN** задача остаётся в шаге, исполнитель получает уведомление, запуск продолжается после ответа

#### Scenario: Отменено пользователем
- **WHEN** пользователь отменил запуск на шаге
- **THEN** перехода нет, делегат снят, в истории задачи — «отменено пользователем»

**ID:** `R-AP-16` · **Реализует задача:** [3.6](../../../../../docs/tasks/3.6-icplan-process-engine.md)

<a id="r-ap-17"></a>
### Requirement: Очередь агента
У каждого агента SHALL быть очередь запусков по всем процессам, где он исполнитель шага. Runner SHALL забирать запуск из головы очереди: порядок — приоритет задачи, затем время постановки; запуск выдаётся одному Runner с арендой, у задачи не более одного активного запуска.

#### Scenario: Порядок очереди
- **WHEN** в очереди агента задача «срочно» поставлена позже задачи «обычный»
- **THEN** Runner получает сначала задачу «срочно»

#### Scenario: Задача уже в работе
- **WHEN** задача уже имеет активный запуск
- **THEN** второй запуск по ней не выдаётся, пока первый не завершён

#### Scenario: Runner пропал с арендой
- **WHEN** Runner взял запуск и перестал отвечать
- **THEN** по истечении аренды запуск снова доступен в голове очереди

**ID:** `R-AP-17` · **Реализует задача:** [3.6](../../../../../docs/tasks/3.6-icplan-process-engine.md)

<a id="r-ap-18"></a>
### Requirement: Проверка пользователем перед переходом
Шаг процесса SHALL иметь настройку «нужна проверка», а задача — флаг «проверять со мной» для всех её шагов. После успешного запуска на таком шаге ICPlan SHALL оставить задачу на шаге в состоянии «ждёт проверки», уведомить исполнителя и MUST NOT переводить задачу до вердикта.

#### Scenario: Шаг с проверкой
- **WHEN** агент шага «SDD» с настройкой «нужна проверка» завершил запуск успешно
- **THEN** задача остаётся на шаге «SDD» в состоянии «ждёт проверки», исполнителю уведомление

#### Scenario: Флаг на задаче
- **WHEN** у задачи включён флаг «проверять со мной», шаг без проверки
- **THEN** после каждого успешного шага задача ждёт вердикта

#### Scenario: Нет вердикта
- **WHEN** вердикта нет дольше `review_reminder_hours`
- **THEN** повторное уведомление, задача не двигается

**ID:** `R-AP-18` · **Реализует задача:** [3.7](../../../../../docs/tasks/3.7-icplan-task-control.md)

<a id="r-ap-19"></a>
### Requirement: Вердикт по результату
Исполнитель или владелец процесса SHALL выносить вердикт по результату шага: «принято» — ICPlan выполняет переход при успехе; «не выполнено» с обязательной заметкой — новый запуск того же шага, заметка в задании. Возврат MUST учитываться в лимите запусков шага. Ревьюер (агент или человек) MAY добавить критерий при возврате; он сохраняется с пометкой автора (D20).

#### Scenario: Принято
- **WHEN** пользователь отметил результат шага «Код» как «принято»
- **THEN** задача переходит по переходу при успехе

#### Scenario: Не выполнено
- **WHEN** пользователь отметил «не выполнено» с заметкой «нет тестов»
- **THEN** новый запуск агента шага «Код», заметка в задании и в истории задачи

#### Scenario: Лимит возвратов
- **WHEN** возврат превышает лимит запусков шага
- **THEN** переход при ошибке с причиной «лимит шага», уведомление владельцу процесса

#### Scenario: Нет прав
- **WHEN** вердикт выносит не исполнитель и не владелец процесса
- **THEN** действие недоступно

#### Scenario: Ревьюер добавил критерий
- **WHEN** агент-ревьюер возвращает задачу «не выполнено» и добавляет критерий «покрыть тестами»
- **THEN** критерий добавлен с пометкой «ревьюер», следующий запуск исполнителя проверяется и по нему

**ID:** `R-AP-19` · **Реализует задача:** [3.7](../../../../../docs/tasks/3.7-icplan-task-control.md)

<a id="r-ap-20"></a>
### Requirement: Остановка и возобновление процесса по задаче
Пользователь SHALL останавливать процесс по задаче: активный запуск отменяется, входы в шаги не создают запусков, ручные переводы разрешены. Возобновление SHALL запускать агента текущего шага. Остановленная задача MUST быть видна в сводке и истории.

#### Scenario: Остановка
- **WHEN** пользователь остановил процесс задачи во время запуска на шаге «Код»
- **THEN** запуск отменён, Runner узнаёт об отмене по heartbeat, новые запуски не создаются

#### Scenario: Ручной перевод
- **WHEN** остановленную задачу перевели в колонку шага с агентом
- **THEN** запуск не создаётся, в истории «процесс остановлен»

#### Scenario: Возобновление
- **WHEN** пользователь возобновил процесс
- **THEN** запуск агента текущего шага

**ID:** `R-AP-20` · **Реализует задача:** [3.7](../../../../../docs/tasks/3.7-icplan-task-control.md)

<a id="r-ap-21"></a>
### Requirement: Повтор шага
Пользователь SHALL повторять шаг (новый запуск того же шага с итогом прошлого запуска в контексте) и перезапускать задачу с выбранного шага (обычный вход в шаг). Повтор сверх лимита запусков шага MUST быть доступен только владельцу процесса и сбрасывать счётчик шага.

#### Scenario: Повтор после ошибки
- **WHEN** шаг «Код» завершился ошибкой, пользователь нажал «повторить шаг»
- **THEN** новый запуск агента шага, итог ошибки в задании

#### Scenario: С выбранного шага
- **WHEN** пользователь выбрал «начать с шага SDD»
- **THEN** задача в колонке шага SDD, запуск его агента, счётчики следующих шагов сброшены

#### Scenario: Лимит исчерпан
- **WHEN** лимит запусков шага исчерпан, повтор просит исполнитель
- **THEN** повтор недоступен, предложение обратиться к владельцу процесса

**ID:** `R-AP-21` · **Реализует задача:** [3.7](../../../../../docs/tasks/3.7-icplan-task-control.md)

<a id="r-ap-22"></a>
### Requirement: Изменение процесса
Изменение процесса SHALL создавать новую версию, действующую для новых переходов; активные запуски доделываются на шаге, где начались. Удаление шага, на котором стоят задачи, MUST требовать указать шаг, куда их перенести (как сопоставление статусов при публикации workflow).

#### Scenario: Новая версия
- **WHEN** администратор изменил переход шага «Код» при задачах в работе
- **THEN** задачи после текущего шага идут по новой версии

#### Scenario: Удаление шага с задачами
- **WHEN** администратор удаляет шаг, на котором стоят 3 задачи
- **THEN** сохранение требует выбрать шаг для переноса; без выбора не сохраняется

#### Scenario: Активный запуск на изменённом шаге
- **WHEN** агент шага изменён во время запуска
- **THEN** запуск доделывает прежний агент, следующий вход — новый

**ID:** `R-AP-22` · **Реализует задача:** [3.7](../../../../../docs/tasks/3.7-icplan-task-control.md)

<a id="r-ap-23"></a>
### Requirement: Триггеры запуска ICPlan
ICPlan SHALL ставить запуск агента в очередь при: назначении делегатом (с задержкой `delegation_delay_sec`), упоминании в комментарии, срабатывании расписания агента, изменении поля-триггера, ручном запуске. Автоназначение колонки SHALL менять только исполнителя и MUST NOT создавать запуск. Это базовое поведение ICPlan, на нём строится процесс.

#### Scenario: Делегирование
- **WHEN** пользователь назначил агента делегатом задачи
- **THEN** через `delegation_delay_sec` запуск доступен раннеру, триггер `delegation`

#### Scenario: Упоминание
- **WHEN** в комментарии упомянут агент
- **THEN** запуск с триггером `mention`, ответ — в ветке комментария

#### Scenario: Автоназначение колонки
- **WHEN** задача вошла в колонку с автоназначением человека
- **THEN** исполнитель сменён, запуск не создаётся

**ID:** `R-AP-23` · **Реализует задача:** ✅ есть в ICPlan (базовое поведение)

<a id="r-ap-09"></a>
### Requirement: Конфигурация модуля
Модуль SHALL брать свои параметры (10, таблица «Параметры модуля» в `interfaces.md`) с уровней L2 (S1), L3 (S1), L0 (S9): значение — с самого конкретного уровня; значение вне границ «Мин»–«Макс» таблицы MUST отклоняться с ошибкой, называющей параметр и границы. Изменение настройки SHALL действовать со следующего запуска; обязательные поля MUST проверяться при сохранении.

#### Scenario: Значение по умолчанию
- **WHEN** `step.agent` (агент шага (пусто — ручной шаг)) не задан в настройках
- **THEN** применяется значение по умолчанию: нет

#### Scenario: Выше максимума
- **WHEN** `step.max_runs` задан больше 10
- **THEN** значение отклонено, ошибка называет `step.max_runs` и границы 1–10

#### Scenario: Нет обязательного поля
- **WHEN** настройку сохраняют без `process.issue_type`
- **THEN** сохранение отклонено, ошибка называет `process.issue_type`

**ID:** `R-AP-09` · **Реализует задача:** [3.1](../../../../../docs/tasks/3.1-icplan-process-step-agent.md)

<a id="r-ap-10"></a>
### Requirement: Хранилища данных
Модуль SHALL хранить свои данные только в S1 (PostgreSQL 17 (CloudNativePG), БД `itsaplan`) (`interfaces.md`). Секреты MUST NOT храниться в БД и git.

#### Scenario: Запись в своё хранилище
- **WHEN** модуль сохраняет процессы и шаги (`process`, `process_step`), флаги задач, Действия,…
- **THEN** запись попадает в S1 (PostgreSQL 17 (CloudNativePG), БД `itsaplan`)

#### Scenario: S1 недоступно
- **WHEN** S1 (PostgreSQL 17 (CloudNativePG), БД `itsaplan`) не отвечает
- **THEN** итог не принимается и остаётся у Runner, который повторяет отправку (R-ICP-13); переход по итогу выполняется, когда итог принят

#### Scenario: Доступ вне своих хранилищ
- **WHEN** код icplan-agent-autopickup обращается к таблицам вне S1
- **THEN** доступа нет: роль БД icplan-agent-autopickup ограничена S1

**ID:** `R-AP-10` · **Реализует задача:** [3.1](../../../../../docs/tasks/3.1-icplan-process-step-agent.md)

<a id="r-ap-11"></a>
### Requirement: Интерфейсы обмена
Интерфейсы модуля (I20, I1) SHALL соблюдать протокол, формат, аутентификацию, таймаут и политику повтора из `interfaces.md`; неидемпотентные вызовы MUST NOT повторяться автоматически.

#### Scenario: Таймаут I1
- **WHEN** ICPlan Run Queue → Agent Runner (I1) не ответил за 10 с
- **THEN** вызов прерывается; повтор: backoff до 60 с

#### Scenario: Права по I20
- **WHEN** пользователь без права изменения меняет процессы и шаги (`process`, `process_step`), флаги задач, Действия, история переходов
- **THEN** API ICPlan отклоняет запрос (403), данные не меняются, событие в журнале

#### Scenario: Повтор I1 без дублей
- **WHEN** вызов I1 повторён после сбоя
- **THEN** дубля нет: аренда запуска: выдаётся одному Runner

**ID:** `R-AP-11` · **Реализует задача:** [3.1](../../../../../docs/tasks/3.1-icplan-process-step-agent.md)

<a id="r-ap-12"></a>
### Requirement: Поведение при отказах зависимостей
Модуль SHALL вести себя при отказах зависимостей по таблице FMEA (`interfaces.md`): отказ обнаруживается, поведение предсказуемо и безопасно (fail-closed для проверок безопасности), восстановление не теряет данные.

#### Scenario: Агент правила не участник проекта
- **WHEN** агент правила не участник проекта
- **THEN** запуск не создаётся, предупреждение в истории

#### Scenario: Очередь недоступна
- **WHEN** постановка запуска в очередь не удалась
- **THEN** делегат установлен, worker ICPlan повторяет постановку с backoff до 60 с (как повторы I1), не более 5 попыток; не удалось — запись в истории задачи «запуск не поставлен» и уведомление владельцу процесса

#### Scenario: Восстановление после неудачной постановки
- **WHEN** 5 попыток постановки не удались, очередь снова доступна
- **THEN** сам запуск не ставится: владелец процесса или исполнитель нажимает «повторить шаг» (R-AP-21), создаётся один запуск; попытка постановки не считается в `step.max_runs`

#### Scenario: Цикл переходов
- **WHEN** задача входит в шаг в (`step.max_runs` + 1)-й раз
- **THEN** запуск не создаётся, задача — по переходу при ошибке с причиной «лимит шага», уведомление владельцу процесса

**ID:** `R-AP-12` · **Реализует задача:** [3.1](../../../../../docs/tasks/3.1-icplan-process-step-agent.md)

### Requirement: Нагрузка и производительность
Модуль SHALL выдерживать профиль нагрузки (`interfaces.md`, «Нагрузка и развёртывание»): срабатывание правила на каждый перевод статуса (~100 в час в пике); постановка в очередь < 1 с. Превышение профиля MUST приводить к очереди или отказу с причиной, а не к деградации всей платформы.

#### Scenario: Пик профиля
- **WHEN** нагрузка достигает профиля: срабатывание правила на каждый перевод статуса (~100 в час в пике)
- **THEN** выполняется: постановка в очередь < 1 с

#### Scenario: Превышение профиля
- **WHEN** нагрузка вдвое выше профиля (срабатывание правила на каждый перевод статуса (~100 в час в пике))
- **THEN** API ICPlan отвечает отказом с причиной на лишние запросы, интерфейс пользователей не деградирует

#### Scenario: Замер
- **WHEN** нагрузочный тест 4.8 на профиле «срабатывание правила на каждый перевод статуса (~100 в час в пике)»
- **THEN** фактические значения (постановка в очередь < 1 с) записаны и сравнены с профилем

**ID:** `R-AP-13` · **Реализует задача:** [4.8](../../../../../docs/tasks/4.8-load-test.md)

### Requirement: Развёртывание
Модуль SHALL разворачиваться так: часть api / worker ICPlan (`itsaplan-core`). Ресурсы MUST задаваться requests / limits, версии образов — закреплены; публичный доступ — только через ingress, если он указан.

#### Scenario: Установка в составе ICPlan
- **WHEN** разворачивается релиз ICPlan (часть api / worker ICPlan (`itsaplan-core`)) с модулем icplan-agent-autopickup
- **THEN** миграции icplan-agent-autopickup применены до старта `api`, модуль доступен в ICPlan

#### Scenario: Обновление
- **WHEN** выходит новая версия форка ICPlan с изменениями icplan-agent-autopickup
- **THEN** миграции icplan-agent-autopickup обратно совместимы, `api` обновляется по одной реплике без простоя

#### Scenario: Откат
- **WHEN** версия с изменениями icplan-agent-autopickup не прошла проверки готовности
- **THEN** Helm откатывает ревизию, данные icplan-agent-autopickup сохранены

**ID:** `R-AP-14` · **Реализует задача:** [4.6](../../../../../docs/tasks/4.6-k8s-helm-ingress.md)
