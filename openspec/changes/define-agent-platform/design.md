# Design

## Context

Проект новый, кода нет. Мотивация и состав — см. proposal.md, требования — specs/. Верхнеуровневая схема — `architecture.md` в корне проекта.

Принятые решения по стеку: sandbox — Docker с переходом на K8s; харнес — LangGraph; Runner и Control Plane — Go, Harness — Python; память — Postgres + отдельная векторная БД.

## Goals / Non-Goals

**Goals:**
- Агент собирается из конфига Registry без кода.
- Все вызовы LLM — только через LiteLLM.
- Абстракция sandbox, позволяющая сменить Docker на K8s без изменения спек.
- Guardrails в 4 точках из одного источника правил.

**Non-Goals:**
- Планирование и выбор агента (это ICPlan).
- Прямое взаимодействие агентов друг с другом.
- UI в первой итерации (сначала API + CLI).

## Decisions

R&D по каждому решению: [docs/rnd](../../../docs/rnd/README.md).

### D1. Sandbox: тёплый пул + одноразовое использование, Docker за интерфейсом `SandboxProvider`
Runner работает с интерфейсом `create / claim / exec / destroy`; первая реализация — Docker, следующая — K8s Pod. По каждому профилю держится пул из N запущенных sandbox; запуск забирает готовый, после запуска sandbox уничтожается, пул доливается (подход Copilot coding agent, E2B, Daytona).
- Альтернативы: контейнер на запуск без пула (2–10 с старта), контейнер на агента (запуски видят друг друга), контейнер на задачу (ресурсы заняты в простое), microVM (сильнее изоляция, сложнее) — можно добавить как провайдера.
- Ориентиры ресурсов: harness 150–300 МБ RAM, агент-разработчик 0.5–2 ГБ, CPU почти не нужен (ожидание LLM).

### D2. Harness: LangGraph (Python) внутри sandbox — подтверждено
Агентский цикл — граф LangGraph: `context → llm → tools → context`. Hooks (G2) реализуются как узлы/обёртки графа до и после `llm` и `tools`. LLM-клиент настроен на endpoint LiteLLM (OpenAI-совместимый API).
- Альтернативы ([R&D v3.1](../../../docs/rnd/harness-framework.md), 11.10.2026): OpenAI Agents SDK (запасной: пауза через `RunState`, сравнение прототипом в 1.3.9), PydanticAI, Google ADK, Microsoft Agent Framework, Claude Agent SDK (формат Anthropic, CLI в образе), Hermes Agent (готовый агент: заменил бы Runner, Sandbox, Memory, Guardrails), свой минимальный цикл (всё писать самим).
- Почему LangGraph: `interrupt` для approve (G2), checkpointer в Postgres для возобновления, стрим шагов для таймлайна. Версию фиксируем, LangGraph держим за своим интерфейсом harness.
- Следствие: скиллы и MCP подключаем сами — MCP через `langchain[mcp]` (`langchain.mcp`; архивный `langchain-mcp-adapters` перенесён туда), скилл = промпт-фрагмент + набор тулов.

### D3. Go для Runner, TypeScript для Platform module (в ICPlan), Python для Harness
Go — долгоживущий Runner, конкурентность, работа с Docker/K8s API. Platform module — модуль форка ICPlan на его стеке. Python — экосистема LLM (LangGraph, LiteLLM, MCP).
- Граница: Runner ↔ Harness по gRPC или HTTP + поток событий; Harness — образ контейнера.
- Альтернатива: всё на Python — проще, но слабее для Runner под нагрузкой.

### D4. Хранилища
| Данные | Хранилище |
|---|---|
| Определения агентов, версии, данные guardrails, профили | БД ICPlan (Postgres), Platform module — отдельная схема |
| Запуски, статусы, события запуска | БД ICPlan |
| M1 сессионная, M2 эпизодическая, M3 задачная, M5 процедурная | БД ICPlan |
| M6 организационная | Документы ICPlan |
| M4 семантическая (после MVP, вместе с RAG) | pgvector в Postgres ICPlan |
| Логика guardrails (Rego) | git |

Права и TTL памяти проверяет Memory Service, агенты не ходят в БД напрямую.
- Пересмотрено: Qdrant заменён на pgvector — расширение уже установлено в Postgres ICPlan, меньше компонентов; отдельный движок — по данным нагрузки.

### D5. LLM Gateway — LiteLLM Proxy
Алиасы моделей, virtual keys на агента (лимиты, бюджеты), fallback; callbacks в Langfuse — после MVP. G4 — guardrail-хуки LiteLLM (PII-маскирование, модерация, детект injection).

### D6. Guardrail Policy
Движок решений G1 и G2 — OPA (Apache 2.0, CNCF): логика (Rego) в git с тестами `opa test`, данные (allowlist, лимиты) в БД ICPlan. Каждая точка G1–G4 включается и выключается в конфиге деплоя (`guardrails.gN.enabled`), режим отказа движка — `on_engine_error: deny | allow`. Точки применения: G1 — проверяет сам Runner; G2 — передаются в Harness при старте; G3 — транслируются в параметры контейнера и egress-прокси; G4 — в конфиг virtual key LiteLLM.

### D7. Сеть и секреты (G3)
Sandbox в изолированной сети; исходящий трафик только через egress-прокси с allowlist. Секреты подставляет прокси, в контейнер не передаются.

### D8. Контракт ICPlan
Agent Runner работает как внешний раннер ICPlan: опрашивает очередь запусков по ключу агента и стримит результат обратно (протокол `@itsaplan/runner`). Прежний вариант `POST /runs` (push) заменён — см. `add-icplan-integration`.

### D9. Хранение конфигурации
Источник правды — БД ICPlan; версии определений агента; экспорт/импорт YAML для ревью и переноса между окружениями. Наши настройки — Platform module в ICPlan. Альтернатива (Config Repo в git, проект AI-агент) отклонена: два источника правды и синхронизация с UI.

### D10. MCP или прямой вызов
Гибрид по правилам R1–R7 (`architecture.md`, раздел «MCP или прямой вызов»): решает модель — тул; тул для нескольких агентов или с секретом — MCP; детерминированное, пакетное и внутреннее — прямой вызов; админ-функции — отдельные MCP по уровню доверия.

### D11. Рабочие данные
Workspace эфемерный; код — ветка `agent/<KEY>` + PR; документы и артефакты — в задачу ICPlan (RustFS, S3 API); M2/M3 — БД. Доступ к репозиториям — allowlist агента и короткоживущий токен на запуск через прокси. Общая папка на хосте (проект AI-агент) отклонена: изоляция и масштабирование.

### D12. Observability
MVP — таблица событий запуска в БД ICPlan → таймлайн в задаче. Langfuse — после MVP (тяжёлый self-host: Postgres + ClickHouse + Redis + S3). Prometheus / Grafana / Loki — в бэклоге.

### D14. Очередь и планирование запусков
Альтернативы ([R&D v3.1](../../../docs/rnd/runner-and-scheduling.md), 11.10.2026): Hatchet (ключи параллельности CEL — вторая очередь и новый сервис), River Pro (лимиты по аргументам — платно), Temporal (кластер), Kueue (квоты ресурсов — на этапе 4, лимит модели остаётся у нас).
Очередь запусков — в ICPlan; Agent Runner забирает запуски и решает, когда стартовать, планировщиком со слотами (вариант B): запуск стартует, только когда свободны все его слоты — глобальный (`global_max`), агента (`parallel`, `max`), модели (`models.<alias>.max`), задачи (`per_issue: 1`). Режим `scheduling.mode: sequential | parallel` переключает всю платформу. Порядок `fifo | priority`. Несколько экземпляров Runner делят слоты через блокировку в Postgres. Сравнение вариантов A/B/C — [R&D](../../../docs/rnd/runner-and-scheduling.md).

### D15. Развёртывание и инфраструктура
k3s на одном узле; namespaces `itsaplan-core`, `itsaplan-data`, `itsaplan-agents`, `itsaplan-platform`; Helm-чарты с `existingSecret`; Traefik (в k3s) — ingress и TLS, админки без ingress; Service — балансировка по репликам; PostgreSQL 17 + pgvector под CloudNativePG с пулером PgBouncer (transaction); RustFS (S3) для вложений и копий; бэкап вне узла; NetworkPolicy по списку интерфейсов. Локально — compose (этапы 1–2) и k3d. Отклонены: ingress-nginx и MinIO (архивированы). R&D: [Kubernetes](../../../docs/rnd/kubernetes-runtime.md), [ingress](../../../docs/rnd/ingress-and-balancing.md), [СУБД](../../../docs/rnd/data-stores.md).

### D16. Профиль нагрузки
Базовые гипотезы: 15 одновременных пользователей, ~20 RPS на API ICPlan (p95 < 300 мс), до 6 запусков в очереди и 4 активных, ~1 RPS и ~55 тыс. токенов/мин к LiteLLM; узел 8 vCPU / 32 ГБ / 400 ГБ. Подтверждаются нагрузочным тестом (задача 4.8). R&D: [профиль нагрузки](../../../docs/rnd/load-profile.md).

### D13. RAG
Не в MVP: документы — через `get_document`, код — агентный поиск. RAG (pgvector + локальный эмбеддер) — механизм чтения M4/M6, вводится по мере роста корпуса.

## Risks / Trade-offs

- [Тёплый пул постоянно занимает ресурсы] → размер пула — параметр профиля, 1–2 на старте.
- [LangGraph не даёт готовых skills/hooks] → тонкий собственный слой поверх графа, покрыть тестами.
- [Два языка] → чёткий контракт Runner↔Harness (proto/OpenAPI), контрактные тесты.
- [Модуль в форке ICPlan расходится с upstream] → отдельная схема БД и отдельный модуль кода.
- [LiteLLM как единая точка отказа] → несколько реплик, health-check.
- [Hooks в Harness можно обойти при компрометации sandbox] → критичные проверки дублируются в G3/G4.

## Migration Plan

Не применимо — новый проект. Переход Docker → K8s: новая реализация `SandboxProvider`, переключение конфигом.

## Open Questions

- Формат событий для ICPlan (webhook или брокер) — уточняется при интеграции, на спеки не влияет.
- Конкретный движок human approval (G2) — UI/мессенджер — решается при появлении UI.

### D19. Проверка тулов вне sandbox и зависимости проекта

Закрывает вопросы Q-MCP-01 и Q-SBX-01 по исследованию ([R&D MCP](../../../docs/rnd/mcp-vs-direct.md), [R&D рабочего пространства](../../../docs/rnd/agent-workspace.md)).

| Вопрос | Решение | Почему |
|---|---|---|
| Где проверять allowlist тулов и G2 для MCP | **MCP-прокси Agent Runner**: Harness ходит к MCP только через Runner (`/runs/:id/mcp/:server`, I9); Runner фильтрует `tools/list` и проверяет `tools/call` по allowlist манифеста запуска, вызывает G2 в OPA (I10) и подставляет учётные данные сервера из Secret. Sandbox к MCP-серверам напрямую не ходит; egress-прокси ключ агента к MCP не подставляет | проверка вне недоверенной среды; у Runner уже есть манифест, токен запуска, подтверждения и клиент OPA; нового сервиса нет; MCP ~1 RPS; официальный MCP SDK для Go (v1.8.0). Шлюзы (ContextForge, agentgateway) потребовали бы настройки на каждый запуск и нового сервиса |
| Как агенту ставить зависимости проекта | **Шаг подготовки**: до старта агента Runner выполняет `setup.script` проекта в контейнере подготовки в сети `sbx-setup`, где Squid пускает к `setup.registries`; результат кэшируется по хешу lock-файлов (`setup.cache_ttl_h`) и подключается в `/workspace/.deps`. Среда агента к реестрам не ходит; секреты приватных реестров — только в шаге подготовки | как Codex (скрипт подготовки, секреты только в нём) и Copilot (шаги подготовки вне firewall агента); Squid умеет списки доменов по подсети источника; канал утечки через реестры закрыт |
| Этап 1 (без Runner) | Harness подключается к MCP напрямую только в разработке (CLI, mock) | Runner появляется на этапе 2 |
