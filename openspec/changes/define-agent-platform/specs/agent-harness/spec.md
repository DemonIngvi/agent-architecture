# Spec Delta

## Purpose

Рантайм внутри sandbox, который выполняет агентский цикл (контекст → LLM → тул → результат) и навязывает агенту правила платформы через hooks и policy. Обоснование: [R&D](../../../../../docs/rnd/harness-framework.md).

## ADDED Requirements

### Requirement: Инициализация из определения агента
Harness SHALL собирать агента из определения: системный промпт, скиллы, доступные тулы/MCP, профиль памяти, лимиты.

#### Scenario: Старт агента
- **WHEN** Agent Runner запускает Harness с определением агента и задачей
- **THEN** агенту доступны только тулы и скиллы из его определения

#### Scenario: Битое определение
- **WHEN** определение агента не проходит схему
- **THEN** Harness не стартует цикл и завершает запуск с ошибкой `invalid_definition`

#### Scenario: Скилл недоступен
- **WHEN** скилл из определения не найден
- **THEN** запуск завершается с ошибкой и именем отсутствующего скилла

<a id="r-hrn-01"></a>**ID:** `R-HRN-01` · **Реализует задача:** [1.3](../../../../../docs/tasks/1.3-harness-core.md)

### Requirement: Агентский цикл
Harness SHALL повторять цикл «вызов LLM → выполнение запрошенных тулов → передача результатов в контекст» до завершения, лимита или ошибки.

#### Scenario: Вызов тула
- **WHEN** LLM возвращает запрос вызова тула
- **THEN** Harness выполняет тул и передаёт результат в следующий вызов LLM

#### Scenario: Ответ без тулов
- **WHEN** модель вернула финальный ответ без вызова тулов
- **THEN** цикл завершается, итог передаётся дальше

#### Scenario: Несколько тулов за шаг
- **WHEN** модель запросила два тула в одном ответе при `model.parallel_tool_calls: true`
- **THEN** оба проходят G2 по очереди и выполняются, результаты возвращаются в одном следующем шаге; при `false` (по умолчанию) модель запрашивает по одному

<a id="r-hrn-02"></a>**ID:** `R-HRN-02` · **Реализует задача:** [1.3](../../../../../docs/tasks/1.3-harness-core.md)

### Requirement: Вызов LLM только через шлюз
Harness MUST вызывать модели только через LLM Gateway.

#### Scenario: Прямой вызов провайдера
- **WHEN** код в sandbox пытается обратиться к провайдеру LLM напрямую
- **THEN** вызов недоступен (заблокирован сетью sandbox)

#### Scenario: Вызов через шлюз
- **WHEN** Harness вызывает модель по алиасу
- **THEN** запрос уходит в LiteLLM с ключом агента

#### Scenario: Шлюз недоступен
- **WHEN** LiteLLM не отвечает
- **THEN** повтор с задержкой; после лимита ошибок — завершение `failed`

<a id="r-hrn-03"></a>**ID:** `R-HRN-03` · **Реализует задача:** [1.3](../../../../../docs/tasks/1.3-harness-core.md)

### Requirement: Hooks
Harness SHALL предоставлять точки расширения: before/after LLM call, before/after tool call, on_stop. Hook SHALL иметь возможность модифицировать или отклонить действие.

#### Scenario: Отклонение тула хуком
- **WHEN** hook `before_tool` отклоняет вызов
- **THEN** тул не выполняется, агент получает сообщение об отказе

#### Scenario: Hook изменил аргументы
- **WHEN** hook `before_tool` нормализует путь в аргументах
- **THEN** тул вызывается с изменёнными аргументами, изменение видно в событии

#### Scenario: Ошибка в hook
- **WHEN** hook упал с исключением
- **THEN** действие отклоняется (fail-closed), запуск получает событие об ошибке hook

<a id="r-hrn-04"></a>**ID:** `R-HRN-04` · **Реализует задача:** [1.5](../../../../../docs/tasks/1.5-harness-hooks-approve.md)

### Requirement: Пауза и возобновление
Harness SHALL уметь приостановить запуск на подтверждение человека (G2) или вопрос пользователю, сохранить состояние и продолжить с того же шага после ответа; после падения процесса запуск SHALL возобновляться с последнего сохранённого шага.

#### Scenario: Подтверждение действия
- **WHEN** hook G2 требует подтверждения
- **THEN** запуск ждёт, после подтверждения продолжает с того же шага без повтора предыдущих

#### Scenario: Падение процесса
- **WHEN** процесс Harness упал посреди запуска
- **THEN** новый процесс продолжает с последнего сохранённого шага

#### Scenario: Истёк таймаут ожидания
- **WHEN** подтверждение не пришло за `approval_timeout`
- **THEN** действие считается отклонённым, запуск продолжается без него или завершается по политике

<a id="r-hrn-05"></a>**ID:** `R-HRN-05` · **Реализует задача:** [1.5](../../../../../docs/tasks/1.5-harness-hooks-approve.md)

### Requirement: Стрим шагов
Harness SHALL отдавать события каждого шага (вызов LLM, тула, результат) по мере выполнения.

#### Scenario: Таймлайн
- **WHEN** агент вызвал тул
- **THEN** событие о вызове доступно Observability до завершения запуска

#### Scenario: Порядок событий
- **WHEN** события пришли с задержкой
- **THEN** получатель упорядочивает их по `seq`

#### Scenario: Потребитель недоступен
- **WHEN** Runner временно не принимает события
- **THEN** Harness буферизует их и дошлёт, не теряя шагов

<a id="r-hrn-06"></a>**ID:** `R-HRN-06` · **Реализует задача:** [1.3](../../../../../docs/tasks/1.3-harness-core.md)

### Requirement: Управление контекстом
Harness SHALL удерживать контекст в пределах окна модели, сжимая историю и подгружая память по профилю агента.

#### Scenario: Переполнение контекста
- **WHEN** история превышает порог окна модели
- **THEN** старая часть истории сжимается, ключевые факты сохраняются

#### Scenario: Короткая история
- **WHEN** история меньше порога
- **THEN** сжатие не выполняется

#### Scenario: Сжатие невозможно
- **WHEN** даже после сжатия контекст не помещается
- **THEN** запуск завершается `limit` с причиной `context_overflow`

<a id="r-hrn-07"></a>**ID:** `R-HRN-07` · **Реализует задача:** [1.6](../../../../../docs/tasks/1.6-harness-limits-context.md)

### Requirement: Quality gate результата
Если у задачи заданы критерии приёмки, Harness SHALL проверять итог перед завершением: формат и обязательные поля — детерминированно (кодом); смысловое соответствие — опциональным валидатором. Результат проверки MUST записываться в итог; при провале — повтор до N раз или завершение со статусом `gate_failed`.

#### Scenario: Gate пройден
- **WHEN** итог содержит все обязательные разделы из критериев
- **THEN** запуск завершается `succeeded`, в итоге отметка «gate пройден»

#### Scenario: Gate не пройден
- **WHEN** в итоге нет обязательного раздела и повторы исчерпаны
- **THEN** запуск завершается `gate_failed` с перечнем непрошедших критериев

#### Scenario: Критериев нет
- **WHEN** у задачи нет критериев приёмки
- **THEN** gate пропускается, в итоге отметка «gate не задан»

<a id="r-hrn-08"></a>**ID:** `R-HRN-08` · **Реализует задача:** [1.6](../../../../../docs/tasks/1.6-harness-limits-context.md)

### Requirement: Завершение
Harness SHALL завершаться с причиной `done`, `limit`, `gate_failed` или `error` и передавать результат в Agent Runner.

#### Scenario: Достигнут лимит шагов
- **WHEN** агент превысил максимальное число шагов
- **THEN** Harness останавливается с причиной `limit` и частичным результатом

#### Scenario: Успешное завершение
- **WHEN** агент вернул итог
- **THEN** статус `done`, итог передан Runner

#### Scenario: Ошибка модели
- **WHEN** модель возвращает ошибку после всех повторов
- **THEN** статус `error` с причиной и частичным итогом

<a id="r-hrn-09"></a>**ID:** `R-HRN-09` · **Реализует задача:** [1.6](../../../../../docs/tasks/1.6-harness-limits-context.md)

### Requirement: Указания пользователя в цикле
Harness SHALL принимать сообщения пользователя от Runner во время цикла и добавлять их в контекст на следующем шаге; во время вызова тула — после его завершения. Сообщение «стоп» MUST завершать цикл с итогом сделанного.

#### Scenario: Указание
- **WHEN** во время работы пришло сообщение «используй pytest»
- **THEN** на следующем шаге сообщение в контексте, в событиях «учтено»

#### Scenario: Во время тула
- **WHEN** сообщение пришло во время вызова тула
- **THEN** учитывается после завершения тула

#### Scenario: Стоп
- **WHEN** пришло сообщение «стоп»
- **THEN** цикл завершается со статусом `done` и итогом сделанного

<a id="r-hrn-16"></a>**ID:** `R-HRN-16` · **Реализует задача:** [3.8](../../../../../docs/tasks/3.8-agent-chat-control.md)

### Requirement: Рабочее пространство в контексте агента
Harness SHALL давать агенту описание рабочего пространства из `RunBundle` (пути, источники, права) и ограничивать файловые и git-тулы путями `/workspace`. В конце запуска Harness SHALL перечислять в `RunResult` опубликованные артефакты: файлы выгруженных папок, ветку и PR.

#### Scenario: Описание в контексте
- **WHEN** запуск стартовал с манифестом из двух источников
- **THEN** агент видит пути и права в контексте

#### Scenario: Путь вне workspace
- **WHEN** агент вызывает файловый тул с путём вне `/workspace`
- **THEN** вызов отклонён с причиной

#### Scenario: Итог
- **WHEN** агент завершил работу
- **THEN** `RunResult` содержит список артефактов: файлы, ветку, PR

#### Scenario: Новые зависимости
- **WHEN** агент изменил lock-файл и вызвал тул `install_dependencies`
- **THEN** Runner повторяет шаг подготовки (D19), `/workspace/.deps` обновлён, цикл продолжается

<a id="r-hrn-17"></a>**ID:** `R-HRN-17` · **Реализует задача:** [1.4](../../../../../docs/tasks/1.4-harness-mcp-tools.md)

### Requirement: Сборка запроса к модели
Harness SHALL собирать запрос к модели из слоёв в порядке: системный промпт платформы → руководство проекта → инструкция и навыки агента → описание тулов и рабочего пространства → контекст памяти → задание запуска → указания пользователя. Параметры модели SHALL браться из таблицы параметров (`model.*`); нижний слой MUST NOT отменять правила системного промпта платформы.

#### Scenario: Порядок слоёв
- **WHEN** стартует запуск агента с руководством проекта и двумя навыками
- **THEN** запрос содержит слои по порядку, у каждого в событиях указан источник и версия

#### Scenario: Попытка отменить правила
- **WHEN** инструкция агента или текст задачи требует игнорировать правила платформы
- **THEN** правила системного промпта платформы действуют, событие «конфликт слоёв»

#### Scenario: Параметр не поддерживается моделью
- **WHEN** у модели нет режима размышлений, а `model.reasoning_effort` задан
- **THEN** LiteLLM отбрасывает параметр (`drop_params`), событие с именем параметра

#### Scenario: Размышления в бюджете
- **WHEN** модель вернула токены размышлений
- **THEN** они учитываются в бюджете запуска и затратах; текст размышлений в события не пишется, если `events.level` не «всё»

<a id="r-hrn-18"></a>**ID:** `R-HRN-18` · **Реализует задача:** [1.3](../../../../../docs/tasks/1.3-harness-core.md)

### Requirement: Конфигурация модуля
Модуль SHALL брать свои параметры (18, таблица «Параметры модуля» в `interfaces.md`) с уровней L2 (S1), L0 (S9): значение — с самого конкретного уровня; значение вне границ «Мин»–«Макс» таблицы MUST отклоняться с ошибкой, называющей параметр и границы.

#### Scenario: Значение по умолчанию
- **WHEN** `model.temperature` (температура выборки) не задан в конфигурации
- **THEN** применяется значение по умолчанию: 0.2

#### Scenario: Выше максимума
- **WHEN** `model.temperature` задан больше 1.0
- **THEN** значение отклонено, ошибка называет `model.temperature` и границы 0–1.0

#### Scenario: Граница от другого параметра
- **WHEN** `limits.max_tokens` задан больше, чем потолок `budget.per_run_tokens` L0
- **THEN** значение отклонено: `limits.max_tokens` не может быть больше потолок `budget.per_run_tokens` L0

<a id="r-hrn-10"></a>**ID:** `R-HRN-10` · **Реализует задача:** [1.2](../../../../../docs/tasks/1.2-agent-definition-yaml.md), [1.3](../../../../../docs/tasks/1.3-harness-core.md), [2.8](../../../../../docs/tasks/2.8-config-storage-interfaces-fmea.md)

### Requirement: Хранилища данных
Harness MUST NOT хранить данные постоянно: рабочие файлы SHALL писаться в S10 среды запуска (владелец — Sandbox), состояние цикла — через API Runner в S5 (I12). Секреты MUST NOT храниться в файлах и контексте.

#### Scenario: Состояние цикла
- **WHEN** Harness сохраняет состояние после шага
- **THEN** checkpoint уходит в Runner по I12 и пишется в S5; на диске среды его нет

#### Scenario: Перезапуск процесса
- **WHEN** процесс Harness перезапустился в той же среде
- **THEN** состояние восстанавливается из checkpoint Runner, а не из файлов

#### Scenario: Файлы результата
- **WHEN** агент создал файл итога
- **THEN** файл пишется в `/workspace` и перечисляется в `RunResult`, публикацию выполняет Runner

### Requirement: Интерфейсы обмена
Интерфейсы модуля (I7, I8, I9, I10, I11, I12) SHALL соблюдать протокол, формат, аутентификацию, таймаут и политику повтора из `interfaces.md`; неидемпотентные вызовы MUST NOT повторяться автоматически.

#### Scenario: Таймаут I7
- **WHEN** Agent Runner ↔ Harness (I7) не ответил за = `timeout_s`
- **THEN** вызов прерывается; повтор: переподключение с последнего `seq`

#### Scenario: Аутентификация I8
- **WHEN** собеседник по I8 отклонил учётные данные (bearer virtual key (подставляет…)
- **THEN** вызов не повторяется, событие с причиной

#### Scenario: Неидемпотентный вызов I9
- **WHEN** вызов I9 (Harness → MCP-серверы) прервался сбоем сети
- **THEN** автоматического повтора нет, решение принимает вызывающий

### Requirement: Поведение при отказах зависимостей
Модуль SHALL вести себя при отказах зависимостей по таблице FMEA (`interfaces.md`): отказ обнаруживается, поведение предсказуемо и безопасно (fail-closed для проверок безопасности), восстановление не теряет данные.

#### Scenario: LiteLLM недоступен
- **WHEN** litellm недоступен
- **THEN** повтор с backoff; после `circuit.max_errors` — `failed`

#### Scenario: MCP-сервер недоступен
- **WHEN** mcp-сервер недоступен
- **THEN** ошибка тула возвращается агенту, цикл продолжается

#### Scenario: Checkpointer недоступен
- **WHEN** checkpointer недоступен
- **THEN** пауза на approve невозможна — опасные действия отклоняются

#### Scenario: Memory API недоступен
- **WHEN** memory api недоступен
- **THEN** запуск идёт без M3/M2, событие-предупреждение

### Requirement: Нагрузка и производительность
Модуль SHALL выдерживать профиль нагрузки (`interfaces.md`, «Нагрузка и развёртывание»): шаг цикла 5–20 с; ~0.1 RPS к LiteLLM на запуск; до 200 тыс. токенов на запуск. Превышение профиля MUST приводить к очереди или отказу с причиной, а не к деградации всей платформы.

#### Scenario: Пик профиля
- **WHEN** нагрузка достигает профиля: шаг цикла 5–20 с
- **THEN** выполняется: до 200 тыс. токенов на запуск

#### Scenario: Превышение профиля
- **WHEN** нагрузка вдвое выше профиля (шаг цикла 5–20 с)
- **THEN** лишние вызовы ждут в очереди или получают отказ с причиной, активные запуски не страдают

#### Scenario: Замер
- **WHEN** нагрузочный тест 4.8 на профиле «шаг цикла 5–20 с»
- **THEN** фактические значения (до 200 тыс. токенов на запуск) записаны и сравнены с профилем

<a id="r-hrn-14"></a>**ID:** `R-HRN-14` · **Реализует задача:** [4.8](../../../../../docs/tasks/4.8-load-test.md)

### Requirement: Развёртывание
Модуль SHALL разворачиваться так: процесс внутри контейнера sandbox, образ `ghcr.io/demoningvi/agent-agent-harness:<версия>`; ресурсы — профиль sandbox. Образ закреплён по версии и digest, контейнер создаёт Runner на каждый запуск; ресурсы MUST задаваться профилем sandbox.

#### Scenario: Новый образ
- **WHEN** опубликован новый образ Harness (`HARNESS_IMAGE`)
- **THEN** Runner использует его для новых запусков, активные доделываются на прежнем

#### Scenario: Образ недоступен
- **WHEN** образ Harness не скачивается из реестра
- **THEN** запуск не стартует, статус `failed` с причиной «образ недоступен», событие эксплуатации

#### Scenario: Нехватка ресурсов
- **WHEN** узлу не хватает ресурсов для среды запуска по профилю
- **THEN** запуск ждёт в `queued` до освобождения слотов

<a id="r-hrn-15"></a>**ID:** `R-HRN-15` · **Реализует задача:** [4.6](../../../../../docs/tasks/4.6-k8s-helm-ingress.md)
