# Spec Delta

## Purpose

Единая настраиваемая политика безопасности и ограничений агентов, хранимая в Registry и применяемая в четырёх точках: G1 Admission, G2 Action, G3 Isolation, G4 LLM. Обоснование: [R&D](../../../../../docs/rnd/guardrails-engine.md).

## ADDED Requirements

### Requirement: Единый источник правил
Логика правил SHALL храниться в git (Rego, S8), данные правил агента (allowlist, подтверждения, лимиты) — в Platform module (S2); OPA SHALL получать их бандлом (I16). Каждое правило MUST иметь точку применения (G1–G4).

#### Scenario: Новое правило
- **WHEN** администратор добавляет правило с точкой G2 агенту
- **THEN** правило применяется в следующих запусках этого агента

#### Scenario: Правило без точки
- **WHEN** правило не указывает точку G1–G4
- **THEN** сохранение отклоняется

#### Scenario: Удаление правила
- **WHEN** администратор удаляет правило
- **THEN** следующие запуски проверяются без него

<a id="r-grd-01"></a>**ID:** `R-GRD-01` · **Реализует задача:** [4.3](../../../../../docs/tasks/4.3-guardrails-opa.md)

### Requirement: G1 Admission
До создания sandbox система MUST проверять: допуск агента к задаче/инициатору, бюджет токенов/$, лимит параллельных запусков, kill switch.

#### Scenario: Исчерпан бюджет
- **WHEN** бюджет агента исчерпан
- **THEN** запуск отклоняется со статусом `limit_exceeded`, sandbox не создаётся

#### Scenario: Допуск пройден
- **WHEN** у агента есть бюджет и доступ к задаче
- **THEN** sandbox создаётся, запуск стартует

#### Scenario: Kill switch агента
- **WHEN** для агента включён kill switch
- **THEN** запуск отклоняется до создания sandbox

<a id="r-grd-02"></a>**ID:** `R-GRD-02` · **Реализует задача:** [4.3](../../../../../docs/tasks/4.3-guardrails-opa.md)

### Requirement: G2 Action
Harness MUST проверять каждый вызов тула (allowlist, валидация аргументов), доступ к памяти и итоговый результат; для действий, помеченных опасными, SHALL требоваться подтверждение человека.

#### Scenario: Опасное действие
- **WHEN** агент вызывает тул, помеченный как требующий подтверждения
- **THEN** вызов приостанавливается до подтверждения человеком

#### Scenario: Injection в результате тула
- **WHEN** результат тула содержит признаки prompt injection
- **THEN** результат помечается или фильтруется до передачи в LLM

#### Scenario: Разрешённый тул
- **WHEN** агент вызывает тул из allowlist без пометки опасности
- **THEN** тул выполняется без паузы

<a id="r-grd-03"></a>**ID:** `R-GRD-03` · **Реализует задача:** [4.3](../../../../../docs/tasks/4.3-guardrails-opa.md), [1.5](../../../../../docs/tasks/1.5-harness-hooks-approve.md)

### Requirement: G3 Isolation
Sandbox MUST применять сетевой allowlist, ограничение записи ФС рабочей директорией, лимиты ресурсов и запрет привилегированного режима.

#### Scenario: Запись вне workspace
- **WHEN** агент пытается записать файл вне рабочей директории
- **THEN** запись запрещена

#### Scenario: Запись в workspace
- **WHEN** агент пишет файл в `/workspace`
- **THEN** запись разрешена

#### Scenario: G3 выключен
- **WHEN** в конфиге `g3.enabled: false`
- **THEN** профиль ограничений не применяется, в логе старта — предупреждение

<a id="r-grd-04"></a>**ID:** `R-GRD-04` · **Реализует задача:** [4.2](../../../../../docs/tasks/4.2-egress-repo-access.md)

### Requirement: G4 LLM
LLM Gateway MUST применять allowlist моделей агента, лимиты токенов/$, маскирование PII и секретов во входе, детект jailbreak/injection и модерацию ответа.

#### Scenario: Секрет в промпте
- **WHEN** промпт содержит строку, похожую на ключ API
- **THEN** строка маскируется до отправки провайдеру

#### Scenario: Чистый промпт
- **WHEN** в промпте нет секретов и PII
- **THEN** запрос уходит без изменений

#### Scenario: Модерация ответа
- **WHEN** ответ модели нарушает политику модерации
- **THEN** ответ блокируется, агент получает отказ

<a id="r-grd-05"></a>**ID:** `R-GRD-05` · **Реализует задача:** [4.5](../../../../../docs/tasks/4.5-litellm-budgets-fallback-g4.md)

### Requirement: Включение и выключение точек
Каждая точка G1–G4 SHALL включаться и выключаться независимо конфигурацией деплоя (YAML). Выключенная точка MUST NOT блокировать работу платформы; факт выключения SHALL логироваться при старте.

#### Scenario: G2 выключен
- **WHEN** в конфиге деплоя `guardrails.g2.enabled: false`
- **THEN** Harness не вызывает проверку G2, запуски работают, в логе старта — «G2 disabled»

#### Scenario: Все точки включены
- **WHEN** все `gN.enabled: true`
- **THEN** проверки идут во всех точках

#### Scenario: Неверный конфиг
- **WHEN** в конфиге неизвестная точка `g5`
- **THEN** сервис не стартует с понятной ошибкой

<a id="r-grd-06"></a>**ID:** `R-GRD-06` · **Реализует задача:** [4.3](../../../../../docs/tasks/4.3-guardrails-opa.md)

### Requirement: Движок решений для G1 и G2
Решения G1 и G2 SHALL приниматься движком политик (OPA): логика правил (Rego) хранится в git, данные правил (allowlist, лимиты агента) — в БД ICPlan. При недоступности движка включённая точка MUST отказывать (fail-closed), если в конфиге не задано иное.

#### Scenario: Движок недоступен
- **WHEN** G2 включён, а OPA не отвечает
- **THEN** вызов тула отклоняется с причиной `policy_unavailable`

#### Scenario: Режим allow при сбое
- **WHEN** задано `on_engine_error: allow`, OPA недоступен
- **THEN** вызов разрешается, решение помечается «без проверки»

#### Scenario: Задержка решения
- **WHEN** OPA отвечает медленнее таймаута
- **THEN** считается недоступным, действует `on_engine_error`

<a id="r-grd-07"></a>**ID:** `R-GRD-07` · **Реализует задача:** [4.3](../../../../../docs/tasks/4.3-guardrails-opa.md)

### Requirement: Уровень автономии агента
Агенту SHALL назначаться уровень автономии R0–R5, определяющий политику подтверждений: R0 — только предлагает; R1 — подтверждение каждого действия с записью; R2 — подтверждение опасных действий; R3 — подтверждение только необратимых; R4 — без подтверждений, с аудитом; R5 — полностью сам. Необратимые действия в продуктивной среде MUST требовать подтверждения на любом уровне.

#### Scenario: Агент R2
- **WHEN** агент уровня R2 вызывает тул, помеченный опасным
- **THEN** вызов ждёт подтверждения человека

#### Scenario: Релиз в prod
- **WHEN** агент уровня R5 пытается выполнить релиз в продуктивную среду
- **THEN** действие всё равно ждёт подтверждения

#### Scenario: Агент R4
- **WHEN** агент уровня R4 выполняет опасное, но обратимое действие
- **THEN** действие выполняется без паузы и пишется в аудит

<a id="r-grd-08"></a>**ID:** `R-GRD-08` · **Реализует задача:** [4.3](../../../../../docs/tasks/4.3-guardrails-opa.md), [3.4](../../../../../docs/tasks/3.4-icplan-approve-ui.md)

### Requirement: Защита от зацикливания
Harness MUST останавливать запуск со статусом `limit_exceeded` и причиной `loop_detected`, если агент повторяет один и тот же вызов тула с теми же аргументами больше N раз подряд (по умолчанию 3) или K шагов подряд не меняет состояние задачи (по умолчанию 8). Детерминированная проверка, без LLM.

#### Scenario: Повтор вызова
- **WHEN** агент третий раз подряд вызывает `get_issue` с теми же аргументами
- **THEN** запуск останавливается: статус `limit_exceeded`, причина `loop_detected`, частичный итог сохраняется, в таймлайне — причина

#### Scenario: Разные аргументы
- **WHEN** агент трижды вызывает тул с разными аргументами
- **THEN** это не считается зацикливанием

#### Scenario: Нет прогресса
- **WHEN** 8 шагов подряд состояние задачи не меняется
- **THEN** запуск останавливается: статус `limit_exceeded`, причина `loop_detected`

<a id="r-grd-09"></a>**ID:** `R-GRD-09` · **Реализует задача:** [1.6](../../../../../docs/tasks/1.6-harness-limits-context.md), [4.3](../../../../../docs/tasks/4.3-guardrails-opa.md)

### Requirement: Лимит шагов и времени
Каждый запуск MUST иметь лимит шагов цикла, общего времени и времени простоя (нет событий); при превышении запуск SHALL завершаться со статусом `limit_exceeded`.

#### Scenario: Превышен лимит шагов
- **WHEN** агент сделал `max_steps` шагов и не завершил задачу
- **THEN** запуск завершается со статусом `limit_exceeded` и частичным итогом

#### Scenario: Превышено время
- **WHEN** запуск идёт дольше `timeout_s`
- **THEN** статус `limit_exceeded` с причиной `timeout`

#### Scenario: Простой
- **WHEN** нет событий дольше `idle_s`
- **THEN** запуск останавливается и освобождает слот

<a id="r-grd-10"></a>**ID:** `R-GRD-10` · **Реализует задача:** [1.6](../../../../../docs/tasks/1.6-harness-limits-context.md)

### Requirement: Иерархия бюджетов токенов и денег
Система SHALL ограничивать расход на уровнях: вызов модели (max output tokens), запуск (токены и $), агент в сутки, проект и команда в месяц. При 80% лимита SHALL отправляться предупреждение, при 100% новый вызов или запуск MUST отклоняться (G1 до старта, G4 на каждом вызове).

#### Scenario: Исчерпан дневной бюджет агента
- **WHEN** расход агента за сутки достиг лимита
- **THEN** новые запуски отклоняются со статусом `limit_exceeded`, активный запуск останавливается после текущего шага

#### Scenario: Порог предупреждения
- **WHEN** расход проекта за месяц достиг 80% лимита
- **THEN** администратор получает уведомление, запуски продолжаются

#### Scenario: Превышен бюджет запуска
- **WHEN** запуск потратил лимит токенов
- **THEN** останавливается после текущего шага со статусом `limit_exceeded`

<a id="r-grd-11"></a>**ID:** `R-GRD-11` · **Реализует задача:** [4.5](../../../../../docs/tasks/4.5-litellm-budgets-fallback-g4.md), [4.3](../../../../../docs/tasks/4.3-guardrails-opa.md)

### Requirement: Аномальный расход
Harness SHALL приостанавливать запуск на подтверждение человека, если расход токенов одного шага превышает порог (по умолчанию в 5 раз больше медианы шагов этого запуска или абсолютный предел).

#### Scenario: Скачок расхода
- **WHEN** один шаг потратил в 6 раз больше токенов, чем медиана
- **THEN** запуск переходит в `waiting_approval` с причиной «аномальный расход»

#### Scenario: Обычный шаг
- **WHEN** шаг потратил столько же, сколько медиана
- **THEN** пауза не нужна

#### Scenario: Первые шаги
- **WHEN** медианы ещё нет (меньше 3 шагов)
- **THEN** срабатывает только абсолютный предел

<a id="r-grd-12"></a>**ID:** `R-GRD-12` · **Реализует задача:** [4.3](../../../../../docs/tasks/4.3-guardrails-opa.md)

### Requirement: Circuit breaker на ошибки
Harness MUST останавливать запуск со статусом `failed`, если подряд M вызовов модели или тулов завершились ошибкой (по умолчанию 3); повторы SHALL идти с экспоненциальной задержкой.

#### Scenario: Сервис недоступен
- **WHEN** три вызова MCP подряд вернули ошибку
- **THEN** запуск останавливается с причиной `circuit_open`, а не крутится дальше

#### Scenario: Единичная ошибка
- **WHEN** одна ошибка тула, следующий вызов успешен
- **THEN** счётчик сбрасывается, запуск продолжается

#### Scenario: Повтор с задержкой
- **WHEN** вторая ошибка подряд
- **THEN** следующий вызов идёт с увеличенной задержкой

<a id="r-grd-13"></a>**ID:** `R-GRD-13` · **Реализует задача:** [1.6](../../../../../docs/tasks/1.6-harness-limits-context.md)

### Requirement: Лимиты пропускной способности модели
LLM Gateway SHALL ограничивать запросы и токены в минуту на модель и на агента (RPM / TPM); превышение MUST ставить вызов в ожидание или отклонять, а не передавать провайдеру.

#### Scenario: Превышен TPM модели
- **WHEN** суммарный поток токенов к модели превысил TPM
- **THEN** новые вызовы ждут освобождения окна или отклоняются с ошибкой лимита

#### Scenario: В пределах лимита
- **WHEN** поток токенов ниже TPM
- **THEN** вызовы проходят без задержки

#### Scenario: Лимит агента
- **WHEN** агент превысил свой RPM, модель свободна
- **THEN** вызовы этого агента ждут, другие агенты не затронуты

<a id="r-grd-14"></a>**ID:** `R-GRD-14` · **Реализует задача:** [4.5](../../../../../docs/tasks/4.5-litellm-budgets-fallback-g4.md)

### Requirement: Аварийная остановка
Администратор SHALL иметь kill switch на уровне агента и всей платформы: новые запуски не принимаются, активные останавливаются после текущего шага.

#### Scenario: Остановка платформы
- **WHEN** администратор включил глобальный kill switch
- **THEN** очередь не выдаёт запуски, активные завершаются со статусом `canceled`

#### Scenario: Kill switch агента
- **WHEN** включён kill switch одного агента
- **THEN** останавливаются только его запуски

#### Scenario: Снятие остановки
- **WHEN** администратор выключил kill switch
- **THEN** очередь снова выдаёт запуски

<a id="r-grd-15"></a>**ID:** `R-GRD-15` · **Реализует задача:** [4.3](../../../../../docs/tasks/4.3-guardrails-opa.md)

### Requirement: Аудит срабатываний
Каждое срабатывание guardrail SHALL логироваться с ID точки, правилом, агентом и `run_id`.

#### Scenario: Разбор отказа
- **WHEN** администратор ищет причину отказа в запуске
- **THEN** находит сработавшее правило и точку G1–G4

#### Scenario: Срабатывание в таймлайне
- **WHEN** G2 отклонил тул
- **THEN** в таймлайне задачи событие с точкой, правилом и причиной

#### Scenario: Хранение аудита
- **WHEN** срок хранения событий истёк
- **THEN** агрегаты срабатываний сохраняются

<a id="r-grd-16"></a>**ID:** `R-GRD-16` · **Реализует задача:** [4.3](../../../../../docs/tasks/4.3-guardrails-opa.md), [3.3](../../../../../docs/tasks/3.3-run-events-timeline.md)

### Requirement: Конфигурация модуля
Модуль SHALL брать свои параметры (14, таблица «Параметры модуля» в `interfaces.md`) с уровней L0 (S9), L1 (S2), L0 (S8): значение — с самого конкретного уровня; значение вне границ «Мин»–«Макс» таблицы MUST отклоняться с ошибкой, называющей параметр и границы.

#### Scenario: Значение по умолчанию
- **WHEN** `opa.cache_ttl_s` (кэш решения OPA для одинакового входа в запуске) не задан в конфигурации
- **THEN** применяется значение по умолчанию: 60

#### Scenario: Выше максимума
- **WHEN** `opa.cache_ttl_s` задан больше 300
- **THEN** значение отклонено, ошибка называет `opa.cache_ttl_s` и границы 0–300

#### Scenario: Граница от другого параметра
- **WHEN** `loop.no_progress_steps` задан больше, чем `limits.max_steps`
- **THEN** значение отклонено: `loop.no_progress_steps` не может быть больше `limits.max_steps`

<a id="r-grd-17"></a>**ID:** `R-GRD-17` · **Реализует задача:** [4.3](../../../../../docs/tasks/4.3-guardrails-opa.md)

### Requirement: Хранилища данных
Модуль SHALL хранить свои данные только в S11 (OPA в памяти (bundle)) (`interfaces.md`); данные S2, S8, S9 — доступ только через API или конфигурацию владельца. Секреты MUST NOT храниться в БД и git.

#### Scenario: Запись в своё хранилище
- **WHEN** модуль сохраняет правила и данные для решений
- **THEN** запись попадает в S11 (OPA в памяти (bundle))

#### Scenario: S11 недоступно
- **WHEN** S11 (OPA в памяти (bundle)) не отвечает
- **THEN** по `on_engine_error`: deny (по умолчанию) или allow с пометкой

#### Scenario: Прямой доступ к БД
- **WHEN** код guardrails пытается подключиться к БД платформы напрямую
- **THEN** подключение невозможно: в среде нет учётных данных БД и сетевого доступа к ней

<a id="r-grd-18"></a>**ID:** `R-GRD-18` · **Реализует задача:** [4.3](../../../../../docs/tasks/4.3-guardrails-opa.md)

### Requirement: Интерфейсы обмена
Интерфейсы модуля (I5, I10, I16, I8) SHALL соблюдать протокол, формат, аутентификацию, таймаут и политику повтора из `interfaces.md`; неидемпотентные вызовы MUST NOT повторяться автоматически.

#### Scenario: Таймаут I5
- **WHEN** Agent Runner → OPA (G1) (I5) не ответил за 200 мс
- **THEN** вызов прерывается; повтор: нет → `on_engine_error`

#### Scenario: Аутентификация I16
- **WHEN** собеседник по I16 отклонил учётные данные (токен bundle-сервера)
- **THEN** вызов не повторяется, событие с причиной

#### Scenario: Неидемпотентный вызов I8
- **WHEN** вызов I8 (Harness → LiteLLM) прервался сбоем сети
- **THEN** автоматического повтора нет, решение принимает вызывающий

<a id="r-grd-19"></a>**ID:** `R-GRD-19` · **Реализует задача:** [4.3](../../../../../docs/tasks/4.3-guardrails-opa.md)

### Requirement: Поведение при отказах зависимостей
Модуль SHALL вести себя при отказах зависимостей по таблице FMEA (`interfaces.md`): отказ обнаруживается, поведение предсказуемо и безопасно (fail-closed для проверок безопасности), восстановление не теряет данные.

#### Scenario: OPA недоступен
- **WHEN** opa недоступен
- **THEN** по `on_engine_error`: deny (по умолчанию) или allow с пометкой

#### Scenario: Битый Rego
- **WHEN** битый rego
- **THEN** OPA остаётся на прежнем bundle

#### Scenario: Точка выключена
- **WHEN** точка выключена
- **THEN** проверка не выполняется, запись в лог старта

#### Scenario: Нет данных правил агента
- **WHEN** нет данных правил агента
- **THEN** deny всех тулов кроме явно разрешённых в L0

### Requirement: Нагрузка и производительность
Модуль SHALL выдерживать профиль нагрузки (`interfaces.md`, «Нагрузка и развёртывание»): OPA 1–2 RPS, p95 ≤ 20 мс (D18), таймаут 200 мс; хуки G4 в LiteLLM на каждый вызов. Превышение профиля MUST приводить к очереди или отказу с причиной, а не к деградации всей платформы.

#### Scenario: Пик профиля
- **WHEN** нагрузка достигает профиля: OPA 1–2 RPS
- **THEN** выполняется: p95 ≤ 20 мс (D18)

#### Scenario: Превышение профиля
- **WHEN** нагрузка вдвое выше профиля (OPA 1–2 RPS)
- **THEN** лишние вызовы ждут в очереди или получают отказ с причиной, активные запуски не страдают

#### Scenario: Замер
- **WHEN** нагрузочный тест 4.8 на профиле «OPA 1–2 RPS»
- **THEN** фактические значения (p95 ≤ 20 мс (D18)) записаны и сравнены с профилем

### Requirement: Развёртывание
Модуль SHALL разворачиваться так: OPA — Deployment `opa` в `itsaplan-agents`, 2 реплики, Service ClusterIP; Rego — bundle; без ingress. Ресурсы MUST задаваться requests / limits, версии образов — закреплены; публичный доступ — только через ingress, если он указан.

#### Scenario: Установка
- **WHEN** выполняется `helm install`: OPA — Deployment `opa` в `itsaplan-agents`, 2 реплики, Service ClusterIP; Rego — bundle; без ingress
- **THEN** объекты созданы в своём namespace с заданными requests / limits, проверки готовности зелёные

#### Scenario: Обновление
- **WHEN** выходит новая версия образа `opa` (2 реплики)
- **THEN** `opa` заменяется по одной реплике; работа, начатая на старой версии, доделывается

#### Scenario: Нехватка ресурсов
- **WHEN** узлу не хватает ресурсов для пода `opa`
- **THEN** под `opa` ждёт размещения, событие эксплуатации
