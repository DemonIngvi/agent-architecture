# Spec Delta

## Purpose

Изолированная среда исполнения, создаваемая на каждый запуск агента, чтобы запуски не влияли друг на друга и на хост. Обоснование: [R&D](../../../../../docs/rnd/sandbox-isolation.md).

## ADDED Requirements

### Requirement: Среда на каждый запуск
Система SHALL выделять отдельный sandbox на каждый запуск и MUST NOT переиспользовать его между запусками.

#### Scenario: Два параллельных запуска
- **WHEN** один агент запущен дважды параллельно
- **THEN** у запусков разные sandbox и они не видят файлы друг друга

#### Scenario: Последовательные запуски одного агента
- **WHEN** агент запущен дважды подряд
- **THEN** второй запуск получает новый контейнер без файлов первого

#### Scenario: Повторное использование запрещено
- **WHEN** контейнер вернули после запуска
- **THEN** он уничтожается, а не возвращается в пул

<a id="r-sbx-01"></a>**ID:** `R-SBX-01` · **Реализует задача:** [2.2](../../../../../docs/tasks/2.2-sandbox-docker-oneshot.md)

### Requirement: Тёплый пул
Система SHALL держать по каждому sandbox-профилю заранее запущенные sandbox (размер пула — параметр профиля); запуск SHALL забирать готовый sandbox из пула, а после запуска sandbox MUST уничтожаться, а пул — доливаться.

#### Scenario: Быстрый старт
- **WHEN** в пуле профиля есть свободный sandbox
- **THEN** запуск начинается без создания контейнера, после завершения контейнер уничтожен, в пуле снова N свободных

#### Scenario: Пул пуст
- **WHEN** свободных sandbox в пуле нет
- **THEN** sandbox создаётся заново, запуск ждёт его старта

#### Scenario: Изменён профиль
- **WHEN** в профиле изменён образ
- **THEN** пул пересоздаёт контейнеры с новым образом

<a id="r-sbx-02"></a>**ID:** `R-SBX-02` · **Реализует задача:** [4.1](../../../../../docs/tasks/4.1-sandbox-warm-pool.md)

### Requirement: Эфемерный workspace
Рабочие файлы запуска SHALL лежать в `/workspace` внутри sandbox и MUST уничтожаться вместе с ним; результаты SHALL сохраняться вне sandbox: код — веткой и PR в целевой репозиторий, документы и артефакты — в задачу ICPlan, состояние задачи и лог — в БД.

#### Scenario: После запуска
- **WHEN** запуск завершился
- **THEN** `/workspace` удалён, код в ветке `agent/<KEY>`, артефакты во вложениях задачи

#### Scenario: Агент создал артефакт
- **WHEN** агент сохранил файл-результат
- **THEN** файл загружен во вложения задачи до уничтожения контейнера

#### Scenario: Переполнен диск
- **WHEN** workspace превысил лимит диска
- **THEN** запись отклоняется, запуск получает ошибку

<a id="r-sbx-03"></a>**ID:** `R-SBX-03` · **Реализует задача:** [2.2](../../../../../docs/tasks/2.2-sandbox-docker-oneshot.md), [4.2](../../../../../docs/tasks/4.2-egress-repo-access.md)

### Requirement: Доступ к репозиториям
Sandbox SHALL получать доступ только к репозиториям из allowlist агента с указанным уровнем (read или write); токен MUST быть короткоживущим, выдаваться на запуск и подставляться прокси или credential helper, а не через env. Запись в защищённые ветки MUST быть запрещена.

#### Scenario: Репозиторий вне allowlist
- **WHEN** агент пытается клонировать репозиторий не из allowlist
- **THEN** доступ отклонён

#### Scenario: Push в main
- **WHEN** агент пытается сделать push в защищённую ветку
- **THEN** push отклонён, разрешена только ветка с префиксом агента

#### Scenario: Разрешённый репозиторий
- **WHEN** агент клонирует репозиторий из allowlist
- **THEN** клон в `/workspace` проходит с короткоживущим токеном

<a id="r-sbx-04"></a>**ID:** `R-SBX-04` · **Реализует задача:** [4.2](../../../../../docs/tasks/4.2-egress-repo-access.md)

### Requirement: Профиль sandbox
Параметры sandbox (образ, CPU, RAM, диск, сетевые правила) SHALL задаваться sandbox-профилем из определения агента.

#### Scenario: Тяжёлый агент
- **WHEN** агент ссылается на профиль с увеличенной RAM
- **THEN** его sandbox создаётся с этой RAM

#### Scenario: Превышение памяти
- **WHEN** процесс превысил лимит RAM
- **THEN** контейнер останавливается, запуск получает `failed` с причиной

#### Scenario: Профиль не найден
- **WHEN** агент ссылается на несуществующий профиль
- **THEN** запуск отклоняется до создания контейнера

<a id="r-sbx-05"></a>**ID:** `R-SBX-05` · **Реализует задача:** [2.2](../../../../../docs/tasks/2.2-sandbox-docker-oneshot.md)

### Requirement: Сетевая изоляция
Sandbox MUST разрешать исходящие соединения только к LLM Gateway, Memory Service, разрешённым MCP/тулам и доменам из allowlist профиля.

#### Scenario: Запрещённый домен
- **WHEN** агент обращается к домену вне allowlist
- **THEN** соединение блокируется и событие фиксируется

#### Scenario: Разрешённый хост
- **WHEN** агент обращается к LiteLLM
- **THEN** соединение проходит через egress-прокси

#### Scenario: Прокси недоступен
- **WHEN** egress-прокси не отвечает
- **THEN** исходящие соединения запрещены (fail-closed)

<a id="r-sbx-06"></a>**ID:** `R-SBX-06` · **Реализует задача:** [4.2](../../../../../docs/tasks/4.2-egress-repo-access.md)

### Requirement: Секреты
Секреты MUST NOT передаваться в sandbox в открытом виде; доступ к внешним системам SHALL идти через прокси с подстановкой учётных данных.

#### Scenario: Вызов тула с ключом
- **WHEN** тул обращается к внешнему API
- **THEN** ключ подставляется прокси, агент его не видит

#### Scenario: Секрета нет в env
- **WHEN** агент читает переменные окружения
- **THEN** значений секретов там нет

#### Scenario: Секрет в выводе
- **WHEN** агент пытается вывести заголовок авторизации
- **THEN** прокси не возвращает подставленный секрет агенту

<a id="r-sbx-07"></a>**ID:** `R-SBX-07` · **Реализует задача:** [4.2](../../../../../docs/tasks/4.2-egress-repo-access.md)

### Requirement: Конфигурация модуля
Модуль SHALL брать свои параметры (6, таблица «Параметры модуля» в `interfaces.md`) с уровней L1 (S2), L0 (S9): значение — с самого конкретного уровня, но MUST NOT выше потолка L0. Неверное значение параметра MUST останавливать старт с ошибкой, называющей параметр.

#### Scenario: Значение по умолчанию
- **WHEN** `provider` (docker или K8s) не задан на уровнях выше L0
- **THEN** применяется значение по умолчанию: docker

#### Scenario: Потолок L0
- **WHEN** на уровне L1 `image` задан выше потолка L0
- **THEN** применяется потолок L0, событие в журнал

#### Scenario: Неверное значение
- **WHEN** `resources` задан неверного типа или вне допустимых значений
- **THEN** модуль не стартует, ошибка называет `resources` и уровень L1

<a id="r-sbx-08"></a>**ID:** `R-SBX-08` · **Реализует задача:** [2.2](../../../../../docs/tasks/2.2-sandbox-docker-oneshot.md), [2.8](../../../../../docs/tasks/2.8-config-storage-interfaces-fmea.md)

### Requirement: Хранилища данных
Модуль SHALL хранить и читать свои данные только в S9 (Конфиг деплоя: `values.yaml` (git, без секретов) + Secret / `.env` (вне git)), S10 (`/workspace` в контейнере) (`interfaces.md`); к данным других модулей — только через их API. Секреты MUST NOT храниться в БД и git.

#### Scenario: Запись в своё хранилище
- **WHEN** модуль сохраняет рабочие файлы запуска
- **THEN** запись попадает в S10 (`/workspace` в контейнере)

#### Scenario: S10 недоступно
- **WHEN** S10 (`/workspace` в контейнере) не отвечает
- **THEN** операция завершается ошибкой без частичной записи, поведение — по FMEA, событие оператору

#### Scenario: Прямой доступ к чужим данным
- **WHEN** код модуля обращается к таблицам другого модуля
- **THEN** доступа нет: роль БД ограничена своими хранилищами

<a id="r-sbx-09"></a>**ID:** `R-SBX-09` · **Реализует задача:** [2.2](../../../../../docs/tasks/2.2-sandbox-docker-oneshot.md)

### Requirement: Интерфейсы обмена
Интерфейсы модуля (I6, I7, I17, I18) SHALL соблюдать протокол, формат, аутентификацию, таймаут и политику повтора из `interfaces.md`; неидемпотентные вызовы MUST NOT повторяться автоматически.

#### Scenario: Таймаут I6
- **WHEN** Agent Runner → Docker Engine API (I6) не ответил за 30 с
- **THEN** вызов прерывается; повтор: 1 раз

#### Scenario: Аутентификация I7
- **WHEN** собеседник по I7 отклонил учётные данные (одноразовый токен запуска)
- **THEN** вызов не повторяется, событие с причиной

#### Scenario: Неидемпотентный вызов I6
- **WHEN** вызов I6 (Agent Runner → Docker Engine API) прервался сбоем сети
- **THEN** автоматического повтора нет, решение принимает вызывающий

<a id="r-sbx-10"></a>**ID:** `R-SBX-10` · **Реализует задача:** [2.2](../../../../../docs/tasks/2.2-sandbox-docker-oneshot.md), [4.2](../../../../../docs/tasks/4.2-egress-repo-access.md)

### Requirement: Поведение при отказах зависимостей
Модуль SHALL вести себя при отказах зависимостей по таблице FMEA (`interfaces.md`): отказ обнаруживается, поведение предсказуемо и безопасно (fail-closed для проверок безопасности), восстановление не теряет данные.

#### Scenario: Нет ресурсов хоста
- **WHEN** нет ресурсов хоста
- **THEN** запуск ждёт в `queued`

#### Scenario: Образ недоступен
- **WHEN** образ недоступен
- **THEN** профиль помечен недоступным, запуски отклоняются

#### Scenario: Egress-прокси упал
- **WHEN** egress-прокси упал
- **THEN** исходящий трафик запрещён (fail-closed)

#### Scenario: Переполнен диск workspace
- **WHEN** переполнен диск workspace
- **THEN** запись отклоняется, агент получает ошибку

<a id="r-sbx-11"></a>**ID:** `R-SBX-11` · **Реализует задача:** [2.2](../../../../../docs/tasks/2.2-sandbox-docker-oneshot.md), [4.1](../../../../../docs/tasks/4.1-sandbox-warm-pool.md)

### Requirement: Нагрузка и производительность
Модуль SHALL выдерживать нагрузку профиля (`interfaces.md`, раздел «Нагрузка и развёртывание»): до 6 контейнеров одновременно + пул 2 на профиль; обычный 0.3 ГБ / 0.2 CPU, «coder» 1–2 ГБ / 1–2 CPU. Превышение профиля MUST приводить к очереди или отказу с причиной, а не к деградации всей платформы.

#### Scenario: Пиковая нагрузка профиля
- **WHEN** нагрузка достигает пика профиля
- **THEN** целевые показатели времени ответа и пропускной способности выполняются

#### Scenario: Превышение профиля
- **WHEN** нагрузка превышает профиль
- **THEN** лишние запросы ждут в очереди или получают отказ с причиной, остальные обслуживаются

#### Scenario: Замер
- **WHEN** выполняется нагрузочный тест
- **THEN** фактические показатели записаны и сравнены с профилем

<a id="r-sbx-12"></a>**ID:** `R-SBX-12` · **Реализует задача:** [4.8](../../../../../docs/tasks/4.8-load-test.md)

### Requirement: Развёртывание
Модуль SHALL разворачиваться так: этапы 1–3 — Docker на узле; этап 4 — Pod на запуск в `itsaplan-agents`, NetworkPolicy только к egress-прокси; egress-прокси — Deployment 1 реплика. Ресурсы MUST задаваться requests / limits, публичный доступ — только через ingress, если указан.

#### Scenario: Установка
- **WHEN** модуль разворачивается в кластере
- **THEN** объекты созданы в указанном namespace с заданными ресурсами

#### Scenario: Нехватка ресурсов
- **WHEN** узлу не хватает ресурсов для пода модуля
- **THEN** под ждёт размещения, событие для оператора

#### Scenario: Обновление
- **WHEN** выходит новая версия модуля
- **THEN** обновление проходит без потери данных и по правилам Helm-релиза
