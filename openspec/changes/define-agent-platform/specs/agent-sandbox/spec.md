# Spec Delta

## Purpose

Изолированная среда исполнения, создаваемая на каждый запуск агента, чтобы запуски не влияли друг на друга и на хост. Обоснование: [R&D](../../../../../docs/rnd/sandbox-isolation.md).

## ADDED Requirements

<a id="r-sbx-01"></a>
### Requirement: Среда на каждый запуск
Система SHALL выделять отдельный sandbox на каждый запуск и MUST NOT переиспользовать его между запусками.

#### Scenario: Два параллельных запуска
- **WHEN** один агент запущен дважды параллельно
- **THEN** у запусков разные sandbox и они не видят файлы друг друга

#### Scenario: Последовательные запуски одного агента
- **WHEN** агент запущен дважды подряд
- **THEN** второй запуск получает новый контейнер без файлов первого

#### Scenario: Повторное использование запрещено
- **WHEN** контейнер вернули после запуска
- **THEN** он уничтожается, а не возвращается в пул

**ID:** `R-SBX-01` · **Реализует задача:** [2.2](../../../../../docs/tasks/2.2-sandbox-docker-oneshot.md)

<a id="r-sbx-02"></a>
### Requirement: Тёплый пул
Система SHALL держать по каждому sandbox-профилю заранее запущенные sandbox (размер пула — параметр профиля); запуск SHALL забирать готовый sandbox из пула, а после запуска sandbox MUST уничтожаться, а пул — доливаться.

#### Scenario: Быстрый старт
- **WHEN** в пуле профиля есть свободный sandbox
- **THEN** запуск начинается без создания контейнера, после завершения контейнер уничтожен, в пуле снова N свободных

#### Scenario: Пул пуст
- **WHEN** свободных sandbox в пуле нет
- **THEN** sandbox создаётся заново, запуск ждёт его старта

#### Scenario: Изменён профиль
- **WHEN** в профиле изменён образ
- **THEN** пул пересоздаёт контейнеры с новым образом

**ID:** `R-SBX-02` · **Реализует задача:** [4.1](../../../../../docs/tasks/4.1-sandbox-warm-pool.md)

<a id="r-sbx-03"></a>
### Requirement: Эфемерный workspace
Рабочие файлы запуска SHALL лежать в `/workspace` внутри sandbox и MUST уничтожаться вместе с ним; результаты SHALL сохраняться вне sandbox: код — веткой и PR в целевой репозиторий, документы и артефакты — в задачу ICPlan, состояние задачи и лог — в БД.

#### Scenario: После запуска
- **WHEN** запуск завершился
- **THEN** `/workspace` удалён, код в ветке `agent/<KEY>`, артефакты во вложениях задачи

#### Scenario: Агент создал артефакт
- **WHEN** агент сохранил файл-результат
- **THEN** файл загружен во вложения задачи до уничтожения контейнера

#### Scenario: Переполнен диск
- **WHEN** workspace превысил лимит диска
- **THEN** запись отклоняется, запуск получает ошибку

**ID:** `R-SBX-03` · **Реализует задача:** [2.2](../../../../../docs/tasks/2.2-sandbox-docker-oneshot.md), [4.2](../../../../../docs/tasks/4.2-egress-repo-access.md)

<a id="r-sbx-04"></a>
### Requirement: Доступ к репозиториям
Sandbox SHALL получать доступ только к репозиториям из allowlist агента с указанным уровнем (read или write); токен MUST быть короткоживущим, выдаваться на запуск и подставляться прокси или credential helper, а не через env. Запись в защищённые ветки MUST быть запрещена.

#### Scenario: Репозиторий вне allowlist
- **WHEN** агент пытается клонировать репозиторий не из allowlist
- **THEN** доступ отклонён

#### Scenario: Push в main
- **WHEN** агент пытается сделать push в защищённую ветку
- **THEN** push отклонён, разрешена только ветка с префиксом агента

#### Scenario: Разрешённый репозиторий
- **WHEN** агент клонирует репозиторий из allowlist
- **THEN** клон в `/workspace` проходит с короткоживущим токеном

**ID:** `R-SBX-04` · **Реализует задача:** [4.2](../../../../../docs/tasks/4.2-egress-repo-access.md)

<a id="r-sbx-05"></a>
### Requirement: Профиль sandbox
Параметры sandbox (образ, runtime, CPU, RAM, диск, сетевые правила) SHALL задаваться sandbox-профилем агента из настроек Platform module (`sandbox_profile`, L1).

#### Scenario: Тяжёлый агент
- **WHEN** агент ссылается на профиль с увеличенной RAM
- **THEN** его sandbox создаётся с этой RAM

#### Scenario: Превышение памяти
- **WHEN** процесс превысил лимит RAM
- **THEN** контейнер останавливается, запуск получает `failed` с причиной

#### Scenario: Профиль не найден
- **WHEN** агент ссылается на несуществующий профиль
- **THEN** запуск отклоняется до создания контейнера

#### Scenario: Runtime gVisor
- **WHEN** профиль задаёт `runtime: runsc`, а на узле нет runsc
- **THEN** запуск отклоняется до создания контейнера с причиной «runtime недоступен»

**ID:** `R-SBX-05` · **Реализует задача:** [2.2](../../../../../docs/tasks/2.2-sandbox-docker-oneshot.md)

<a id="r-sbx-06"></a>
### Requirement: Сетевая изоляция
Sandbox MUST разрешать исходящие соединения только к Agent Runner (I7, I12, I9 — MCP через прокси Runner), LLM Gateway (I8), OPA (I10), Memory API (I11) и доменам из allowlist профиля — внешние только через egress-прокси (I17). Реестры пакетов MUST быть доступны только шагу подготовки (сеть `sbx-setup`, D19).

#### Scenario: Запрещённый домен
- **WHEN** агент обращается к домену вне allowlist
- **THEN** соединение блокируется и событие фиксируется

#### Scenario: Разрешённый хост
- **WHEN** агент обращается к LiteLLM
- **THEN** соединение проходит через egress-прокси

#### Scenario: Прокси недоступен
- **WHEN** egress-прокси не отвечает
- **THEN** исходящие соединения запрещены (fail-closed)

#### Scenario: Реестр пакетов из среды агента
- **WHEN** агент из своей среды обращается к `pypi.org`
- **THEN** соединение блокируется; зависимости ставит шаг подготовки

**ID:** `R-SBX-06` · **Реализует задача:** [4.2](../../../../../docs/tasks/4.2-egress-repo-access.md)

<a id="r-sbx-07"></a>
### Requirement: Секреты
Секреты MUST NOT передаваться в sandbox в открытом виде; доступ к внешним системам SHALL идти через прокси с подстановкой учётных данных: внешние хосты — egress-прокси, MCP-серверы — MCP-прокси Runner (D19).

#### Scenario: Вызов тула с ключом
- **WHEN** тул обращается к внешнему API
- **THEN** ключ подставляется прокси, агент его не видит

#### Scenario: Секрета нет в env
- **WHEN** агент читает переменные окружения
- **THEN** значений секретов там нет

#### Scenario: Секрет в выводе
- **WHEN** агент пытается вывести заголовок авторизации
- **THEN** прокси не возвращает подставленный секрет агенту

#### Scenario: Ключ MCP-сервера
- **WHEN** агент вызывает тул MCP-сервера
- **THEN** учётные данные сервера подставляет MCP-прокси Runner, в sandbox их нет

**ID:** `R-SBX-07` · **Реализует задача:** [4.2](../../../../../docs/tasks/4.2-egress-repo-access.md)

<a id="r-sbx-14"></a>
### Requirement: Подключение рабочего пространства по манифесту
Sandbox SHALL подключать источники манифеста в `/workspace/<имя>`: git — клон с короткоживущим токеном и веткой агента; папка — копия из объектного хранилища при старте, своя подпапка шага выгружается обратно в конце запуска. Право read MUST запрещать запись и выгрузку; источник вне манифеста MUST быть недоступен. Модель — D18, зависимости — шаг подготовки D19 ([R&D](../../../../../docs/rnd/agent-workspace.md)).

#### Scenario: Git и папка
- **WHEN** в манифесте репозиторий (write) и папка задачи (read)
- **THEN** репозиторий склонирован в `/workspace/repo`, папка скопирована в `/workspace/task`, запись — только в репозиторий

#### Scenario: Выгрузка папки
- **WHEN** у агента право write на свою подпапку шага
- **THEN** в конце запуска подпапка выгружена в объектное хранилище новой версией

#### Scenario: Нет права записи
- **WHEN** агент пишет в папку с правом read
- **THEN** запись отклонена, выгрузки нет

#### Scenario: Шаг подготовки
- **WHEN** у проекта задан `setup.script`, а кэша для хеша lock-файлов нет
- **THEN** Runner выполняет скрипт в контейнере подготовки с доступом к `setup.registries`; результат подключён в `/workspace/.deps` до старта агента

#### Scenario: Кэш подготовки
- **WHEN** lock-файлы не менялись и кэш моложе `setup.cache_ttl_h`
- **THEN** шаг подготовки пропускается, подключается кэш

**ID:** `R-SBX-14` · **Реализует задача:** [2.2](../../../../../docs/tasks/2.2-sandbox-docker-oneshot.md), [4.2](../../../../../docs/tasks/4.2-egress-repo-access.md)

<a id="r-sbx-08"></a>
### Requirement: Конфигурация модуля
Модуль SHALL брать свои параметры (7, таблица «Параметры модуля» в `interfaces.md`) с уровней L1 (S2), L0 (S9): значение — с самого конкретного уровня; значение вне границ «Мин»–«Макс» таблицы MUST отклоняться с ошибкой, называющей параметр и границы.

#### Scenario: Значение по умолчанию
- **WHEN** `workspace.sources` (источники рабочего пространства запуска: git,…) не задан в конфигурации
- **THEN** применяется значение по умолчанию: нет

#### Scenario: Граница от другого параметра
- **WHEN** `pool.size` задан больше, чем `scheduling.global_max`
- **THEN** значение отклонено: `pool.size` не может быть больше `scheduling.global_max`

#### Scenario: Недопустимое значение
- **WHEN** `resources` задан вне допустимых значений (0,25 CPU, 256 МБ, 1 ГБ … 4 CPU, 8 ГБ, 20 ГБ)
- **THEN** значение отклонено, ошибка называет `resources` и допустимые значения

**ID:** `R-SBX-08` · **Реализует задача:** [2.2](../../../../../docs/tasks/2.2-sandbox-docker-oneshot.md), [2.8](../../../../../docs/tasks/2.8-config-storage-interfaces-fmea.md)

<a id="r-sbx-09"></a>
### Requirement: Хранилища данных
Sandbox SHALL выделять каждому запуску свой диск S10 (`/workspace`) по профилю и MUST уничтожать его вместе со средой; общих томов между запусками MUST NOT быть. Секреты MUST NOT записываться на диск среды.

#### Scenario: Выделение диска
- **WHEN** Runner создаёт среду запуска по профилю `light`
- **THEN** у среды свой `/workspace` размером по профилю, чужих томов нет

#### Scenario: S10 переполнен
- **WHEN** `/workspace` превысил лимит диска профиля sandbox
- **THEN** запись отклоняется, агент получает ошибку тула, запуск продолжается или завершается `limit`

#### Scenario: Уничтожение
- **WHEN** запуск завершён
- **THEN** диск `/workspace` удалён вместе со средой, данные не переходят в следующий запуск

**ID:** `R-SBX-09` · **Реализует задача:** [2.2](../../../../../docs/tasks/2.2-sandbox-docker-oneshot.md)

<a id="r-sbx-10"></a>
### Requirement: Интерфейсы обмена
Интерфейсы модуля (I6, I7, I17, I18) SHALL соблюдать протокол, формат, аутентификацию, таймаут и политику повтора из `interfaces.md`; неидемпотентные вызовы MUST NOT повторяться автоматически.

#### Scenario: Таймаут I6
- **WHEN** Agent Runner → Docker Engine API (I6) не ответил за 30 с
- **THEN** вызов прерывается; повтор: 1 раз

#### Scenario: Аутентификация I7
- **WHEN** собеседник по I7 отклонил учётные данные (одноразовый токен запуска)
- **THEN** вызов не повторяется, событие с причиной

#### Scenario: Неидемпотентный вызов I6
- **WHEN** вызов I6 (Agent Runner → Docker Engine API) прервался сбоем сети
- **THEN** автоматического повтора нет, решение принимает вызывающий

**ID:** `R-SBX-10` · **Реализует задача:** [2.2](../../../../../docs/tasks/2.2-sandbox-docker-oneshot.md), [4.2](../../../../../docs/tasks/4.2-egress-repo-access.md)

<a id="r-sbx-11"></a>
### Requirement: Поведение при отказах зависимостей
Модуль SHALL вести себя при отказах зависимостей по таблице FMEA (`interfaces.md`): отказ обнаруживается, поведение предсказуемо и безопасно (fail-closed для проверок безопасности), восстановление не теряет данные.

#### Scenario: Нет ресурсов хоста
- **WHEN** нет ресурсов хоста
- **THEN** запуск ждёт в `queued`

#### Scenario: Образ недоступен
- **WHEN** образ недоступен
- **THEN** профиль помечен недоступным, запуски отклоняются

#### Scenario: Egress-прокси упал
- **WHEN** egress-прокси упал
- **THEN** исходящий трафик запрещён (fail-closed)

#### Scenario: Переполнен диск workspace
- **WHEN** переполнен диск workspace
- **THEN** запись отклоняется, агент получает ошибку

**ID:** `R-SBX-11` · **Реализует задача:** [2.2](../../../../../docs/tasks/2.2-sandbox-docker-oneshot.md), [4.1](../../../../../docs/tasks/4.1-sandbox-warm-pool.md)

<a id="r-sbx-12"></a>
### Requirement: Нагрузка и производительность
Модуль SHALL выдерживать профиль нагрузки (`interfaces.md`, «Нагрузка и развёртывание»): до 6 контейнеров одновременно + пул 2 на профиль; обычный 0.3 ГБ / 0.2 CPU, «coder» 1–2 ГБ / 1–2 CPU. Превышение профиля MUST приводить к очереди или отказу с причиной, а не к деградации всей платформы.

#### Scenario: Пик профиля
- **WHEN** нагрузка достигает профиля: до 6 контейнеров одновременно + пул 2 на профиль
- **THEN** выполняется: профиль выдерживается без ошибок

#### Scenario: Превышение профиля
- **WHEN** нагрузка вдвое выше профиля (до 6 контейнеров одновременно + пул 2 на профиль)
- **THEN** лишние вызовы ждут в очереди или получают отказ с причиной, активные запуски не страдают

#### Scenario: Замер
- **WHEN** нагрузочный тест 4.8 на профиле «до 6 контейнеров одновременно + пул 2 на профиль»
- **THEN** фактические значения (профиль выдерживается без ошибок) записаны и сравнены с профилем

**ID:** `R-SBX-12` · **Реализует задача:** [4.8](../../../../../docs/tasks/4.8-load-test.md)

<a id="r-sbx-13"></a>
### Requirement: Развёртывание
Модуль SHALL разворачиваться так: этапы 1–3 — Docker на узле; этап 4 — Pod на запуск в `itsaplan-agents`, NetworkPolicy только к egress-прокси; egress-прокси — Deployment 1 реплика. Контейнер среды создаёт Runner на каждый запуск, образ закреплён по digest; ресурсы MUST задаваться профилем sandbox.

#### Scenario: Новый образ среды
- **WHEN** опубликован новый образ среды (`HARNESS_IMAGE`)
- **THEN** пул пересоздаёт тёплые контейнеры, новые запуски идут на новом образе, активные доделываются

#### Scenario: Egress-прокси обновляется
- **WHEN** выходит новая версия `egress-proxy`
- **THEN** прокси заменяется без разрыва активных соединений больше чем на время переподключения; без прокси исходящий трафик запрещён

#### Scenario: Нехватка ресурсов
- **WHEN** узлу не хватает ресурсов для контейнера по профилю
- **THEN** запуск ждёт в `queued`, тёплый пул не доливается до освобождения ресурсов

**ID:** `R-SBX-13` · **Реализует задача:** [4.6](../../../../../docs/tasks/4.6-k8s-helm-ingress.md)
