# Spec Delta

## Purpose

Инфраструктура платформы: профиль нагрузки и ёмкость, кластер Kubernetes (k3s), упаковка Helm, ingress и балансировка, СУБД и пул соединений, объектное хранилище, секреты, резервное копирование, сетевые политики, локальная среда. Обоснование: [R&D](../../../../../docs/rnd/kubernetes-runtime.md).

## ADDED Requirements

### Requirement: Профиль нагрузки и ёмкость
Платформа SHALL выдерживать базовый профиль: 15 одновременных пользователей ICPlan, ~20 RPS на API в пике с p95 < 300 мс, до 6 запусков в очереди и 4 активных, ~55 тыс. токенов/мин к LiteLLM, на одном узле 8 vCPU / 32 ГБ / 400 ГБ. Профиль — гипотеза, MUST подтверждаться нагрузочным тестом перед продуктивом.

#### Scenario: Пиковая нагрузка
- **WHEN** 15 пользователей работают в ICPlan и идут 4 запуска агентов
- **THEN** p95 ответа API < 300 мс, запуски не теряются, лишние ждут в очереди

#### Scenario: Превышение профиля
- **WHEN** нагрузка превышает профиль (например, 12 запусков «coder» одновременно)
- **THEN** планировщик держит лишние запуски в очереди, узел не уходит в нехватку памяти

#### Scenario: Подтверждение замером
- **WHEN** выполняется нагрузочный тест перед продуктивом
- **THEN** фактические p95, RPS и потребление записаны, гипотезы профиля обновлены

<a id="r-inf-01"></a>**ID:** `R-INF-01` · **Реализует задача:** [4.8](../../../../../docs/tasks/4.8-load-test.md)

### Requirement: Кластер Kubernetes
Платформа SHALL разворачиваться в k3s на одном узле с разделением по namespaces: `itsaplan-core` (ICPlan), `itsaplan-data` (Postgres, PgBouncer, RustFS), `itsaplan-agents` (Runner, LiteLLM, OPA, Memory, egress-прокси, запуски), `itsaplan-platform` (бэклог: мониторинг, Gitea).

#### Scenario: Установка с нуля
- **WHEN** администратор запускает установку на чистом сервере
- **THEN** k3s установлен, namespaces созданы, все сервисы готовы

#### Scenario: Ресурс в чужом namespace
- **WHEN** сервис агента пытается создать объект в `itsaplan-core`
- **THEN** операция отклонена правами ServiceAccount

#### Scenario: Повторная установка
- **WHEN** установку запускают повторно на работающем кластере
- **THEN** изменения применяются без пересоздания данных

<a id="r-inf-02"></a>**ID:** `R-INF-02` · **Реализует задача:** [4.6](../../../../../docs/tasks/4.6-k8s-helm-ingress.md)

### Requirement: Упаковка и развёртывание Helm
Каждый компонент SHALL разворачиваться Helm-чартом с версией; значения окружения — в `values-<среда>.yaml`, секреты — только через `existingSecret`. Обновление MUST выполняться без простоя для сервисов с ≥ 2 репликами.

#### Scenario: Обновление версии
- **WHEN** администратор обновляет чарт LiteLLM на новую версию
- **THEN** реплики заменяются по одной, вызовы агентов не прерываются

#### Scenario: Откат
- **WHEN** новая версия не проходит проверки готовности
- **THEN** выполняется откат на предыдущую ревизию релиза

#### Scenario: Секрет в values
- **WHEN** в `values.yaml` указано значение секрета
- **THEN** установка отклоняется проверкой чарта

<a id="r-inf-03"></a>**ID:** `R-INF-03` · **Реализует задача:** [4.6](../../../../../docs/tasks/4.6-k8s-helm-ingress.md)

### Requirement: Ingress и TLS
Публичный вход SHALL идти только через Traefik по HTTPS с сертификатом ACME: `web`, `api`, `/mcp`. Админки (LiteLLM, OPA, Memory API, базы) MUST NOT иметь публичного ingress.

#### Scenario: Вход пользователя
- **WHEN** пользователь открывает адрес ICPlan
- **THEN** запрос идёт по HTTPS через Traefik к `web`

#### Scenario: Попытка открыть админку
- **WHEN** запрос снаружи идёт на адрес LiteLLM
- **THEN** маршрута нет, ответ 404

#### Scenario: HTTP без TLS
- **WHEN** запрос пришёл по HTTP
- **THEN** выполняется перенаправление на HTTPS

<a id="r-inf-04"></a>**ID:** `R-INF-04` · **Реализует задача:** [4.6](../../../../../docs/tasks/4.6-k8s-helm-ingress.md)

### Requirement: Балансировка между репликами
Сервисы с несколькими репликами SHALL получать трафик через Service (ClusterIP) с проверками готовности; реплика, не прошедшая проверку, MUST исключаться из балансировки.

#### Scenario: Реплика не готова
- **WHEN** одна из двух реплик LiteLLM не проходит readiness
- **THEN** трафик идёт только на здоровую реплику

#### Scenario: Все реплики готовы
- **WHEN** обе реплики OPA готовы
- **THEN** запросы распределяются между ними

#### Scenario: Нет готовых реплик
- **WHEN** ни одна реплика сервиса не готова
- **THEN** клиенты получают ошибку соединения и действуют по FMEA своей спеки

<a id="r-inf-05"></a>**ID:** `R-INF-05` · **Реализует задача:** [4.6](../../../../../docs/tasks/4.6-k8s-helm-ingress.md)

### Requirement: СУБД и пул соединений
Данные SHALL храниться в одном кластере PostgreSQL 17 (CloudNativePG) с БД `itsaplan` (схемы `public`, `platform`, `harness_ckpt`) и БД `litellm`; клиенты MUST подключаться через PgBouncer (transaction pooling, не более 30 серверных соединений).

#### Scenario: Рост числа клиентов
- **WHEN** 60 клиентских соединений открыто одновременно
- **THEN** Postgres держит не более 30 серверных соединений, запросы обслуживаются

#### Scenario: Сессионная функция
- **WHEN** клиенту нужна функция уровня сессии (LISTEN / NOTIFY)
- **THEN** он подключается к отдельному session-пулу или напрямую, по согласованному списку

#### Scenario: Миграции
- **WHEN** выходит новая версия ICPlan с миграциями
- **THEN** миграции выполняются до старта новых реплик, схема `platform` не затрагивается

<a id="r-inf-06"></a>**ID:** `R-INF-06` · **Реализует задача:** [4.7](../../../../../docs/tasks/4.7-postgres-storage-backup.md)

### Requirement: Объектное хранилище
Вложения, артефакты и резервные копии SHALL храниться в S3-совместимом хранилище RustFS; клиенты MUST использовать только S3 API, чтобы хранилище можно было заменить (например, на SeaweedFS) без изменения кода.

#### Scenario: Загрузка вложения
- **WHEN** агент публикует артефакт в задачу
- **THEN** файл сохранён в бакете `planner-attachments`

#### Scenario: Замена хранилища
- **WHEN** RustFS заменяется другим S3-совместимым хранилищем
- **THEN** меняются только адрес и ключи в конфигурации

#### Scenario: Хранилище недоступно
- **WHEN** RustFS не отвечает
- **THEN** итог публикуется без вложений, загрузка повторяется

<a id="r-inf-07"></a>**ID:** `R-INF-07` · **Реализует задача:** [4.7](../../../../../docs/tasks/4.7-postgres-storage-backup.md)

### Requirement: Резервное копирование
Postgres SHALL резервироваться базовыми копиями и WAL в S3 вне узла (не на том же диске); объектное хранилище MUST копироваться вне узла. Восстановление MUST проверяться не реже раза в месяц.

#### Scenario: Потеря узла
- **WHEN** узел утрачен вместе с диском
- **THEN** данные восстанавливаются из копий вне узла

#### Scenario: Проверка восстановления
- **WHEN** выполняется ежемесячная проверка
- **THEN** копия восстанавливается в отдельный namespace, результат записан

#### Scenario: Копия не создалась
- **WHEN** резервная копия не создана по расписанию
- **THEN** администратор получает предупреждение

<a id="r-inf-08"></a>**ID:** `R-INF-08` · **Реализует задача:** [4.7](../../../../../docs/tasks/4.7-postgres-storage-backup.md)

### Requirement: Секреты
Секреты SHALL храниться только в Kubernetes Secret (создаются скриптом из локального `.env`, вне git) и подключаться через `existingSecret`; в git, values и образах их MUST NOT быть.

#### Scenario: Новый секрет
- **WHEN** администратор добавляет ключ провайдера
- **THEN** он попадает в Secret, сервис перечитывает его без пересборки образа

#### Scenario: Секрет в репозитории
- **WHEN** в коммит попадает значение секрета
- **THEN** проверка перед коммитом его останавливает

#### Scenario: Секрета нет
- **WHEN** обязательный Secret отсутствует
- **THEN** сервис не стартует, ошибка называет Secret

<a id="r-inf-09"></a>**ID:** `R-INF-09` · **Реализует задача:** [4.6](../../../../../docs/tasks/4.6-k8s-helm-ingress.md)

### Requirement: Сетевые политики
Трафик между namespaces SHALL быть запрещён по умолчанию и разрешён только по списку интерфейсов (I1–I23); контейнеры запусков MUST выходить наружу только через egress-прокси.

#### Scenario: Разрешённый интерфейс
- **WHEN** Runner обращается к API ICPlan
- **THEN** соединение разрешено политикой

#### Scenario: Запрещённый маршрут
- **WHEN** контейнер запуска пытается подключиться к Postgres напрямую
- **THEN** соединение блокируется

#### Scenario: Новый интерфейс
- **WHEN** добавлен новый интерфейс в `interfaces.md`
- **THEN** политика дополняется до выпуска

<a id="r-inf-10"></a>**ID:** `R-INF-10` · **Реализует задача:** [4.6](../../../../../docs/tasks/4.6-k8s-helm-ingress.md), [4.2](../../../../../docs/tasks/4.2-egress-repo-access.md)

### Requirement: Проверки готовности и порядок запуска
Каждый сервис SHALL иметь liveness и readiness проверки; зависимые сервисы MUST NOT принимать трафик, пока их обязательные зависимости (БД, секреты) не готовы.

#### Scenario: Холодный старт
- **WHEN** кластер запускается после остановки
- **THEN** сначала готовы Postgres и PgBouncer, затем api, LiteLLM, OPA, затем Runner

#### Scenario: Зависимость пропала
- **WHEN** Postgres недоступен у работающего api
- **THEN** api перестаёт быть готовым, ingress не шлёт на него трафик

#### Scenario: Зависший процесс
- **WHEN** процесс не отвечает на liveness
- **THEN** под перезапускается

### Requirement: Локальная среда
Для разработки SHALL поддерживаться две локальные среды: docker compose (этапы 1–2) и k3d с теми же чартами (этап 4); образы и версии MUST совпадать с серверными.

#### Scenario: Разработка Harness
- **WHEN** разработчик запускает compose
- **THEN** поднимаются ICPlan, Postgres, RustFS, LiteLLM с mock

#### Scenario: Проверка чартов
- **WHEN** разработчик разворачивает чарты в k3d
- **THEN** результат совпадает с серверной установкой, кроме адресов и ресурсов

#### Scenario: Расхождение версий
- **WHEN** версия образа в compose отличается от чарта
- **THEN** проверка согласованности сообщает о расхождении

<a id="r-inf-12"></a>**ID:** `R-INF-12` · **Реализует задача:** [2.2](../../../../../docs/tasks/2.2-sandbox-docker-oneshot.md), [4.6](../../../../../docs/tasks/4.6-k8s-helm-ingress.md)

### Requirement: Конфигурация модуля
Модуль SHALL брать свои параметры (8, таблица «Параметры модуля» в `interfaces.md`) с уровней L0 (S9): значение — с самого конкретного уровня. Неверное значение MUST отклоняться с ошибкой, называющей параметр.

#### Scenario: Значение по умолчанию
- **WHEN** `k3s.version` (версия кластера) не задан на уровнях выше L0
- **THEN** применяется значение по умолчанию: v1.37.1+k3s1

#### Scenario: Изменение конфига деплоя
- **WHEN** `ingress.host / tls` изменён в S9
- **THEN** новое значение действует после перезапуска модуля, до этого — прежнее

#### Scenario: Изменение конфига деплоя
- **WHEN** `<сервис>.replicas` изменён в S9
- **THEN** новое значение действует после перезапуска модуля, до этого — прежнее

<a id="r-inf-13"></a>**ID:** `R-INF-13` · **Реализует задача:** [4.6](../../../../../docs/tasks/4.6-k8s-helm-ingress.md)

### Requirement: Хранилища данных
Модуль SHALL хранить и читать свои данные только в S1 (PostgreSQL 17 (CloudNativePG), БД `itsaplan`), S6 (PostgreSQL 17 (тот же кластер), БД `litellm`), S7 (RustFS (S3 API), бакет `planner-attachments`), S9 (Конфиг деплоя: `values.yaml` (git, без секретов) + Secret / `.env` (вне git)) (`interfaces.md`); к данным других модулей — только через их API. Секреты MUST NOT храниться в БД и git.

#### Scenario: Запись в своё хранилище
- **WHEN** модуль сохраняет вложения задач, артефакты агентов, резервные копии
- **THEN** запись попадает в S7 (RustFS (S3 API), бакет `planner-attachments`)

#### Scenario: S7 недоступно
- **WHEN** S7 (RustFS (S3 API), бакет `planner-attachments`) не отвечает
- **THEN** операция завершается ошибкой без частичной записи, поведение — по FMEA, событие оператору

#### Scenario: Прямой доступ к чужим данным
- **WHEN** код модуля обращается к таблицам другого модуля
- **THEN** доступа нет: роль БД ограничена своими хранилищами

### Requirement: Интерфейсы обмена
Интерфейсы модуля (I21, I22, I23, I19) SHALL соблюдать протокол, формат, аутентификацию, таймаут и политику повтора из `interfaces.md`; неидемпотентные вызовы MUST NOT повторяться автоматически.

#### Scenario: Таймаут I21
- **WHEN** Пользователи → Traefik → web / api / mcp (I21) не ответил за 60 с (ingress)
- **THEN** вызов прерывается; повтор: нет

#### Scenario: Аутентификация I22
- **WHEN** собеседник по I22 отклонил учётные данные (логин / пароль из Secret, роль на схему)
- **THEN** вызов не повторяется, событие с причиной

#### Scenario: Неидемпотентный вызов I23
- **WHEN** вызов I23 (Agent Runner → Kubernetes API (этап 4)) прервался сбоем сети
- **THEN** автоматического повтора нет, решение принимает вызывающий

### Requirement: Поведение при отказах зависимостей
Модуль SHALL вести себя при отказах зависимостей по таблице FMEA (`interfaces.md`): отказ обнаруживается, поведение предсказуемо и безопасно (fail-closed для проверок безопасности), восстановление не теряет данные.

#### Scenario: Узел недоступен
- **WHEN** узел недоступен
- **THEN** вся платформа недоступна (один узел)

#### Scenario: Postgres недоступен
- **WHEN** postgres недоступен
- **THEN** сервисы не готовы, запуски не стартуют

#### Scenario: PgBouncer исчерпал пул
- **WHEN** pgbouncer исчерпал пул
- **THEN** запросы ждут до таймаута, ошибка с причиной

#### Scenario: Истёк TLS-сертификат
- **WHEN** истёк tls-сертификат
- **THEN** Traefik обновляет по ACME; при сбое — предупреждение

<a id="r-inf-16"></a>**ID:** `R-INF-16` · **Реализует задача:** [4.7](../../../../../docs/tasks/4.7-postgres-storage-backup.md)

### Requirement: Нагрузка и производительность
Модуль SHALL выдерживать нагрузку профиля (`interfaces.md`, раздел «Нагрузка и развёртывание»): один узел 8 vCPU / 32 ГБ / 400 ГБ; постоянно ~13 ГБ RAM, ~5 vCPU; запас под 10 обычных или 4–5 «coder» запусков. Превышение профиля MUST приводить к очереди или отказу с причиной, а не к деградации всей платформы.

#### Scenario: Пиковая нагрузка профиля
- **WHEN** нагрузка достигает пика профиля
- **THEN** целевые показатели времени ответа и пропускной способности выполняются

#### Scenario: Превышение профиля
- **WHEN** нагрузка превышает профиль
- **THEN** лишние запросы ждут в очереди или получают отказ с причиной, остальные обслуживаются

#### Scenario: Замер
- **WHEN** выполняется нагрузочный тест
- **THEN** фактические показатели записаны и сравнены с профилем

<a id="r-inf-17"></a>**ID:** `R-INF-17` · **Реализует задача:** [4.8](../../../../../docs/tasks/4.8-load-test.md)

### Requirement: Развёртывание
Модуль SHALL разворачиваться так: k3s один узел; namespaces `itsaplan-core`, `itsaplan-data`, `itsaplan-agents`, `itsaplan-platform`; Traefik ingress; CloudNativePG + PgBouncer; RustFS. Ресурсы MUST задаваться requests / limits, публичный доступ — только через ingress, если указан.

#### Scenario: Установка
- **WHEN** модуль разворачивается в кластере
- **THEN** объекты созданы в указанном namespace с заданными ресурсами

#### Scenario: Нехватка ресурсов
- **WHEN** узлу не хватает ресурсов для пода модуля
- **THEN** под ждёт размещения, событие для оператора

#### Scenario: Обновление
- **WHEN** выходит новая версия модуля
- **THEN** обновление проходит без потери данных и по правилам Helm-релиза

<a id="r-inf-18"></a>**ID:** `R-INF-18` · **Реализует задача:** [4.6](../../../../../docs/tasks/4.6-k8s-helm-ingress.md)
