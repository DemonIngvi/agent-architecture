# Spec Delta

## Purpose

Platform module — модуль ICPlan для настроек агентов, которых нет в ICPlan: алиасы моделей, бюджеты, профили sandbox и памяти, данные guardrails, параметры планирования, версии определений. UI — экраны ICPlan. Обоснование: [R&D](../../../../../docs/rnd/config-storage.md).

## ADDED Requirements

### Requirement: Настройки агента
Модуль SHALL хранить для агента: алиас модели, бюджеты (запуск, сутки), лимиты запуска, профиль sandbox, профиль памяти, данные guardrails (разрешённые тулы, тулы с подтверждением), флаги планирования (`parallel`, `max`), allowlist репозиториев.

#### Scenario: Сохранение настроек
- **WHEN** администратор задаёт агенту бюджет 5 $ в сутки и профиль sandbox `light`
- **THEN** настройки сохранены и видны в карточке агента в ICPlan

#### Scenario: Недопустимое значение
- **WHEN** администратор задаёт отрицательный бюджет или несуществующий профиль
- **THEN** сохранение отклоняется с указанием поля и причины

#### Scenario: Сброс к умолчаниям
- **WHEN** администратор сбрасывает настройку
- **THEN** используется значение по умолчанию из таблицы конфигурации

### Requirement: Хранение в БД ICPlan
Настройки MUST храниться в БД ICPlan в отдельной схеме модуля; доступ исполнителей SHALL идти через API модуля, а не напрямую к таблицам.

#### Scenario: Чтение Runner
- **WHEN** Agent Runner запрашивает настройки агента перед запуском
- **THEN** получает их через API модуля

#### Scenario: Прямой доступ запрещён
- **WHEN** сервис пытается читать таблицы модуля напрямую
- **THEN** доступа нет, только через API

#### Scenario: Обновление ICPlan
- **WHEN** форк обновлён из upstream
- **THEN** схема модуля не затрагивается миграциями ICPlan

### Requirement: Применение к следующему запуску
Изменение настроек SHALL применяться к следующим запускам и MUST NOT менять активные запуски.

#### Scenario: Смена бюджета во время запуска
- **WHEN** администратор уменьшает бюджет, пока идёт запуск
- **THEN** активный запуск работает по прежним настройкам, следующий — по новым

#### Scenario: Запуск в очереди
- **WHEN** настройки изменены, пока запуск ждёт в `queued`
- **THEN** запуск стартует с новыми настройками

#### Scenario: Откат настроек
- **WHEN** администратор возвращает прежнюю версию настроек
- **THEN** следующий запуск идёт по прежним

### Requirement: Версии определения агента
Каждое изменение определения агента SHALL создавать версию; запуск MAY указывать версию явно, иначе MUST использоваться последняя.

#### Scenario: Запуск на прежней версии
- **WHEN** в запуске указана версия 3, а последняя — 5
- **THEN** агент исполняется по версии 3

#### Scenario: Последняя версия
- **WHEN** версия в запуске не указана
- **THEN** используется последняя

#### Scenario: Удалённая версия
- **WHEN** запуск указывает удалённую версию
- **THEN** запуск отклоняется с ошибкой версии

### Requirement: Экспорт и импорт YAML
Модуль SHALL экспортировать определение агента с настройками в YAML `agent/v1` и импортировать его, проверяя схему и ссылки.

#### Scenario: Перенос в prod
- **WHEN** администратор импортирует YAML, выгруженный из dev
- **THEN** в prod создаётся новая версия агента с тем же содержимым

#### Scenario: Битая ссылка при импорте
- **WHEN** YAML ссылается на несуществующий MCP-сервер
- **THEN** импорт отклоняется с указанием ссылки

#### Scenario: Секреты не экспортируются
- **WHEN** администратор экспортирует агента
- **THEN** в YAML только ссылки на секреты, без значений

### Requirement: Раздача настроек исполнителям
Модуль SHALL передавать алиасы и бюджеты в LiteLLM, а данные правил — в OPA; рассинхронизация MUST обнаруживаться и показываться администратору.

#### Scenario: Новое правило
- **WHEN** администратор добавляет тул в список с подтверждением
- **THEN** следующий вызов этого тула агентом ждёт approve (данные в OPA обновлены)

#### Scenario: LiteLLM недоступен
- **WHEN** при сохранении бюджета LiteLLM не отвечает
- **THEN** изменение помечается «не применено» и повторяется

#### Scenario: Рассинхронизация
- **WHEN** бюджет в модуле и в LiteLLM различается
- **THEN** администратор видит предупреждение

### Requirement: Права на настройки
Изменять настройки SHALL только роли с правом управления агентами; остальные MUST получать отказ.

#### Scenario: Нет прав
- **WHEN** участник без права пытается изменить бюджет агента
- **THEN** запрос отклоняется с ошибкой доступа

#### Scenario: Есть права
- **WHEN** администратор меняет бюджет
- **THEN** изменение сохраняется и попадает в историю

#### Scenario: Только чтение
- **WHEN** участник с правом чтения открывает настройки
- **THEN** видит, но не может менять

### Requirement: Конфигурация модуля
Параметры модуля SHALL храниться по уровням L0–L3 (`interfaces.md`): значение берётся с самого конкретного уровня, но MUST NOT превышать потолок, заданный на L0. Отсутствие обязательного параметра MUST останавливать старт модуля с ошибкой, называющей параметр.

#### Scenario: Значение по умолчанию
- **WHEN** параметр не задан на уровнях L1–L3
- **THEN** применяется значение L0

#### Scenario: Превышение потолка
- **WHEN** на уровне агента задано значение выше потолка L0
- **THEN** применяется потолок, в журнал пишется событие

#### Scenario: Нет обязательного параметра
- **WHEN** при старте не задан обязательный параметр
- **THEN** модуль не стартует, ошибка называет параметр и уровень

### Requirement: Хранилища данных
Модуль SHALL хранить данные только в хранилищах S2, S6, S9 (`interfaces.md`) и MUST обращаться к данным других модулей только через их API, не напрямую к таблицам. Секреты MUST NOT храниться в БД и git.

#### Scenario: Запись в своё хранилище
- **WHEN** модуль сохраняет свои данные
- **THEN** запись попадает в хранилище из перечня

#### Scenario: Хранилище недоступно
- **WHEN** хранилище модуля не отвечает
- **THEN** операция завершается ошибкой без частичной записи, событие для оператора

#### Scenario: Прямой доступ к чужим данным
- **WHEN** код модуля обращается к таблицам другого модуля
- **THEN** доступа нет: роль БД ограничена своей схемой

### Requirement: Интерфейсы обмена
Интерфейсы модуля (I4, I15, I16, I20) SHALL соблюдать протокол, формат, аутентификацию, таймаут и политику повтора из `interfaces.md`; неидемпотентные вызовы MUST NOT повторяться автоматически.

#### Scenario: Таймаут
- **WHEN** ответ не пришёл за таймаут интерфейса
- **THEN** вызов прерывается и обрабатывается по политике повтора

#### Scenario: Ошибка аутентификации
- **WHEN** собеседник отклонил учётные данные
- **THEN** вызов не повторяется, событие с причиной

#### Scenario: Неидемпотентный вызов
- **WHEN** неидемпотентный вызов завершился сбоем сети
- **THEN** автоматического повтора нет, решение принимает вызывающий

### Requirement: Поведение при отказах зависимостей
Модуль SHALL вести себя при отказах зависимостей по таблице FMEA (`interfaces.md`): отказ обнаруживается, поведение предсказуемо и безопасно (fail-closed для проверок безопасности), восстановление не теряет данные.

#### Scenario: LiteLLM admin API недоступен
- **WHEN** litellm admin api недоступен
- **THEN** изменение помечено «не применено», повтор

#### Scenario: OPA не забрал bundle
- **WHEN** opa не забрал bundle
- **THEN** решения по старым данным, предупреждение администратору

#### Scenario: Рассинхронизация настроек
- **WHEN** рассинхронизация настроек
- **THEN** предупреждение, новые запуски используют S2
