# Spec Delta

## Purpose

Единый версионируемый каталог ресурсов платформы и декларативных определений агентов, из которых агент собирается без написания кода. Обоснование: [R&D](../../../../../docs/rnd/config-storage.md).

## ADDED Requirements

### Requirement: Каталог ресурсов
Registry SHALL хранить ресурсы типов: `model`, `prompt`, `skill`, `tool`, `mcp_server`, `guardrail_rule`, `memory_profile`, `sandbox_profile`, `agent`.

#### Scenario: Регистрация ресурса
- **WHEN** администратор добавляет ресурс любого из типов
- **THEN** ресурс получает идентификатор и версию и становится доступен для ссылок

#### Scenario: Дубликат
- **WHEN** добавляется ресурс с существующим идентификатором
- **THEN** добавление отклоняется

#### Scenario: Неизвестный тип
- **WHEN** добавляется ресурс неподдерживаемого типа
- **THEN** отказ с перечнем допустимых типов

<a id="r-reg-01"></a>**ID:** `R-REG-01` · **Реализует задача:** [1.2](../../../../../docs/tasks/1.2-agent-definition-yaml.md)

### Requirement: Определение агента
Определение агента SHALL состоять из ссылок на ресурсы Registry: модель, системный промпт, скиллы, тулы/MCP, профиль памяти, guardrail-правила, sandbox-профиль, формат результата.

#### Scenario: Добавление агента без кода
- **WHEN** администратор сохраняет новое определение агента
- **THEN** агент доступен для запуска по `agent_id` без изменения кода платформы

#### Scenario: Обязательное поле отсутствует
- **WHEN** в определении нет модели
- **THEN** сохранение отклоняется с указанием поля

#### Scenario: Отключение агента
- **WHEN** агент отключён
- **THEN** новые запуски не создаются, история сохраняется

<a id="r-reg-02"></a>**ID:** `R-REG-02` · **Реализует задача:** [1.2](../../../../../docs/tasks/1.2-agent-definition-yaml.md), [2.3](../../../../../docs/tasks/2.3-config-from-icplan.md)

### Requirement: Версионирование
Каждое изменение ресурса SHALL создавать новую версию; прежние версии MUST оставаться доступными.

#### Scenario: Запуск на прежней версии
- **WHEN** задача указывает конкретную версию агента
- **THEN** запуск использует эту версию, даже если есть более новая

#### Scenario: Новая версия
- **WHEN** администратор меняет инструкцию
- **THEN** создаётся новая версия, прежние доступны

#### Scenario: Несуществующая версия
- **WHEN** задача указывает версию, которой нет
- **THEN** запуск отклоняется с ошибкой версии

<a id="r-reg-03"></a>**ID:** `R-REG-03` · **Реализует задача:** [4.4](../../../../../docs/tasks/4.4-platform-module.md)

### Requirement: Источник правды и экспорт
Определения агентов SHALL храниться в БД ICPlan как источнике правды; система SHALL поддерживать экспорт и импорт определений в YAML для ревью и переноса между окружениями.

#### Scenario: Перенос в prod
- **WHEN** администратор экспортирует агента из dev и импортирует в prod
- **THEN** в prod создаётся новая версия агента с тем же содержимым

#### Scenario: Экспорт
- **WHEN** администратор выгружает агента
- **THEN** получает YAML `agent/v1` без секретов

#### Scenario: Импорт с другой схемой
- **WHEN** YAML другой версии схемы
- **THEN** импорт отклоняется или мигрирует с предупреждением

<a id="r-reg-04"></a>**ID:** `R-REG-04` · **Реализует задача:** [4.4](../../../../../docs/tasks/4.4-platform-module.md)

### Requirement: Валидация связей
Registry MUST отклонять сохранение определения агента со ссылками на несуществующие ресурсы.

#### Scenario: Битая ссылка
- **WHEN** определение агента ссылается на несуществующий скилл
- **THEN** сохранение отклоняется с указанием битой ссылки

#### Scenario: Все ссылки верны
- **WHEN** определение ссылается на существующие ресурсы
- **THEN** сохранение проходит

#### Scenario: Удаление используемого ресурса
- **WHEN** удаляют MCP-сервер, на который ссылается агент
- **THEN** удаление отклоняется со списком агентов

<a id="r-reg-05"></a>**ID:** `R-REG-05` · **Реализует задача:** [1.2](../../../../../docs/tasks/1.2-agent-definition-yaml.md)

### Requirement: Смена модели агента
Смена модели агента SHALL выполняться изменением ссылки на модель в определении, без изменения остальных частей.

#### Scenario: Замена модели
- **WHEN** администратор меняет модель агента
- **THEN** новые запуски используют новую модель, активные запуски не затронуты

#### Scenario: Модель без доступа
- **WHEN** новая модель не настроена в шлюзе
- **THEN** смена отклоняется

#### Scenario: Откат модели
- **WHEN** администратор возвращает прежнюю модель
- **THEN** следующий запуск идёт на прежней модели

<a id="r-reg-06"></a>**ID:** `R-REG-06` · **Реализует задача:** [2.3](../../../../../docs/tasks/2.3-config-from-icplan.md)

### Requirement: Конфигурация модуля
Модуль SHALL брать свои параметры (7, таблица «Параметры модуля» в `interfaces.md`) с уровней L2 (S1), L3 (запуск): значение — с самого конкретного уровня. Настройка без `agent.model`, `agent.instruction` MUST NOT сохраняться.

#### Scenario: Значение по умолчанию
- **WHEN** `agent.tools` (тулы агента из каталога) не задан на уровне L2
- **THEN** применяется значение по умолчанию: нет

#### Scenario: Нет обязательного поля
- **WHEN** настройку сохраняют без `agent.model` (алиас модели агента)
- **THEN** сохранение отклонено, ошибка называет `agent.model`

#### Scenario: Изменение настройки
- **WHEN** `agent.instruction` изменён на уровне L2 во время работы
- **THEN** активный запуск работает со старым значением, новое — со следующего

<a id="r-reg-07"></a>**ID:** `R-REG-07` · **Реализует задача:** [2.3](../../../../../docs/tasks/2.3-config-from-icplan.md)

### Requirement: Хранилища данных
Модуль SHALL хранить и читать свои данные только в S1 (PostgreSQL 17 (CloudNativePG), БД `itsaplan`), S2 (Postgres ICPlan, схема `platform`) (`interfaces.md`); к данным других модулей — только через их API. Секреты MUST NOT храниться в БД и git.

#### Scenario: Запись в своё хранилище
- **WHEN** модуль сохраняет задачи, агенты, `agent_run`, `issue_activity`, статусы, документы
- **THEN** запись попадает в S1 (PostgreSQL 17 (CloudNativePG), БД `itsaplan`)

#### Scenario: S1 недоступно
- **WHEN** S1 (PostgreSQL 17 (CloudNativePG), БД `itsaplan`) не отвечает
- **THEN** операция завершается ошибкой без частичной записи, поведение — по FMEA, событие оператору

#### Scenario: Прямой доступ к чужим данным
- **WHEN** код модуля обращается к таблицам другого модуля
- **THEN** доступа нет: роль БД ограничена своими хранилищами

<a id="r-reg-08"></a>**ID:** `R-REG-08` · **Реализует задача:** [2.3](../../../../../docs/tasks/2.3-config-from-icplan.md), [4.4](../../../../../docs/tasks/4.4-platform-module.md)

### Requirement: Интерфейсы обмена
Интерфейсы модуля (I20, I4) SHALL соблюдать протокол, формат, аутентификацию, таймаут и политику повтора из `interfaces.md`; неидемпотентные вызовы MUST NOT повторяться автоматически.

#### Scenario: Таймаут I4
- **WHEN** Agent Runner → Platform module API (I4) не ответил за 2 с
- **THEN** вызов прерывается; повтор: 3 раза

#### Scenario: Аутентификация I20
- **WHEN** собеседник по I20 отклонил учётные данные (сессия пользователя)
- **THEN** вызов не повторяется, событие с причиной

#### Scenario: Повтор I4 без дублей
- **WHEN** вызов I4 повторён после сбоя
- **THEN** дубля нет: чтение

<a id="r-reg-09"></a>**ID:** `R-REG-09` · **Реализует задача:** [2.3](../../../../../docs/tasks/2.3-config-from-icplan.md)

### Requirement: Поведение при отказах зависимостей
Модуль SHALL вести себя при отказах зависимостей по таблице FMEA (`interfaces.md`): отказ обнаруживается, поведение предсказуемо и безопасно (fail-closed для проверок безопасности), восстановление не теряет данные.

#### Scenario: БД ICPlan недоступна
- **WHEN** бд icplan недоступна
- **THEN** определения не читаются — запуски не стартуют

#### Scenario: Удалён ресурс, на который ссылаются
- **WHEN** удалён ресурс, на который ссылаются
- **THEN** удаление отклоняется

#### Scenario: Импорт с неверной схемой
- **WHEN** импорт с неверной схемой
- **THEN** импорт отклоняется

<a id="r-reg-10"></a>**ID:** `R-REG-10` · **Реализует задача:** [2.3](../../../../../docs/tasks/2.3-config-from-icplan.md)

### Requirement: Нагрузка и производительность
Модуль SHALL выдерживать нагрузку профиля (`interfaces.md`, раздел «Нагрузка и развёртывание»): чтение определения на каждый запуск (~30 в час в пике); изменения — единицы в день. Превышение профиля MUST приводить к очереди или отказу с причиной, а не к деградации всей платформы.

#### Scenario: Пиковая нагрузка профиля
- **WHEN** нагрузка достигает пика профиля
- **THEN** целевые показатели времени ответа и пропускной способности выполняются

#### Scenario: Превышение профиля
- **WHEN** нагрузка превышает профиль
- **THEN** лишние запросы ждут в очереди или получают отказ с причиной, остальные обслуживаются

#### Scenario: Замер
- **WHEN** выполняется нагрузочный тест
- **THEN** фактические показатели записаны и сравнены с профилем

<a id="r-reg-11"></a>**ID:** `R-REG-11` · **Реализует задача:** [4.8](../../../../../docs/tasks/4.8-load-test.md)

### Requirement: Развёртывание
Модуль SHALL разворачиваться так: часть ICPlan api (Deployment `api` в `itsaplan-core`). Ресурсы MUST задаваться requests / limits, публичный доступ — только через ingress, если указан.

#### Scenario: Установка
- **WHEN** модуль разворачивается в кластере
- **THEN** объекты созданы в указанном namespace с заданными ресурсами

#### Scenario: Нехватка ресурсов
- **WHEN** узлу не хватает ресурсов для пода модуля
- **THEN** под ждёт размещения, событие для оператора

#### Scenario: Обновление
- **WHEN** выходит новая версия модуля
- **THEN** обновление проходит без потери данных и по правилам Helm-релиза
