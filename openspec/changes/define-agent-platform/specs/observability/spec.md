# Spec Delta

## Purpose

Прозрачность работы агентов: пошаговые события запуска, затраты токенов и денег, события guardrails — для пользователя задачи, отладки и аудита. Обоснование: [R&D](../../../../../docs/rnd/observability.md).

## ADDED Requirements

### Requirement: События запуска
Система SHALL записывать события каждого запуска (вызов LLM, вызов тула, обращение к памяти, срабатывание guardrail, смена статуса) в БД с привязкой к `run_id` и задаче.

#### Scenario: Разбор запуска
- **WHEN** администратор открывает запуск по `run_id`
- **THEN** видит последовательность шагов с входами, выходами и временем

#### Scenario: Чувствительные данные
- **WHEN** аргументы тула содержат секрет
- **THEN** в событии значение маскируется

#### Scenario: БД событий недоступна
- **WHEN** запись события не удалась
- **THEN** Runner буферизует и дописывает события позже

### Requirement: Таймлайн в задаче
Пользователь задачи SHALL видеть пошаговый таймлайн запуска агента в задаче ICPlan, построенный из событий запуска.

#### Scenario: Ход выполнения
- **WHEN** агент работает над задачей
- **THEN** в задаче появляются шаги по мере выполнения

#### Scenario: Завершённый запуск
- **WHEN** пользователь открывает задачу после завершения
- **THEN** видит полный таймлайн и итог

#### Scenario: Несколько запусков
- **WHEN** по задаче было три запуска
- **THEN** таймлайн разделён по запускам и агентам

### Requirement: Трассировка
Каждый запуск SHALL хранить задачу, агента, версию определения агента и связь с итогом; по задаче MUST быть доступны все её запуски с событиями.

#### Scenario: Разбор задачи
- **WHEN** администратор открывает задачу
- **THEN** видит все запуски по ней, версии агентов и итоги

#### Scenario: Запуск без задачи
- **WHEN** запуск по расписанию без задачи
- **THEN** трассировка идёт по агенту и расписанию

#### Scenario: Удалённый агент
- **WHEN** агент удалён, запуски остались
- **THEN** история показывает агента и версию на момент запуска

### Requirement: Маскирование чувствительных данных
Перед записью события система MUST маскировать секреты и персональные данные в аргументах и ответах: по полям из подключённых секретов и по шаблонам (ключи API, токены, e-mail, телефоны). Исходные значения MUST NOT попадать в хранилище событий. Источник: US-OBS-03.

#### Scenario: Ключ в аргументах тула
- **WHEN** аргументы тула содержат строку, похожую на ключ API
- **THEN** в событии значение заменено на `***`

#### Scenario: Значение подключённого секрета
- **WHEN** ответ тула содержит значение секрета, подставленного прокси
- **THEN** значение маскируется, даже если не совпадает с шаблонами

#### Scenario: Нет чувствительных данных
- **WHEN** событие не содержит секретов и персональных данных
- **THEN** событие записывается без изменений

### Requirement: Затраты
Система SHALL агрегировать токены и $ по запуску, задаче, агенту, модели и периоду.

#### Scenario: Отчёт по модели
- **WHEN** запрашиваются затраты по модели за месяц
- **THEN** возвращается сумма по всем агентам, использовавшим модель

#### Scenario: Затраты задачи
- **WHEN** открыта задача с тремя запусками
- **THEN** показана сумма токенов и $ по задаче

#### Scenario: Нет данных о цене
- **WHEN** у модели не задана цена
- **THEN** токены учтены, стоимость помечена «неизвестна»

### Requirement: Политика хранения
События запусков MUST храниться в пределах настраиваемого срока и удаляться по его истечении; агрегаты затрат SHALL сохраняться.

#### Scenario: Истёк срок
- **WHEN** срок хранения событий истёк
- **THEN** события удалены, агрегаты затрат сохранены

#### Scenario: Срок не истёк
- **WHEN** событию 10 дней при сроке 90
- **THEN** событие доступно

#### Scenario: Изменён срок
- **WHEN** срок хранения уменьшен
- **THEN** старые события удаляются при следующей очистке

### Requirement: Конфигурация модуля
Параметры модуля SHALL храниться по уровням L0–L3 (`interfaces.md`): значение берётся с самого конкретного уровня, но MUST NOT превышать потолок, заданный на L0. Отсутствие обязательного параметра MUST останавливать старт модуля с ошибкой, называющей параметр.

#### Scenario: Значение по умолчанию
- **WHEN** параметр не задан на уровнях L1–L3
- **THEN** применяется значение L0

#### Scenario: Превышение потолка
- **WHEN** на уровне агента задано значение выше потолка L0
- **THEN** применяется потолок, в журнал пишется событие

#### Scenario: Нет обязательного параметра
- **WHEN** при старте не задан обязательный параметр
- **THEN** модуль не стартует, ошибка называет параметр и уровень

### Requirement: Хранилища данных
Модуль SHALL хранить данные только в хранилищах S3, S6 (`interfaces.md`) и MUST обращаться к данным других модулей только через их API, не напрямую к таблицам. Секреты MUST NOT храниться в БД и git.

#### Scenario: Запись в своё хранилище
- **WHEN** модуль сохраняет свои данные
- **THEN** запись попадает в хранилище из перечня

#### Scenario: Хранилище недоступно
- **WHEN** хранилище модуля не отвечает
- **THEN** операция завершается ошибкой без частичной записи, событие для оператора

#### Scenario: Прямой доступ к чужим данным
- **WHEN** код модуля обращается к таблицам другого модуля
- **THEN** доступа нет: роль БД ограничена своей схемой

### Requirement: Интерфейсы обмена
Интерфейсы модуля (I2, I14, I20) SHALL соблюдать протокол, формат, аутентификацию, таймаут и политику повтора из `interfaces.md`; неидемпотентные вызовы MUST NOT повторяться автоматически.

#### Scenario: Таймаут
- **WHEN** ответ не пришёл за таймаут интерфейса
- **THEN** вызов прерывается и обрабатывается по политике повтора

#### Scenario: Ошибка аутентификации
- **WHEN** собеседник отклонил учётные данные
- **THEN** вызов не повторяется, событие с причиной

#### Scenario: Неидемпотентный вызов
- **WHEN** неидемпотентный вызов завершился сбоем сети
- **THEN** автоматического повтора нет, решение принимает вызывающий

### Requirement: Поведение при отказах зависимостей
Модуль SHALL вести себя при отказах зависимостей по таблице FMEA (`interfaces.md`): отказ обнаруживается, поведение предсказуемо и безопасно (fail-closed для проверок безопасности), восстановление не теряет данные.

#### Scenario: Нет записи событий
- **WHEN** нет записи событий
- **THEN** буфер в Runner, досылка

#### Scenario: Нет цены модели
- **WHEN** нет цены модели
- **THEN** токены учтены, стоимость «неизвестна»

#### Scenario: Переполнение таблицы событий
- **WHEN** переполнение таблицы событий
- **THEN** очистка по сроку, уровень детализации снижается

### Requirement: Нагрузка и производительность
Модуль SHALL выдерживать нагрузку профиля (`interfaces.md`, раздел «Нагрузка и развёртывание»): запись событий ~4 RPS в пике, ~25 МБ/день; таймлайн обновляется < 3 с. Превышение профиля MUST приводить к очереди или отказу с причиной, а не к деградации всей платформы.

#### Scenario: Пиковая нагрузка профиля
- **WHEN** нагрузка достигает пика профиля
- **THEN** целевые показатели времени ответа и пропускной способности выполняются

#### Scenario: Превышение профиля
- **WHEN** нагрузка превышает профиль
- **THEN** лишние запросы ждут в очереди или получают отказ с причиной, остальные обслуживаются

#### Scenario: Замер
- **WHEN** выполняется нагрузочный тест
- **THEN** фактические показатели записаны и сравнены с профилем

### Requirement: Развёртывание
Модуль SHALL разворачиваться так: таблица событий в Postgres; чтение — через api ICPlan; Langfuse / Prometheus — бэклог. Ресурсы MUST задаваться requests / limits, публичный доступ — только через ingress, если указан.

#### Scenario: Установка
- **WHEN** модуль разворачивается в кластере
- **THEN** объекты созданы в указанном namespace с заданными ресурсами

#### Scenario: Нехватка ресурсов
- **WHEN** узлу не хватает ресурсов для пода модуля
- **THEN** под ждёт размещения, событие для оператора

#### Scenario: Обновление
- **WHEN** выходит новая версия модуля
- **THEN** обновление проходит без потери данных и по правилам Helm-релиза
