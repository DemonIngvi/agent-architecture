# Spec Delta

## Purpose

Прозрачность работы агентов: пошаговые события запуска, затраты токенов и денег, события guardrails — для пользователя задачи, отладки и аудита. Обоснование: [R&D](../../../../../docs/rnd/observability.md).

## ADDED Requirements

<a id="r-obs-01"></a>
### Requirement: События запуска
Система SHALL записывать события каждого запуска в формате AG-UI (запуск, шаги, реплики, рассуждения, вызовы тулов, план) и события платформы как `CUSTOM` (вопрос, подтверждение, guardrail, память, вызов LLM) в БД с привязкой к `run_id` и задаче (D21).

#### Scenario: Разбор запуска
- **WHEN** администратор открывает запуск по `run_id`
- **THEN** видит последовательность шагов с входами, выходами (в пределах `events.level`) и временем

#### Scenario: Чувствительные данные
- **WHEN** аргументы тула содержат секрет
- **THEN** в событии значение маскируется

#### Scenario: БД событий недоступна
- **WHEN** запись события не удалась
- **THEN** Runner буферизует и дописывает события позже

#### Scenario: Дельты сообщения
- **WHEN** приходят `TEXT_MESSAGE_CONTENT` или `REASONING_MESSAGE_CONTENT` по одному сообщению
- **THEN** в БД сохраняется одно собранное сообщение на `*_END`, дельты уходят только в живой поток

**ID:** `R-OBS-01` · **Реализует задача:** [3.3](../../../../../docs/tasks/3.3-run-events-timeline.md)

<a id="r-obs-02"></a>
### Requirement: Чат запуска в задаче
Пользователь задачи SHALL видеть в задаче ICPlan чат запуска (D21): реплики агента, свёрнутые рассуждения и вызовы тулов, план, вопросы и подтверждения с кнопками, свои указания и карточку итога с критериями; лента обновляется без перезагрузки.

#### Scenario: Ход выполнения
- **WHEN** агент работает над задачей
- **THEN** в задаче появляются шаги по мере выполнения

#### Scenario: Завершённый запуск
- **WHEN** пользователь открывает задачу после завершения
- **THEN** видит полный чат запуска и итог

#### Scenario: Несколько запусков
- **WHEN** по задаче было три запуска
- **THEN** чат запуска разделён по запускам и агентам

#### Scenario: Почему агент это делает
- **WHEN** агент вызывает тул
- **THEN** перед вызовом в ленте есть реплика агента о намерении, а рассуждение модели (если есть) доступно по раскрытию

#### Scenario: Итог шага
- **WHEN** запуск завершён
- **THEN** карточка итога показывает результат, артефакты, критерии приёмки ✓ / ✗ и кнопки вердикта шага

#### Scenario: Агент взял задачу
- **WHEN** Runner взял запуск из очереди (I1)
- **THEN** в чате запуска появляется шаг «агент взял задачу» не позже 10 с после взятия

**ID:** `R-OBS-02` · **Реализует задача:** [3.3](../../../../../docs/tasks/3.3-run-events-timeline.md)

<a id="r-obs-03"></a>
### Requirement: Трассировка
Каждый запуск SHALL хранить задачу, агента, версию определения агента и связь с итогом; по задаче MUST быть доступны все её запуски с событиями.

#### Scenario: Разбор задачи
- **WHEN** администратор открывает задачу
- **THEN** видит все запуски по ней, версии агентов и итоги

#### Scenario: Запуск без задачи
- **WHEN** запуск по расписанию без задачи
- **THEN** трассировка идёт по агенту и расписанию

#### Scenario: Удалённый агент
- **WHEN** агент удалён, запуски остались
- **THEN** история показывает агента и версию на момент запуска

**ID:** `R-OBS-03` · **Реализует задача:** [3.3](../../../../../docs/tasks/3.3-run-events-timeline.md)

<a id="r-obs-04"></a>
### Requirement: Маскирование чувствительных данных
Перед записью события система MUST маскировать секреты и персональные данные в аргументах и ответах: по полям из подключённых секретов и по шаблонам (ключи API, токены, e-mail, телефоны). Исходные значения MUST NOT попадать в хранилище событий. Источник: US-OBS-03.

#### Scenario: Ключ в аргументах тула
- **WHEN** аргументы тула содержат строку, похожую на ключ API
- **THEN** в событии значение заменено на `***`

#### Scenario: Значение подключённого секрета
- **WHEN** ответ тула содержит значение секрета, подставленного прокси
- **THEN** значение маскируется, даже если не совпадает с шаблонами

#### Scenario: Нет чувствительных данных
- **WHEN** событие не содержит секретов и персональных данных
- **THEN** событие записывается без изменений

#### Scenario: Секрет в промпте
- **WHEN** промпт или ответ модели содержит значение секрета или персональные данные
- **THEN** значение маскируется до записи события; полный текст без секрета сохраняется

**ID:** `R-OBS-04` · **Реализует задача:** [3.3](../../../../../docs/tasks/3.3-run-events-timeline.md)

<a id="r-obs-05"></a>
### Requirement: Затраты
Система SHALL агрегировать токены и $ по запуску, задаче, агенту, модели и периоду.

#### Scenario: Отчёт по модели
- **WHEN** запрашиваются затраты по модели за месяц
- **THEN** возвращается сумма по всем агентам, использовавшим модель

#### Scenario: Затраты задачи
- **WHEN** открыта задача с тремя запусками
- **THEN** показана сумма токенов и $ по задаче

#### Scenario: Нет данных о цене
- **WHEN** у модели не задана цена
- **THEN** токены учтены, стоимость помечена «неизвестна»

**ID:** `R-OBS-05` · **Реализует задача:** [3.5](../../../../../docs/tasks/3.5-icplan-type-actions-cost.md)

<a id="r-obs-06"></a>
### Requirement: Политика хранения
События запусков MUST храниться в пределах настраиваемого срока и удаляться по его истечении; агрегаты затрат SHALL сохраняться.

#### Scenario: Истёк срок
- **WHEN** срок хранения событий истёк
- **THEN** события удалены, агрегаты затрат сохранены

#### Scenario: Срок не истёк
- **WHEN** событию 10 дней при сроке 90
- **THEN** событие доступно

#### Scenario: Изменён срок
- **WHEN** срок хранения уменьшен
- **THEN** старые события удаляются при следующей очистке

**ID:** `R-OBS-06` · **Реализует задача:** [3.3](../../../../../docs/tasks/3.3-run-events-timeline.md)

<a id="r-obs-13"></a>
### Requirement: Сводка и статистика агентов
Observability SHALL отдавать сводку по задачам с агентами (в работе, в очереди, ждут человека, открыто, закрыто, время в работе и в ожидании, токены и $) и статистику агентов (запуски, успешные, возвращённые пользователем, среднее время, затраты) с фильтром по проекту, пользователю, агенту и периоду — из `agent_run`, событий запуска и затрат LiteLLM.

#### Scenario: Сводка пользователя
- **WHEN** пользователь открыл «Мои задачи с агентами» за неделю
- **THEN** видны счётчики по состояниям, время и затраты по задачам

#### Scenario: Статистика агента
- **WHEN** администратор открыл статистику агента за месяц
- **THEN** запуски, доля успешных и возвращённых, среднее время, затраты

#### Scenario: Затраты недоступны
- **WHEN** LiteLLM недоступен
- **THEN** сводка без затрат с пометкой, остальное показано

**ID:** `R-OBS-13` · **Реализует задача:** [3.9](../../../../../docs/tasks/3.9-agent-summary-stats.md)

<a id="r-obs-07"></a>
### Requirement: Конфигурация модуля
Модуль SHALL брать свои параметры (3, таблица «Параметры модуля» в `interfaces.md`) с уровней L0 (S9): значение — с самого конкретного уровня; значение вне границ «Мин»–«Макс» таблицы MUST отклоняться с ошибкой, называющей параметр и границы.

#### Scenario: Значение по умолчанию
- **WHEN** `events.level` (детализация событий) не задан в конфигурации
- **THEN** применяется значение по умолчанию: всё

#### Scenario: Выше максимума
- **WHEN** `retention_days` задан больше 365
- **THEN** значение отклонено, ошибка называет `retention_days` и границы 7–365

#### Scenario: Недопустимое значение
- **WHEN** `events.level` задан вне допустимых значений (итоги … всё)
- **THEN** значение отклонено, ошибка называет `events.level` и допустимые значения

**ID:** `R-OBS-07` · **Реализует задача:** [3.3](../../../../../docs/tasks/3.3-run-events-timeline.md)

<a id="r-obs-08"></a>
### Requirement: Хранилища данных
Модуль SHALL хранить свои данные только в S3 (Postgres ICPlan, схема `platform`) (`interfaces.md`); данные S6 — доступ только через API или конфигурацию владельца. Секреты MUST NOT храниться в БД и git.

#### Scenario: Запись в своё хранилище
- **WHEN** модуль сохраняет события запусков (`run_event`)
- **THEN** запись попадает в S3 (Postgres ICPlan, схема `platform`)

#### Scenario: S3 недоступно
- **WHEN** S3 (Postgres ICPlan, схема `platform`) не отвечает
- **THEN** события буферизуются у Runner, запуск продолжается; чат запуска временно неполный

#### Scenario: Доступ вне своих хранилищ
- **WHEN** код observability обращается к таблицам вне S3
- **THEN** доступа нет: роль БД observability ограничена S3

**ID:** `R-OBS-08` · **Реализует задача:** [3.3](../../../../../docs/tasks/3.3-run-events-timeline.md)

<a id="r-obs-09"></a>
### Requirement: Интерфейсы обмена
Интерфейсы модуля (I2, I14, I20, I22) SHALL соблюдать протокол, формат, аутентификацию, таймаут и политику повтора из `interfaces.md`; неидемпотентные вызовы MUST NOT повторяться автоматически.

#### Scenario: Таймаут I2
- **WHEN** Agent Runner → ICPlan (шаги, итог) (I2) не ответил за 10 с
- **THEN** вызов прерывается; повтор: повтор с дедупликацией по (run_id, seq)

#### Scenario: Аутентификация I14
- **WHEN** собеседник по I14 отклонил учётные данные (пароль из Secret)
- **THEN** вызов не повторяется, событие с причиной

#### Scenario: Повтор I2 без дублей
- **WHEN** вызов I2 повторён после сбоя
- **THEN** дубля нет: да, по (run_id, seq)

**ID:** `R-OBS-09` · **Реализует задача:** [3.3](../../../../../docs/tasks/3.3-run-events-timeline.md)

<a id="r-obs-10"></a>
### Requirement: Поведение при отказах зависимостей
Модуль SHALL вести себя при отказах зависимостей по таблице FMEA (`interfaces.md`): отказ обнаруживается, поведение предсказуемо и безопасно (fail-closed для проверок безопасности), восстановление не теряет данные.

#### Scenario: Нет записи событий
- **WHEN** нет записи событий
- **THEN** буфер в Runner, досылка

#### Scenario: Нет цены модели
- **WHEN** нет цены модели
- **THEN** токены учтены, стоимость «неизвестна»

#### Scenario: Переполнение таблицы событий
- **WHEN** переполнение таблицы событий
- **THEN** очистка по сроку, предупреждение эксплуатации; уровень детализации меняет только эксплуатация (`events.level`)

**ID:** `R-OBS-10` · **Реализует задача:** [3.3](../../../../../docs/tasks/3.3-run-events-timeline.md)

<a id="r-obs-11"></a>
### Requirement: Нагрузка и производительность
Модуль SHALL выдерживать профиль нагрузки (`interfaces.md`, «Нагрузка и развёртывание»): запись событий ~4 RPS в пике, ~250 МБ/день; чат запуска обновляется < 3 с. Превышение профиля MUST приводить к очереди или отказу с причиной, а не к деградации всей платформы.

#### Scenario: Пик профиля
- **WHEN** нагрузка достигает профиля: запись событий ~4 RPS в пике
- **THEN** выполняется: чат запуска обновляется < 3 с

#### Scenario: Превышение профиля
- **WHEN** нагрузка вдвое выше профиля (запись событий ~4 RPS в пике)
- **THEN** лишние вызовы ждут в очереди или получают отказ с причиной, активные запуски не страдают

#### Scenario: Замер
- **WHEN** нагрузочный тест 4.8 на профиле «запись событий ~4 RPS в пике»
- **THEN** фактические значения (чат запуска обновляется < 3 с) записаны и сравнены с профилем

**ID:** `R-OBS-11` · **Реализует задача:** [4.8](../../../../../docs/tasks/4.8-load-test.md)

<a id="r-obs-12"></a>
### Requirement: Развёртывание
Модуль SHALL разворачиваться так: таблица событий в Postgres; чтение — через api ICPlan; Langfuse / Prometheus — бэклог. Ресурсы MUST задаваться requests / limits, версии образов — закреплены; публичный доступ — только через ingress, если он указан.

#### Scenario: Установка в составе ICPlan
- **WHEN** разворачивается релиз ICPlan (таблица событий в Postgres; чтение — через api ICPlan; Langfuse / Prometheus — бэклог) с модулем observability
- **THEN** миграции observability применены до старта `api`, модуль доступен в ICPlan

#### Scenario: Обновление
- **WHEN** выходит новая версия форка ICPlan с изменениями observability
- **THEN** миграции observability обратно совместимы, `api` обновляется по одной реплике без простоя

#### Scenario: Откат
- **WHEN** версия с изменениями observability не прошла проверки готовности
- **THEN** Helm откатывает ревизию, данные observability сохранены

**ID:** `R-OBS-12` · **Реализует задача:** [4.6](../../../../../docs/tasks/4.6-k8s-helm-ingress.md)
