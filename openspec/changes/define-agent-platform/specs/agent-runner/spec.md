# Spec Delta

## Purpose

Исполняет задачу, назначенную ICPlan конкретному агенту: поднимает изолированную среду, контролирует лимиты запуска, возвращает результат и убирает среду. Не выбирает агента и не планирует задачи. Обоснование: [R&D](../../../../../docs/rnd/runner-and-scheduling.md).

## ADDED Requirements

### Requirement: Запуск из очереди ICPlan
Runner SHALL забирать запуск из очереди ICPlan по ключу агента и исполнять агента по его актуальной (или указанной в запуске) версии определения.

#### Scenario: Успешный запуск
- **WHEN** в очереди есть запуск агента, обслуживаемого Runner
- **THEN** Runner берёт его, создаёт запись с `run_id` и статусом `queued`

#### Scenario: Агент отключён или не найден
- **WHEN** определение агента отключено или отсутствует
- **THEN** запуск завершается с ошибкой `agent_unavailable`, sandbox не создаётся

#### Scenario: Указана версия агента
- **WHEN** в запуске указана версия 3 при последней 5
- **THEN** агент исполняется по версии 3

<a id="r-run-01"></a>**ID:** `R-RUN-01` · **Реализует задача:** [2.1](../../../../../docs/tasks/2.1-runner-external.md)

### Requirement: Планирование по слотам
Runner SHALL запускать взятый из очереди запуск, только когда свободны все его слоты: глобальный, агента, модели и задачи; иначе запуск MUST ждать в статусе `queued` в порядке очереди (`fifo` или `priority`).

#### Scenario: Занят слот модели
- **WHEN** у модели `team-default` заняты все слоты, а агент свободен
- **THEN** запуск ждёт в `queued` и стартует при освобождении слота модели

#### Scenario: Все слоты свободны
- **WHEN** свободны глобальный слот, слот агента, модели и задачи
- **THEN** запуск стартует сразу

#### Scenario: Приоритет
- **WHEN** при `order: priority` в очереди задачи разного приоритета
- **THEN** первым стартует запуск с высшим приоритетом

#### Scenario: Старение приоритета
- **WHEN** при `order: priority` запуск низкого приоритета ждёт дольше `scheduling.aging_s`
- **THEN** его приоритет повышается на уровень за каждый такой интервал, запуск не голодает

<a id="r-run-02"></a>**ID:** `R-RUN-02` · **Реализует задача:** [2.7](../../../../../docs/tasks/2.7-runner-scheduler.md)

### Requirement: Режим последовательно или параллельно
Режим `scheduling.mode` SHALL задаваться конфигурацией: `sequential` — одновременно не более одного запуска на всю платформу; `parallel` — по лимитам слотов. Агент с `parallel: false` MUST исполняться строго по одному в любом режиме.

#### Scenario: Последовательный режим
- **WHEN** включён `sequential` и в очереди три запуска разных агентов
- **THEN** они выполняются по одному в порядке очереди

#### Scenario: Параллельный режим
- **WHEN** включён `parallel`, `global_max: 4`, три запуска разных агентов
- **THEN** все три идут одновременно

#### Scenario: Агент без параллели
- **WHEN** агенту задано `parallel: false`, в очереди два его запуска
- **THEN** второй ждёт завершения первого в любом режиме

<a id="r-run-03"></a>**ID:** `R-RUN-03` · **Реализует задача:** [2.7](../../../../../docs/tasks/2.7-runner-scheduler.md)

### Requirement: Слоты при ожидании подтверждения
Запуск в статусе `waiting_approval` SHALL освобождать глобальный слот и слот модели, но MUST удерживать слот задачи; после решения пользователя запуск снова ждёт свободных слотов. Источник: US-RUN-04.

#### Scenario: Ожидание approve
- **WHEN** запуск перешёл в `waiting_approval`
- **THEN** глобальный слот и слот модели освобождены, другие запуски могут стартовать

#### Scenario: Другой запуск по той же задаче
- **WHEN** запуск задачи ждёт подтверждения, а в очереди второй запуск этой задачи
- **THEN** второй запуск ждёт: слот задачи занят

#### Scenario: Решение принято при занятых слотах
- **WHEN** пользователь одобрил действие, а глобальные слоты заняты
- **THEN** запуск ждёт в `queued` и продолжает с того же шага при освобождении слота

<a id="r-run-04"></a>**ID:** `R-RUN-04` · **Реализует задача:** [2.7](../../../../../docs/tasks/2.7-runner-scheduler.md)

### Requirement: Один запуск на задачу
Runner MUST NOT запускать второй запуск по задаче, пока активен первый (`per_issue: 1`).

#### Scenario: Два агента на одну задачу
- **WHEN** по задаче уже идёт запуск, а в очереди появился второй
- **THEN** второй ждёт завершения первого

#### Scenario: Разные задачи
- **WHEN** два запуска по разным задачам
- **THEN** оба могут идти одновременно

#### Scenario: Первый упал
- **WHEN** активный запуск по задаче завершился ошибкой
- **THEN** следующий запуск по задаче стартует

<a id="r-run-05"></a>**ID:** `R-RUN-05` · **Реализует задача:** [2.7](../../../../../docs/tasks/2.7-runner-scheduler.md)

### Requirement: Общие слоты для нескольких Runner
Несколько экземпляров Runner SHALL использовать общие слоты, чтобы лимиты соблюдались суммарно.

#### Scenario: Два экземпляра
- **WHEN** работают два Runner и `global_max: 2`
- **THEN** одновременно идут не более двух запусков на оба экземпляра

#### Scenario: Один Runner упал
- **WHEN** экземпляр Runner упал с занятыми слотами
- **THEN** слоты освобождаются по истечении аренды

#### Scenario: Хранилище слотов недоступно
- **WHEN** таблица слотов недоступна
- **THEN** новые запуски не стартуют (fail-closed), активные продолжаются

<a id="r-run-06"></a>**ID:** `R-RUN-06` · **Реализует задача:** [2.7](../../../../../docs/tasks/2.7-runner-scheduler.md)

### Requirement: Статусы запуска
Система SHALL вести статус каждого запуска: `queued`, `starting`, `running`, `succeeded`, `failed`, `cancelled`, `limit_exceeded`, и отдавать его по `run_id` и событиями.

#### Scenario: Запрос статуса
- **WHEN** ICPlan запрашивает статус по `run_id`
- **THEN** система возвращает текущий статус, потраченные токены/$ и время

#### Scenario: Неизвестный run_id
- **WHEN** запрошен статус несуществующего запуска
- **THEN** ошибка `run_not_found`

#### Scenario: Событие смены статуса
- **WHEN** запуск перешёл из `queued` в `running`
- **THEN** ICPlan получает событие смены статуса

<a id="r-run-07"></a>**ID:** `R-RUN-07` · **Реализует задача:** [2.1](../../../../../docs/tasks/2.1-runner-external.md)

### Requirement: Возврат результата
Система SHALL по завершении запуска вернуть результат агента в формате, объявленном в определении агента.

#### Scenario: Успешное завершение
- **WHEN** агент завершает работу с результатом
- **THEN** статус становится `succeeded`, результат доступен по `run_id`

#### Scenario: Результат не по формату
- **WHEN** итог не соответствует формату из определения
- **THEN** запуск завершается `gate_failed` или с пометкой несоответствия

#### Scenario: Частичный результат
- **WHEN** запуск остановлен по лимиту
- **THEN** в задачу передаётся частичный итог с пометкой «не завершено»

<a id="r-run-08"></a>**ID:** `R-RUN-08` · **Реализует задача:** [2.1](../../../../../docs/tasks/2.1-runner-external.md), [2.6](../../../../../docs/tasks/2.6-e2e-icplan.md)

### Requirement: Отмена запуска
Система SHALL позволять отменить активный запуск.

#### Scenario: Отмена в очереди
- **WHEN** запуск отменён, пока ждёт слот в `queued`
- **THEN** он снимается с очереди без создания sandbox

#### Scenario: Отмена
- **WHEN** ICPlan отменяет запуск
- **THEN** агент останавливается, sandbox уничтожается, статус `cancelled`

#### Scenario: Повторная отмена
- **WHEN** отмена приходит для уже отменённого запуска
- **THEN** статус не меняется, ошибки нет

<a id="r-run-09"></a>**ID:** `R-RUN-09` · **Реализует задача:** [2.1](../../../../../docs/tasks/2.1-runner-external.md)

### Requirement: Очистка среды
Система MUST уничтожать sandbox после любого терминального статуса.

#### Scenario: Падение агента
- **WHEN** запуск завершается со статусом `failed`
- **THEN** sandbox уничтожен, логи и трейсы сохранены в Observability

#### Scenario: Успешное завершение
- **WHEN** запуск завершился `succeeded`
- **THEN** sandbox уничтожен, пул долит

#### Scenario: Ошибка уничтожения
- **WHEN** контейнер не удалился
- **THEN** Runner повторяет удаление и пишет событие; слот не занимается

<a id="r-run-10"></a>**ID:** `R-RUN-10` · **Реализует задача:** [2.2](../../../../../docs/tasks/2.2-sandbox-docker-oneshot.md)

### Requirement: Манифест рабочего пространства
Runner SHALL собирать для запуска манифест рабочего пространства — список источников с правом (git-репозиторий: адрес, ветка, read / write; папка: префикс в объектном хранилище, read / write) — из политики доступа агента и передавать его в Sandbox и Harness (`RunBundle`). Источник вне политики MUST NOT попадать в манифест. Модель общего пространства между агентами и место политики — открытый вопрос 📌 ОВ-WS-1, ОВ-WS-2 ([R&D](../../../../../docs/rnd/agent-workspace.md)).

#### Scenario: Манифест собран
- **WHEN** у агента в политике репозиторий (write) и папка задачи (read)
- **THEN** манифест содержит оба источника с правами и уходит в Sandbox и `RunBundle`

#### Scenario: Нет политики
- **WHEN** у агента нет ни одного разрешённого источника
- **THEN** манифест пустой, запуск идёт без рабочего пространства, событие

#### Scenario: Политика недоступна
- **WHEN** Platform module не ответил
- **THEN** запуск не стартует, причина «нет политики доступа»

<a id="r-run-17"></a>**ID:** `R-RUN-17` · **Реализует задача:** [2.1](../../../../../docs/tasks/2.1-runner-external.md)

### Requirement: Конфигурация модуля
Модуль SHALL брать свои параметры (13, таблица «Параметры модуля» в `interfaces.md`) с уровней L0 (S9), L1 (S2): значение — с самого конкретного уровня; значение вне границ «Мин»–«Макс» таблицы MUST отклоняться с ошибкой, называющей параметр и границы. Без обязательных параметров L0 модуль MUST NOT стартовать.

#### Scenario: Значение по умолчанию
- **WHEN** `scheduling.aging_s` (интервал повышения приоритета ждущего запуска при…) не задан в конфигурации
- **THEN** применяется значение по умолчанию: 600

#### Scenario: Выше максимума
- **WHEN** `scheduling.aging_s` задан больше 3600
- **THEN** значение отклонено, ошибка называет `scheduling.aging_s` и границы 60–3600

#### Scenario: Граница от другого параметра
- **WHEN** `concurrency` задан больше, чем `scheduling.global_max`
- **THEN** значение отклонено: `concurrency` не может быть больше `scheduling.global_max`

### Requirement: Хранилища данных
Модуль SHALL хранить и читать свои данные только в S2 (Postgres ICPlan, схема `platform`), S3 (Postgres ICPlan, схема `platform`), S9 (Конфиг деплоя: `values.yaml` (git, без секретов) + Secret / `.env` (вне git)) (`interfaces.md`); к данным других модулей — только через их API. Секреты MUST NOT храниться в БД и git.

#### Scenario: Запись в своё хранилище
- **WHEN** модуль сохраняет события запусков, слоты планировщика
- **THEN** запись попадает в S3 (Postgres ICPlan, схема `platform`)

#### Scenario: S3 недоступно
- **WHEN** S3 (Postgres ICPlan, схема `platform`) не отвечает
- **THEN** новые запуски не стартуют; события активных буферизуются в памяти Runner

#### Scenario: Доступ вне своих хранилищ
- **WHEN** код agent-runner обращается к таблицам вне S2, S3, S9
- **THEN** доступа нет: роль БД agent-runner ограничена S2, S3, S9

### Requirement: Интерфейсы обмена
Интерфейсы модуля (I1, I2, I3, I4, I5, I6, I7, I18, I19, I22, I23) SHALL соблюдать протокол, формат, аутентификацию, таймаут и политику повтора из `interfaces.md`; неидемпотентные вызовы MUST NOT повторяться автоматически.

#### Scenario: Таймаут I1
- **WHEN** ICPlan Run Queue → Agent Runner (I1) не ответил за 10 с
- **THEN** вызов прерывается; повтор: backoff до 60 с

#### Scenario: Аутентификация I2
- **WHEN** собеседник по I2 отклонил учётные данные (bearer API-ключ агента)
- **THEN** вызов не повторяется, событие с причиной

#### Scenario: Неидемпотентный вызов I6
- **WHEN** вызов I6 (Agent Runner → Docker Engine API) прервался сбоем сети
- **THEN** автоматического повтора нет, решение принимает вызывающий

### Requirement: Поведение при отказах зависимостей
Модуль SHALL вести себя при отказах зависимостей по таблице FMEA (`interfaces.md`): отказ обнаруживается, поведение предсказуемо и безопасно (fail-closed для проверок безопасности), восстановление не теряет данные.

#### Scenario: ICPlan недоступен
- **WHEN** icplan недоступен
- **THEN** опрос с backoff, активные запуски продолжаются, события буферизуются

#### Scenario: Platform module недоступен
- **WHEN** platform module недоступен
- **THEN** новые запуски не стартуют (нет настроек)

#### Scenario: Docker / пул недоступен
- **WHEN** docker / пул недоступен
- **THEN** запуск остаётся в `queued`

#### Scenario: Runner упал
- **WHEN** runner упал
- **THEN** запуски возвращаются в очередь, слоты освобождаются

<a id="r-run-14"></a>**ID:** `R-RUN-14` · **Реализует задача:** [2.1](../../../../../docs/tasks/2.1-runner-external.md), [2.6](../../../../../docs/tasks/2.6-e2e-icplan.md)

### Requirement: Нагрузка и производительность
Модуль SHALL выдерживать профиль нагрузки (`interfaces.md`, «Нагрузка и развёртывание»): опрос очереди ~0.3 RPS на агента; до 6 запусков в очереди, 4 активны; старт запуска после взятия < 5 с (с пулом < 1 с). Превышение профиля MUST приводить к очереди или отказу с причиной, а не к деградации всей платформы.

#### Scenario: Пик профиля
- **WHEN** нагрузка достигает профиля: опрос очереди ~0.3 RPS на агента
- **THEN** выполняется: до 6 запусков в очереди; старт запуска после взятия < 5 с (с пулом < 1 с)

#### Scenario: Превышение профиля
- **WHEN** нагрузка вдвое выше профиля (опрос очереди ~0.3 RPS на агента)
- **THEN** лишние вызовы ждут в очереди или получают отказ с причиной, активные запуски не страдают

#### Scenario: Замер
- **WHEN** нагрузочный тест 4.8 на профиле «опрос очереди ~0.3 RPS на агента»
- **THEN** фактические значения (до 6 запусков в очереди; старт запуска после взятия < 5 с (с пулом < 1 с)) записаны и сравнены с профилем

<a id="r-run-15"></a>**ID:** `R-RUN-15` · **Реализует задача:** [4.8](../../../../../docs/tasks/4.8-load-test.md)

### Requirement: Развёртывание
Модуль SHALL разворачиваться так: Deployment `agent-runner` в `itsaplan-agents`, 1 реплика (MVP), 2 — с общими слотами; requests 0.1 CPU / 128 МиБ, limits 0.5 / 512 МиБ; без ingress. Ресурсы MUST задаваться requests / limits, версии образов — закреплены; публичный доступ — только через ingress, если он указан.

#### Scenario: Установка
- **WHEN** выполняется `helm install`: Deployment `agent-runner` в `itsaplan-agents`, 1 реплика (MVP), 2 — с общими слотами; requests 0.1 CPU / 128 МиБ, limits 0.5 / 512 МиБ; без ingress
- **THEN** объекты созданы в своём namespace с заданными requests / limits, проверки готовности зелёные

#### Scenario: Обновление
- **WHEN** выходит новая версия образа `agent-runner` (1 реплика)
- **THEN** `agent-runner` заменяется по одной реплике; работа, начатая на старой версии, доделывается

#### Scenario: Нехватка ресурсов
- **WHEN** узлу не хватает ресурсов для пода `agent-runner`
- **THEN** под `agent-runner` ждёт размещения, событие эксплуатации
